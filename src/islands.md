# คู่มือ: Islands

Leptos 0.5 เปิดตัวฟีเจอร์ `islands` ใหม่ คู่มือนี้จะพาคุณไปรู้จักฟีเจอร์ islands และแนวคิดหลักๆ พร้อมทั้งสร้างแอปเดโมโดยใช้สถาปัตยกรรมแบบเกาะ (islands)

## สถาปัตยกรรมแบบเกาะ (Islands)

เฟรมเวิร์ก JavaScript ฝั่งฟรอนต์เอนด์ที่เป็นที่นิยม (React, Vue, Svelte, Solid, Angular) ล้วนถือกำเนิดมาเป็นเฟรมเวิร์กสำหรับสร้างแอปพลิเคชันหน้าเดียว (SPA) ที่เรนเดอร์ฝั่งไคลเอนต์ การโหลดหน้าเพจครั้งแรกจะถูกเรนเดอร์เป็น HTML จากนั้นจึงทำการไฮเดรต (hydrate) และการนำทางครั้งถัดๆ ไปจะถูกจัดการที่ไคลเอนต์โดยตรง (จึงเรียกว่า “หน้าเดียว”: ทุกอย่างเกิดขึ้นจากการโหลดหน้าเพจครั้งเดียวจากเซิร์ฟเวอร์ แม้ว่าจะมีการจัดเส้นทางฝั่งไคลเอนต์ในภายหลังก็ตาม) ต่อมาเฟรมเวิร์กแต่ละตัวเหล่านี้ได้เพิ่มการเรนเดอร์ฝั่งเซิร์ฟเวอร์ (SSR) เพื่อปรับปรุงเวลาในการโหลดครั้งแรก SEO และประสบการณ์ของผู้ใช้

นั่นหมายความว่าโดยค่าเริ่มต้น แอปพลิเคชันทั้งหมดเป็นแบบอินเทอร์แอกทีฟ และยังหมายความว่าแอปพลิเคชันทั้งหมดต้องถูกส่งไปยังไคลเอนต์ในรูปแบบ JavaScript เพื่อทำการไฮเดรต Leptos ก็ทำตามรูปแบบเดียวกันนี้

> คุณสามารถอ่านเพิ่มเติมได้ในบทเกี่ยวกับ[การเรนเดอร์ฝั่งเซิร์ฟเวอร์](./ssr/22_life_cycle.md)

แต่ก็เป็นไปได้เช่นกันที่จะทำในทิศทางตรงกันข้าม แทนที่จะเริ่มจากแอปพลิเคชันแบบอินเทอร์แอกทีฟทั้งหมด เรนเดอร์มันเป็น HTML บนเซิร์ฟเวอร์ แล้วไฮเดรตในเบราว์เซอร์ คุณสามารถเริ่มจากหน้า HTML ธรรมดาๆ แล้วเพิ่มพื้นที่อินเทอร์แอกทีฟเล็กๆ เข้าไปได้ นี่คือรูปแบบดั้งเดิมของเว็บไซต์หรือแอปใดๆ ก่อนช่วงทศวรรษ 2010: เบราว์เซอร์ของคุณส่งคำขอหลายคำขอไปยังเซิร์ฟเวอร์ และได้รับ HTML ของแต่ละหน้าใหม่เป็นการตอบกลับ หลังจากการเกิดขึ้นของ “แอปพลิเคชันหน้าเดียว” (SPA) แนวทางนี้บางครั้งจึงเป็นที่รู้จักในชื่อ “แอปพลิเคชันหลายหน้า” (MPA) เมื่อนำมาเปรียบเทียบกัน

วลี “สถาปัตยกรรมแบบเกาะ” (islands architecture) เพิ่งเกิดขึ้นเมื่อไม่นานมานี้เพื่ออธิบายแนวทางที่เริ่มต้นจาก “ทะเล” ของหน้า HTML ที่เรนเดอร์บนเซิร์ฟเวอร์ แล้วเพิ่ม “เกาะ” แห่งความอินเทอร์แอกทีฟเข้าไปทั่วทั้งหน้า

## การเปิดใช้งานโหมด Islands

มาเริ่มกันด้วยแอป `cargo-leptos` ใหม่:

```bash
cargo leptos new --git leptos-rs/start-axum
```

> ในตัวอย่างนี้ไม่น่าจะมีความแตกต่างที่แท้จริงระหว่าง Actix กับ Axum

ผมจะรัน

```bash
cargo leptos build
```

ไว้เบื้องหลังระหว่างที่ผมเปิดเอดิเตอร์และเขียนต่อไป

สิ่งแรกที่ผมจะทำคือเพิ่มฟีเจอร์ `islands` ใน `Cargo.toml` ของผม ผมแค่ต้องเพิ่มมันให้ครีต `leptos` เท่านั้น

```toml
leptos = { version = "0.7", features = ["islands"] }
```

ต่อไปผมจะแก้ไขฟังก์ชัน `hydrate` ที่เอ็กซ์พอร์ตจาก `src/lib.rs` ผมจะลบบรรทัดที่เรียก `leptos::mount::hydrate_body(App)` แล้วแทนที่ด้วย

```rust
leptos::mount::hydrate_islands();
```

แทนที่จะรันแอปพลิเคชันทั้งหมดและไฮเดรตวิวที่มันสร้างขึ้น วิธีนี้จะไฮเดรตแต่ละเกาะทีละอันตามลำดับ

ใน `app.rs` ในฟังก์ชัน `shell` เรายังต้องเพิ่ม `islands=true` ให้คอมโพเนนต์ `HydrationScripts` ด้วย:

```rust
<HydrationScripts options islands=true/>
```

เอาละ ตอนนี้รัน `cargo leptos watch` ของคุณแล้วไปที่ [`http://localhost:3000`](http://localhost:3000) (หรือที่ใดก็ตาม)

คลิกปุ่ม แล้ว...

ไม่มีอะไรเกิดขึ้น!

สมบูรณ์แบบ

```admonish note
เทมเพลตเริ่มต้นมี `use app::*;` อยู่ในนิยามฟังก์ชัน `hydrate()` ของพวกมัน เมื่อคุณเปลี่ยนมาใช้โหมด islands แล้ว คุณจะไม่ใช้ฟังก์ชัน `App` หลักที่อิมพอร์ตเข้ามาอีกต่อไป คุณอาจคิดว่าลบมันได้ (และที่จริง เครื่องมือ lint ของ Rust อาจออกคำเตือนถ้าคุณไม่ลบ!)

อย่างไรก็ตาม เรื่องนี้อาจทำให้เกิดปัญหาได้ถ้าคุณใช้การตั้งค่าแบบ workspace เราใช้ `wasm-bindgen` เพื่อเอ็กซ์พอร์ต entrypoint แยกต่างหากสำหรับแต่ละฟังก์ชัน จากประสบการณ์ของผม ถ้าคุณใช้การตั้งค่าแบบ workspace และไม่มีอะไรในครีต `frontend` ของคุณที่ใช้ครีต `app` จริงๆ การผูก (bindings) เหล่านั้นจะไม่ถูกสร้างขึ้นอย่างถูกต้อง [ดูการสนทนานี้สำหรับข้อมูลเพิ่มเติม](https://github.com/leptos-rs/leptos/issues/2083#issuecomment-1868053733)
```

## การใช้งาน Islands

ไม่มีอะไรเกิดขึ้นเพราะเราเพิ่งกลับด้านโมเดลความคิดของแอปพลิเคชันไปทั้งหมด แทนที่จะเป็นแบบอินเทอร์แอกทีฟโดยค่าเริ่มต้นและไฮเดรตทุกอย่าง ตอนนี้แอปพลิเคชันเป็น HTML ธรรมดาโดยค่าเริ่มต้น และเราต้องเลือกเปิดใช้งานความอินเทอร์แอกทีฟเอง

เรื่องนี้มีผลอย่างมากต่อขนาดไบนารี WASM: ถ้าผมคอมไพล์ในโหมด release แอปนี้จะมี WASM เพียง 24kb (ไม่บีบอัด) เทียบกับ 274kb ในโหมดที่ไม่ใช่ islands (274kb ถือว่าใหญ่ทีเดียวสำหรับ “Hello, world!” จริงๆ แล้วมันก็แค่โค้ดทั้งหมดที่เกี่ยวข้องกับการจัดเส้นทางฝั่งไคลเอนต์ ซึ่งไม่ได้ถูกใช้ในเดโมนี้)

เมื่อเราคลิกปุ่ม ไม่มีอะไรเกิดขึ้น เพราะทั้งหน้าเป็นแบบสแตติก

แล้วเราจะทำให้อะไรบางอย่างเกิดขึ้นได้อย่างไร?

มาเปลี่ยนคอมโพเนนต์ `HomePage` ให้เป็นเกาะกันเถอะ!

นี่คือเวอร์ชันที่ไม่เป็นอินเทอร์แอกทีฟ:

```rust
#[component]
fn HomePage() -> impl IntoView {
    // Creates a reactive value to update the button
    let count = RwSignal::new(0);
    let on_click = move |_| *count.write() += 1;

    view! {
        <h1>"Welcome to Leptos!"</h1>
        <button on:click=on_click>"Click Me: " {count}</button>
    }
}
```

นี่คือเวอร์ชันที่เป็นอินเทอร์แอกทีฟ:

```rust
#[island]
fn HomePage() -> impl IntoView {
    // Creates a reactive value to update the button
    let count = RwSignal::new(0);
    let on_click = move |_| *count.write() += 1;

    view! {
        <h1>"Welcome to Leptos!"</h1>
        <button on:click=on_click>"Click Me: " {count}</button>
    }
}
```

ตอนนี้เมื่อผมคลิกปุ่ม มันก็ทำงานได้แล้ว!

มาโคร `#[island]` ทำงานเหมือนมาโคร `#[component]` ทุกประการ ต่างกันแค่ในโหมด islands มันจะกำหนดว่าสิ่งนี้เป็นเกาะแบบอินเทอร์แอกทีฟ ถ้าเราดูขนาดไบนารีอีกครั้ง ในโหมด release จะอยู่ที่ 166kb แบบไม่บีบอัด ใหญ่กว่าเวอร์ชันสแตติกทั้งหมดที่ 24kb มาก แต่ก็เล็กกว่าเวอร์ชันไฮเดรตเต็มรูปแบบที่ 355kb มากเช่นกัน

ถ้าคุณเปิดดูซอร์สของหน้าเพจตอนนี้ คุณจะเห็นว่าเกาะ `HomePage` ของคุณถูกเรนเดอร์เป็นเอลิเมนต์ HTML พิเศษ `<leptos-island>` ซึ่งระบุว่าควรใช้คอมโพเนนต์ใดในการไฮเดรต:

```html
<leptos-island data-component="HomePage_7432294943247405892">
  <h1>Welcome to Leptos!</h1>
  <button>
    Click Me:
    <!>0
  </button>
</leptos-island>
```

มีเพียงโค้ดที่อยู่ภายใน `<leptos-island>` นี้เท่านั้นที่ถูกคอมไพล์เป็น WASM และมีเพียงโค้ดนั้นเท่านั้นที่รันตอนไฮเดรต

## การใช้งาน Islands อย่างมีประสิทธิภาพ

จำไว้ว่าโค้ด _เฉพาะ_ ที่อยู่ภายใน `#[island]` เท่านั้นที่ต้องถูกคอมไพล์เป็น WASM และส่งไปยังเบราว์เซอร์ นั่นหมายความว่าเกาะควรมีขนาดเล็กและเจาะจงที่สุดเท่าที่เป็นไปได้ ตัวอย่างเช่น `HomePage` ของผมจะดีกว่าถ้าแยกออกเป็นคอมโพเนนต์ปกติกับเกาะ:

```rust
#[component]
fn HomePage() -> impl IntoView {
    view! {
        <h1>"Welcome to Leptos!"</h1>
        <Counter/>
    }
}

#[island]
fn Counter() -> impl IntoView {
    // Creates a reactive value to update the button
    let (count, set_count) = signal(0);
    let on_click = move |_| *set_count.write() += 1;

    view! {
        <button on:click=on_click>"Click Me: " {count}</button>
    }
}
```

ตอนนี้ `<h1>` ไม่จำเป็นต้องถูกรวมไว้ในบันเดิลฝั่งไคลเอนต์ หรือถูกไฮเดรต เรื่องนี้อาจดูเหมือนเป็นความแตกต่างที่ไม่สำคัญในตอนนี้ แต่ลองนึกดูว่าตอนนี้คุณสามารถเพิ่มเนื้อหา HTML ที่ไม่ทำงานอะไรลงใน `HomePage` ได้มากเท่าที่ต้องการ และขนาดไบนารี WASM จะยังคงเท่าเดิมเป๊ะ

ในโหมดไฮเดรตปกติ ขนาดไบนารี WASM ของคุณจะโตขึ้นตามขนาด/ความซับซ้อนของแอป ในโหมด islands ไบนารี WASM ของคุณจะโตขึ้นตามปริมาณความอินเทอร์แอกทีฟในแอป คุณสามารถเพิ่มเนื้อหาที่ไม่เป็นอินเทอร์แอกทีฟได้มากเท่าที่ต้องการนอกเกาะ และมันจะไม่เพิ่มขนาดไบนารีนั้นเลย

## ปลดล็อกพลังพิเศษ

ดังนั้น การลดขนาดไบนารี WASM ลง 50% นี้ก็ดีอยู่ แต่จริงๆ แล้วประเด็นมันอยู่ตรงไหน?

ประเด็นจะปรากฏเมื่อคุณรวมข้อเท็จจริงสำคัญสองข้อเข้าด้วยกัน:

1. โค้ดภายในฟังก์ชัน `#[component]` ตอนนี้จะรันบนเซิร์ฟเวอร์ _เท่านั้น_ เว้นแต่คุณจะใช้มันในเกาะ\*
2. children และพร็อพสามารถถูกส่งจากเซิร์ฟเวอร์ไปยังเกาะได้ โดยไม่ถูกวมไว้ในไบนารี WASM

นั่นหมายความว่าคุณสามารถรันโค้ดที่เป็นเซิร์ฟเวอร์เท่านั้นโดยตรงในบอดีของคอมโพเนนต์ และส่งมันเข้าไปใน children ได้โดยตรง งานบางอย่างที่ต้องใช้ส่วนผสมที่ซับซ้อนของฟังก์ชันฝั่งเซิร์ฟเวอร์และซัสเพนส์ (Suspense) ในแอปแบบไฮเดรตเต็มรูปแบบ สามารถทำแบบอินไลน์ในเกาะได้

> \* คำว่า “เว้นแต่คุณจะใช้มันในเกาะ” นี้สำคัญ มัน _ไม่ใช่_ กรณีที่คอมโพเนนต์ `#[component]` รันบนเซิร์ฟเวอร์เท่านั้น แต่พวกมันเป็น “คอมโพเนนต์ที่ใช้ร่วมกัน” ที่จะถูกคอมไพล์เข้าไปในไบนารี WASM ก็ต่อเมื่อถูกใช้ในบอดีของ `#[island]` เท่านั้น แต่ถ้าคุณไม่ใช้มันในเกาะ พวกมันก็จะไม่รันในเบราว์เซอร์

เราจะอาศัยข้อเท็จจริงข้อที่สามในส่วนที่เหลือของเดโมนี้:

3. คอนเท็กซ์สามารถถูกส่งระหว่างเกาะที่เป็นอิสระต่อกันได้

ดังนั้น แทนที่จะเป็นเดโมตัวนับของเรา มาทำอะไรที่สนุกขึ้นหน่อยดีกว่า: อินเทอร์เฟซแบบแท็บที่อ่านข้อมูลจากไฟล์บนเซิร์ฟเวอร์

## การส่ง children ฝั่งเซิร์ฟเวอร์ให้ Islands

หนึ่งในสิ่งที่ทรงพลังที่สุดเกี่ยวกับ islands คือคุณสามารถส่ง children ที่เรนเดอร์บนเซิร์ฟเวอร์เข้าไปในเกาะได้ โดยที่เกาะไม่ต้องรู้อะไรเกี่ยวกับ children เหล่านั้นเลย เกาะจะไฮเดรตเนื้อหาของตัวเอง แต่ไม่ไฮเดรต children ที่ถูกส่งเข้ามา

ดังที่ Dan Abramov แห่ง React พูดไว้ (ในบริบทที่คล้ายคลึงกันมากของ RSC) เกาะนั้นที่จริงไม่ใช่เกาะ แต่เป็นโดนัท คุณสามารถส่งเนื้อหาที่เป็นเซิร์ฟเวอร์เท่านั้นเข้าไปใน “รูโดนัท” ได้โดยตรง ทำให้คุณสร้างเกาะปะการังเล็กๆ แห่งความอินเทอร์แอกทีฟที่ถูกล้อมรอบด้วยทะเล HTML สแตติกจากเซิร์ฟเวอร์ทั้ง _สอง_ ด้าน

> ในโค้ดเดโมที่ให้ไว้ด้านล่าง ผมได้เพิ่มสไตล์เพื่อแสดงเนื้อหาฝั่งเซิร์ฟเวอร์ทั้งหมดเป็น “ทะเล” สีฟ้าอ่อน และเกาะทั้งหมดเป็น “แผ่นดิน” สีเขียวอ่อน หวังว่าจะช่วยให้เห็นภาพสิ่งที่ผมกำลังพูดถึง!

มาต่อกับเดโมกัน: ผมจะสร้างคอมโพเนนต์ `Tabs` การสลับแท็บจะต้องมีความอินเทอร์แอกทีฟ ดังนั้นแน่นอนว่ามันจะเป็นเกาะ เริ่มง่ายๆ ก่อนตอนนี้:

```rust
#[island]
fn Tabs(labels: Vec<String>) -> impl IntoView {
    let buttons = labels
        .into_iter()
        .map(|label| view! { <button>{label}</button> })
        .collect_view();
    view! {
        <div style="display: flex; width: 100%; justify-content: space-between;">
            {buttons}
        </div>
    }
}
```

อุ๊ปส์ มันให้ข้อผิดพลาดกับผม

```
error[E0463]: can't find crate for `serde`
  --> src/app.rs:43:1
   |
43 | #[island]
   | ^^^^^^^^^ can't find crate
```

แก้ไขง่ายๆ: รัน `cargo add serde --features=derive` มาโคร `#[island]` ต้องการดึง `serde` เข้ามาในกรณีนี้ เพราะมันต้องซีเรียลไลซ์และดีซีเรียลไลซ์พร็อพ `labels`

ตอนนี้มาอัปเดต `HomePage` ให้ใช้ `Tabs` กัน

```rust
#[component]
fn HomePage() -> impl IntoView {
	// these are the files we’re going to read
    let files = ["a.txt", "b.txt", "c.txt"];
	// the tab labels will just be the file names
	let labels = files.iter().copied().map(Into::into).collect();
    view! {
        <h1>"Welcome to Leptos!"</h1>
        <p>"Click any of the tabs below to read a recipe."</p>
        <Tabs labels/>
    }
}
```

ถ้าคุณดูใน DOM inspector คุณจะเห็นว่าเกาะตอนนี้มีลักษณะประมาณนี้

```html
<leptos-island
  data-component="Tabs_1030591929019274801"
  data-props='{"labels":["a.txt","b.txt","c.txt"]}'
>
  <div style="display: flex; width: 100%; justify-content: space-between;;">
    <button>a.txt</button>
    <button>b.txt</button>
    <button>c.txt</button>
    <!---->
  </div>
</leptos-island>
```

พร็อพ `labels` ของเราถูกซีเรียลไลซ์เป็น JSON และเก็บไว้ในแอตทริบิวต์ HTML เพื่อให้สามารถใช้ไฮเดรตเกาะได้

ตอนนี้มาเพิ่มแท็บกันบ้าง ตอนนี้เกาะ `Tab` จะเรียบง่ายมาก:

```rust
#[island]
fn Tab(index: usize, children: Children) -> impl IntoView {
    view! {
        <div>{children()}</div>
    }
}
```

แต่ละแท็บ ตอนนี้จะเป็นแค่ `<div>` ที่ห่อหุ้ม children ของมัน

คอมโพเนนต์ `Tabs` ของเราก็จะได้รับ children ด้วย: ตอนนี้ขอแค่แสดงทั้งหมดก่อน

```rust
#[island]
fn Tabs(labels: Vec<String>, children: Children) -> impl IntoView {
    let buttons = labels
        .into_iter()
        .map(|label| view! { <button>{label}</button> })
        .collect_view();
    view! {
        <div style="display: flex; width: 100%; justify-content: space-around;">
            {buttons}
        </div>
        {children()}
    }
}
```

เอาละ ตอนนี้กลับไปที่ `HomePage` กัน เราจะสร้างรายการแท็บเพื่อใส่ในกล่องแท็บของเรา

```rust
#[component]
fn HomePage() -> impl IntoView {
    let files = ["a.txt", "b.txt", "c.txt"];
    let labels = files.iter().copied().map(Into::into).collect();
	let tabs = move || {
        files
            .into_iter()
            .enumerate()
            .map(|(index, filename)| {
                let content = std::fs::read_to_string(filename).unwrap();
                view! {
                    <Tab index>
                        <h2>{filename.to_string()}</h2>
                        <p>{content}</p>
                    </Tab>
                }
            })
            .collect_view()
    };

    view! {
        <h1>"Welcome to Leptos!"</h1>
        <p>"Click any of the tabs below to read a recipe."</p>
        <Tabs labels>
            <div>{tabs()}</div>
        </Tabs>
    }
}
```

เอ่อ... อะไรนะ?

ถ้าคุณคุ้นเคยกับการใช้ Leptos คุณจะรู้ว่าคุณทำแบบนี้ไม่ได้ โค้ดทั้งหมดในบอดีของคอมโพเนนต์ต้องรันบนเซิร์ฟเวอร์ (เพื่อเรนเดอร์เป็น HTML) และในเบราว์เซอร์ (เพื่อไฮเดรต) ดังนั้นคุณจึงเรียก `std::fs` เฉยๆ ไม่ได้ มันจะแพนิก เพราะในเบราว์เซอร์ไม่มีการเข้าถึงไฟล์ซิสเต็มภายในเครื่อง (และแน่นอนว่าไม่มีการเข้าถึงไฟล์ซิสเต็มของเซิร์ฟเวอร์ด้วย!) นี่คงเป็นฝันร้ายด้านความปลอดภัยเลย!

แต่... เดี๋ยวก่อน เราอยู่ในโหมด islands คอมโพเนนต์ `HomePage` นี้รันบนเซิร์ฟเวอร์ _จริงๆ_ เท่านั้น ดังนั้นเราจึงใช้โค้ดฝั่งเซิร์ฟเวอร์ธรรมดาแบบนี้ได้เลย

> **นี่เป็นตัวอย่างที่โง่หรือเปล่า?** ใช่! การอ่านไฟล์โลคอลสามไฟล์ต่างกันแบบซิงโครนัสใน `.map()` ไม่ใช่ทางเลือกที่ดีในชีวิตจริง ประเด็นตรงนี้ก็แค่เพื่อแสดงว่านี่เป็นเนื้อหาที่เป็นเซิร์ฟเวอร์เท่านั้นอย่างแน่นอน

ลองสร้างไฟล์สามไฟล์ในรากของโปรเจกต์ชื่อ `a.txt`, `b.txt` และ `c.txt` แล้วใส่เนื้อหาอะไรก็ได้ตามใจคุณ

รีเฟรชหน้าเพจแล้วคุณควรเห็นเนื้อหาในเบราว์เซอร์ แก้ไขไฟล์แล้วรีเฟรชอีกครั้ง มันจะอัปเดตตาม

คุณสามารถส่งเนื้อหาที่เป็นเซิร์ฟเวอร์เท่านั้นจาก `#[component]` ไปยัง children ของ `#[island]` ได้ โดยที่เกาะไม่ต้องรู้อะไรเลยเกี่ยวกับวิธีการเข้าถึงข้อมูลนั้นหรือเรนเดอร์เนื้อหานั้น

**นี่สำคัญมาก** การส่ง `children` ฝั่งเซิร์ฟเวอร์ให้เกาะหมายความว่าคุณสามารถทำให้เกาะมีขนาดเล็กได้ ตามอุดมคติแล้ว คุณไม่อยากเอา `#[island]` ไปครอบทั้งก้อนใหญ่ของหน้าเพจ แต่คุณอยากแยกก้อนนั้นออกเป็นส่วนอินเทอร์แอกทีฟ ซึ่งเป็น `#[island]` ได้ และเนื้อหาฝั่งเซิร์ฟเวอร์เพิ่มเติมอีกจำนวนหนึ่งที่ส่งให้เกาะนั้นเป็น `children` เพื่อให้ส่วนย่อยที่ไม่เป็นอินเทอร์แอกทีฟของส่วนที่เป็นอินเทอร์แอกทีฟในหน้าเพจถูกกันออกไปจากไบนารี WASM

## การส่งคอนเท็กซ์ระหว่าง Islands

ตอนนี้ยังไม่ใช่ “แท็บ” จริงๆ มันแค่แสดงทุกแท็บตลอดเวลา ดังนั้นมาเพิ่มลอจิกง่ายๆ ให้คอมโพเนนต์ `Tabs` และ `Tab` กัน

เราจะแก้ `Tabs` ให้สร้างสัญญาณ `selected` ง่ายๆ เรามอบครึ่งที่เป็นการอ่านผ่านคอนเท็กซ์ และตั้งค่าของสัญญาณทุกครั้งที่มีคนคลิกปุ่มของเราสักปุ่ม

```rust
#[island]
fn Tabs(labels: Vec<String>, children: Children) -> impl IntoView {
    let (selected, set_selected) = signal(0);
    provide_context(selected);

    let buttons = labels
        .into_iter()
        .enumerate()
        .map(|(index, label)| view! {
            <button on:click=move |_| set_selected.set(index)>
                {label}
            </button>
        })
        .collect_view();
// ...
```

และมาแก้เกาะ `Tab` ให้ใช้คอนเท็กซ์นั้นเพื่อแสดงหรือซ่อนตัวเอง:

```rust
#[island]
fn Tab(index: usize, children: Children) -> impl IntoView {
    let selected = expect_context::<ReadSignal<usize>>();
    view! {
        <div
            style:background-color="lightgreen"
            style:padding="10px"
            style:display=move || if selected.get() == index {
                "block"
            } else {
                "none"
            }
        >
            {children()}
        </div>
    }
}
```

ตอนนี้แท็บทำงานตามที่ผมคาดหวังเป๊ะ `Tabs` ส่งสัญญาณผ่านคอนเท็กซ์ให้แต่ละ `Tab` ซึ่งใช้มันเพื่อตัดสินว่าควรเปิดหรือไม่

> นั่นคือเหตุผลว่าใน `HomePage` ผมทำให้ `let tabs = move ||` เป็นฟังก์ชัน แล้วเรียกมันแบบ `{tabs()}`: การสร้างแท็บแบบแลซี่ด้วยวิธีนี้ทำให้เกาะ `Tabs` ได้มอบคอนเท็กซ์ `selected` ไว้แล้วก่อนที่แต่ละ `Tab` จะเริ่มมองหามัน

เดโมแท็บที่สมบูรณ์ของเรามีขนาดประมาณ 200kb แบบไม่บีบอัด ไม่ใช่เดโมที่เล็กที่สุดในโลก แต่ก็ยังเล็กกว่า “Hello, world” ที่ใช้การจัดเส้นทางฝั่งไคลเอนต์ที่เราเริ่มต้นด้วยอย่างมีนัยสำคัญ เพื่อความสนุก ผมบิลด์เดโมเดียวกันโดยไม่ใช้โหมด islands โดยใช้ฟังก์ชัน `#[server]` และ `Suspense` และมันมีขนาดเกิน 400kb ดังนั้นอีกครั้ง นี่เป็นการประหยัดขนาดไบนารีประมาณ 50% และแอปนี้มีเนื้อหาที่เป็นเซิร์ฟเวอร์เท่านั้นค่อนข้างน้อย จำไว้ว่าเมื่อเราเพิ่มคอมโพเนนต์และหน้าเพจที่เป็นเซิร์ฟเวอร์เท่านั้นอีก 200kb นี้จะไม่โตขึ้น

## การแทนที่เราเตอร์ฝั่งไคลเอนต์

หนึ่งในจุดประสงค์หลักของการใช้ islands คือการกันการจัดเส้นทางออกจากไคลเอนต์ เมื่อคุณมีเราเตอร์ฝั่งไคลเอนต์ คุณต้องสามารถเรนเดอร์ทุกหน้าบนไคลเอนต์ได้ การใช้ islands ช่วยให้คุณลดปริมาณโค้ดที่ส่งไปยังเบราว์เซอร์ได้ แลกกับการที่คุณสูญเสียความสะดวกของเราเตอร์ฝั่งไคลเอนต์

มีโหมด "islands router" ที่ผสานการจัดเส้นทางฝั่งไคลเอนต์เข้ากับ islands โดยใช้ JavaScript จำนวนเล็กน้อยบนฟรอนต์เอนด์เพื่อดึงหน้าเพจที่เรนเดอร์บนเซิร์ฟเวอร์ใหม่และทำ diff อย่างมีประสิทธิภาพ คุณอ่านเพิ่มเติมได้ใน[ตัวอย่าง `islands_router`](https://github.com/leptos-rs/leptos/tree/main/examples/islands_router) มันทำงานได้ค่อนข้างดี และรองรับทั้งการนำทางผ่านลิงก์และฟอร์ม

โปรดทราบว่าถ้าไม่มีเราเตอร์ฝั่งไคลเอนต์ คุณจะสูญเสียความสามารถในการเรียก `redirect()` โดยตรงจากฟังก์ชันฝั่งเซิร์ฟเวอร์และให้มันเปลี่ยนเส้นทางบนไคลเอนต์ ความสามารถนี้จัดหาโดยเราเตอร์ อย่างไรก็ตาม คุณสามารถสร้างเวอร์ชันมินิมอลของคุณเองได้โดยเรียก [`set_redirect_hook`](https://docs.rs/leptos/latest/leptos/server_fn/redirect/fn.set_redirect_hook.html):
```rust
set_redirect_hook(|url| {
    window().location().set_href(url);
});
```
ตอนนี้ ฟังก์ชันฝั่งเซิร์ฟเวอร์ใดๆ ที่เรียก `redirect()` จะถูกจัดการบนไคลเอนต์ด้วยการนำทางหน้าเพจแบบปกติ

## ภาพรวม

เดโมนี้ดูอาจจะเรียบง่ายมาก ก็ใช่ แต่มีข้อสรุปที่ได้ทันทีหลายประการ:

- **ลดขนาดไบนารี WASM ลง 50%** ซึ่งหมายถึงการปรับปรุงเวลาในการตอบสนองต่อการโต้ตอบและเวลาโหลดเริ่มต้นสำหรับไคลเอนต์ได้อย่างวัดผลได้
- **ลดต้นทุนการซีเรียลไลซ์ข้อมูล** การสร้างรีซอร์สและอ่านมันบนไคลเอนต์หมายความว่าคุณต้องซีเรียลไลซ์ข้อมูล เพื่อให้สามารถใช้ไฮเดรตได้ ถ้าคุณอ่านข้อมูลนั้นเพื่อสร้าง HTML ใน `Suspense` ด้วย คุณจะได้ “ข้อมูลซ้ำซ้อน” กล่าวคือ ข้อมูลชุดเดียวกันถูกเรนเดอร์เป็น HTML และซีเรียลไลซ์เป็น JSON พร้อมกัน ทำให้ขนาดการตอบกลับเพิ่มขึ้นและทำให้ช้าลง
- **ใช้ API ที่เป็นเซิร์ฟเวอร์เท่านั้นได้ง่ายๆ** ภายใน `#[component]` ราวกับว่ามันเป็นฟังก์ชัน Rust ปกติที่รันบนเซิร์ฟเวอร์ ซึ่งในโหมด islands มันเป็นเช่นนั้นจริงๆ!
- **ลดโค้ดซ้ำซากของ `#[server]`/`create_resource`/`Suspense`** สำหรับการโหลดข้อมูลจากเซิร์ฟเวอร์

## การสำรวจในอนาคต

ฟีเจอร์ `islands` สะท้อนงานที่อยู่แนวหน้าสุดของการสำรวจของเฟรมเวิร์กเว็บฝั่งฟรอนต์เอนด์ในตอนนี้ ในสถานะปัจจุบัน แนวทาง islands ของเราคล้ายกับ Astro มาก (ก่อนการรองรับ View Transitions ครั้งล่าสุดของมัน): มันช่วยให้คุณสร้างแอปพลิเคชันหลายหน้าแบบเรนเดอร์บนเซิร์ฟเวอร์แบบดั้งเดิม และผสานเกาะแห่งความอินเทอร์แอกทีฟได้อย่างราบรื่น

มีการปรับปรุงเล็กๆ บางอย่างที่เพิ่มได้ง่าย ตัวอย่างเช่น เราทำอะไรที่คล้ายกับแนวทาง View Transitions ของ Astro ได้มากทีเดียว:

- เพิ่มการจัดเส้นทางฝั่งไคลเอนต์สำหรับแอป islands โดยดึงการนำทางครั้งถัดไปจากเซิร์ฟเวอร์และแทนที่เอกสาร HTML ด้วยฉบับใหม่
- เพิ่มทรานซิชันแบบแอนิเมชันระหว่างเอกสารเก่าและใหม่โดยใช้ View Transitions API
- รองรับเกาะแบบคงอยู่ถาวรอย่างชัดเจน คือเกาะที่คุณทำเครื่องหมายด้วย ID เฉพาะ (อะไรประมาณ `persist:searchbar` บนคอมโพเนนต์ในวิว) ซึ่งสามารถคัดลอกจากเอกสารเก่าไปยังเอกสารใหม่ได้โดยไม่สูญเสียสถานะปัจจุบัน

ยังมีการเปลี่ยนแปลงเชิงสถาปัตยกรรมอื่นๆ ที่ใหญ่กว่าซึ่งผม[ยังไม่ปักใจเชื่อ](https://github.com/leptos-rs/leptos/issues/1830)

## ข้อมูลเพิ่มเติม

ลองดู[ตัวอย่าง `islands`](https://github.com/leptos-rs/leptos/blob/main/examples/islands/src/app.rs), [โรดแมป](https://github.com/leptos-rs/leptos/issues/1830) และ[เดโม Hackernews](https://github.com/leptos-rs/leptos/tree/leptos_0.6/examples/hackernews_islands_axum) สำหรับการอภิปรายเพิ่มเติม

## โค้ดเดโม

```rust
use leptos::prelude::*;

#[component]
pub fn App() -> impl IntoView {
    view! {
        <main style="background-color: lightblue; padding: 10px">
            <HomePage/>
        </main>
    }
}

/// Renders the home page of your application.
#[component]
fn HomePage() -> impl IntoView {
    let files = ["a.txt", "b.txt", "c.txt"];
    let labels = files.iter().copied().map(Into::into).collect();
    let tabs = move || {
        files
            .into_iter()
            .enumerate()
            .map(|(index, filename)| {
                let content = std::fs::read_to_string(filename).unwrap();
                view! {
                    <Tab index>
                        <div style="background-color: lightblue; padding: 10px">
                            <h2>{filename.to_string()}</h2>
                            <p>{content}</p>
                        </div>
                    </Tab>
                }
            })
            .collect_view()
    };

    view! {
        <h1>"Welcome to Leptos!"</h1>
        <p>"Click any of the tabs below to read a recipe."</p>
        <Tabs labels>
            <div>{tabs()}</div>
        </Tabs>
    }
}

#[island]
fn Tabs(labels: Vec<String>, children: Children) -> impl IntoView {
    let (selected, set_selected) = signal(0);
    provide_context(selected);

    let buttons = labels
        .into_iter()
        .enumerate()
        .map(|(index, label)| {
            view! {
                <button on:click=move |_| set_selected.set(index)>
                    {label}
                </button>
            }
        })
        .collect_view();
    view! {
        <div
            style="display: flex; width: 100%; justify-content: space-around;\
            background-color: lightgreen; padding: 10px;"
        >
            {buttons}
        </div>
        {children()}
    }
}

#[island]
fn Tab(index: usize, children: Children) -> impl IntoView {
    let selected = expect_context::<ReadSignal<usize>>();
    view! {
        <div
            style:background-color="lightgreen"
            style:padding="10px"
            style:display=move || if selected.get() == index {
                "block"
            } else {
                "none"
            }
        >
            {children()}
        </div>
    }
}
```
