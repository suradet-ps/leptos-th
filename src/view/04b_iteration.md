# การวนซ้ำข้อมูลที่ซับซ้อนขึ้นด้วย `<For/>`

บทนี้จะเจาะลึกขึ้นอีกเล็กน้อยเกี่ยวกับการวนลูปบนโครงสร้างข้อมูลแบบซ้อน แม้เนื้อหาจะถูกจัดวางไว้คู่กับบทการวนลูป แต่หากคุณอยากโฟกัสกับเรื่องพื้นฐานก่อน ก็สามารถข้ามบทนี้ไปก่อนแล้วค่อยย้อนกลับมาอ่านในภายหลังได้ตามสะดวก

## ปัญหา

ในบทที่แล้ว เราได้เรียนรู้ไปว่าเฟรมเวิร์กจะไม่เรนเดอร์แถวเดิมซ้ำอีก ตราบใดที่คีย์ของแถวนั้นยังไม่เปลี่ยนแปลง ซึ่งในตอนแรกก็ฟังดูสมเหตุสมผลดี แต่มันอาจทำให้คุณสะดุดได้ง่าย ๆ

ลองพิจารณาสถานการณ์ที่ไอเท็มแต่ละรายการในแถวเป็นโครงสร้างข้อมูล เช่น สมมติว่าข้อมูลมาจาก JSON array ที่ประกอบด้วยคีย์และค่าดังนี้:

```rust
#[derive(Debug, Clone)]
struct DatabaseEntry {
    key: String,
    value: i32,
}
```

มาเขียนคอมโพเนนต์ง่าย ๆ เพื่อวนลูปบนแถวต่าง ๆ แล้วแสดงแต่ละแถวกัน:

```rust
#[component]
pub fn App() -> impl IntoView {
    // start with a set of three rows
    let (data, set_data) = signal(vec![
        DatabaseEntry {
            key: "foo".to_string(),
            value: 10,
        },
        DatabaseEntry {
            key: "bar".to_string(),
            value: 20,
        },
        DatabaseEntry {
            key: "baz".to_string(),
            value: 15,
        },
    ]);
    view! {
        // when we click, update each row,
        // doubling its value
        <button on:click=move |_| {
            set_data.update(|data| {
                for row in data {
                    row.value *= 2;
                }
            });
            // log the new value of the signal
            leptos::logging::log!("{:?}", data.get());
        }>
            "Update Values"
        </button>
        // iterate over the rows and display each value
        <For
            each=move || data.get()
            key=|state| state.key.clone()
            let(child)
        >
            <p>{child.value}</p>
        </For>
    }
}
```

> สังเกตไวยากรณ์ `let(child)` ตรงนี้: ในบทก่อนหน้าเราได้แนะนำ `<For/>`
> พร้อมพร็อพ `children` อันที่จริงเราสามารถสร้างค่านี้โดยตรงในลูก (children)
> ของคอมโพเนนต์ `<For/>` ได้ โดยไม่ต้องออกจากมาโคร `view`: `let(child)`
> ที่ใช้ร่วมกับ `<p>{child.value}</p>` ข้างต้นนั้นเทียบเท่ากับ
>
> ```rust
> children=|child| view! { <p>{child.value}</p> }
> ```
>
> เพื่อความสะดวก คุณยังสามารถทำ destructuring กับข้อมูลของคุณได้ทันทีอีกด้วย:
>
> ```rust
> <For
>     each=move || data.get()
>     key=|state| state.key.clone()
>     let(DatabaseEntry { key, value })
> >
> ```

เมื่อคุณคลิกปุ่ม `Update Values`... กลับไม่มีอะไรเกิดขึ้นบนหน้าจอเลย! หรือพูดให้ชัดกว่านั้นคือ สัญญาณถูกอัปเดตแล้วจริง ๆ ค่าใหม่ถูกบันทึกลงล็อกเรียบร้อย แต่ค่าใน `{child.value}` ของแต่ละแถวกลับไม่อัปเดตตาม

มาดูกันว่าที่เป็นอย่างนี้เพราะเราลืมใส่โคลเชอร์เพื่อทำให้มันรีแอกทีฟหรือเปล่า? ลองเปลี่ยนเป็น `{move || child.value}` ดูสิ...

...ก็ยังไม่มีอะไรเกิดขึ้นอยู่ดี

สาเหตุของปัญหาคือ: ดังที่ได้บอกไปแล้วว่าแต่ละแถวจะถูกเรนเดอร์ซ้ำก็ต่อเมื่อคีย์เปลี่ยน เราอัปเดตค่าให้แต่ละแถวแล้ว แต่ไม่ได้เปลี่ยนคีย์ของแถวไหนเลย จึงไม่มีอะไรถูกเรนเดอร์ใหม่ และยิ่งไปกว่านั้น ถ้าคุณดูชนิดข้อมูลของ `child.value` มันก็เป็น `i32` ธรรมดา ไม่ใช่ `ReadSignal<i32>` หรืออะไรที่รีแอกทีฟได้ ซึ่งหมายความว่าแม้เราจะห่อมันด้วยโคลเชอร์ ค่าในแถวนี้ก็จะไม่มีวันตรวจพบการเปลี่ยนแปลงเพื่ออัปเดตได้อยู่ดี

เรามีทางแก้ที่เป็นไปได้ 4 ทาง:

1. เปลี่ยน `key` ให้อัปเดตทุกครั้งที่โครงสร้างข้อมูลเปลี่ยน
2. เปลี่ยน `value` ให้เป็นรีแอกทีฟ
3. ดึงสไลซ์รีแอกทีฟของโครงสร้างข้อมูลมาใช้ แทนที่จะใช้แต่ละแถวโดยตรง
4. ใช้ `Store`

## ทางเลือกที่ 1: เปลี่ยนคีย์

ในเมื่อแต่ละแถวจะถูกเรนเดอร์ซ้ำก็ต่อเมื่อคีย์เปลี่ยน และแถวของเราข้างต้นไม่ได้ถูกเรนเดอร์ซ้ำเพราะคีย์ไม่ได้เปลี่ยน ถ้างั้นทำไมเราไม่บังคับให้คีย์เปลี่ยนตามค่าไปเลยล่ะ?

```rust
<For
	each=move || data.get()
	key=|state| (state.key.clone(), state.value)
	let(child)
>
	<p>{child.value}</p>
</For>
```

ตอนนี้เราใส่ทั้งคีย์และค่าลงใน `key` ซึ่งหมายความว่าเมื่อใดก็ตามที่ค่าของแถวเปลี่ยน `<For/>` จะมองมันเป็นแถวใหม่ทั้งหมด แล้วแทนที่แถวก่อนหน้าทิ้ง

### ข้อดี

วิธีนี้ง่ายมาก และเราทำให้ง่ายยิ่งขึ้นได้ด้วยการ derive `PartialEq`, `Eq` และ `Hash` บน `DatabaseEntry` ซึ่งในกรณีนั้นเราก็ใช้แค่ `key=|state| state.clone()` ได้เลย

### ข้อเสีย

**วิธีนี้มีประสิทธิภาพต่ำที่สุดในบรรดาสี่ทางเลือก** ทุกครั้งที่ค่าของแถวเปลี่ยน มันจะทิ้งเอลิเมนต์ `<p>` เดิมแล้วแทนที่ด้วยอันใหม่ทั้งหมด พูดอีกอย่างคือ แทนที่จะอัปเดตโหนดข้อความแบบละเอียด มันเรนเดอร์ทั้งแถวซ้ำจริง ๆ ทุกครั้งที่เปลี่ยน และค่าใช้จ่ายตรงนี้จะสูงขึ้นตามความซับซ้อนของ UI ในแถวนั้น

คุณจะสังเกตว่าเราต้องโคลนโครงสร้างข้อมูลทั้งก้อนด้วย เพื่อให้ `<For/>` เก็บสำเนาของคีย์ไว้ได้ สำหรับโครงสร้างที่ซับซ้อนกว่านี้ สิ่งนี้อาจกลายเป็นปัญหาด้านประสิทธิภาพได้อย่างรวดเร็ว!

## ทางเลือกที่ 2: สัญญาณซ้อน

หากเราต้องการการตอบสนองแบบละเอียด (fine-grained reactivity) ให้กับค่านั้นจริง ๆ ทางออกหนึ่งคือการห่อ `value` ของแต่ละแถวไว้ในสัญญาณ (signal)

```rust
#[derive(Debug, Clone)]
struct DatabaseEntry {
    key: String,
    value: RwSignal<i32>,
}
```

`RwSignal<_>` คือ "สัญญาณอ่าน-เขียน" ที่รวม getter และ setter ไว้ในตัวเดียว เราเลือกใช้ตรงนี้เพราะเก็บในสตรัคต์ได้สะดวกกว่าการแยก getter กับ setter ออกจากกัน

```rust
#[component]
pub fn App() -> impl IntoView {
    // start with a set of three rows
    let (data, _set_data) = signal(vec![
        DatabaseEntry {
            key: "foo".to_string(),
            value: RwSignal::new(10),
        },
        DatabaseEntry {
            key: "bar".to_string(),
            value: RwSignal::new(20),
        },
        DatabaseEntry {
            key: "baz".to_string(),
            value: RwSignal::new(15),
        },
    ]);
    view! {
        // when we click, update each row,
        // doubling its value
        <button on:click=move |_| {
            for row in &*data.read() {
                row.value.update(|value| *value *= 2);
            }
            // log the new value of the signal
            leptos::logging::log!("{:?}", data.get());
        }>
            "Update Values"
        </button>
        // iterate over the rows and display each value
        <For
            each=move || data.get()
            key=|state| state.key.clone()
            let(child)
        >
            <p>{child.value}</p>
        </For>
    }
}
```

เวอร์ชันนี้ทำงานได้อย่างสมบูรณ์แบบ! หากคุณเปิด DOM inspector ในเบราว์เซอร์ดู จะเห็นความแตกต่างชัดเจนจากทางเลือกแรก เพราะคราวนี้มีเพียงแค่โหนดข้อความ (text node) ของแต่ละแถวเท่านั้นที่ถูกอัปเดต การส่งสัญญาณเข้าไปใน `{child.value}` โดยตรงให้ผลลัพธ์ที่ดีเยี่ยม เพราะสัญญาณยังคงรักษารีแอกทิวิตีไว้เมื่อถูกส่งเข้าไปในวิว

สังเกตว่าเราเปลี่ยนจากการเรียก `set_data.update()` มาเป็น `data.read()` โดย `.read()` เป็นวิธีเข้าถึงค่าในสัญญาณแบบที่ไม่ต้องโคลนข้อมูล และในกรณีนี้เราอัปเดตแค่ค่าภายใน ไม่ได้อัปเดตตัวรายการของข้อมูล เพราะสัญญาณแต่ละตัวดูแลสถานะของตัวเองอยู่แล้ว เราจึงไม่จำเป็นต้องอัปเดตสัญญาณ `data` หลักเลย การใช้ `.read()` ที่ไม่เปลี่ยนแปลงค่าจึงเหมาะสมอย่างยิ่งในจุดนี้

> อันที่จริง เวอร์ชันนี้ไม่ได้สั่งอัปเดต `data` เลย ดังนั้น `<For/>` จึงทำหน้าที่
> เหมือนรายการสแตติกในบทที่แล้ว และตรงนี้จะใช้อิเทอเรเตอร์ธรรมดาก็ได้
> แต่การใช้ `<For/>` จะมีประโยชน์เมื่อเราต้องการเพิ่มหรือลบแถวในอนาคต

### ข้อดี

นี่คือทางเลือกที่มีประสิทธิภาพสูงสุด และสอดคล้องกับโมเดลทางความคิด (mental model) ของเฟรมเวิร์กอย่างลงตัว: ข้อมูลใดที่เปลี่ยนแปลงไปตามเวลา ให้ห่อไว้ในสัญญาณ เพื่อให้อินเทอร์เฟซตอบสนองต่อค่าเหล่านั้นได้อย่างตรงจุด

### ข้อเสีย

การใช้สัญญาณซ้อนอาจเพิ่มความยุ่งยากหากคุณได้รับข้อมูลมาจาก API หรือแหล่งข้อมูลภายนอกที่คุณควบคุมโครงสร้างไม่ได้ และไม่อยากต้องมาคอยแปลงข้อมูลเพื่อห่อแต่ละฟิลด์ไว้ในสัญญาณ

## ทางเลือกที่ 3: สไลซ์แบบเมโม

Leptos มีพริมิทีฟที่เรียกว่า [`Memo`](https://docs.rs/leptos/latest/leptos/reactive/computed/struct.Memo.html) ซึ่งสร้างการคำนวณอนุพัทธ์ที่จะกระตุ้นการอัปเดตรีแอกทีฟก็ต่อเมื่อค่าผลลัพธ์จริง ๆ มีการเปลี่ยนแปลงแล้วเท่านั้น

วิธีนี้เปิดโอกาสให้คุณสร้างค่ารีแอกทีฟสำหรับฟิลด์ย่อยของโครงสร้างข้อมูลขนาดใหญ่ได้ โดยไม่ต้องห่อฟิลด์ของโครงสร้างนั้นในสัญญาณ และเมื่อใช้ร่วมกับ [`<ForEnumerate/>`](https://docs.rs/leptos/latest/leptos/control_flow/fn.ForEnumerate.html) จะทำให้เราเรนเดอร์ซ้ำเฉพาะค่าข้อมูลที่เปลี่ยนแปลงเท่านั้น

แอปพลิเคชันส่วนใหญ่ยังคงเหมือนกับเวอร์ชันแรกได้ แต่ `<For/>` จะถูกปรับเปลี่ยนเป็นแบบนี้:

```rust
<ForEnumerate
    each=move || data.get()
    key=|state| state.key.clone()
    children=move |index, _| {
        let value = Memo::new(move |_| {
            data.with(|data| data.get(index.get()).map(|d| d.value).unwrap_or(0))
        });
        view! {
            <p>{value}</p>
        }
    }
/>
```

คุณจะสังเกตเห็นความแตกต่างสองสามอย่างตรงนี้:

- เราใช้ `ForEnumerate` แทน `For` เพื่อให้เข้าถึงสัญญาณ `index` ได้
- เราใช้พร็อพ `children` อย่างชัดเจน เพื่อให้เขียนโค้ดเตรียมค่าก่อนสร้าง `view` ได้สะดวกขึ้น
- เรานิยามเมโม `value` แล้วนำไปใช้ในวิว โดยฟิลด์ `value` นี้ไม่ได้ใช้ `child` ที่ส่งเข้ามาในแต่ละแถวตรง ๆ แต่ใช้ดัชนี (index) ย้อนกลับไปดึงค่าจากสัญญาณ `data` ต้นฉบับแทน

ตอนนี้ทุกครั้งที่ `data` เปลี่ยน เมโมแต่ละตัวจะถูกคำนวณใหม่ และถ้าค่าของมันเปลี่ยนไป มันก็จะอัปเดตเฉพาะโหนดข้อความของตัวเอง โดยไม่ต้องเรนเดอร์ทั้งแถวซ้ำ

**หมายเหตุ**: การใช้ `For` กับอิเทอเรเตอร์ที่ผ่านการ enumerate แบบนี้ไม่ปลอดภัย ดังในตัวอย่างเวอร์ชันก่อนหน้านี้:

```rust
<For
    each=move || data.get().into_iter().enumerate()
    key=|(_, state)| state.key.clone()
    children=move |(index, _)| {
        let value = Memo::new(move |_| {
            data.with(|data| data.get(index).map(|d| d.value).unwrap_or(0))
        });
        view! {
            <p>{value}</p>
        }
    }
/>
```

ในกรณีนี้ การเปลี่ยนแปลงค่าภายใน `data` จะได้รับการตอบสนอง แต่การเปลี่ยนแปลงลำดับตำแหน่งจะไม่ตอบสนอง เพราะเมโมจะจำค่า `index` ที่มันถูกสร้างขึ้นครั้งแรกเสมอ ซึ่งจะทำให้เกิดข้อมูลซ้ำในผลลัพธ์ที่เรนเดอร์ออกมา หากมีการย้ายสลับตำแหน่งไอเท็ม

### ข้อดี

เราได้รีแอกทิวิตีแบบละเอียดเหมือนกับเวอร์ชันที่ห่อด้วยสัญญาณ โดยไม่ต้องนำข้อมูลไปห่อในสัญญาณตั้งแต่ต้น

### ข้อเสีย

การตั้งค่าเมโมแยกรายแถวแบบนี้ภายในลูป `<ForEnumerate/>` ซับซ้อนกว่าการใช้สัญญาณซ้อนเล็กน้อย ตัวอย่างเช่น คุณจะสังเกตว่าเราต้องป้องกันไม่ให้ `data[index.get()]` เกิด panic ด้วยการใช้ `data.get(index.get())` เพราะเมโมตัวนี้อาจถูกกระตุ้นให้ทำงานอีกครั้งในจังหวะเดียวกับที่แถวเพิ่งถูกลบออกไป (นี่เป็นเพราะทั้งเมโมของแต่ละแถวและคอมโพเนนต์ `<ForEnumerate/>` ต่างพึ่งพาสัญญาณ `data` ตัวเดียวกัน และลำดับการทำงานของตัวรีแอกทีฟหลายตัวที่พึ่งพาสัญญาณเดียวกันนั้นไม่มีการรับประกันลำดับก่อนหลัง)

นอกจากนี้ แม้เมโมจะช่วยป้องกันไม่ให้อัปเดต DOM ซ้ำซ้อน แต่ฟังก์ชันคำนวณก็ยังต้องรันเพื่อตรวจสอบค่าทุกครั้ง ดังนั้นสัญญาณรีแอกทีฟแบบซ้อนจะยังมีประสิทธิภาพสูงกว่าสำหรับการอัปเดตแบบเจาะจงตรงนี้

## ทางเลือกที่ 4: สโตร์

> เนื้อหาบางส่วนในหัวข้อนี้จะสอดคล้องกับหัวข้อการจัดการสถานะส่วนกลางด้วยสโตร์[ที่นี่](../15_global_state.md#ทางเลือกที-3-สรางสโตรสถานะสวนกลาง) เนื่องจากทั้งสองส่วนเป็นเนื้อหาระดับกลางและเป็นทางเลือกเสริม การมีเนื้อหาที่ทับซ้อนกันบ้างจึงช่วยให้เห็นภาพการใช้งานในแต่ละบริบทได้ชัดเจนยิ่งขึ้น

Leptos 0.7 ได้เปิดตัวพริมิทีฟรีแอกทีฟตัวใหม่ที่เรียกว่า "สโตร์" (stores) ซึ่งถูกออกแบบมาโดยตรงเพื่อแก้ปัญหาความท้าทายต่าง ๆ ที่เราได้อธิบายมาตั้งแต่ต้นบทนี้ โดยฟีเจอร์นี้ยังอยู่ในช่วงพัฒนา จึงต้องเพิ่มดีเพนเดนซี `reactive_stores` เข้ามาใน `Cargo.toml` ของคุณ

สโตร์เปิดโอกาสให้คุณเข้าถึงแต่ละฟิลด์ของสตรัคต์ และแต่ละไอเท็มในคอลเลกชันอย่าง `Vec<_>` ได้อย่างละเอียดแบบรีแอกทีฟ โดยไม่ต้องสร้างสัญญาณซ้อนหรือเขียนเมโมด้วยตนเองเหมือนแนวทางก่อนหน้า

เบื้องหลังของสโตร์ทำงานผ่าน derive macro `Store` ซึ่งจะสร้างเก็ตเตอร์ให้กับทุกฟิลด์ของสตรัคต์ การเรียกเก็ตเตอร์นี้จะทำให้เราเข้าถึงฟิลด์นั้น ๆ แบบรีแอกทีฟ โดยการอ่านค่าจะติดตาม (track) เฉพาะฟิลด์นั้นกับพ่อแม่/children ของมัน และการอัปเดตก็จะแจ้งเตือนเฉพาะฟิลด์นั้นกับพ่อแม่/children ของมัน แต่จะไม่แจ้งเตือนฟิลด์พี่น้อง พูดง่าย ๆ คือ การแก้ไข `value` จะไม่ไปกระตุ้นการแจ้งเตือนของ `key` เป็นต้น

เราสามารถนำโครงสร้างข้อมูลที่ใช้ในตัวอย่างข้างต้นมาปรับใช้ได้ดังนี้:

ระดับบนสุดของสโตร์จำเป็นต้องเป็นสตรัคต์เสมอ เราจึงจะสร้าง `Data` ที่ทำหน้าที่เป็นตัวห่อพร้อมฟิลด์ `rows` เพียงฟิลด์เดียว:

```rust
#[derive(Store, Debug, Clone)]
pub struct Data {
    #[store(key: String = |row| row.key.clone())]
    rows: Vec<DatabaseEntry>,
}

#[derive(Store, Debug, Clone)]
struct DatabaseEntry {
    key: String,
    value: i32,
}
```

การใส่ `#[store(key)]` ให้กับฟิลด์ `rows` ทำให้เราเข้าถึงแต่ละฟิลด์ของสโตร์แบบมีคีย์ได้ ซึ่งมีประโยชน์มากในคอมโพเนนต์ `<For/>` ด้านล่าง โดยเราสามารถใช้ `key` เดียวกับที่เราตั้งใจจะใช้ใน `<For/>` ได้เลย

การเขียนคอมโพเนนต์ `<For/>` ร่วมกับสโตร์นั้นตรงไปตรงมามาก:

```rust
<For
    each=move || data.rows()
    key=|row| row.read().key.clone()
    children=|child| {
        let value = child.value();
        view! { <p>{move || value.get()}</p> }
    }
/>
```

เนื่องจาก `rows` เป็นฟิลด์แบบมีคีย์ มันจึงอิมพลีเมนต์ `IntoIterator` ทำให้เราสามารถส่ง `move || data.rows()` เข้าไปที่พร็อพ `each` ได้โดยตรง ซึ่งจะตอบสนองต่อการเปลี่ยนแปลงใด ๆ ของรายการ `rows` เช่นเดียวกับที่ `move || data.get()` ทำในเวอร์ชันสัญญาณซ้อน

ส่วนของ `key` เราจะเรียก `.read()` เพื่อเข้าถึงค่าปัจจุบันของแถวนั้น แล้วโคลนค่าจากฟิลด์ `key` ส่งกลับไป

ในพร็อพ `children` การเรียก `child.value()` จะทำให้เราเข้าถึงฟิลด์ `value` ของแถวที่มีคีย์นี้แบบรีแอกทีฟ และหากแถวถูกสลับลำดับ เพิ่ม หรือลบ ฟิลด์ของสโตร์แบบมีคีย์นี้จะคอยซิงก์ตำแหน่งให้เสมอ ทำให้ `value` นี้เชื่อมโยงกับแถวและคีย์ที่ถูกต้องตลอดเวลา

สำหรับตัวจัดการเหตุการณ์ของปุ่ม เราจะวนลูปบนรายการใน `rows` แล้วอัปเดตค่าทีละรายการ:

```rust
for row in data.rows().iter_unkeyed() {
    *row.value().write() *= 2;
}
```

### ข้อดี

เราได้รีแอกทิวิตีแบบละเอียดเหมือนกับเวอร์ชันสัญญาณซ้อนและเวอร์ชันเมโม โดยไม่ต้องมาสร้างสัญญาณซ้อนหรือสไลซ์เมโมด้วยตัวเอง เราสามารถทำงานกับข้อมูลธรรมดา (สตรัคต์และ `Vec<_>`) ที่กำกับด้วย derive macro แทนที่จะต้องใช้ชนิดข้อมูลรีแอกทีฟพิเศษแบบซ้อนกัน

โดยส่วนตัวแล้ว คิดว่าเวอร์ชันสโตร์เป็นรูปแบบที่สวยงามและลงตัวที่สุด ซึ่งก็ไม่น่าแปลกใจ เพราะเป็น API ใหม่ล่าสุดที่กลั่นกรองมาจากประสบการณ์และบทเรียนตลอดหลายปีในการพัฒนา Leptos

### ข้อเสีย

ในทางกลับกัน เนื่องจากเป็น API ใหม่ล่าสุด (ธันวาคม 2024) สโตร์เพิ่งเปิดตัวได้ไม่นาน จึงอาจยังมีบั๊กหรือกรณีขอบ (edge case) บางประการที่ต้องขัดเกลาเพิ่มเติม

### ตัวอย่างเต็ม

นี่คือตัวอย่างสโตร์ฉบับเต็ม คุณสามารถดูตัวอย่างอื่นที่สมบูรณ์กว่าได้[ที่นี่](https://github.com/leptos-rs/leptos/blob/main/examples/stores/src/lib.rs) และอ่านการอภิปรายเพิ่มเติมในหนังสือได้[ที่นี่](../15_global_state.md)

```
use reactive_stores::Store;

#[derive(Store, Debug, Clone)]
pub struct Data {
    #[store(key: String = |row| row.key.clone())]
    rows: Vec<DatabaseEntry>,
}

#[derive(Store, Debug, Clone)]
struct DatabaseEntry {
    key: String,
    value: i32,
}

#[component]
pub fn App() -> impl IntoView {
    // instead of a signal with the rows, we create a store for Data
    let data = Store::new(Data {
        rows: vec![
            DatabaseEntry {
                key: "foo".to_string(),
                value: 10,
            },
            DatabaseEntry {
                key: "bar".to_string(),
                value: 20,
            },
            DatabaseEntry {
                key: "baz".to_string(),
                value: 15,
            },
        ],
    });

    view! {
        // when we click, update each row,
        // doubling its value
        <button on:click=move |_| {
            // allows iterating over the entries in an iterable store field
            use reactive_stores::StoreFieldIterator;

            // calling rows() gives us access to the rows
            for row in data.rows().iter_unkeyed() {
                *row.value().write() *= 2;
            }
            // log the new value of the signal
            leptos::logging::log!("{:?}", data.get());
        }>
            "Update Values"
        </button>
        // iterate over the rows and display each value
        <For
            each=move || data.rows()
            key=|row| row.read().key.clone()
            children=|child| {
                let value = child.value();
                view! { <p>{move || value.get()}</p> }
            }
        />
    }
}
```
