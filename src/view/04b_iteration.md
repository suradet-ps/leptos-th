# การวนซ้ำข้อมูลที่ซับซ้อนขึ้นด้วย `<For/>`

บทนี้จะลงลึกกว่าที่ผ่านมาเล็กน้อยเกี่ยวกับการวนซ้ำบนโครงสร้างข้อมูลแบบซ้อน บทนี้อยู่ในตำแหน่งนี้คู่กับบทอื่นว่าด้วยการวนซ้ำ แต่คุณสามารถข้ามไปก่อนแล้วค่อยกลับมาอ่านทีหลังได้ตามสบาย ถ้าตอนนี้คุณอยากอยู่กับเรื่องที่ง่ายกว่านี้ก่อน

## ปัญหา

เมื่อครู่นี้ผมเพิ่งบอกว่าเฟรมเวิร์กจะไม่เรนเดอร์ไอเท็มใดๆ ในแถวซ้ำอีก ตราบใดที่คีย์ไม่เปลี่ยน ซึ่งตอนแรกก็อาจดูสมเหตุสมผลดี แต่มันอาจทำให้คุณสะดุดได้ง่ายๆ

ลองพิจารณาตัวอย่างที่ไอเท็มแต่ละรายการในแถวของเราเป็นโครงสร้างข้อมูลอะไรสักอย่าง ตัวอย่างเช่น จินตนาการว่าไอเท็มเหล่านั้นมาจากอาร์เรย์ JSON ของคีย์และค่าดังนี้:

```rust
#[derive(Debug, Clone)]
struct DatabaseEntry {
    key: String,
    value: i32,
}
```

มาเขียนคอมโพเนนต์ง่ายๆ ที่จะวนซ้ำบนแถวต่างๆ แล้วแสดงแต่ละแถวกัน:

```rust
#[component]
pub fn App() -> impl IntoView {
    // start with a set of three rows
    let (data, set_data) = signal(vec![
        DatabaseEntry {
            key: "foo".to_string(),
            value: 10,
        },
        DatabaseEntry {
            key: "bar".to_string(),
            value: 20,
        },
        DatabaseEntry {
            key: "baz".to_string(),
            value: 15,
        },
    ]);
    view! {
        // when we click, update each row,
        // doubling its value
        <button on:click=move |_| {
            set_data.update(|data| {
                for row in data {
                    row.value *= 2;
                }
            });
            // log the new value of the signal
            leptos::logging::log!("{:?}", data.get());
        }>
            "Update Values"
        </button>
        // iterate over the rows and display each value
        <For
            each=move || data.get()
            key=|state| state.key.clone()
            let(child)
        >
            <p>{child.value}</p>
        </For>
    }
}
```

> สังเกตไวยากรณ์ `let(child)` ตรงนี้ ในบทที่แล้วเราได้แนะนำ `<For/>`
> พร้อมพร็อพ `children` อันที่จริงเราสามารถสร้างค่านี้โดยตรงในลูก (children)
> ของคอมโพเนนต์ `<For/>` ได้ โดยไม่ต้องออกจากมาโคร `view`: `let(child)`
> ที่ใช้ร่วมกับ `<p>{child.value}</p>` ข้างต้นนั้นเทียบเท่ากับ
>
> ```rust
> children=|child| view! { <p>{child.value}</p> }
> ```
>
> เพื่อความสะดวก คุณยังเลือกดีสตรัคเจอร์แพตเทิร์นของข้อมูลของคุณได้ด้วย:
>
> ```rust
> <For
>     each=move || data.get()
>     key=|state| state.key.clone()
>     let(DatabaseEntry { key, value })
> >
> ```

เมื่อคุณคลิกปุ่ม `Update Values`... ไม่มีอะไรเกิดขึ้น หรือพูดให้ชัดกว่านั้นคือ สัญญาณถูกอัปเดต ค่าใหม่ถูกบันทึกลงล็อก แต่ `{child.value}` ของแต่ละแถวกลับไม่อัปเดต

มาดูกันว่าที่เป็นอย่างนี้เพราะเราลืมใส่โคลเชอร์เพื่อทำให้มันรีแอกทีฟหรือเปล่า? ลองเปลี่ยนเป็น `{move || child.value}` ดูสิ

...ไม่หรอก ก็ยังไม่มีอะไรเกิดขึ้นอยู่ดี

นี่คือปัญหา: อย่างที่ผมบอกไปแล้วว่าแต่ละแถวจะถูกเรนเดอร์ซ้ำก็ต่อเมื่อคีย์เปลี่ยน เราอัปเดตค่าให้แต่ละแถวแล้ว แต่ไม่ได้เปลี่ยนคีย์ของแถวไหนเลย จึงไม่มีอะไรถูกเรนเดอร์ซ้ำ และถ้าคุณดูชนิดข้อมูลของ `child.value` มันก็เป็น `i32` ธรรมดา ไม่ใช่ `ReadSignal<i32>` หรืออะไรที่รีแอกทีฟได้ ซึ่งหมายความว่าแม้เราจะห่อมันด้วยโคลเชอร์ ค่าในแถวนี้ก็จะไม่มีวันอัปเดต

เรามีทางแก้ที่เป็นไปได้สี่ทาง:

1. เปลี่ยน `key` ให้อัปเดตทุกครั้งที่โครงสร้างข้อมูลเปลี่ยน
2. เปลี่ยน `value` ให้เป็นรีแอกทีฟ
3. ดึงสไลซ์รีแอกทีฟของโครงสร้างข้อมูลมาใช้ แทนที่จะใช้แต่ละแถวโดยตรง
4. ใช้ `Store`

## ทางเลือกที่ 1: เปลี่ยนคีย์

แต่ละแถวจะถูกเรนเดอร์ซ้ำก็ต่อเมื่อคีย์เปลี่ยน แถวของเราข้างต้นไม่ได้ถูกเรนเดอร์ซ้ำ เพราะคีย์ไม่ได้เปลี่ยน ถ้างั้นทำไมเราไม่บังคับให้คีย์เปลี่ยนไปเลยล่ะ?

```rust
<For
	each=move || data.get()
	key=|state| (state.key.clone(), state.value)
	let(child)
>
	<p>{child.value}</p>
</For>
```

ตอนนี้เราใส่ทั้งคีย์และค่าลงใน `key` ซึ่งหมายความว่าเมื่อใดก็ตามที่ค่าของแถวเปลี่ยน `<For/>` จะมองมันเป็นแถวใหม่ทั้งหมด แล้วแทนที่แถวก่อนหน้าทิ้ง

### ข้อดี

วิธีนี้ง่ายมาก และเราทำให้ง่ายยิ่งขึ้นได้ด้วยการดีไรฟ์ `PartialEq`, `Eq` และ `Hash` บน `DatabaseEntry` ซึ่งในกรณีนั้นเราก็ใช้แค่ `key=|state| state.clone()` ได้เลย

### ข้อเสีย

**วิธีนี้มีประสิทธิภาพต่ำที่สุดในบรรดาสี่ทางเลือก** ทุกครั้งที่ค่าของแถวเปลี่ยน มันจะทิ้งเอลิเมนต์ `<p>` เดิมแล้วแทนที่ด้วยอันใหม่ทั้งหมด พูดอีกอย่างคือ แทนที่จะอัปเดตโหนดข้อความแบบละเอียด มันเรนเดอร์ทั้งแถวซ้ำจริงๆ ทุกครั้งที่เปลี่ยน และค่าใช้จ่ายตรงนี้จะสูงขึ้นตามความซับซ้อนของ UI ในแถวนั้น

คุณจะสังเกตว่าเราต้องโคลนโครงสร้างข้อมูลทั้งก้อนด้วย เพื่อให้ `<For/>` เก็บสำเนาของคีย์ไว้ได้ สำหรับโครงสร้างที่ซับซ้อนกว่านี้ สิ่งนี้อาจกลายเป็นความคิดที่ไม่ดีอย่างรวดเร็ว!

## ทางเลือกที่ 2: สัญญาณซ้อน

ถ้าเราต้องการรีแอกทิวิตีแบบละเอียดสำหรับค่านั้นจริงๆ ทางเลือกหนึ่งคือห่อ `value` ของแต่ละแถวไว้ในสัญญาณ

```rust
#[derive(Debug, Clone)]
struct DatabaseEntry {
    key: String,
    value: RwSignal<i32>,
}
```

`RwSignal<_>` คือ "สัญญาณอ่าน-เขียน" ที่รวมเก็ตเตอร์และเซ็ตเตอร์ไว้ในออบเจกต์เดียว ผมใช้มันตรงนี้เพราะมันเก็บในสตรัคต์ได้ง่ายกว่าการแยกเก็ตเตอร์กับเซ็ตเตอร์ออกจากกันนิดหน่อย

```rust
#[component]
pub fn App() -> impl IntoView {
    // start with a set of three rows
    let (data, _set_data) = signal(vec![
        DatabaseEntry {
            key: "foo".to_string(),
            value: RwSignal::new(10),
        },
        DatabaseEntry {
            key: "bar".to_string(),
            value: RwSignal::new(20),
        },
        DatabaseEntry {
            key: "baz".to_string(),
            value: RwSignal::new(15),
        },
    ]);
    view! {
        // when we click, update each row,
        // doubling its value
        <button on:click=move |_| {
            for row in &*data.read() {
                row.value.update(|value| *value *= 2);
            }
            // log the new value of the signal
            leptos::logging::log!("{:?}", data.get());
        }>
            "Update Values"
        </button>
        // iterate over the rows and display each value
        <For
            each=move || data.get()
            key=|state| state.key.clone()
            let(child)
        >
            <p>{child.value}</p>
        </For>
    }
}
```

เวอร์ชันนี้ได้ผล! และถ้าคุณดูใน DOM inspector ของเบราว์เซอร์ คุณจะเห็นว่าต่างจากเวอร์ชันก่อน ตรงที่ในเวอร์ชันนี้มีแค่โหนดข้อความแต่ละอันที่ถูกอัปเดต การส่งสัญญาณเข้าไปใน `{child.value}` โดยตรงนั้นได้ผล เพราะสัญญาณยังคงรักษารีแอกทิวิตีไว้เมื่อคุณส่งมันเข้าไปในวิว

สังเกตว่าผมเปลี่ยน `set_data.update()` เป็น `data.read()` โดย `.read()` เป็นวิธีเข้าถึงค่าของสัญญาณแบบที่ไม่ต้องโคลน ในกรณีนี้ เราอัปเดตแค่ค่าภายใน ไม่ได้อัปเดตรายการของค่า เพราะสัญญาณดูแลสถานะของตัวเองอยู่แล้ว เราจึงไม่จำเป็นต้องอัปเดตสัญญาณ `data` เลย การใช้ `.read()` ที่ไม่เปลี่ยนค่าจึงเหมาะสมตรงนี้

> อันที่จริง เวอร์ชันนี้ไม่ได้อัปเดต `data` เลย ดังนั้น `<For/>` จึงเป็นได้
> แค่รายการสแตติกเหมือนในบทที่แล้ว และตรงนี้จะใช้อิเทอเรเตอร์ธรรมดาก็ได้
> แต่ `<For/>` จะมีประโยชน์ถ้าเราต้องการเพิ่มหรือลบแถวในอนาคต

### ข้อดี

นี่คือทางเลือกที่มีประสิทธิภาพที่สุด และสอดคล้องโดยตรงกับแบบจำลองทางความคิดส่วนที่เหลือของเฟรมเวิร์ก: ค่าที่เปลี่ยนแปลงไปตามเวลาจะถูกห่อไว้ในสัญญาณ เพื่อให้อินเทอร์เฟซตอบสนองต่อค่าเหล่านั้นได้

### ข้อเสีย

รีแอกทิวิตีแบบซ้อนอาจยุ่งยากถ้าคุณได้รับข้อมูลจาก API หรือแหล่งข้อมูลอื่นที่คุณควบคุมไม่ได้ และคุณไม่อยากสร้างสตรัคต์อีกแบบที่ห่อแต่ละฟิลด์ไว้ในสัญญาณ

## ทางเลือกที่ 3: สไลซ์แบบเมโม

Leptos มีพริมิทีฟที่เรียกว่า [`Memo`](https://docs.rs/leptos/latest/leptos/reactive/computed/struct.Memo.html) ซึ่งสร้างการคำนวณอนุพัทธ์ที่กระตุ้นการอัปเดตรีแอกทีฟก็ต่อเมื่อค่าของมันเปลี่ยนไปแล้วเท่านั้น

วิธีนี้ให้คุณสร้างค่ารีแอกทีฟสำหรับฟิลด์ย่อยของโครงสร้างข้อมูลขนาดใหญ่ได้ โดยไม่ต้องห่อฟิลด์ของโครงสร้างนั้นในสัญญาณ เมื่อใช้ร่วมกับ [`<ForEnumerate/>`](https://docs.rs/leptos/latest/leptos/control_flow/fn.ForEnumerate.html) จะทำให้เราเรนเดอร์ซ้ำเฉพาะค่าข้อมูลที่เปลี่ยนแปลงเท่านั้น

แอปพลิเคชันส่วนใหญ่ยังคงเหมือนกับเวอร์ชันแรก (ที่พัง) ได้ แต่ `<For/>` จะถูกเปลี่ยนเป็นแบบนี้:

```rust
<ForEnumerate
    each=move || data.get()
    key=|state| state.key.clone()
    children=move |index, _| {
        let value = Memo::new(move |_| {
            data.with(|data| data.get(index.get()).map(|d| d.value).unwrap_or(0))
        });
        view! {
            <p>{value}</p>
        }
    }
/>
```

คุณจะสังเกตเห็นความแตกต่างสองสามอย่างตรงนี้:

- เราใช้ `ForEnumerate` แทน `For` เพื่อให้เข้าถึงสัญญาณ `index` ได้
- เราใช้พร็อพ `children` อย่างชัดเจน เพื่อให้เขียนโค้ดที่ไม่ใช่ `view` ได้ง่ายขึ้น
- เรานิยามเมโม `value` แล้วใช้มันในวิว ฟิลด์ `value` นี้ไม่ได้ใช้ `child` ที่ส่งเข้ามาในแต่ละแถวจริงๆ แต่ใช้อินเด็กซ์แล้วย้อนกลับไปดึงค่าจาก `data` ต้นฉบับแทน

ตอนนี้ทุกครั้งที่ `data` เปลี่ยน เมโมแต่ละตัวจะถูกคำนวณใหม่ ถ้าค่าของมันเปลี่ยนไป มันก็จะอัปเดตโหนดข้อความของตัวเอง โดยไม่ต้องเรนเดอร์ทั้งแถวซ้ำ

**หมายเหตุ**: การใช้ `For` กับอิเทอเรเตอร์ที่ผ่านการ enumerate แบบนี้ไม่ปลอดภัย ดังในตัวอย่างเวอร์ชันก่อนหน้าของเรานี้:

```rust
<For
    each=move || data.get().into_iter().enumerate()
    key=|(_, state)| state.key.clone()
    children=move |(index, _)| {
        let value = Memo::new(move |_| {
            data.with(|data| data.get(index).map(|d| d.value).unwrap_or(0))
        });
        view! {
            <p>{value}</p>
        }
    }
/>
```

ในกรณีนี้ การเปลี่ยนแปลงค่าภายใน `data` จะได้รับการตอบสนอง แต่การเปลี่ยนแปลงลำดับจะไม่ เพราะเมโมจะใช้ `index` ที่มันถูกสร้างขึ้นครั้งแรกเสมอ ซึ่งจะทำให้เกิดรายการซ้ำในผลลัพธ์ที่เรนเดอร์ออกมา ถ้ามีการย้ายไอเท็มใดๆ

### ข้อดี

เราได้รีแอกทิวิตีแบบละเอียดเหมือนกับเวอร์ชันที่ห่อด้วยสัญญาณ โดยไม่ต้องห่อข้อมูลในสัญญาณ

### ข้อเสีย

การตั้งค่าเมโมต่อแถวแบบนี้ภายในลูป `<ForEnumerate/>` ซับซ้อนกว่าการใช้สัญญาณซ้อนเล็กน้อย ตัวอย่างเช่น คุณจะสังเกตว่าเราต้องป้องกันความเป็นไปได้ที่ `data[index.get()]` จะ panic ด้วยการใช้ `data.get(index.get())` เพราะเมโมตัวนี้อาจถูกกระตุ้นให้รันอีกครั้งหนึ่งทันทีหลังจากแถวถูกลบออก (นี่เป็นเพราะเมโมของแต่ละแถวกับ `<ForEnumerate/>` ทั้งตัวต่างก็พึ่งพาสัญญาณ `data` ตัวเดียวกัน และลำดับการทำงานของค่ารีแอกทีฟหลายตัวที่พึ่งพาสัญญาณตัวเดียวกันนั้นไม่มีการรับประกัน)

และขอสังเกตด้วยว่า แม้เมโมจะทำการเมโมไมซ์การเปลี่ยนแปลงแบบรีแอกทีฟของตัวเอง แต่การคำนวณเดิมก็ยังต้องรันซ้ำเพื่อตรวจสอบค่าทุกครั้ง ดังนั้นสัญญาณรีแอกทีฟแบบซ้อนจะยังมีประสิทธิภาพมากกว่าสำหรับการอัปเดตแบบเจาะจงตรงนี้

## ทางเลือกที่ 4: สโตร์

> เนื้อหาบางส่วนซ้ำกับหัวข้อว่าด้วยการจัดการสถานะส่วนกลางด้วยสโตร์[ที่นี่](../15_global_state.md#option-3-create-a-global-state-store) ทั้งสองส่วนเป็นเนื้อหาระดับกลาง/ไม่บังคับ ผมจึงคิดว่าการซ้ำกันบ้างคงไม่เป็นไร

Leptos 0.7 แนะนำพริมิทีฟรีแอกทีฟตัวใหม่ที่เรียกว่า "สโตร์" (stores) สโตร์ถูกออกแบบมาเพื่อแก้ปัญหาต่างๆ ที่อธิบายในบทนี้มาตั้งแต่ต้น มันยังค่อนข้างทดลอง ดังนั้นจึงต้องเพิ่มดีเพนเดนซีชื่อ `reactive_stores` ใน `Cargo.toml` ของคุณ

สโตร์ให้คุณเข้าถึงฟิลด์แต่ละฟิลด์ของสตรัคต์ และไอเท็มแต่ละตัวในคอลเลกชันอย่าง `Vec<_>` แบบรีแอกทีฟและละเอียด โดยไม่ต้องสร้างสัญญาณซ้อนหรือเมโมด้วยมือเหมือนในทางเลือกข้างต้น

สโตร์สร้างขึ้นบนมาโครดีไรฟ์ `Store` ซึ่งสร้างเก็ตเตอร์ให้ทุกฟิลด์ของสตรัคต์ การเรียกเก็ตเตอร์นี้จะให้การเข้าถึงฟิลด์นั้นๆ แบบรีแอกทีฟ การอ่านจากมันจะติดตามเฉพาะฟิลด์นั้นกับพ่อแม่/children ของมัน และการอัปเดตมันจะแจ้งเตือนเฉพาะฟิลด์นั้นกับพ่อแม่/children ของมัน แต่ไม่แจ้งเตือนฟิลด์พี่น้อง พูดอีกอย่างคือ การเปลี่ยนแปลง `value` จะไม่แจ้งเตือน `key` เป็นต้น

เราสามารถปรับใช้ชนิดข้อมูลที่เราใช้ในตัวอย่างข้างต้นได้

ระดับบนสุดของสโตร์จำเป็นต้องเป็นสตรัคต์เสมอ เราจึงจะสร้าง `Data` ที่เป็นตัวห่อพร้อมฟิลด์ `rows` เพียงฟิลด์เดียว

```rust
#[derive(Store, Debug, Clone)]
pub struct Data {
    #[store(key: String = |row| row.key.clone())]
    rows: Vec<DatabaseEntry>,
}

#[derive(Store, Debug, Clone)]
struct DatabaseEntry {
    key: String,
    value: i32,
}
```

การเพิ่ม `#[store(key)]` ให้ฟิลด์ `rows` ทำให้เราเข้าถึงฟิลด์ต่างๆ ของสโตร์แบบมีคีย์ได้ ซึ่งจะเป็นประโยชน์ในคอมโพเนนต์ `<For/>` ด้านล่าง เราใช้ `key` ได้เลย ซึ่งเป็นคีย์เดียวกับที่เราจะใช้ใน `<For/>`

คอมโพเนนต์ `<For/>` นั้นตรงไปตรงมาทีเดียว:

```rust
<For
    each=move || data.rows()
    key=|row| row.read().key.clone()
    children=|child| {
        let value = child.value();
        view! { <p>{move || value.get()}</p> }
    }
/>
```

เนื่องจาก `rows` เป็นฟิลด์แบบมีคีย์ มันจึงอิมพลีเมนต์ `IntoIterator` และเราใช้ `move || data.rows()` เป็นพร็อพ `each` ได้เลย ตัวนี้จะตอบสนองต่อการเปลี่ยนแปลงใดๆ ของรายการ `rows` เหมือนที่ `move || data.get()` ทำในเวอร์ชันสัญญาณซ้อนของเรา

ฟิลด์ `key` จะเรียก `.read()` เพื่อเข้าถึงค่าปัจจุบันของแถว แล้วโคลนและคืนค่าฟิลด์ `key` ออกมา

ในพร็อพ `children` การเรียก `child.value()` ให้การเข้าถึงฟิลด์ `value` ของแถวที่มีคีย์นี้แบบรีแอกทีฟ ถ้าแถวถูกจัดลำดับใหม่ เพิ่ม หรือลบ ฟิลด์สโตร์แบบมีคีย์จะซิงก์กันอยู่เสมอ เพื่อให้ `value` นี้เชื่อมกับคีย์ที่ถูกต้องเสมอ

ในตัวจัดการเหตุการณ์ของปุ่มอัปเดต เราจะวนซ้ำบนรายการใน `rows` แล้วอัปเดตทีละรายการ:

```rust
for row in data.rows().iter_unkeyed() {
    *row.value().write() *= 2;
}
```

### ข้อดี

เราได้รีแอกทิวิตีแบบละเอียดเหมือนเวอร์ชันสัญญาณซ้อนและเวอร์ชันเมโม โดยไม่ต้องสร้างสัญญาณซ้อนหรือสไลซ์แบบเมโมด้วยมือ เราทำงานกับข้อมูลธรรมดา (สตรัคต์และ `Vec<_>`) ที่ติดแอนโนเทชันด้วยมาโครดีไรฟ์ได้ แทนที่จะใช้ชนิดข้อมูลรีแอกทีฟแบบซ้อนพิเศษ

ส่วนตัวแล้วผมคิดว่าเวอร์ชันสโตร์เป็นเวอร์ชันที่สวยงามที่สุดในที่นี้ และก็ไม่น่าแปลกใจ เพราะมันเป็น API ใหม่ล่าสุด เรามีเวลาหลายปีในการคิดเรื่องพวกนี้ และสโตร์ก็รวมบทเรียนบางอย่างที่เราได้เรียนรู้ไว้ด้วย!

### ข้อเสีย

ในทางกลับกัน มันก็เป็น API ใหม่ล่าสุด ณ ตอนที่เขียนประโยคนี้ (ธันวาคม 2024) สโตร์เพิ่งเปิดตัวได้ไม่กี่สัปดาห์ ผมแน่ใจว่ายังมีบั๊กหรือกรณีขอบ (edge case) บางอย่างที่ยังต้องไขกันอยู่

### ตัวอย่างเต็ม

นี่คือตัวอย่างสโตร์ฉบับเต็ม คุณหาตัวอย่างอื่นที่สมบูรณ์กว่าได้[ที่นี่](https://github.com/leptos-rs/leptos/blob/main/examples/stores/src/lib.rs) และอ่านการอภิปรายเพิ่มเติมในหนังสือได้[ที่นี่](../15_global_state.md)

```
use reactive_stores::Store;

#[derive(Store, Debug, Clone)]
pub struct Data {
    #[store(key: String = |row| row.key.clone())]
    rows: Vec<DatabaseEntry>,
}

#[derive(Store, Debug, Clone)]
struct DatabaseEntry {
    key: String,
    value: i32,
}

#[component]
pub fn App() -> impl IntoView {
    // instead of a signal with the rows, we create a store for Data
    let data = Store::new(Data {
        rows: vec![
            DatabaseEntry {
                key: "foo".to_string(),
                value: 10,
            },
            DatabaseEntry {
                key: "bar".to_string(),
                value: 20,
            },
            DatabaseEntry {
                key: "baz".to_string(),
                value: 15,
            },
        ],
    });

    view! {
        // when we click, update each row,
        // doubling its value
        <button on:click=move |_| {
            // allows iterating over the entries in an iterable store field
            use reactive_stores::StoreFieldIterator;

            // calling rows() gives us access to the rows
            for row in data.rows().iter_unkeyed() {
                *row.value().write() *= 2;
            }
            // log the new value of the signal
            leptos::logging::log!("{:?}", data.get());
        }>
            "Update Values"
        </button>
        // iterate over the rows and display each value
        <For
            each=move || data.rows()
            key=|row| row.read().key.clone()
            children=|child| {
                let value = child.value();
                view! { <p>{move || value.get()}</p> }
            }
        />
    }
}
```
