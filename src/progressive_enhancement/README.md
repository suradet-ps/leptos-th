# การเสริมความสามารถแบบก้าวหน้า (และการลดทอนอย่างสง่างาม)

ผมขับรถไปทั่วบอสตันมานานราว ๆ 15 ปีแล้ว หากคุณไม่คุ้นเคยกับบอสตัน ผมบอกได้เลยว่า: รัฐแมสซาชูเซตส์มีผู้ขับขี่ (รวมถึงคนเดินเท้า!) ที่ขับรถและข้ามถนนได้ดุดันที่สุดแห่งหนึ่งในโลก จนผมได้เรียนรู้หลักการที่เรียกกันว่า “การขับขี่เชิงป้องกัน” (defensive driving): นั่นคือการสันนิษฐานไว้ก่อนเสมอว่าอาจมีใครบางคนหักเลี้ยวปาดหน้ารถคุณกลางสี่แยกแม้คุณจะได้สัญญาณไฟเขียว, เตรียมพร้อมรับมือคนเดินเท้าที่อาจก้าวลงสู่ถนนได้ทุกเมื่อ และขับขี่ด้วยความระมัดระวังตามสถานการณ์เหล่านั้น

“การเสริมประสิทธิภาพอย่างต่อเนื่อง” (Progressive Enhancement) ก็เปรียบเสมือน “การขับขี่เชิงป้องกัน” ของวงการออกแบบเว็บไซต์ หรือพูดให้ถูกจริง ๆ ก็คือ “การลดทอนประสิทธิภาพอย่างสง่างาม” (Graceful Degradation) ซึ่งแท้จริงแล้วทั้งสองสิ่งนี้คือสองด้านของเหรียญเดียวกัน หรือเป็นกระบวนการเดียวกันที่มองจากสองมุมมองที่แตกต่างกัน

**การเสริมความสามารถแบบก้าวหน้า (Progressive enhancement)** ในบริบทนี้ หมายถึงการเริ่มต้นพัฒนาจากเว็บไซต์หรือเว็บแอปพลิเคชันด้วยโครงสร้าง HTML เรียบง่ายที่สามารถทำงานได้จริงสำหรับผู้ใช้ทุกคนที่เปิดเข้ามายังหน้าเพจ จากนั้นจึงค่อย ๆ ต่อยอดเสริมชั้นของฟีเจอร์เพิ่มเติมเข้าไปเป็นลำดับ: ใช้ CSS สำหรับตกแต่งความสวยงาม, ใช้ JavaScript เพื่อเพิ่มการตอบสนองและลูกเล่น, ใช้ WebAssembly เพื่อมอบพลังการโต้ตอบอันทรงพลังที่ขับเคลื่อนด้วย Rust และเลือกเรียกใช้ Web API เฉพาะทางต่าง ๆ หากอุปกรณ์นั้นรองรับและมีความจำเป็น เพื่อส่งมอบประสบการณ์การใช้งานที่สมบูรณ์แบบยิ่งขึ้น

**การลดทอนอย่างสง่างาม (Graceful degradation)** หมายถึงการเตรียมพร้อมรับมือกับความล้มเหลวหรือข้อจำกัดอย่างนุ่มนวล เมื่อชั้นเลเยอร์การทำงานบางส่วนของระบบ*ไม่พร้อมใช้งาน* นี่คือตัวอย่างของสาเหตุความล้มเหลวที่ผู้ใช้อาจพบเจอเมื่อใช้งานแอปของคุณ:

- เบราว์เซอร์ของผู้ใช้ไม่รองรับ WebAssembly เพราะยังไม่ได้อัปเดตเวอร์ชัน
- เบราว์เซอร์ของผู้ใช้ไม่สามารถรองรับ WebAssembly ได้ เนื่องจากข้อจำกัดของการอัปเดตเบราว์เซอร์ที่ผูกติดกับระบบปฏิบัติการเวอร์ชันใหม่ ซึ่งไม่สามารถติดตั้งลงในอุปกรณ์รุ่นเก่าได้ (ใช่แล้วครับ เรากำลังมองคุณอยู่นะ Apple)
- ผู้ใช้ปิดการทำงานของ WASM ไว้ด้วยเหตุผลด้านความปลอดภัยหรือความเป็นส่วนตัว
- ผู้ใช้ปิดการทำงานของ JavaScript ไว้ด้วยเหตุผลด้านความปลอดภัยหรือความเป็นส่วนตัว
- อุปกรณ์ของผู้ใช้ไม่รองรับ JavaScript (เช่น อุปกรณ์ช่วยเหลือผู้พิการบางประเภทที่รองรับเฉพาะการเปิดดูเว็บแบบ HTML เท่านั้น)
- ไฟล์ JavaScript (หรือ WASM) ส่งไปไม่ถึงอุปกรณ์ของผู้ใช้ เพราะผู้ใช้เดินออกไปนอกอาคารแล้วสัญญาณ Wi-Fi หลุดกะทันหัน
- ผู้ใช้ก้าวขึ้นรถไฟใต้ดินหลังจากโหลดหน้าเพจแรกเสร็จ ทำให้การนำทางไปยังหน้าถัด ๆ ไปไม่สามารถโหลดข้อมูลเพิ่มเติมได้
- ... และสถานการณ์อื่น ๆ อีกมากมาย

คำถามคือ แอปของคุณจะยังคงใช้งานได้มากน้อยเพียงใดหากเกิดเหตุการณ์ใดเหตุการณ์หนึ่งข้างต้นขึ้น? ถ้าเกิดพร้อมกันสองข้อล่ะ? หรือสามข้อล่ะ?

หากคำตอบคือ “ยังใช้งานได้สัก 95%... หรืออาจจะ 90%... หรืออย่างน้อยก็ 75%” นั่นแหละคือสิ่งที่เรียกว่าการลดทอนอย่างสง่างาม แต่หากคำตอบคือ “แอปของผมจะกลายเป็นหน้าจอว่างเปล่าสนิททันที เว้นแต่ทุกอย่างจะสมบูรณ์แบบครบถ้วน 100%” นั่นก็คงไม่ต่างอะไรกับ... การแตกกระจายพังทลายลงในพริบตาโดยไม่มีการเตือนล่วงหน้า

**การลดทอนอย่างสง่างามมีความสำคัญเป็นพิเศษสำหรับแอปพลิเคชันที่สร้างด้วย WASM** เพราะ WASM เป็นเทคโนโลยีที่ใหม่ที่สุดและมีโอกาสที่จะไม่ได้รับการรองรับมากที่สุด ในบรรดา 4 ภาษาที่ทำงานบนเบราว์เซอร์ (HTML, CSS, JS, WASM)

โชคดีที่ Leptos มีเครื่องมือและแนวทางที่จะช่วยให้คุณรับมือกับเรื่องนี้ได้อย่างยอดเยี่ยม

## การออกแบบแบบตั้งรับ

มีแนวปฏิบัติที่ดีหลายประการที่จะช่วยให้แอปพลิเคชันของคุณลดทอนประสิทธิภาพลงได้อย่างสง่างามยิ่งขึ้น:

1. **การเรนเดอร์ฝั่งเซิร์ฟเวอร์ (Server-side rendering)** หากไม่มี SSR แอปของคุณก็จะไม่สามารถทำงานได้เลยหากดาวน์โหลดทั้ง JS และ WASM ไม่สำเร็จ ในบางกรณีสิ่งนี้อาจเป็นที่ยอมรับได้ (เช่น เว็บแอปภายในองค์กรที่ต้องล็อกอินก่อนเข้าใช้งาน) แต่ในกรณีทั่วไป มันคือการที่ระบบพังโดยสิ้นเชิง
2. **เลือกใช้เอลิเมนต์ HTML แบบเนทีฟ (Native HTML elements)** เลือกใช้เอลิเมนต์ HTML ดั้งเดิมที่สามารถทำงานตามความต้องการได้เองโดยไม่ต้องพึ่งพาโค้ดเพิ่มเติม: เช่น ใช้ `<a>` สำหรับการนำทางลิงก์ (รวมถึงการเลื่อนไปยังแฮชแองเคอร์ภายในหน้า), ใช้ `<details>` สำหรับสร้างแอคคอร์เดียน (accordion) ยุบ-ขยายเนื้อหา, ใช้ `<form>` เพื่อจัดเก็บและส่งต่อข้อมูลผ่าน URL เป็นต้น
3. **สถานะที่ขับเคลื่อนผ่าน URL (URL-driven state)** ยิ่งคุณเก็บสถานะส่วนกลางของแอปพลิเคชันไว้บน URL มากเท่าใด (ไม่ว่าจะเป็นพารามิเตอร์เส้นทางหรือสตริงคิวรี) หน้าเว็บก็จะยิ่งถูกสร้างขึ้นได้ตั้งแต่ขั้นตอนการเรนเดอร์บนเซิร์ฟเวอร์ และสามารถอัปเดตค่าผ่านแท็ก `<a>` หรือ `<form>` ได้มากเท่านั้น ซึ่งหมายความว่าไม่เพียงแค่การเปลี่ยนหน้าเท่านั้น แต่การอัปเดตสถานะของแอปก็ยังคงทำงานได้แม้ไม่มี JS/WASM
4. **[`SsrMode::PartiallyBlocked` หรือ `SsrMode::InOrder`](https://docs.rs/leptos_router/latest/leptos_router/enum.SsrMode.html)** การสตรีมแบบไม่เรียงลำดับ (out-of-order) ต้องอาศัยสคริปต์ JS ขนาดเล็กแบบอินไลน์ แต่ก็อาจเกิดปัญหาได้หาก 1) การเชื่อมต่ออินเทอร์เน็ตขาดหายไประหว่างกำลังส่งคำตอบ หรือ 2) อุปกรณ์ของผู้ใช้ไม่รองรับ JS สำหรับการสตรีมแบบ async จะส่งมอบหน้า HTML ที่สมบูรณ์แบบกลับไป แต่ต้องแลกกับการรอให้รีซอร์สทั้งหมดโหลดเสร็จเสียก่อน ส่วนการสตรีมแบบตามลำดับ (in-order) จะเริ่มแสดงชิ้นส่วนของหน้าเว็บได้เร็วกว่า โดยเรียงลำดับจากบนลงล่าง ขณะที่ SSR แบบบล็อกบางส่วน (“Partially-blocked”) จะต่อยอดจากการสตรีมแบบไม่เรียงลำดับ โดยทำการแทนที่ชิ้นส่วน `<Suspense/>` ที่อ่านข้อมูลจากรีซอร์สแบบบล็อกตั้งแต่บนเซิร์ฟเวอร์ วิธีนี้จะเพิ่มเวลาตอบสนองในรอบแรกเพียงเล็กน้อย (เนื่องจากภาระงานแทนที่สตริงระดับ `O(n)`) เพื่อแลกกับการได้คำตอบ HTML เริ่มต้นที่สมบูรณ์ยิ่งขึ้น จึงเป็นตัวเลือกที่ยอดเยี่ยมสำหรับหน้าเพจที่มีการแบ่งแยกเนื้อหา “สำคัญมาก” กับ “สำคัญน้อยกว่า” อย่างชัดเจน เช่น เนื้อหาบทความบล็อกกับส่วนความคิดเห็น หรือรายละเอียดสินค้ากับรีวิวจากผู้ใช้ ทว่าหากคุณเลือกที่จะบล็อกเนื้อหาทั้งหมด มันก็แทบจะไม่ต่างอะไรกับการสร้างการเรนเดอร์แบบ async ขึ้นมาใหม่นั่นเอง
5. **พึ่งพาการทำงานของ `<form>`** ในช่วงหลังมานี้ กระแสความนิยมของ `<form>` ได้หวนกลับมาอีกครั้ง ซึ่งไม่ใช่เรื่องน่าแปลกใจเลย ความสามารถของ `<form>` ในการจัดการคำขอ `POST` หรือ `GET` ที่ซับซ้อนในรูปแบบที่สามารถนำมาเสริมประสิทธิภาพต่อยอดได้อย่างง่ายดาย ทำให้มันกลายเป็นอาวุธที่ทรงพลังที่สุดชิ้นหนึ่งสำหรับการทำ graceful degradation ตัวอย่างเช่น โค้ดใน [บทว่าด้วย `<Form/>`](../router/20_form.md) สามารถทำงานได้อย่างสมบูรณ์แบบแม้ไม่มี JS/WASM เลย: เพราะมันใช้ `<form method="GET">` เพื่อจัดเก็บสถานะไว้บน URL จึงทำงานกับ HTML ล้วน ๆ ผ่านคำขอ HTTP มาตรฐานได้ทันที จากนั้นจึงค่อยเสริมประสิทธิภาพให้กลายเป็นการนำทางบนฝั่งไคลเอนต์เมื่อสคริปต์โหลดเสร็จสมบูรณ์

ยังมีฟีเจอร์สำคัญอีกหนึ่งอย่างของเฟรมเวิร์กที่เรายังไม่ได้พูดถึง ซึ่งต่อยอดคุณลักษณะอันยอดเยี่ยมนี้ของฟอร์มมาสร้างแอปพลิเคชันที่ทรงพลัง นั่นคือ `<ActionForm/>`
