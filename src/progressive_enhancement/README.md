# การเสริมความสามารถแบบก้าวหน้า (และการลดทอนอย่างสง่างาม)

ผมขับรถไปทั่วบอสตันมาประมาณสิบห้าปีแล้ว ถ้าคุณไม่รู้จักบอสตัน ขอเล่าให้ฟังหน่อย: รัฐแมสซาชูเซตส์มีคนขับรถ (และคนเดินถนน!) ที่ก้าวร้าวที่สุดในโลกส่วนหนึ่ง ผมเรียนรู้ที่จะฝึกสิ่งที่บางครั้งเรียกว่า “การขับขี่แบบตั้งรับ”: สมมติไว้ว่ามีใครบางคนกำลังจะหักพวงมาลัยปาดหน้ารถคุณตรงสี่แยกทั้งที่คุณมีสิทธิ์ไปก่อน, เตรียมพร้อมสำหรับคนเดินถนนที่จะเดินลงสู่ถนนได้ทุกเมื่อ และขับขี่ให้สอดคล้องกัน

“การเสริมความสามารถแบบก้าวหน้า” คือ “การขับขี่แบบตั้งรับ” ของการออกแบบเว็บ หรือพูดให้ถูกจริงๆ นั่นคือ “การลดทอนอย่างสง่างาม” แม้ว่าทั้งสองจะเป็นสองด้านของเหรียญเดียวกัน หรือเป็นกระบวนการเดียวกันที่มองจากสองทิศทางที่ต่างกัน

**การเสริมความสามารถแบบก้าวหน้า** ในบริบทนี้ หมายถึงการเริ่มต้นด้วยเว็บไซต์หรือแอปพลิเคชัน HTML เรียบง่ายที่ทำงานได้สำหรับผู้ใช้ทุกคนที่เข้ามาที่หน้าเพจของคุณ แล้วค่อยๆ เสริมความสามารถด้วยชั้นของฟีเจอร์เพิ่มเติม: CSS สำหรับการจัดสไตล์, JavaScript สำหรับการโต้ตอบ, WebAssembly สำหรับการโต้ตอบที่ขับเคลื่อนด้วย Rust; โดยใช้เว็บ API เฉพาะเจาะจงเพื่อประสบการณ์ที่สมบูรณ์ยิ่งขึ้นหากมีให้ใช้และเมื่อจำเป็น

**การลดทอนอย่างสง่างาม** หมายถึงการรับมือกับความล้มเหลวอย่างสง่างามเมื่อบางส่วนของชั้นการเสริมความสามารถนั้น_ไม่มี_ให้ใช้ นี่คือสาเหตุความล้มเหลวบางประการที่ผู้ใช้ของคุณอาจพบเจอในแอปของคุณ:

- เบราว์เซอร์ของผู้ใช้ไม่รองรับ WebAssembly เพราะจำเป็นต้องอัปเดต
- เบราว์เซอร์ของผู้ใช้ไม่สามารถรองรับ WebAssembly ได้ เพราะการอัปเดตเบราว์เซอร์จำกัดอยู่แค่ระบบปฏิบัติการเวอร์ชันใหม่กว่า ซึ่งติดตั้งลงในอุปกรณ์นี้ไม่ได้ (กำลังมองคุณอยู่นะ Apple)
- ผู้ใช้ปิด WASM ไว้ด้วยเหตุผลด้านความปลอดภัยหรือความเป็นส่วนตัว
- ผู้ใช้ปิด JavaScript ไว้ด้วยเหตุผลด้านความปลอดภัยหรือความเป็นส่วนตัว
- JavaScript ไม่ได้รับการรองรับบนอุปกรณ์ของผู้ใช้ (ตัวอย่างเช่น อุปกรณ์ช่วยการเข้าถึงบางชนิดรองรับเฉพาะการท่องเว็บด้วย HTML เท่านั้น)
- JavaScript (หรือ WASM) ไม่เคยไปถึงอุปกรณ์ของผู้ใช้ เพราะพวกเขาเดินออกไปข้างนอกแล้ว WiFi หลุด
- พวกเขาก้าวขึ้นรถไฟใต้ดินหลังจากโหลดหน้าเพจแรกไปแล้ว และการนำทางครั้งต่อๆ ไปไม่สามารถโหลดข้อมูลได้
- ... และอื่นๆ อีกมากมาย

แอปของคุณยังทำงานได้มากแค่ไหนหากข้อใดข้อหนึ่งเหล่านี้เป็นจริง? สองข้อล่ะ? สามข้อล่ะ?

หากคำตอบเป็นอะไรทำนองว่า “95%... โอเค งั้น 90%... โอเค งั้น 75%” นั่นแหละคือการลดทอนอย่างสง่างาม หากคำตอบคือ “แอปของผมแสดงหน้าจอว่างเปล่า เว้นแต่ทุกอย่างจะทำงานถูกต้องทั้งหมด” นั่นคือ... การแยกชิ้นส่วนอย่างรวดเร็วโดยไม่แจ้งล่วงหน้า

**การลดทอนอย่างสง่างามมีความสำคัญเป็นพิเศษสำหรับแอป WASM** เพราะ WASM เป็นภาษาที่ใหม่ที่สุดและมีโอกาสได้รับการรองรับน้อยที่สุดในบรรดาสี่ภาษาที่ทำงานในเบราว์เซอร์ (HTML, CSS, JS, WASM)

โชคดีที่เรามีเครื่องมือบางอย่างช่วยได้

## การออกแบบแบบตั้งรับ

มีแนวปฏิบัติสองสามข้อที่ช่วยให้แอปของคุณลดทอนได้อย่างสง่างามยิ่งขึ้น:

1. **การเรนเดอร์ฝั่งเซิร์ฟเวอร์ (SSR)** หากไม่มี SSR แอปของคุณก็ใช้งานไม่ได้เลยหากทั้ง JS และ WASM ไม่โหลดขึ้นมา ในบางกรณีสิ่งนี้อาจเหมาะสม (ลองนึกถึงแอปภายในที่ปิดกั้นไว้หลังการล็อกอิน) แต่ในกรณีอื่นๆ มันก็แค่พังไปเฉยๆ
2. **เอลิเมนต์ HTML แบบเนทีฟ** ใช้เอลิเมนต์ HTML ที่ทำงานในสิ่งที่คุณต้องการได้โดยไม่ต้องมีโค้ดเพิ่มเติม: `<a>` สำหรับการนำทาง (รวมถึงไปยังแฮชภายในหน้าเพจ), `<details>` สำหรับแอคคอร์เดียน, `<form>` สำหรับเก็บข้อมูลไว้ใน URL เป็นต้น
3. **สถานะที่ขับเคลื่อนด้วย URL** ยิ่งสถานะส่วนกลางของคุณถูกเก็บไว้ใน URL มากเท่าไร (ในรูปของพารามิเตอร์เส้นทางหรือส่วนหนึ่งของสตริงควิรี) หน้าเพจก็จะยิ่งถูกสร้างขึ้นระหว่างการเรนเดอร์ฝั่งเซิร์ฟเวอร์และอัปเดตด้วย `<a>` หรือ `<form>` ได้มากขึ้นเท่านั้น ซึ่งหมายความว่าไม่ใช่แค่การนำทาง แต่การเปลี่ยนแปลงสถานะก็สามารถทำงานได้โดยไม่ต้องใช้ JS/WASM
4. **[`SsrMode::PartiallyBlocked` หรือ `SsrMode::InOrder`](https://docs.rs/leptos_router/latest/leptos_router/enum.SsrMode.html)** การสตรีมแบบไม่เรียงลำดับ (out-of-order) ต้องใช้ JS แบบอินไลน์จำนวนเล็กน้อย แต่ล้มเหลวได้หาก 1) การเชื่อมต่อขาดกลางทางระหว่างการตอบกลับ หรือ 2) อุปกรณ์ของไคลเอนต์ไม่รองรับ JS การสตรีมแบบอะซิงก์จะให้หน้า HTML ที่สมบูรณ์ แต่จะได้หลังจากรีซอร์สทั้งหมดโหลดเสร็จแล้วเท่านั้น การสตรีมแบบเรียงลำดับ (in-order) เริ่มแสดงส่วนต่างๆ ของหน้าเพจได้เร็วขึ้นตามลำดับจากบนลงล่าง SSR แบบ “partially-blocked” ต่อยอดจากการสตรีมแบบไม่เรียงลำดับ โดยแทนที่แฟรกเมนต์ `<Suspense/>` ที่อ่านจากรีซอร์สแบบบล็อกบนเซิร์ฟเวอร์ วิธีนี้เพิ่มเวลาในการตอบกลับครั้งแรกเล็กน้อย (เนื่องจากงานแทนที่สตริงแบบ `O(n)`) เพื่อแลกกับการตอบกลับ HTML เริ่มต้นที่สมบูรณ์ยิ่งขึ้น ทางเลือกนี้อาจเหมาะกับสถานการณ์ที่มีความแตกต่างชัดเจนระหว่างเนื้อหา “สำคัญกว่า” กับ “สำคัญน้อยกว่า” เช่น บทความบล็อกกับคอมเมนต์ หรือข้อมูลสินค้ากับรีวิว หากคุณเลือกบล็อกเนื้อหาทั้งหมด คุณก็เท่ากับสร้างการเรนเดอร์แบบอะซิงก์ขึ้นมาใหม่นั่นเอง
5. **พึ่งพา `<form>`** ช่วงหลังๆ นี้มีการฟื้นคืนชีพของ `<form>` กันเล็กน้อย ซึ่งก็ไม่น่าแปลกใจเลย ความสามารถของ `<form>` ในการจัดการคำขอ `POST` หรือ `GET` ที่ซับซ้อนด้วยวิธีที่เสริมความสามารถได้ง่าย ทำให้มันเป็นเครื่องมือที่ทรงพลังสำหรับการลดทอนอย่างสง่างาม ตัวอย่างใน[บทว่าด้วย `<Form/>`](../router/20_form.md) ก็เช่นกัน มันจะทำงานได้ดีโดยไม่ต้องมี JS/WASM เลย: เพราะมันใช้ `<form method="GET">` เพื่อเก็บสถานะไว้ใน URL มันจึงทำงานกับ HTML ล้วนๆ ด้วยการส่งคำขอ HTTP ปกติ แล้วค่อยๆ เสริมความสามารถให้ใช้การนำทางฝั่งไคลเอนต์แทน

ยังมีฟีเจอร์สุดท้ายของเฟรมเวิร์กที่เรายังไม่ได้เห็น และต่อยอดจากคุณลักษณะนี้ของฟอร์มเพื่อสร้างแอปพลิเคชันที่ทรงพลัง นั่นก็คือ `<ActionForm/>`
