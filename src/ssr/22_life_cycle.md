# วงจรชีวิตของการโหลดหน้าเพจ

ก่อนที่เราจะลงลึกในรายละเอียด อาจเป็นประโยชน์หากเรามองภาพรวมในระดับที่สูงขึ้นก่อน เกิดอะไรขึ้นกันแน่ระหว่างช่วงเวลาที่คุณพิมพ์ URL ของแอป Leptos ที่เรนเดอร์ฝั่งเซิร์ฟเวอร์ กับช่วงเวลาที่คุณคลิกปุ่มแล้วตัวนับเพิ่มขึ้น?

ผมสมมติว่าคุณมีความรู้พื้นฐานเกี่ยวกับวิธีการทำงานของอินเทอร์เน็ตตรงนี้ และจะไม่ลงลึกเรื่อง HTTP หรืออะไรทำนองนั้น แต่จะพยายามแสดงให้เห็นว่าส่วนต่างๆ ของ API ของ Leptos สอดคล้องกับแต่ละขั้นตอนของกระบวนการอย่างไร

คำอธิบายนี้ยังเริ่มจากสมมติฐานว่าแอปของคุณถูกคอมไพล์สำหรับสองเป้าหมายแยกจากกัน:

1. เวอร์ชันเซิร์ฟเวอร์ ซึ่งมักรันบน Actix หรือ Axum คอมไพล์ด้วยฟีเจอร์ `ssr` ของ Leptos
2. เวอร์ชันเบราว์เซอร์ คอมไพล์เป็น WebAssembly (WASM) ด้วยฟีเจอร์ `hydrate` ของ Leptos

เครื่องมือบิลด์ [`cargo-leptos`](https://github.com/leptos-rs/cargo-leptos) มีไว้เพื่อประสานกระบวนการคอมไพล์แอปของคุณสำหรับสองเป้าหมายที่แตกต่างกันนี้

## บนเซิร์ฟเวอร์

- เบราว์เซอร์ของคุณส่งคำขอ `GET` สำหรับ URL นั้นไปยังเซิร์ฟเวอร์ของคุณ ณ จุดนี้ เบราว์เซอร์แทบไม่รู้อะไรเลยเกี่ยวกับหน้าเพจที่จะถูกเรนเดอร์ (คำถามที่ว่า “เบราว์เซอร์รู้ได้อย่างไรว่าต้องขอหน้าเพจจากที่ไหน?” เป็นคำถามที่น่าสนใจ แต่ไม่อยู่ในขอบเขตของบทเรียนนี้!)
- เซิร์ฟเวอร์ได้รับคำขอนั้น และตรวจสอบว่ามีวิธีจัดการคำขอ `GET` ที่พาธนั้นหรือไม่ นี่คือสิ่งที่เมธอด `.leptos_routes()` ใน [`leptos_axum`](https://docs.rs/leptos_axum/latest/leptos_axum/trait.LeptosRoutes.html) และ [`leptos_actix`](https://docs.rs/leptos_actix/latest/leptos_actix/trait.LeptosRoutes.html) มีไว้สำหรับ เมื่อเซิร์ฟเวอร์เริ่มทำงาน เมธอดเหล่านี้จะไล่ดูโครงสร้างเส้นทางที่คุณให้ไว้ใน `<Routes/>` สร้างรายการเส้นทางทั้งหมดที่แอปของคุณสามารถจัดการได้ และบอกเราเตอร์ของเซิร์ฟเวอร์ว่า “สำหรับแต่ละเส้นทางเหล่านี้ ถ้าได้รับคำขอ... ให้ส่งต่อให้ Leptos”
- เซิร์ฟเวอร์เห็นว่าเส้นทางนี้สามารถจัดการได้โดย Leptos จึงเรนเดอร์คอมโพเนนต์รากของคุณ (ซึ่งมักชื่อประมาณ `<App/>`) โดยให้ URL ที่ถูกขอและข้อมูลอื่นๆ เช่น HTTP headers และเมทาดาทาของคำขอแก่คอมโพเนนต์นั้น
- แอปพลิเคชันของคุณรันหนึ่งครั้งบนเซิร์ฟเวอร์ สร้างเวอร์ชัน HTML ของต้นไม้คอมโพเนนต์ที่จะถูกเรนเดอร์ที่เส้นทางนั้น (ยังมีเรื่องที่ต้องพูดถึงอีกเกี่ยวกับรีซอร์สและ `<Suspense/>` ในบทถัดไป)
- เซิร์ฟเวอร์ส่งคืนหน้า HTML นี้ พร้อมกับฉีดข้อมูลเกี่ยวกับวิธีโหลดเวอร์ชันของแอปคุณที่คอมไพล์เป็น WASM เพื่อให้มันรันในเบราว์เซอร์ได้

> หน้า HTML ที่ส่งคืนมานั้นโดยพื้นฐานแล้วคือแอปของคุณที่ “ดีไฮเดรต” หรือ “อบแห้งแบบแช่แข็ง”: มันเป็น HTML ที่ไม่มีความเป็นรีแอกทีฟหรือตัวรับฟังเหตุการณ์ใดๆ ที่คุณเพิ่มไว้ เบราว์เซอร์จะ “ไฮเดรต” หน้า HTML นี้ใหม่โดยเพิ่มระบบรีแอกทีฟและแนบตัวรับฟังเหตุการณ์เข้ากับ HTML ที่เรนเดอร์จากเซิร์ฟเวอร์นั้น ดังนั้นจึงมีฟีเจอร์แฟล็กสองตัวที่ใช้กับสองครึ่งของกระบวนการนี้: `ssr` บนเซิร์ฟเวอร์สำหรับ “การเรนเดอร์ฝั่งเซิร์ฟเวอร์” และ `hydrate` ในเบราว์เซอร์สำหรับกระบวนการไฮเดรตใหม่นั้น

## ในเบราว์เซอร์

- เบราว์เซอร์ได้รับหน้า HTML นี้จากเซิร์ฟเวอร์ แล้วกลับไปที่เซิร์ฟเวอร์ทันทีเพื่อเริ่มโหลด JS และ WASM ที่จำเป็นสำหรับรันเวอร์ชันอินเทอร์แอกทีฟฝั่งไคลเอนต์ของแอป
- ในระหว่างนั้น มันเรนเดอร์เวอร์ชัน HTML
- เมื่อเวอร์ชัน WASM โหลดเสร็จแล้ว มันจะทำกระบวนการจับคู่เส้นทางแบบเดียวกับที่เซิร์ฟเวอร์ทำ เนื่องจากคอมโพเนนต์ `<Routes/>` เหมือนกันทั้งบนเซิร์ฟเวอร์และไคลเอนต์ เวอร์ชันเบราว์เซอร์จึงอ่าน URL และเรนเดอร์หน้าเดียวกันกับที่เซิร์ฟเวอร์ส่งคืนมาก่อนแล้ว
- ในช่วง “การไฮเดรต” ครั้งแรกนี้ เวอร์ชัน WASM ของแอปคุณจะไม่สร้างโหนด DOM ที่ประกอบกันเป็นแอปพลิเคชันของคุณใหม่ แต่จะไล่ดูต้นไม้ HTML ที่มีอยู่ “หยิบ” เอลิเมนต์ที่มีอยู่แล้วขึ้นมา และเพิ่มความสามารถในการโต้ตอบที่จำเป็น

> โปรดทราบว่ามีข้อแลกเปลี่ยนบางอย่างตรงนี้ ก่อนกระบวนการไฮเดรตนี้จะเสร็จสมบูรณ์ หน้าเพจจะ_ดูเหมือน_โต้ตอบได้ แต่จะไม่ตอบสนองต่อการโต้ตอบจริงๆ ตัวอย่างเช่น ถ้าคุณมีปุ่มตัวนับและคลิกมันก่อนที่ WASM จะโหลดเสร็จ ตัวนับจะไม่เพิ่มขึ้น เพราะตัวรับฟังเหตุการณ์และระบบรีแอกทีฟที่จำเป็นยังไม่ถูกเพิ่มเข้าไป เราจะดูวิธีสร้าง “การลดทอนอย่างสง่างาม” ในบทต่อๆ ไป

## การนำทางฝั่งไคลเอนต์

ขั้นตอนถัดไปสำคัญมาก ลองจินตนาการว่าตอนนี้ผู้ใช้คลิกที่ลิงก์เพื่อไปยังหน้าอื่นในแอปพลิเคชันของคุณ

เบราว์เซอร์จะ_ไม่_ส่งคำขอไปกลับเซิร์ฟเวอร์อีกครั้งเพื่อโหลดหน้าเต็มใหม่เหมือนกับการนำทางระหว่างหน้า HTML ธรรมดา หรือแอปพลิเคชันที่ใช้การเรนเดอร์ฝั่งเซิร์ฟเวอร์ (เช่น ด้วย PHP) แต่ไม่มีครึ่งฝั่งไคลเอนต์

แต่เวอร์ชัน WASM ของแอปคุณจะโหลดหน้าใหม่ให้ตรงนั้นในเบราว์เซอร์ โดยไม่ร้องขอหน้าใหม่จากเซิร์ฟเวอร์ โดยพื้นฐานแล้ว แอปของคุณอัปเกรดตัวเองจาก “แอปหลายหน้า” ที่โหลดจากเซิร์ฟเวอร์ ไปเป็น “แอปหน้าเดียว” ที่เรนเดอร์ในเบราว์เซอร์ ซึ่งให้ผลดีที่สุดของทั้งสองโลก: เวลาโหลดครั้งแรกที่รวดเร็วเพราะ HTML ที่เรนเดอร์ฝั่งเซิร์ฟเวอร์ และการนำทางครั้งต่อๆ ไปที่รวดเร็วเพราะการจัดเส้นทางฝั่งไคลเอนต์

บางส่วนของสิ่งที่อธิบายในบทต่อๆ ไป เช่น ปฏิสัมพันธ์ระหว่างฟังก์ชันฝั่งเซิร์ฟเวอร์ รีซอร์ส และ `<Suspense/>` อาจดูซับซ้อนเกินไป คุณอาจพบว่าตัวเองถามว่า “ถ้าหน้าของฉันถูกเรนเดอร์เป็น HTML บนเซิร์ฟเวอร์ ทำไมฉันถึงแค่ `.await` มันบนเซิร์ฟเวอร์ไม่ได้? ถ้าฉันเรียกไลบรารี X ในฟังก์ชันฝั่งเซิร์ฟเวอร์ได้ ทำไมฉันถึงเรียกมันในคอมโพเนนต์ของฉันไม่ได้?” เหตุผลง่ายมาก: เพื่อให้สามารถอัปเกรดจากการเรนเดอร์ฝั่งเซิร์ฟเวอร์ไปเป็นการเรนเดอร์ฝั่งไคลเอนต์ได้ ทุกสิ่งในแอปพลิเคชันของคุณต้องสามารถรันได้ทั้งบนไคลเอนต์และเซิร์ฟเวอร์

นี่ไม่ใช่วิธีเดียวในการสร้างเว็บไซต์หรือเว็บเฟรมเวิร์ก แน่นอน แต่มันเป็นวิธีที่พบได้บ่อยที่สุด และเราเองก็คิดว่ามันเป็นวิธีที่ค่อนข้างดี ในการสร้างประสบการณ์ที่ราบรื่นที่สุดเท่าที่จะเป็นไปได้สำหรับผู้ใช้ของคุณ
