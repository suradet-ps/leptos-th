# วงจรชีวิตของการโหลดหน้าเพจ

ก่อนที่เราจะลงลึกในรายละเอียดทางเทคนิค การมองภาพรวมในระดับสูงก่อนน่าจะมีประโยชน์ไม่น้อย: เกิดอะไรขึ้นกันแน่ระหว่างช่วงเวลาที่คุณพิมพ์ URL ของแอป Leptos ที่เรนเดอร์ฝั่งเซิร์ฟเวอร์ กับช่วงเวลาที่คุณคลิกปุ่มแล้วตัวเลขบนตัวนับเพิ่มขึ้น?

ในที่นี้ เราถือว่าคุณมีความรู้พื้นฐานเกี่ยวกับหลักการทำงานของอินเทอร์เน็ตอยู่แล้ว จึงจะไม่ลงลึกเรื่องโพรโทคอล HTTP หรือรายละเอียดปลีกย่อย แต่จะพยายามแสดงให้เห็นว่า API ส่วนต่าง ๆ ของ Leptos เชื่อมโยงเข้ากับแต่ละขั้นตอนของกระบวนการอย่างไร

คำอธิบายนี้ตั้งอยู่บนสมมติฐานว่าแอปพลิเคชันของคุณถูกคอมไพล์สำหรับ 2 เป้าหมายแยกจากกัน:

1. **เวอร์ชันเซิร์ฟเวอร์**: มักรันบน Actix หรือ Axum และคอมไพล์ด้วยฟีเจอร์ `ssr` ของ Leptos
2. **เวอร์ชันเบราว์เซอร์**: คอมไพล์เป็น WebAssembly (WASM) ด้วยฟีเจอร์ `hydrate` ของ Leptos

เครื่องมือสร้างบิลด์อย่าง [`cargo-leptos`](https://github.com/leptos-rs/cargo-leptos) มีหน้าที่คอยประสานกระบวนการคอมไพล์แอปของคุณสำหรับเป้าหมายทั้งสองนี้ให้ทำงานร่วมกันได้อย่างราบรื่น

## บนเซิร์ฟเวอร์

- เบราว์เซอร์ของคุณส่งคำขอ `GET` สำหรับ URL นั้นไปยังเซิร์ฟเวอร์ ณ จุดนี้ เบราว์เซอร์แทบไม่รู้อะไรเลยเกี่ยวกับหน้าเพจที่จะถูกเรนเดอร์ (คำถามที่ว่า "เบราว์เซอร์รู้ได้อย่างไรว่าต้องส่งคำขอหน้าเพจไปที่ไหน?" เป็นประเด็นที่น่าสนใจ แต่นอกเหนือขอบเขตของบทเรียนนี้!)
- เซิร์ฟเวอร์ได้รับคำขอดังกล่าว และตรวจสอบว่ามีตัวจัดการคำขอ `GET` ที่พาธนั้นหรือไม่ นี่คือหน้าที่ของเมธอด `.leptos_routes()` ใน [`leptos_axum`](https://docs.rs/leptos_axum/latest/leptos_axum/trait.LeptosRoutes.html) และ [`leptos_actix`](https://docs.rs/leptos_actix/latest/leptos_actix/trait.LeptosRoutes.html) เมื่อเซิร์ฟเวอร์เริ่มทำงาน เมธอดเหล่านี้จะไล่สำรวจโครงสร้างเส้นทางที่คุณกำหนดไว้ใน `<Routes/>` เพื่อสร้างรายการเส้นทางทั้งหมดที่แอปสามารถจัดการได้ แล้วแจ้งเราเตอร์ของเซิร์ฟเวอร์ว่า "สำหรับเส้นทางเหล่านี้ หากได้รับคำขอเข้ามา... ให้ส่งต่อให้ Leptos จัดการ"
- เมื่อเซิร์ฟเวอร์พบว่าเส้นทางนี้จัดการได้โดย Leptos มันจะทำการเรนเดอร์คอมโพเนนต์รูทของคุณ (ซึ่งมักจะตั้งชื่อว่า `<App/>`) โดยส่ง URL ที่ถูกร้องขอ พร้อมกับข้อมูลอื่น ๆ เช่น HTTP headers และข้อมูลเมทาดาทาของคำขอ เข้าไปยังคอมโพเนนต์นั้น
- แอปพลิเคชันของคุณจะถูกสั่งรันหนึ่งรอบบนเซิร์ฟเวอร์ เพื่อสร้างโค้ด HTML ของคอมโพเนนต์ทรีที่จะถูกเรนเดอร์ ณ เส้นทางนั้น (ยังมีประเด็นสำคัญเกี่ยวกับรีซอร์สและ `<Suspense/>` ที่เราจะพูดถึงในบทถัดไป)
- เซิร์ฟเวอร์จะส่งหน้า HTML นี้กลับไปยังเบราว์เซอร์ พร้อมกับแทรก (inject) ข้อมูลเกี่ยวกับวิธีโหลดเวอร์ชัน WASM ของแอป เพื่อให้สามารถรันบนเบราว์เซอร์ได้ต่อไป

> หน้า HTML ที่ส่งกลับมานี้เปรียบเสมือนแอปพลิเคชันของคุณที่ถูก "ดึงน้ำออก" (dehydrated) หรือผ่านการ "ฟรีซดราย" (freeze-dried) มาแล้ว กล่าวคือ มันเป็นเพียงโค้ด HTML ที่ยังไม่มีระบบรีแอกทีฟหรือตัวรับฟังเหตุการณ์ (event listeners) ใด ๆ ผูกติดอยู่เลย เบราว์เซอร์จะต้องนำหน้า HTML นี้มาผ่านกระบวนการ "เติมน้ำกลับคืน" หรือที่เรียกว่า "การไฮเดรต" (rehydrate) โดยการสร้างระบบรีแอกทีฟและเชื่อมต่อตัวรับฟังเหตุการณ์เข้ากับเอลิเมนต์ HTML ที่เรนเดอร์มาจากเซิร์ฟเวอร์ นี่จึงเป็นที่มาของฟีเจอร์แฟล็ก 2 ตัวที่ใช้ในกระบวนการนี้: `ssr` สำหรับการเรนเดอร์ฝั่งเซิร์ฟเวอร์ และ `hydrate` สำหรับกระบวนการไฮเดรตบนเบราว์เซอร์

## ในเบราว์เซอร์

- เบราว์เซอร์ได้รับหน้า HTML นี้จากเซิร์ฟเวอร์ และจะส่งคำขอกลับไปยังเซิร์ฟเวอร์ทันทีเพื่อดาวน์โหลดไฟล์ JavaScript และ WASM ที่จำเป็นต่อการรันเวอร์ชันอินเทอร์แอ็กทีฟบนฝั่งไคลเอนต์
- ในระหว่างนั้น เบราว์เซอร์จะเรนเดอร์หน้าตาจากโครงสร้าง HTML ที่ได้รับมาให้ผู้ใช้เห็นทันที
- เมื่อเวอร์ชัน WASM โหลดเสร็จสิ้น มันจะทำกระบวนการจับคู่เส้นทาง (route-matching) แบบเดียวกับที่เซิร์ฟเวอร์ทำ และเนื่องจากคอมโพเนนต์ `<Routes/>` ทั้งบนเซิร์ฟเวอร์และไคลเอนต์เป็นชุดเดียวกัน เวอร์ชันบนเบราว์เซอร์จึงอ่านค่าจาก URL แล้วเรนเดอร์หน้าเดียวกับที่เซิร์ฟเวอร์ส่งมาได้อย่างถูกต้องแม่นยำ
- ในช่วง "การไฮเดรต" (hydration) ครั้งแรกนี้ เวอร์ชัน WASM ของแอปจะไม่สร้างโหนด DOM ขึ้นมาใหม่ทั้งหมด แต่จะไล่สำรวจทรี HTML ที่มีอยู่แล้ว ทำการ "จับจอง" (pick up) เอลิเมนต์เหล่านั้น แล้วผูกความสามารถในการโต้ตอบที่จำเป็นเข้าไป

> โปรดทราบว่ากระบวนการนี้มีข้อแลกเปลี่ยน (trade-off) บางประการ: ก่อนที่ขั้นตอนการไฮเดรตจะเสร็จสิ้น หน้าเว็บจะ *ดูเหมือน* พร้อมใช้งาน แต่แท้จริงแล้วยังไม่ตอบสนองต่อการคลิกหรือการโต้ตอบจริง ตัวอย่างเช่น หากคุณมีปุ่มตัวนับและคลิกปุ่มก่อนที่ไฟล์ WASM จะโหลดเสร็จ ตัวเลขจะไม่เพิ่มขึ้น เพราะยังไม่มีการผูกตัวรับฟังเหตุการณ์และระบบรีแอกทีฟ เราจะได้เรียนรู้วิธีสร้างระบบที่รองรับ "การลดทอนอย่างสง่างาม" (graceful degradation) ในบทต่อ ๆ ไป

## การนำทางฝั่งไคลเอนต์

ขั้นตอนถัดไปนี้มีความสำคัญอย่างยิ่ง ลองจินตนาการว่าตอนนี้ผู้ใช้คลิกลิงก์เพื่อเปลี่ยนไปยังหน้าอื่นภายในแอปพลิเคชันของคุณ

เบราว์เซอร์จะ *ไม่* ส่งคำขอแบบเต็มรูปแบบไปยังเซิร์ฟเวอร์เพื่อโหลดหน้าเว็บใหม่ทั้งหมด เหมือนกับการเปิดดูหน้า HTML แบบดั้งเดิม หรือแอปพลิเคชันที่ใช้การเรนเดอร์ฝั่งเซิร์ฟเวอร์ล้วน ๆ (เช่น PHP) โดยไม่มีส่วนการทำงานบนฝั่งไคลเอนต์

ในทางกลับกัน เวอร์ชัน WASM ของแอปจะทำการโหลดหน้าใหม่ขึ้นมาทันทีบนเบราว์เซอร์ โดยไม่ต้องร้องขอหน้าเว็บใหม่จากเซิร์ฟเวอร์เลย พูดง่าย ๆ คือ แอปของคุณได้ทำการอัปเกรดตัวเองจาก "แอปพลิเคชันหลายหน้า" (Multi-Page App) ที่โหลดจากเซิร์ฟเวอร์ ให้กลายเป็น "แอปพลิเคชันหน้าเดียว" (Single-Page App) ที่เรนเดอร์อย่างรวดเร็วบนเบราว์เซอร์ ทำให้คุณได้รับข้อดีที่ดีที่สุดจากทั้งสองฝั่ง: ความเร็วในการโหลดหน้าเว็บครั้งแรกที่รวดเร็วจาก HTML ที่เรนเดอร์บนเซิร์ฟเวอร์ และความรวดเร็วในการนำทางหน้าถัด ๆ ไปผ่านระบบเราติงบนฝั่งไคลเอนต์

เนื้อหาบางส่วนที่จะอธิบายในบทต่อ ๆ ไป—เช่น การทำงานร่วมกันระหว่างฟังก์ชันฝั่งเซิร์ฟเวอร์, รีซอร์ส และ `<Suspense/>`—อาจดูซับซ้อนไปบ้าง คุณอาจตั้งคำถามขึ้นมาว่า "ถ้าหน้าเว็บถูกเรนเดอร์เป็น HTML บนเซิร์ฟเวอร์อยู่แล้ว ทำไมเราถึงไม่แค่ใช้ `.await` บนเซิร์ฟเวอร์ไปเลยล่ะ? หรือถ้าเราเรียกใช้ไลบรารี X ในฟังก์ชันฝั่งเซิร์ฟเวอร์ได้ ทำไมเราถึงเรียกใช้ในคอมโพเนนต์โดยตรงไม่ได้?" เหตุผลนั้นเรียบง่ายมาก: เพื่อให้สามารถรองรับการอัปเกรดจากการเรนเดอร์ฝั่งเซิร์ฟเวอร์ไปสู่การเรนเดอร์ฝั่งไคลเอนต์ได้อย่างไร้รอยต่อ ทุกสิ่งในแอปพลิเคชันของคุณจึงจำเป็นต้องสามารถรันได้ทั้งบนไคลเอนต์และเซิร์ฟเวอร์

แน่นอนว่านี่ไม่ใช่วิธีเดียวในการสร้างเว็บไซต์หรือพัฒนาเว็บเฟรมเวิร์ก แต่มันเป็นวิธีที่ได้รับความนิยมมากที่สุด และเราเชื่อว่ามันเป็นแนวทางที่ยอดเยี่ยมมากในการส่งมอบประสบการณ์การใช้งานที่ราบรื่นที่สุดให้แก่ผู้ใช้งานของคุณ
