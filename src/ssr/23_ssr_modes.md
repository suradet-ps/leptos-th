# การเรนเดอร์แบบอะซิงก์และ “โหมด” ของ SSR

การเรนเดอร์ฝั่งเซิร์ฟเวอร์สำหรับหน้าเพจที่ใช้เฉพาะข้อมูลซิงโครนัสนั้นค่อนข้างง่าย: คุณเพียงไล่ลงไปตามต้นไม้คอมโพเนนต์ เรนเดอร์แต่ละเอลิเมนต์เป็นสตริง HTML แต่นี่เป็นข้อแม้ที่ค่อนข้างใหญ่: มันไม่ได้ตอบคำถามว่าเราควรทำอย่างไรกับหน้าเพจที่มีข้อมูลแบบอะซิงก์ กล่าวคือ สิ่งที่มักจะถูกเรนเดอร์ภายใต้โหนด `<Suspense/>` บนไคลเอนต์

เมื่อหน้าเพจโหลดข้อมูลแบบอะซิงก์ที่จำเป็นสำหรับการเรนเดอร์ เราควรทำอย่างไร? เราควรรอให้ข้อมูลแบบอะซิงก์ทั้งหมดโหลดเสร็จ แล้วค่อยเรนเดอร์ทุกอย่างพร้อมกันหรือไม่? (เรียกสิ่งนี้ว่าการเรนเดอร์แบบ “async”) เราควรไปในทางตรงกันข้ามสุดขั้ว ส่ง HTML ที่เรามีอยู่ทันทีลงไปให้ไคลเอนต์แล้วปล่อยให้ไคลเอนต์โหลดรีซอร์สและเติมข้อมูลเองหรือไม่? (เรียกสิ่งนี้ว่าการเรนเดอร์แบบ “synchronous”) หรือมีวิธีสายกลางที่เอาชนะทั้งสองแบบได้? (คำใบ้: มีอยู่จริง)

ถ้าคุณเคยฟังเพลงแบบสตรีมมิ่งหรือดูวิดีโอออนไลน์ ผมแน่ใจว่าคุณตระหนักว่า HTTP รองรับการสตรีม ซึ่งทำให้การเชื่อมต่อเดียวสามารถส่งข้อมูลเป็นชิ้นๆ ต่อเนื่องกันโดยไม่ต้องรอให้เนื้อหาทั้งหมดโหลดเสร็จ คุณอาจไม่ตระหนักว่าเบราว์เซอร์ก็เก่งมากในการเรนเดอร์หน้า HTML ที่ยังไม่สมบูรณ์เช่นกัน เมื่อรวมกันแล้ว สิ่งนี้หมายความว่าจริงๆ แล้วคุณสามารถยกระดับประสบการณ์ของผู้ใช้ด้วย**การสตรีม HTML**: และนี่คือสิ่งที่ Leptos รองรับในตัวโดยไม่ต้องตั้งค่าใดๆ เลย และจริงๆ แล้วมีมากกว่าหนึ่งวิธีในการสตรีม HTML: คุณสามารถสตรีมชิ้นส่วน HTML ที่ประกอบกันเป็นหน้าเพจของคุณตามลำดับ เหมือนเฟรมของวิดีโอ หรือคุณสามารถสตรีมมันแบบ... ไม่ตามลำดับก็ได้

ผมขออธิบายเพิ่มเติมอีกเล็กน้อยว่าผมหมายถึงอะไร

Leptos รองรับวิธีหลักทั้งหมดในการเรนเดอร์ HTML ที่มีข้อมูลแบบอะซิงก์:

## การเรนเดอร์แบบซิงโครนัส

1. **ซิงโครนัส**: เสิร์ฟเปลือก HTML ที่มี `fallback` สำหรับ `<Suspense/>` ใดๆ โหลดข้อมูลบนไคลเอนต์โดยใช้ `create_local_resource` แทนที่ `fallback` เมื่อรีซอร์สโหลดเสร็จ

- _ข้อดี_: เปลือกแอปปรากฏขึ้นอย่างรวดเร็วมาก: TTFB (เวลาถึงไบต์แรก) ยอดเยี่ยม
- _ข้อเสีย_
  - รีซอร์สโหลดค่อนข้างช้า; คุณต้องรอให้ JS + WASM โหลดก่อนที่จะเริ่มส่งคำขอด้วยซ้ำ
  - ไม่สามารถนำข้อมูลจากรีซอร์สแบบอะซิงก์ไปใส่ใน `<title>` หรือแท็ก `<meta>` อื่นๆ ได้ ซึ่งส่งผลเสียต่อ SEO และสิ่งอย่างการแสดงตัวอย่างลิงก์บนโซเชียลมีเดีย

ถ้าคุณใช้การเรนเดอร์ฝั่งเซิร์ฟเวอร์ โหมดซิงโครนัสแทบไม่เคยเป็นสิ่งที่คุณต้องการจริงๆ จากมุมมองด้านประสิทธิภาพ นี่เป็นเพราะมันพลาดการเพิ่มประสิทธิภาพที่สำคัญไป หากคุณกำลังโหลดรีซอร์สแบบอะซิงก์ระหว่างการเรนเดอร์ฝั่งเซิร์ฟเวอร์ จริงๆ แล้วคุณสามารถเริ่มโหลดข้อมูลบนเซิร์ฟเวอร์ได้เลย แทนที่จะรอให้ไคลเอนต์ได้รับคำตอบ HTML แล้วโหลด JS + WASM แล้ว_จึง_ตระหนักว่ามันต้องใช้รีซอร์สและเริ่มโหลด การเรนเดอร์ฝั่งเซิร์ฟเวอร์สามารถเริ่มโหลดรีซอร์สได้ทันทีที่ไคลเอนต์ส่งคำขอครั้งแรก ในแง่นี้ ระหว่างการเรนเดอร์ฝั่งเซิร์ฟเวอร์ รีซอร์สแบบอะซิงก์ก็เหมือน `Future` ที่เริ่มโหลดบนเซิร์ฟเวอร์และไปเสร็จสิ้นบนไคลเอนต์ ตราบใดที่รีซอร์สสามารถซีเรียลไลซ์ได้จริง สิ่งนี้จะนำไปสู่เวลาโหลดรวมที่เร็วกว่าเสมอ

> นี่คือเหตุผลว่าทำไม `Resource` จึงต้องการข้อมูลที่ซีเรียลไลซ์ได้ และทำไมคุณจึงควรใช้ `LocalResource` สำหรับข้อมูลแบบอะซิงก์ที่ไม่สามารถซีเรียลไลซ์ได้ และด้วยเหตุนี้จึงควรโหลดในเบราว์เซอร์เท่านั้น การสร้างรีซอร์สแบบโลคอลในเมื่อคุณสร้างรีซอร์สที่ซีเรียลไลซ์ได้อยู่แล้วถือเป็นการลดประสิทธิภาพเสมอ

2. **`async`**: โหลดรีซอร์สทั้งหมดบนเซิร์ฟเวอร์ รอจนกว่าข้อมูลทั้งหมดจะโหลดเสร็จ แล้วเรนเดอร์ HTML ในครั้งเดียว

- _ข้อดี_: จัดการเมตาแท็กได้ดีกว่า (เพราะคุณรู้ข้อมูลแบบอะซิงก์ก่อนที่จะเรนเดอร์ `<head>` ด้วยซ้ำ) โหลดเสร็จสมบูรณ์เร็วกว่าแบบ **ซิงโครนัส** เพราะรีซอร์สแบบอะซิงก์เริ่มโหลดบนเซิร์ฟเวอร์
- _ข้อเสีย_: เวลาโหลด/TTFB ช้ากว่า: คุณต้องรอให้รีซอร์สแบบอะซิงก์ทั้งหมดโหลดก่อนจะแสดงอะไรบนไคลเอนต์ได้ หน้าเพจจะว่างเปล่าจนกว่าทุกอย่างจะโหลดเสร็จ

## การสตรีมแบบตามลำดับ

<video controls>
	<source src="https://github.com/leptos-rs/leptos/blob/main/docs/video/in-order.mov?raw=true" type="video/mp4">
</video>

3. **การสตรีมแบบตามลำดับ**: ไล่ไปตามต้นไม้คอมโพเนนต์ เรนเดอร์ HTML ไปจนกว่าจะเจอ `<Suspense/>` ส่ง HTML ทั้งหมดที่คุณมีตอนนั้นลงไปเป็นชิ้นส่วนในสตรีม รอให้รีซอร์สทั้งหมดที่ถูกเข้าถึงภายใต้ `<Suspense/>` โหลดเสร็จ แล้วเรนเดอร์มันเป็น HTML และเดินต่อไปจนกว่าจะเจอ `<Suspense/>` อีกตัวหรือจุดสิ้นสุดของหน้าเพจ

- _ข้อดี_: แทนที่จะเป็นหน้าจอว่างเปล่า อย่างน้อยก็แสดง_บางสิ่ง_ก่อนที่ข้อมูลจะพร้อม
- _ข้อเสีย_
  - โหลดเปลือกได้ช้ากว่าการเรนเดอร์แบบซิงโครนัส (หรือการสตรีมแบบไม่ตามลำดับ) เพราะต้องหยุดชั่วคราวที่ทุก `<Suspense/>`
  - ไม่สามารถแสดงสถานะฟอลแบ็กสำหรับ `<Suspense/>` ได้
  - เริ่มการไฮเดรตไม่ได้จนกว่าหน้าทั้งหน้าจะโหลดเสร็จ ดังนั้นส่วนก่อนๆ ของหน้าจะยังโต้ตอบไม่ได้จนกว่าชิ้นส่วนที่ถูกระงับจะโหลดเสร็จ

## การสตรีมแบบไม่ตามลำดับ

<video controls>
	<source src="https://github.com/leptos-rs/leptos/blob/main/docs/video/out-of-order.mov?raw=true" type="video/mp4">
</video>

4. **การสตรีมแบบไม่ตามลำดับ**: เหมือนกับการเรนเดอร์แบบซิงโครนัส คือเสิร์ฟเปลือก HTML ที่มี `fallback` สำหรับ `<Suspense/>` ใดๆ แต่โหลดข้อมูลบน**เซิร์ฟเวอร์** สตรีมลงไปให้ไคลเอนต์เมื่อมันเสร็จ และสตรีม HTML สำหรับโหนด `<Suspense/>` ซึ่งจะถูกสลับเข้ามาแทนที่ฟอลแบ็ก

- _ข้อดี_: รวมข้อดีที่สุดของแบบ **ซิงโครนัส** และ **`async`** เข้าด้วยกัน
  - การตอบสนองครั้งแรก/TTFB รวดเร็ว เพราะส่งเปลือกซิงโครนัสทั้งหมดทันที
  - เวลารวมรวดเร็ว เพราะรีซอร์สเริ่มโหลดบนเซิร์ฟเวอร์
  - สามารถแสดงสถานะกำลังโหลดแบบฟอลแบ็กและแทนที่มันแบบไดนามิก แทนที่จะแสดงส่วนว่างเปล่าสำหรับข้อมูลที่ยังโหลดไม่เสร็จ
- _ข้อเสีย_: ต้องเปิดใช้งาน JavaScript เพื่อให้แฟรกเมนต์ที่ถูกระงับปรากฏในลำดับที่ถูกต้อง (ชิ้นส่วน JS เล็กๆ นี้ถูกสตรีมลงมาในแท็ก `<script>` ควบคู่กับแท็ก `<template>` ที่บรรจุแฟรกเมนต์ `<Suspense/>` ที่เรนเดอร์แล้ว จึงไม่จำเป็นต้องโหลดไฟล์ JS เพิ่มเติมใดๆ)

5. **การสตรีมแบบบล็อกบางส่วน**: การสตรีมแบบ “บล็อกบางส่วน” มีประโยชน์เมื่อคุณมีคอมโพเนนต์ `<Suspense/>` หลายตัวแยกจากกันบนหน้าเพจ มันจะถูกกระตุ้นโดยการตั้งค่า `ssr=SsrMode::PartiallyBlocked` บนเส้นทาง และขึ้นอยู่กับรีซอร์สแบบบล็อกภายในวิว หากหนึ่งในคอมโพเนนต์ `<Suspense/>` อ่านจาก “รีซอร์สแบบบล็อก” หนึ่งตัวหรือมากกว่า (ดูด้านล่าง) ระบบจะไม่ส่งฟอลแบ็ก แต่เซิร์ฟเวอร์จะรอจนกว่า `<Suspense/>` นั้นจะเสร็จสิ้น แล้วแทนที่ฟอลแบ็กด้วยแฟรกเมนต์ที่เรนเดอร์เสร็จบนเซิร์ฟเวอร์ ซึ่งหมายความว่ามันถูกรวมไว้ในคำตอบ HTML เริ่มต้นและปรากฏขึ้นแม้ JavaScript จะถูกปิดใช้งานหรือไม่รองรับ ส่วน `<Suspense/>` อื่นๆ จะสตรีมแบบไม่ตามลำดับ คล้ายกับค่าเริ่มต้น `SsrMode::OutOfOrder`

สิ่งนี้มีประโยชน์เมื่อคุณมี `<Suspense/>` หลายตัวบนหน้าเพจ และตัวหนึ่งสำคัญกว่าตัวอื่น: ลองนึกถึงโพสต์บล็อกกับคอมเมนต์ หรือข้อมูลสินค้ากับรีวิว มัน_ไม่_มีประโยชน์ถ้ามี `<Suspense/>` เพียงตัวเดียว หรือถ้าทุก `<Suspense/>` อ่านจากรีซอร์สแบบบล็อก ในกรณีเหล่านั้น มันเป็นรูปแบบการเรนเดอร์แบบ `async` ที่ช้ากว่า

- _ข้อดี_: ทำงานได้หาก JavaScript ถูกปิดใช้งานหรือไม่รองรับบนอุปกรณ์ของผู้ใช้
- _ข้อเสีย_
  - เวลาตอบสนองครั้งแรกช้ากว่าแบบไม่ตามลำดับ
  - การตอบสนองโดยรวมช้ากว่าเล็กน้อยเนื่องจากการทำงานเพิ่มเติมบนเซิร์ฟเวอร์
  - ไม่แสดงสถานะฟอลแบ็ก

## การใช้โหมด SSR

เนื่องจากมันให้ส่วนผสมที่ดีที่สุดของคุณลักษณะด้านประสิทธิภาพ Leptos จึงใช้การสตรีมแบบไม่ตามลำดับเป็นค่าเริ่มต้น แต่มันง่ายมากที่จะเลือกใช้โหมดต่างๆ เหล่านี้ คุณทำได้โดยเพิ่มพร็อพ `ssr` ลงบนคอมโพเนนต์ `<Route/>` หนึ่งตัวหรือมากกว่า ดังใน[ตัวอย่าง `ssr_modes`](https://github.com/leptos-rs/leptos/blob/main/examples/ssr_modes/src/app.rs)

```rust
<Routes fallback=|| "Not found.">
	// We’ll load the home page with out-of-order streaming and <Suspense/>
	<Route path=path!("") view=HomePage/>

	// We'll load the posts with async rendering, so they can set
	// the title and metadata *after* loading the data
	<Route
		path=path!("/post/:id")
		view=BlogPost
		ssr=SsrMode::Async
	/>
</Routes>
```

สำหรับพาธที่มีเส้นทางซ้อนกันหลายเส้นทาง จะใช้โหมดที่จำกัดมากที่สุด กล่าวคือ ถ้าแม้แต่เส้นทางซ้อนกันเพียงเส้นเดียวขอการเรนเดอร์แบบ `async` คำขอเริ่มต้นทั้งหมดจะถูกเรนเดอร์แบบ `async` โดย `async` เป็นข้อกำหนดที่จำกัดมากที่สุด รองลงมาคือแบบตามลำดับ และจากนั้นคือแบบไม่ตามลำดับ (เรื่องนี้น่าจะสมเหตุสมผลถ้าคุณลองคิดดูสักสองสามนาที)

## รีซอร์สแบบบล็อก

รีซอร์สแบบบล็อกสามารถสร้างได้ด้วย `Resource::new_blocking` รีซอร์สแบบบล็อกยังคงโหลดแบบอะซิงโครนัสเหมือน `async`/`.await` อื่นๆ ใน Rust มันไม่ได้บล็อกเธรดของเซิร์ฟเวอร์หรืออะไรทำนองนั้น แต่การอ่านจากรีซอร์สแบบบล็อกภายใต้ `<Suspense/>` จะบล็อก_สตรีม_ HTML ไม่ให้คืนค่าอะไรเลย รวมถึงเปลือกซิงโครนัสเริ่มต้นของมันด้วย จนกว่า `<Suspense/>` นั้นจะเสร็จสิ้น

จากมุมมองด้านประสิทธิภาพ นี่ไม่ใช่เรื่องในอุดมคติ เปลือกซิงโครนัสใดๆ ของหน้าเพจคุณจะไม่โหลดจนกว่ารีซอร์สนั้นจะพร้อม อย่างไรก็ตาม การไม่เรนเดอร์อะไรเลยหมายความว่าคุณสามารถทำสิ่งอย่างตั้งค่าแท็ก `<title>` หรือ `<meta>` ใน `<head>` ของคุณเป็น HTML จริงได้ ฟังดูคล้ายกับการเรนเดอร์แบบ `async` มาก แต่มีความแตกต่างที่สำคัญอย่างหนึ่ง: ถ้าคุณมีส่วน `<Suspense/>` หลายส่วน คุณสามารถบล็อกที่_หนึ่ง_ในนั้นแต่ยังเรนเดอร์ตัวแทนไว้ก่อน แล้วสตรีมส่วนอื่นเข้ามาทีหลังได้

ตัวอย่างเช่น ลองนึกถึงโพสต์บล็อก สำหรับ SEO และการแชร์บนโซเชียล ผมต้องการชื่อเรื่องและเมทาดาทาของโพสต์บล็อกใน `<head>` HTML เริ่มต้นอย่างแน่นอน แต่ผมไม่แคร์เลยว่าคอมเมนต์จะโหลดเสร็จหรือยัง ผมอยากโหลดคอมเมนต์เหล่านั้นแบบ lazy ที่สุดเท่าที่จะเป็นไปได้

ด้วยรีซอร์สแบบบล็อก ผมสามารถทำอะไรแบบนี้ได้:

```rust
#[component]
pub fn BlogPost() -> impl IntoView {
    let post_data = Resource::new_blocking(/* load blog post */);
    let comments_data = Resource::new(/* load blog comments */);
    view! {
        <Suspense fallback=|| ()>
            {move || Suspend::new(async move {
                let data = post_data.await;
                view! {
                    <Title text=data.title/>
                    <Meta name="description" content=data.excerpt/>
                    <article>
                        /* render the post content */
                    </article>
                }
            })}
        </Suspense>
        <Suspense fallback=|| "Loading comments...">
            {move || Suspend::new(async move {
                let comments = comments_data.await;
                todo!()
            })}
        </Suspense>
    }
}
```

`<Suspense/>` ตัวแรก ซึ่งมีเนื้อหาของโพสต์บล็อก จะบล็อกสตรีม HTML ของผม เพราะมันอ่านจากรีซอร์สแบบบล็อก เมตาแท็กและเอลิเมนต์ head อื่นๆ ที่รอรีซอร์สแบบบล็อกจะถูกเรนเดอร์ก่อนที่สตรีมจะถูกส่ง

เมื่อรวมกับนิยามเส้นทางต่อไปนี้ ซึ่งใช้ `SsrMode::PartiallyBlocked` รีซอร์สแบบบล็อกจะถูกเรนเดอร์อย่างสมบูรณ์บนฝั่งเซิร์ฟเวอร์ ทำให้ผู้ใช้ที่ปิดใช้งาน WebAssembly หรือ JavaScript สามารถเข้าถึงได้

```rust
<Routes fallback=|| "Not found.">
	// We’ll load the home page with out-of-order streaming and <Suspense/>
	<Route path=path!("") view=HomePage/>

	// We'll load the posts with async rendering, so they can set
	// the title and metadata *after* loading the data
	<Route
		path=path!("/post/:id")
		view=BlogPost
		ssr=SsrMode::PartiallyBlocked
	/>
</Routes>
```

`<Suspense/>` ตัวที่สอง ซึ่งมีคอมเมนต์ จะไม่บล็อกสตรีม รีซอร์สแบบบล็อกให้พลังและความละเอียดที่ผมต้องการพอดีในการปรับหน้าเพจของผมให้เหมาะสมสำหรับ SEO และประสบการณ์ของผู้ใช้
