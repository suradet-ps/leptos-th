# การเรนเดอร์แบบอะซิงก์และ “โหมด” ของ SSR

การเรนเดอร์ฝั่งเซิร์ฟเวอร์สำหรับหน้าเพจที่ใช้เฉพาะข้อมูลซิงโครนัสนั้นค่อนข้างตรงไปตรงมา: คุณเพียงแค่ไล่สำรวจทรีคอมโพเนนต์ แล้วเรนเดอร์แต่ละเอลิเมนต์ออกมาเป็นสตริง HTML แต่ก็ยังมีข้อแม้สำคัญอยู่ประการหนึ่ง: วิธีนี้ยังไม่ตอบคำถามว่าเราควรจัดการอย่างไรกับหน้าเพจที่มีข้อมูลแบบอะซิงโครนัส (asynchronous data) กล่าวคือ ข้อมูลชนิดที่มักจะถูกเรนเดอร์อยู่ภายใต้โหนด `<Suspense/>` บนฝั่งไคลเอนต์

เมื่อหน้าเพจจำเป็นต้องโหลดข้อมูลแบบอะซิงก์เพื่อนำมาใช้เรนเดอร์ เราควรทำอย่างไร? เราควรรอให้ข้อมูลแบบอะซิงก์ทั้งหมดโหลดเสร็จสมบูรณ์เสียก่อน แล้วค่อยเรนเดอร์ทุกอย่างออกมาพร้อมกันในคราวเดียวดีหรือไม่? (เราจะเรียกสิ่งนี้ว่าการเรนเดอร์แบบ “async”) หรือเราควรไปในทิศทางตรงกันข้ามอย่างสิ้นเชิง โดยรีบส่งเฉพาะโครงสร้าง HTML ที่เรามีอยู่ทันทีไปให้ไคลเอนต์ แล้วปล่อยให้ไคลเอนต์ไปตามโหลดรีซอร์สและนำข้อมูลมาเติมใส่เองทีหลัง? (เราจะเรียกสิ่งนี้ว่าการเรนเดอร์แบบ “synchronous”) หรือว่ามีทางสายกลางที่ให้ผลลัพธ์เหนือกว่าทั้งสองวิธีนี้อยู่กันแน่? (บอกใบ้ให้ว่า: มีอยู่จริง!)

หากคุณเคยฟังเพลงผ่านบริการสตรีมมิงหรือดูวิดีโอออนไลน์ คุณคงทราบดีว่าโพรโทคอล HTTP รองรับการสตรีม ซึ่งทำให้การเชื่อมต่อเพียงครั้งเดียวสามารถส่งชิ้นส่วนข้อมูลต่อเนื่องกันไปเรื่อย ๆ ได้โดยไม่ต้องรอให้เนื้อหาทั้งหมดถูกดาวน์โหลดจนเสร็จสิ้น และคุณอาจยังไม่ทราบว่าเบราว์เซอร์เองก็มีความสามารถอันยอดเยี่ยมในการเรนเดอร์หน้า HTML แม้ว่าจะเพิ่งได้รับข้อมูลมาเพียงบางส่วนก็ตาม เมื่อนำสองสิ่งนี้มารวมกัน นั่นแปลว่าคุณสามารถยกระดับประสบการณ์ของผู้ใช้ได้อย่างมหาศาลด้วย **การสตรีม HTML** (HTML streaming) ซึ่งเป็นฟีเจอร์ที่ Leptos รองรับมาให้ทันทีตั้งแต่แกะกล่องโดยไม่ต้องตั้งค่าเพิ่มเติมใด ๆ เลย ยิ่งไปกว่านั้น วิธีการสตรีม HTML ก็ไม่ได้มีเพียงวิธีเดียว: คุณสามารถเลือกสตรีมชิ้นส่วน HTML ที่ประกอบกันเป็นหน้าเพจของคุณตามลำดับ (in order) ราวกับเฟรมของวิดีโอ หรือจะเลือกสตรีมพวกมันแบบ... ไม่เรียงลำดับ (out of order) ก็ได้เช่นกัน

ให้ผมอธิบายเพิ่มเติมอีกสักนิดว่าสิ่งนี้หมายถึงอะไร

Leptos รองรับวิธีหลักทั้งหมดในการเรนเดอร์ HTML ที่ประกอบด้วยข้อมูลแบบอะซิงก์:

## การเรนเดอร์แบบซิงโครนัส

1. **ซิงโครนัส**: ส่งโครงสร้างเชลล์ (shell) ของ HTML ที่ประกอบด้วยสถานะสำรอง `fallback` สำหรับทุก `<Suspense/>` แล้วไปโหลดข้อมูลบนฝั่งไคลเอนต์ด้วย `create_local_resource` จากนั้นจึงนำข้อมูลที่ได้มาแทนที่ `fallback` เมื่อโหลดเสร็จ

- _ข้อดี_: โครงสร้างเชลล์ของแอปปรากฏขึ้นอย่างรวดเร็วมาก: ค่า TTFB (Time to First Byte) ยอดเยี่ยมเป็นพิเศษ
- _ข้อเสีย_
  - รีซอร์สต่าง ๆ จะโหลดได้ค่อนข้างช้า เพราะคุณต้องรอให้ไฟล์ JS + WASM โหลดลงมาจนเสร็จก่อน ถึงจะเริ่มส่งคำขอขอข้อมูลได้
  - ไม่สามารถนำข้อมูลจากรีซอร์สแบบอะซิงก์ไปใส่ไว้ในแท็ก `<title>` หรือแท็ก `<meta>` อื่น ๆ ได้ ซึ่งส่งผลเสียต่อการทำ SEO และการแสดงผลตัวอย่างลิงก์บนโซเชียลมีเดีย (social previews)

หากคุณเลือกใช้การเรนเดอร์ฝั่งเซิร์ฟเวอร์ โหมดซิงโครนัสนี้แทบจะไม่ใช่ตัวเลือกที่คุณต้องการอย่างแท้จริงในแง่ของประสิทธิภาพ เหตุผลเพราะมันพลาดโอกาสในการทำ optimization สำคัญไปอย่างน่าเสียดาย กล่าวคือ หากคุณกำลังโหลดรีซอร์สแบบอะซิงก์ระหว่างการเรนเดอร์บนเซิร์ฟเวอร์ จริง ๆ แล้วคุณสามารถเริ่มต้นโหลดข้อมูลบนเซิร์ฟเวอร์ได้ทันที แทนที่จะต้องรอให้ไคลเอนต์ได้รับ HTML ตอบกลับมา โหลดไฟล์ JS + WASM จนเสร็จ แล้ว*เพิ่งมารู้ตัว*ว่าต้องใช้รีซอร์สเหล่านี้จึงค่อยเริ่มส่งคำขอ การเรนเดอร์บนเซิร์ฟเวอร์สามารถเริ่มโหลดรีซอร์สได้ตั้งแต่ตอนที่ไคลเอนต์ส่งคำขอเข้ามาในจังหวะแรก ในแง่นี้ ระหว่างขั้นตอนการเรนเดอร์ฝั่งเซิร์ฟเวอร์ รีซอร์สแบบอะซิงก์จึงเปรียบเสมือน `Future` ที่เริ่มต้นโหลดบนเซิร์ฟเวอร์และไปคลี่คลายผลลัพธ์ (resolve) บนฝั่งไคลเอนต์ ตราบใดที่รีซอร์สนั้นสามารถแปลงเป็นอนุกรม (serializable) ได้ วิธีนี้จะช่วยลดระยะเวลาการโหลดโดยรวมลงได้อย่างมหาศาลเสมอ

> นี่คือเหตุผลว่าทำไม `Resource` จึงต้องมีข้อมูลที่สามารถแปลงเป็นอนุกรม (serializable) ได้ และเป็นเหตุผลว่าทำไมคุณจึงควรใช้ `LocalResource` สำหรับข้อมูลแบบอะซิงก์ที่ไม่สามารถแปลงเป็นอนุกรมได้ ซึ่งเหมาะแก่การโหลดบนเบราว์เซอร์เท่านั้น การสร้าง local resource ในขณะที่คุณสามารถสร้างรีซอร์สแบบ serializable ได้นั้นถือเป็นการลดทอนประสิทธิภาพโดยไม่จำเป็นเสมอ

2. **`async`**: โหลดรีซอร์สทั้งหมดบนเซิร์ฟเวอร์ รอจนกว่าข้อมูลทั้งหมดจะโหลดเสร็จสมบูรณ์ แล้วจึงเรนเดอร์ HTML ทั้งหมดออกมาในคราวเดียว

- _ข้อดี_: จัดการเมทาท็ากได้สมบูรณ์แบบ (เพราะคุณทราบข้อมูลแบบอะซิงก์ล่วงหน้าก่อนที่จะเริ่มเรนเดอร์ `<head>`) และโหลดหน้าเว็บจนเสร็จสมบูรณ์ได้เร็วกว่าแบบ **ซิงโครนัส** เนื่องจากรีซอร์สแบบอะซิงก์เริ่มโหลดตั้งแต่บนเซิร์ฟเวอร์
- _ข้อเสีย_: เวลาในการตอบสนองแรกเริ่มหรือ TTFB จะช้าลง เพราะต้องรอให้รีซอร์สแบบอะซิงก์ทั้งหมดโหลดเสร็จเสียก่อน จึงจะเริ่มส่งข้อมูลไปแสดงผลบนไคลเอนต์ได้ หน้าเพจจะว่างเปล่าสนิทจนกว่าทุกอย่างจะโหลดเสร็จ

## การสตรีมแบบตามลำดับ

</video>

3. **การสตรีมแบบตามลำดับ**: ไล่สำรวจทรีคอมโพเนนต์และเรนเดอร์ HTML ไปเรื่อย ๆ จนกว่าจะพบกับ `<Suspense/>` จากนั้นส่งชิ้นส่วน HTML ทั้งหมดที่ได้จนถึงจุดนั้นลงไปในสตรีม รอให้รีซอร์สทั้งหมดที่ถูกเรียกใช้ภายใต้ `<Suspense/>` โหลดจนเสร็จ แล้วเรนเดอร์ส่วนนั้นออกมาเป็น HTML ก่อนจะเดินทางต่อไปจนกว่าจะพบ `<Suspense/>` ตัวถัดไปหรือสิ้นสุดหน้าเพจ

- _ข้อดี_: แทนที่จะปล่อยให้หน้าจอว่างเปล่าสนิท ผู้ใช้จะมองเห็นเนื้อหา*บางส่วน*ขึ้นมาก่อนในระหว่างที่ข้อมูลกำลังโหลด
- _ข้อเสีย_
  - โหลดโครงสร้างเชลล์ได้ช้ากว่าการเรนเดอร์แบบซิงโครนัส (หรือการสตรีมแบบไม่เรียงลำดับ) เพราะต้องหยุดพักรอที่ทุก ๆ `<Suspense/>`
  - ไม่สามารถแสดงผลสถานะสำรอง (fallback) ของ `<Suspense/>` ได้
  - ไม่สามารถเริ่มต้นกระบวนการไฮเดรตได้จนกว่าหน้าเว็บทั้งหน้าจะโหลดจนเสร็จสิ้น ดังนั้นส่วนแรก ๆ ของหน้าเพจจะไม่สามารถโต้ตอบได้จนกว่าชิ้นส่วนที่ถูกระงับไว้จะโหลดเสร็จ

## การสตรีมแบบไม่ตามลำดับ

<video controls>
	<source src="https://github.com/leptos-rs/leptos/blob/main/docs/video/out-of-order.mov?raw=true" type="video/mp4">
</video>

4. **การสตรีมแบบไม่ตามลำดับ**: คล้ายกับการเรนเดอร์แบบซิงโครนัส คือส่งโครงสร้างเชลล์ HTML ที่มี `fallback` สำหรับทุก `<Suspense/>` ออกไปทันที แต่จะสั่งโหลดข้อมูลบน**เซิร์ฟเวอร์** แล้วสตรีมข้อมูลนั้นลงไปให้ไคลเอนต์ทันทีที่ข้อมูลพร้อม ควบคู่ไปกับการสตรีมโค้ด HTML ของโหนด `<Suspense/>` ซึ่งจะถูกนำไปสลับแทนที่ส่วนฟอลแบ็กแบบไดนามิก

- _ข้อดี_: ผสานข้อดีที่สุดของทั้งแบบ **ซิงโครนัส** และแบบ **`async`** เข้าด้วยกัน
  - การตอบสนองแรกเริ่ม (TTFB) รวดเร็วเป็นพิเศษ เพราะส่งโครงสร้างเชลล์ซิงโครนัสทั้งหมดออกไปทันที
  - ระยะเวลาการโหลดโดยรวมรวดเร็วมาก เพราะรีซอร์สต่าง ๆ เริ่มโหลดตั้งแต่บนเซิร์ฟเวอร์
  - สามารถแสดงสถานะกำลังโหลด (fallback) ให้ผู้ใช้เห็นได้ และสลับเนื้อหาจริงเข้ามาแทนที่ได้อย่างลื่นไหล แทนที่จะแสดงพื้นที่ว่างเปล่าสำหรับข้อมูลที่ยังไม่พร้อม
- _ข้อเสีย_: จำเป็นต้องเปิดใช้งาน JavaScript บนเบราว์เซอร์เพื่อให้ชิ้นส่วน HTML ที่ถูกสตรีมมาทีหลังปรากฏในตำแหน่งที่ถูกต้อง (สคริปต์ JS ขนาดเล็กมากนี้จะถูกสตรีมส่งมาในแท็ก `<script>` ควบคู่กับแท็ก `<template>` ที่บรรจุชิ้นส่วน `<Suspense/>` ที่เรนเดอร์แล้ว จึงไม่จำเป็นต้องดาวน์โหลดไฟล์ JS เพิ่มเติมใด ๆ เลย)

5. **การสตรีมแบบบล็อกบางส่วน**: การสตรีมแบบ “บล็อกบางส่วน” มีประโยชน์อย่างยิ่งเมื่อคุณมีคอมโพเนนต์ `<Suspense/>` หลายตัวแยกกันบนหน้าเพจ โหมดนี้จะเปิดใช้งานได้โดยการกำหนด `ssr=SsrMode::PartiallyBlocked` บนเส้นทาง และขึ้นอยู่กับรีซอร์สแบบบล็อก (blocking resources) ภายในมุมมอง หากมีคอมโพเนนต์ `<Suspense/>` ตัวใดตัวหนึ่งอ่านข้อมูลจาก “รีซอร์สแบบบล็อก” หนึ่งตัวหรือมากกว่า (ดูรายละเอียดด้านล่าง) ระบบจะไม่ส่งฟอลแบ็กออกไป แต่เซิร์ฟเวอร์จะรอจนกว่า `<Suspense/>` นั้นจะทำงานเสร็จสิ้น แล้วแทนที่ฟอลแบ็กด้วยชิ้นส่วนที่เรนเดอร์เสร็จสมบูรณ์ตั้งแต่บนเซิร์ฟเวอร์ ซึ่งหมายความว่าเนื้อหานั้นจะถูกรวมอยู่ในคำตอบ HTML รอบแรกสุดและแสดงผลได้ทันทีแม้ผู้ใช้จะปิดใช้งานหรือไม่รองรับ JavaScript ส่วน `<Suspense/>` ตัวอื่น ๆ จะยังคงสตรีมแบบไม่เรียงลำดับตามปกติ คล้ายกับโหมดเริ่มต้น `SsrMode::OutOfOrder`

สิ่งนี้มีประโยชน์มากเมื่อคุณมี `<Suspense/>` หลายตัวบนหน้าเพจ และมีบางส่วนที่สำคัญกว่าส่วนอื่น: ลองนึกถึงเนื้อหาบทความบล็อกกับส่วนความคิดเห็น หรือรายละเอียดสินค้ากับรีวิวจากผู้ใช้ โหมดนี้จะ*ไม่มี*ประโยชน์เลยหากมี `<Suspense/>` เพียงตัวเดียว หรือหากทุก `<Suspense/>` ต่างก็อ่านข้อมูลจากรีซอร์สแบบบล็อก เพราะในกรณีเช่นนั้น มันก็ไม่ต่างอะไรจากการเรนเดอร์แบบ `async` ที่ช้าลง

- _ข้อดี_: ทำงานได้อย่างสมบูรณ์แม้จะปิดการใช้งาน JavaScript หรือไม่รองรับบนอุปกรณ์ของผู้ใช้
- _ข้อเสีย_
  - เวลาตอบสนองครั้งแรก (initial response time) ช้ากว่าแบบไม่เรียงลำดับ
  - การตอบสนองโดยรวมอาจช้าลงเล็กน้อยเนื่องจากมีขั้นตอนการทำงานเพิ่มเติมบนเซิร์ฟเวอร์
  - ไม่แสดงสถานะสำรอง (fallback) สำหรับส่วนที่ถูกบล็อก

## การใช้โหมด SSR

เนื่องจากให้ความสมดุลด้านประสิทธิภาพที่ดีที่สุดในทุกมิติ Leptos จึงเลือกใช้การสตรีมแบบไม่เรียงลำดับ (out-of-order streaming) เป็นค่าเริ่มต้น แต่คุณสามารถสลับไปใช้โหมดอื่น ๆ ได้อย่างง่ายดาย เพียงเพิ่มพร็อพเพอร์ตี `ssr` ให้แก่คอมโพเนนต์ `<Route/>` ของคุณ ดังตัวอย่างใน [`ssr_modes`](https://github.com/leptos-rs/leptos/blob/main/examples/ssr_modes/src/app.rs)

```rust
<Routes fallback=|| "Not found.">
	// We’ll load the home page with out-of-order streaming and <Suspense/>
	<Route path=path!("") view=HomePage/>

	// We'll load the posts with async rendering, so they can set
	// the title and metadata *after* loading the data
	<Route
		path=path!("/post/:id")
		view=BlogPost
		ssr=SsrMode::Async
	/>
</Routes>
```

สำหรับเส้นทางที่ประกอบด้วยเส้นทางซ้อนกันหลายชั้น (nested routes) โหมดที่มีข้อจำกัดเข้มงวดที่สุดจะถูกนำมาใช้งานเสมอ: กล่าวคือ หากมีแม้เพียงเส้นทางซ้อนกันเส้นเดียวที่ร้องขอการเรนเดอร์แบบ `async` คำขอรอบแรกของทั้งหน้านั้นจะถูกเรนเดอร์ในโหมด `async` ทันที โดยที่ `async` มีข้อจำกัดเข้มงวดที่สุด รองลงมาคือแบบตามลำดับ (in-order) และตามด้วยแบบไม่เรียงลำดับ (out-of-order) (ซึ่งเป็นหลักการที่สมเหตุสมผลหากคุณลองพิจารณากระบวนการทำงานของมัน)

## รีซอร์สแบบบล็อก

รีซอร์สแบบบล็อก (blocking resources) สามารถสร้างขึ้นได้โดยใช้ `Resource::new_blocking` โดยที่รีซอร์สแบบบล็อกจะยังคงโหลดแบบอะซิงโครนัสเหมือนกับโค้ด `async`/`.await` ทั่วไปใน Rust มันไม่ได้ไปบล็อกเธรดของเซิร์ฟเวอร์แต่อย่างใด ทว่า การอ่านข้อมูลจากรีซอร์สแบบบล็อกภายใต้ `<Suspense/>` จะไปบล็อก *สตรีม* HTML ไม่ให้ส่งข้อมูลใด ๆ กลับไปเลย รวมถึงโครงสร้างเชลล์ซิงโครนัสเริ่มต้นด้วย จนกว่า `<Suspense/>` นั้นจะทำงานเสร็จสิ้น

ในมุมมองด้านประสิทธิภาพ นี่อาจไม่ใช่เรื่องในอุดมคติ เพราะโครงสร้างเชลล์ของหน้าเว็บจะไม่เริ่มแสดงผลจนกว่ารีซอร์สนั้นจะพร้อมใช้งาน อย่างไรก็ดี การชะลอการเรนเดอร์ไว้ก่อนทำให้คุณสามารถกำหนดแท็ก `<title>` หรือแท็ก `<meta>` ในส่วน `<head>` ของ HTML ตัวจริงได้ ฟังดูอาจคล้ายกับการเรนเดอร์แบบ `async` แต่มีความแตกต่างสำคัญอย่างหนึ่ง: หากคุณมีส่วน `<Suspense/>` หลายส่วน คุณสามารถเลือกที่จะบล็อกเฉพาะ *ส่วนใดส่วนหนึ่ง* ได้ ในขณะที่ยังคงเรนเดอร์ตัวแทนชั่วคราวแล้วค่อยสตรีมข้อมูลของส่วนอื่น ๆ ตามลงไปทีหลัง

ตัวอย่างเช่น ลองพิจารณาหน้าบทความบล็อก เพื่อประโยชน์ด้าน SEO และการแชร์บนโซเชียลมีเดีย เราย่อมต้องการให้ชื่อบทความและเมทาดาทาปรากฏอยู่ใน `<head>` ของ HTML เริ่มต้นอย่างแน่นอน แต่เราอาจไม่ได้สนใจว่าส่วนความคิดเห็นจะโหลดเสร็จทันทีหรือไม่ และอยากให้โหลดส่วนความคิดเห็นนั้นแบบ lazy ให้ช้าที่สุดเท่าที่จะทำได้

เมื่อมีรีซอร์สแบบบล็อก คุณสามารถเขียนโค้ดลักษณะนี้ได้:

```rust
#[component]
pub fn BlogPost() -> impl IntoView {
    let post_data = Resource::new_blocking(/* load blog post */);
    let comments_data = Resource::new(/* load blog comments */);
    view! {
        <Suspense fallback=|| ()>
            {move || Suspend::new(async move {
                let data = post_data.await;
                view! {
                    <Title text=data.title/>
                    <Meta name="description" content=data.excerpt/>
                    <article>
                        /* render the post content */
                    </article>
                }
            })}
        </Suspense>
        <Suspense fallback=|| "Loading comments...">
            {move || Suspend::new(async move {
                let comments = comments_data.await;
                todo!()
            })}
        </Suspense>
    }
}
```

`<Suspense/>` ตัวแรกที่ครอบเนื้อหาบทความบล็อกจะทำการบล็อกสตรีม HTML ของเรา เพราะมันอ่านข้อมูลจากรีซอร์สแบบบล็อก ทำให้เมทาแท็กและเอลิเมนต์อื่น ๆ ในส่วน `<head>` ที่รอคอยรีซอร์สแบบบล็อกนี้ถูกเรนเดอร์ออกมาก่อนที่สตรีมจะถูกส่งไป

เมื่อนำไปใช้ร่วมกับนิยามเส้นทางด้านล่างนี้ที่กำหนดค่า `SsrMode::PartiallyBlocked` รีซอร์สแบบบล็อกดังกล่าวจะถูกเรนเดอร์บนฝั่งเซิร์ฟเวอร์จนเสร็จสมบูรณ์ ทำให้ผู้ใช้ที่ปิดการทำงานของ WebAssembly หรือ JavaScript ยังคงสามารถเข้าถึงและอ่านบทความได้:

```rust
<Routes fallback=|| "Not found.">
	// We’ll load the home page with out-of-order streaming and <Suspense/>
	<Route path=path!("") view=HomePage/>

	// We'll load the posts with async rendering, so they can set
	// the title and metadata *after* loading the data
	<Route
		path=path!("/post/:id")
		view=BlogPost
		ssr=SsrMode::PartiallyBlocked
	/>
</Routes>
```

ในขณะที่ `<Suspense/>` ตัวที่สองซึ่งครอบส่วนความคิดเห็นจะไม่ไปบล็อกการสตรีม รีซอร์สแบบบล็อกจึงมอบทั้งพลังและความยืดหยุ่นในระดับละเอียดที่คุณต้องการ เพื่อปรับแต่งหน้าเพจให้ได้ทั้งประสิทธิภาพด้าน SEO และประสบการณ์การใช้งานที่ดีที่สุดไปพร้อมกัน
