# บั๊กการไฮเดรต _(และวิธีหลีกเลี่ยง)_

## การทดลองทางความคิด

ลองทำการทดลองเพื่อทดสอบสัญชาตญาณของคุณดู: ให้เปิดแอปที่คุณกำลังเรนเดอร์ฝั่งเซิร์ฟเวอร์ด้วย `cargo-leptos` ขึ้นมา (หากก่อนหน้านี้คุณใช้เพียง `trunk` เพื่อทดลองตัวอย่างต่าง ๆ แนะนำให้ลอง [โคลนเทมเพลต `cargo-leptos`](./21_cargo_leptos.md) มาใช้สำหรับแบบฝึกหัดนี้โดยเฉพาะ)

ใส่คำสั่งล็อกไว้ตรงไหนสักแห่งในรูทคอมโพเนนต์ของคุณ (ปกติผมมักตั้งชื่อว่า `<App/>` แต่คุณจะตั้งชื่อว่าอะไรก็ได้):

```rust
#[component]
pub fn App() -> impl IntoView {
	logging::log!("where do I run?");
	// ... whatever
}
```

แล้วลองสั่งรันดู:

```bash
cargo leptos watch
```

คุณคาดว่าข้อความ `where do I run?` จะไปปรากฏอยู่ที่ไหน?

- ในเทอร์มินัลหรือบรรทัดคำสั่งที่คุณสั่งรันเซิร์ฟเวอร์?
- ในคอนโซลของเบราว์เซอร์เมื่อคุณโหลดหน้าเว็บขึ้นมา?
- ไม่ปรากฏทั้งสองที่?
- ปรากฏทั้งสองที่?

ลองรันดูเลยครับ

...

...

...

เอาล่ะ ขอเฉลยเลยแล้วกัน

คุณจะสังเกตเห็นว่ามันล็อกทั้งสองที่แน่นอน หากทุกอย่างทำงานถูกต้องตามแผน ที่จริงแล้วบนเซิร์ฟเวอร์มันจะล็อกถึงสองรอบด้วยกัน—รอบแรกคือตอนที่เซิร์ฟเวอร์เริ่มทำงาน (startup) ซึ่ง Leptos จะสั่งเรนเดอร์แอปหนึ่งรอบเพื่อสกัดโครงสร้างเส้นทาง (route tree) ออกมา และรอบที่สองคือตอนที่คุณส่งคำขอหน้าเว็บเข้ามาจริง ๆ ทุกครั้งที่คุณรีโหลดหน้าเว็บ ข้อความ `where do I run?` จะล็อกหนึ่งครั้งบนเซิร์ฟเวอร์ และอีกหนึ่งครั้งบนไคลเอนต์

หากคุณยังจำคำอธิบายในสองบทก่อนหน้านี้ได้ พฤติกรรมนี้จะดูสมเหตุสมผลในทันที: แอปพลิเคชันของคุณถูกสั่งรันหนึ่งรอบบนเซิร์ฟเวอร์เพื่อสร้างโครงสร้าง HTML ส่งต่อไปยังไคลเอนต์ ในระหว่างขั้นตอนการเรนเดอร์แรกเริ่มนี้ ข้อความ `where do I run?` จึงถูกล็อกบนเซิร์ฟเวอร์

และเมื่อไฟล์ไบนารี WASM โหลดลงบนเบราว์เซอร์จนเสร็จสิ้น แอปพลิเคชันของคุณก็จะถูกสั่งรันอีกเป็นรอบที่สอง โดยจะไล่สำรวจโครงสร้างหน้าตาเดิมเพื่อผูกระบบการโต้ตอบเข้าไป

> ฟังดูสิ้นเปลืองไหม? ในแง่หนึ่งก็อาจจะใช่ แต่การลดความสิ้นเปลืองตรงนี้เป็นโจทย์ที่ท้าทายอย่างยิ่ง และเป็นสิ่งที่เฟรมเวิร์ก JS บางตัวอย่าง Qwik พยายามเข้ามาแก้ไข ถึงแม้ว่าอาจจะยังเร็วเกินไปที่จะสรุปว่ามันให้ความคุ้มค่าด้านประสิทธิภาพโดยรวมเหนือกว่าแนวทางอื่นจริงหรือไม่

## โอกาสและความเสี่ยงที่จะเกิดบั๊ก

โอเค หวังว่าทั้งหมดนั้นจะช่วยให้เห็นภาพชัดเจนขึ้น แต่มันเกี่ยวอะไรกับชื่อบทนี้ ซึ่งก็คือ “บั๊กการไฮเดรต (และวิธีหลีกเลี่ยง)”?

อย่าลืมว่าแอปพลิเคชันจำเป็นต้องรันได้ทั้งบนเซิร์ฟเวอร์และไคลเอนต์ ข้อกำหนดนี้จึงทำให้เกิดชุดของปัญหาที่อาจเกิดขึ้นได้หลายประการ ซึ่งคุณจำเป็นต้องทราบวิธีรับมือและหลีกเลี่ยง

### ความไม่ตรงกันระหว่างโค้ดฝั่งเซิร์ฟเวอร์และฝั่งไคลเอนต์

หนึ่งในสาเหตุที่ทำให้เกิดบั๊กคือความไม่ตรงกันระหว่างโค้ด HTML ที่เซิร์ฟเวอร์ส่งลงมา กับสิ่งที่ไคลเอนต์พยายามเรนเดอร์ จริง ๆ แล้วผมคิดว่าเป็นเรื่องยากพอสมควรที่จะทำให้เกิดปัญหานี้โดยไม่ตั้งใจ (อย่างน้อยก็จากรายงานบั๊กที่มีคนส่งเข้ามา) แต่ลองจินตนาการว่าผมเขียนโค้ดลักษณะนี้:

```rust
#[component]
pub fn App() -> impl IntoView {
    let data = if cfg!(target_arch = "wasm32") {
        vec![0, 1, 2]
    } else {
        vec![]
    };
    data.into_iter()
        .map(|value| view! { <span>{value}</span> })
        .collect_view()
}
```

พูดง่าย ๆ คือ หากโค้ดนี้ถูกคอมไพล์เป็น WASM มันจะมีข้อมูล 3 ตัว แต่หากคอมไพล์บนเซิร์ฟเวอร์ มันจะกลายเป็นเวกเตอร์ว่างเปล่า

เมื่อผมโหลดหน้านี้บนเบราว์เซอร์ ผมจะไม่เห็นอะไรเลย และหากเปิดดูในคอนโซล ก็จะพบกับอาการแพนิก (panic):

```
ssr_modes.js:423 panicked at /.../tachys/src/html/element/mod.rs:352:14:
called `Option::unwrap()` on a `None` value
```

เวอร์ชัน WASM ของแอปที่กำลังรันบนเบราว์เซอร์คาดหวังว่าจะพบเอลิเมนต์หนึ่งตัว (ที่จริงคือคาดหวังถึง 3 เอลิเมนต์!) แต่โค้ด HTML ที่ส่งมาจากเซิร์ฟเวอร์กลับไม่มีเอลิเมนต์เหล่านั้นอยู่เลย

#### วิธีแก้

ปกติแล้วแทบไม่มีใครตั้งใจเขียนโค้ดแบบนี้ แต่ก็อาจเกิดขึ้นได้หากคุณเผลอรันลอจิกที่แตกต่างกันระหว่างเซิร์ฟเวอร์กับเบราว์เซอร์โดยไม่ได้ตั้งใจ หากคุณพบคำเตือนลักษณะนี้และมั่นใจว่าไม่ได้เกิดจากโค้ดของคุณเอง เป็นไปได้สูงว่าอาจเป็นบั๊กภายใน `<Suspense/>` หรือส่วนอื่น ๆ ของเฟรมเวิร์ก คุณสามารถเปิด [issue](https://github.com/leptos-rs/leptos/issues) หรือร่วมพูดคุยใน [discussion](https://github.com/leptos-rs/leptos/discussions) บน GitHub เพื่อขอความช่วยเหลือได้ตลอดเวลา

### HTML ที่ไม่ถูกต้อง/กรณีขอบ และความไม่ตรงกันระหว่าง HTML กับ DOM

เซิร์ฟเวอร์จะตอบกลับคำขอด้วยโค้ด HTML จากนั้นเบราว์เซอร์จะแยกวิเคราะห์ (parse) โค้ด HTML นั้นออกมาเป็นโครงสร้างทรีที่เรียกว่า Document Object Model (DOM) ในระหว่างขั้นตอนการไฮเดรต Leptos จะไล่สำรวจทรีมุมมองของแอปพลิเคชันของคุณ โดยเริ่มทำการไฮเดรตเอลิเมนต์หนึ่งตัว จากนั้นจึงขยับเข้าไปยังโหนดลูก (children) ไฮเดรตลูกตัวแรก แล้วขยับไปยังโหนดพี่น้อง (siblings) ต่อไปเรื่อย ๆ กระบวนการนี้ตั้งอยู่บนสมมติฐานว่าโครงสร้างทรีของ HTML ที่แอปพลิเคชันของคุณสร้างขึ้นบนเซิร์ฟเวอร์ จะต้องแมปตรงกันพอดีกับโครงสร้างทรีของ DOM ที่เบราว์เซอร์แยกวิเคราะห์ออกมาได้

มีบางกรณีที่คุณควรระมัดระวัง ซึ่งโครงสร้าง HTML ที่สร้างขึ้นโดย `view` ของคุณ อาจไม่ตรงกับโครงสร้าง DOM อย่างแม่นยำ และกรณีเหล่านี้เองที่จะนำไปสู่ข้อผิดพลาดในการไฮเดรต (hydration errors)

#### HTML ที่ไม่ถูกต้อง

นี่คือตัวอย่างแอปพลิเคชันง่าย ๆ ที่ทำให้เกิดข้อผิดพลาดในการไฮเดรต:
```rust
#[component]
pub fn App() -> impl IntoView {
    let count = RwSignal::new(0);

    view! {
        <p>
            <div class:blue=move || count.get() == 2>
                 "First"
            </div>
        </p>
    }
}
```

โค้ดนี้จะแจ้งข้อความข้อผิดพลาดประมาณนี้:
```
A hydration error occurred while trying to hydrate an element defined at src/app.rs:6:14.

The framework expected a text node, but found this instead:  <p></p>

The hydration mismatch may have occurred slightly earlier, but this is the first time the framework found a node of an unexpected type.
```

(ในเครื่องมือ devtools ของเบราว์เซอร์ส่วนใหญ่ คุณสามารถคลิกขวาที่ `<p></p>` นั้นเพื่อตรวจสอบตำแหน่งที่มันปรากฏอยู่ใน DOM ได้ ซึ่งสะดวกมาก)

หากคุณตรวจสอบดูใน DOM inspector คุณจะพบว่าแทนที่จะเห็น `<div>` อยู่ภายใน `<p>` โครงสร้างกลับกลายเป็นแบบนี้แทน:
```html
<p></p>
<div>First</div>
<p></p>
```
นั่นเป็นเพราะนี่คือโครงสร้าง HTML ที่ผิดไวยากรณ์ (invalid HTML)! แท็ก `<div>` ไม่สามารถอยู่ภายในแท็ก `<p>` ได้ เมื่อเบราว์เซอร์แยกวิเคราะห์มาเจอ `<div>` มันจะทำการปิดแท็ก `<p>` ที่เปิดไว้ก่อนหน้าโดยอัตโนมัติ แล้วค่อยเปิดแท็ก `<div>` ใหม่ และเมื่อมันมาเจอกับแท็กปิด `</p>` ที่ไม่มีคู่เปิด มันจึงถือว่านั่นคือแท็ก `<p>` เปล่าตัวใหม่

ผลลัพธ์คือ โครงสร้างทรี DOM ของเราจึงไม่ตรงกับโครงสร้างทรีของมุมมองที่ระบบคาดหวังอีกต่อไป ทำให้เกิดข้อผิดพลาดในการไฮเดรตตามมาทันที

น่าเสียดายที่ในปัจจุบัน โมเดลการทำงานของเรายังไม่สามารถรับประกันความถูกต้องของไวยากรณ์ HTML ภายในมุมมองในระหว่างขั้นตอนคอมไพล์ได้โดยไม่ส่งผลกระทบต่อความเร็วในการคอมไพล์โดยรวม ในระหว่างนี้ หากคุณประสบปัญหาลักษณะดังกล่าว แนะนำให้นำผลลัพธ์ HTML ไปตรวจสอบผ่านตัวตรวจความถูกต้อง (ในกรณีข้างต้น W3C HTML Validator ก็จะตรวจพบข้อผิดพลาดนี้เช่นกัน!)

```admonish info
คุณอาจสังเกตเห็นว่ามีบั๊กในลักษณะนี้เกิดขึ้นเมื่ออัปเกรดจากเวอร์ชัน 0.6 เป็น 0.7 ซึ่งเป็นผลมาจากการเปลี่ยนแปลงกลไกการทำงานของระบบไฮเดรต

ใน Leptos 0.1–0.6 เราใช้วิธีการไฮเดรตโดยการกำหนด ID เฉพาะให้แก่ทุกเอลิเมนต์ HTML แล้วค้นหาเอลิเมนต์นั้นใน DOM ด้วย ID ดังกล่าว แต่ใน Leptos 0.7 เราเปลี่ยนมาใช้วิธีไล่สำรวจโหนด DOM โดยตรงและทำการไฮเดรตแต่ละเอลิเมนต์ไปทีละตัว ซึ่งให้ประสิทธิภาพที่ดีขึ้นอย่างมหาศาล (โค้ด HTML ที่ได้สั้นลงและสะอาดขึ้นอย่างเห็นได้ชัด อีกทั้งยังไฮเดรตได้รวดเร็วยิ่งขึ้น) ทว่าความยืดหยุ่นต่อกรณี HTML ที่ผิดไวยากรณ์หรือกรณีขอบแบบตัวอย่างข้างต้นจะลดลง แต่สิ่งที่สำคัญยิ่งกว่าคือ แนวทางใหม่นี้ช่วยขจัดกรณีขอบและบั๊ก*อื่น ๆ* อีกเป็นจำนวนมากในระบบไฮเดรต ทำให้โดยรวมแล้วเฟรมเวิร์กมีความเสถียรและทนทานมากขึ้น
```

#### `<table>` ที่ไม่มี `<tbody>`

ยังมีกรณีขอบอีกกรณีหนึ่งที่ผมพบเจอ ซึ่งโค้ด HTML ที่*ถูกต้องตามไวยากรณ์* กลับให้โครงสร้าง DOM ที่แตกต่างไปจากโครงสร้างในมุมมอง นั่นก็คือแท็ก `<table>` เพราะเมื่อเบราว์เซอร์ (ส่วนใหญ่) แยกวิเคราะห์ HTML `<table>` มันจะแทรกแท็ก `<tbody>` เข้าไปใน DOM ให้โดยอัตโนมัติ ไม่ว่าคุณจะเขียนแท็กดังกล่าวไว้หรือไม่ก็ตาม

```rust
#[component]
pub fn App() -> impl IntoView {
    let count = RwSignal::new(0);

    view! {
        <table>
            <tr>
                <td class:blue=move || count.get() == 0>"First"</td>
            </tr>
        </table>
    }
}
```

และแน่นอนว่าสิ่งนี้ทำให้เกิดข้อผิดพลาดในการไฮเดรต เพราะเบราว์เซอร์ได้แทรกแท็ก `<tbody>` เพิ่มเข้ามาในโครงสร้าง DOM โดยที่ไม่มีอยู่ในมุมมองของคุณ

ในกรณีนี้ วิธีแก้ไขง่ายนิดเดียว: เพียงแค่เพิ่มแท็ก `<tbody>` เข้าไปอย่างชัดเจน:
```rust
#[component]
pub fn App() -> impl IntoView {
    let count = RwSignal::new(0);

    view! {
        <table>
            <tbody>
                <tr>
                    <td class:blue=move || count.get() == 0>"First"</td>
                </tr>
            </tbody>
        </table>
    }
}
```

(ในอนาคตน่าศึกษาเพิ่มเติมว่าเราจะสามารถสร้าง lint เพื่อตรวจจับกรณีเฉพาะนี้ได้ง่ายกว่าการตรวจจับความถูกต้องของไวยากรณ์ HTML ทั่วไปหรือไม่)

#### คำแนะนำทั่วไป

ความไม่ตรงกันในลักษณะนี้อาจสร้างความปวดหัวในการดีบักได้ไม่น้อย โดยทั่วไปแล้ว คำแนะนำของผมในการค้นหาต้นตอของปัญหาคือ:
1. ให้คลิกขวาที่เอลิเมนต์ซึ่งระบุไว้ในข้อความแจ้งเตือน เพื่อดูว่าเฟรมเวิร์กเริ่ม*ตรวจพบ*ความผิดปกติที่จุดใดเป็นจุดแรก
2. เปรียบเทียบโครงสร้าง DOM ณ ตำแหน่งนั้นและโหนดแม่ที่อยู่เหนือขึ้นไป โดยตรวจหาจุดที่ไม่ตรงกับโครงสร้างในทรีมุมมองของคุณ มีเอลิเมนต์ใดเกินมาหรือไม่? หรือมีเอลิเมนต์ใดขาดหายไป?


### ไม่ใช่โค้ดฝั่งไคลเอนต์ทั้งหมดจะรันบนเซิร์ฟเวอร์ได้

ลองจินตนาการว่าคุณอิมพอร์ตดีเพนเดนซีอย่าง `gloo-net` ที่คุณคุ้นเคยกับการใช้ส่งคำขอบนเบราว์เซอร์เข้ามา แล้วนำไปเรียกใช้ใน `create_resource` ภายในแอปที่เรนเดอร์ฝั่งเซิร์ฟเวอร์

คุณคงจะได้เห็นข้อความแจ้งเตือนที่น่าสะพรึงกลัวนี้ในทันที:

```
panicked at 'cannot call wasm-bindgen imported functions on non-wasm targets'
```

โอ๊ะโอ...

แต่แน่นอนว่านี่เป็นเรื่องที่สมเหตุสมผล เพราะเราเพิ่งกล่าวไปว่าแอปพลิเคชันของคุณต้องสามารถรันได้ทั้งบนฝั่งไคลเอนต์และฝั่งเซิร์ฟเวอร์

#### วิธีแก้

มีวิธีง่าย ๆ หลายวิธีในการหลีกเลี่ยงปัญหานี้:

1. เลือกใช้เฉพาะไลบรารีที่รองรับการรันทั้งบนเซิร์ฟเวอร์และไคลเอนต์ เช่น [`reqwest`](https://docs.rs/reqwest/latest/reqwest/) ซึ่งสามารถใช้ส่งคำขอ HTTP ได้อย่างราบรื่นในทั้งสองสภาพแวดล้อม
2. ใช้ไลบรารีคนละตัวกันระหว่างเซิร์ฟเวอร์กับไคลเอนต์ โดยควบคุมการคอมไพล์ผ่านแอตทริบิวต์มาโคร `#[cfg]` ([คลิกที่นี่เพื่อดูตัวอย่าง](https://github.com/leptos-rs/leptos/blob/main/examples/hackernews/src/api.rs))
3. ครอบโค้ดที่ทำงานเฉพาะบนไคลเอนต์ไว้ภายใน `Effect::new` เนื่องจากเอฟเฟกต์จะถูกสั่งรันเฉพาะบนฝั่งไคลเอนต์เท่านั้น วิธีนี้จึงมีประสิทธิภาพอย่างยิ่งในการเรียกใช้ API ของเบราว์เซอร์ที่ไม่จำเป็นต่อขั้นตอนการเรนเดอร์หน้าเว็บในรอบแรก

ตัวอย่างเช่น สมมติว่าผมต้องการเก็บข้อมูลบางอย่างลงใน `localStorage` ของเบราว์เซอร์ทุกครั้งที่ค่าสัญญาณมีการเปลี่ยนแปลง:

```rust
#[component]
pub fn App() -> impl IntoView {
    use gloo_storage::Storage;
	let storage = gloo_storage::LocalStorage::raw();
	logging::log!("{storage:?}");
}
```

โค้ดนี้จะเกิดอาการแพนิกทันที เพราะในระหว่างการเรนเดอร์บนเซิร์ฟเวอร์ เราจะไม่สามารถเข้าถึง `LocalStorage` ได้

แต่หากเรานำมันไปครอบไว้ในเอฟเฟกต์...

```rust
#[component]
pub fn App() -> impl IntoView {
    use gloo_storage::Storage;
    Effect::new(move |_| {
        let storage = gloo_storage::LocalStorage::raw();
		log!("{storage:?}");
    });
}
```

ทุกอย่างก็จะทำงานได้อย่างราบรื่น! โค้ดส่วนนี้จะเรนเดอร์บนเซิร์ฟเวอร์ตามปกติโดยละเว้นโค้ดส่วนของไคลเอนต์ไว้ จากนั้นเมื่อไปถึงเบราว์เซอร์ จึงจะทำการเข้าถึงพื้นที่จัดเก็บข้อมูลและบันทึกข้อความลงคอนโซลต่อไป

### ไม่ใช่โค้ดฝั่งเซิร์ฟเวอร์ทั้งหมดจะรันบนไคลเอนต์ได้

WebAssembly ที่ทำงานอยู่ภายในเบราว์เซอร์นั้นมีสภาพแวดล้อมที่ค่อนข้างจำกัด คุณจะไม่สามารถเข้าถึงระบบไฟล์ (filesystem) หรือความสามารถอื่น ๆ อีกมากมายที่ไลบรารีมาตรฐานทั่วไปคุ้นเคย และไม่ใช่ว่าทุกเครตจะสามารถคอมไพล์เป็น WASM ได้ ไม่ต้องพูดถึงการสั่งรันจริงในสภาพแวดล้อมของ WASM เลย

โดยเฉพาะอย่างยิ่ง คุณอาจเคยพบเจอกับข้อผิดพลาดเกี่ยวกับเครต `mio` หรือการแจ้งว่ามีบางส่วนขาดหายไปจาก `core` ซึ่งโดยทั่วไปแล้วมักเป็นสัญญาณบ่งชี้ว่าคุณกำลังพยายามคอมไพล์สิ่งที่ไม่รองรับ WASM ให้กลายเป็น WASM หากคุณต้องการเพิ่มดีเพนเดนซีที่ทำงานเฉพาะบนเซิร์ฟเวอร์ ให้กำหนดแฟล็ก `optional = true` ในไฟล์ `Cargo.toml` แล้วจึงไปเปิดใช้งานมันภายใต้นิยามฟีเจอร์ `ssr` (สามารถตรวจสอบรายละเอียดเพิ่มเติมได้จากไฟล์เทมเพลต `Cargo.toml` ของเรา)

คุณสามารถสร้าง [`Effect`](https://docs.rs/leptos/latest/leptos/prelude/struct.Effect.html) เพื่อระบุว่าโค้ดส่วนใดควรทำงานเฉพาะบนฝั่งไคลเอนต์เท่านั้นและไม่ให้รันบนเซิร์ฟเวอร์ แล้วถ้าเราอยากกำหนดให้โค้ดบางอย่างทำงานเฉพาะบนเซิร์ฟเวอร์เท่านั้นโดยไม่ให้ไคลเอนต์รันบ้างล่ะ จะทำได้ไหม?

คำตอบคือ ทำได้อย่างแน่นอน! ในบทถัดไป เราจะมาเจาะลึกหัวข้อเกี่ยวกับฟังก์ชันฝั่งเซิร์ฟเวอร์ (server functions) กันอย่างละเอียด (ในระหว่างนี้ คุณสามารถเข้าไปศึกษาเอกสารเพิ่มเติมได้ [ที่นี่](https://docs.rs/leptos/latest/leptos/attr.server.html))
