# บั๊กการไฮเดรต _(และวิธีหลีกเลี่ยง)_

## การทดลองทางความคิด

ลองทำการทดลองเพื่อทดสอบสัญชาตญาณของคุณ เปิดแอปที่คุณกำลังเรนเดอร์ฝั่งเซิร์ฟเวอร์ด้วย `cargo-leptos` (ถ้าจนถึงตอนนี้คุณเพิ่งใช้ `trunk` เล่นกับตัวอย่างต่างๆ ให้ไป[โคลนเทมเพลต `cargo-leptos`](./21_cargo_leptos.md) เพื่อประโยชน์ของการฝึกฝนนี้)

ใส่ล็อกไว้ที่ใดที่หนึ่งในคอมโพเนนต์รากของคุณ (ผมมักเรียกของผมว่า `<App/>` แต่อะไรก็ได้ทั้งนั้น)

```rust
#[component]
pub fn App() -> impl IntoView {
	logging::log!("where do I run?");
	// ... whatever
}
```

และลองรันมันดู

```bash
cargo leptos watch
```

- ทั้งสองที่?

โอเค เตรียมรับคำเฉลยได้เลย

แน่นอนว่าคุณจะสังเกตเห็นว่ามันล็อกทั้งสองที่ สมมติว่าทุกอย่างเป็นไปตามแผน ที่จริงแล้วบนเซิร์ฟเวอร์มันล็อกสองครั้ง ครั้งแรกตอนเริ่มต้นเซิร์ฟเวอร์ครั้งแรก เมื่อ Leptos เรนเดอร์แอปของคุณหนึ่งครั้งเพื่อสกัดต้นไม้เส้นทาง แล้วครั้งที่สองเมื่อคุณส่งคำขอ ทุกครั้งที่คุณโหลดหน้าใหม่ `where do I run?` ควรล็อกหนึ่งครั้งบนเซิร์ฟเวอร์และหนึ่งครั้งบนไคลเอนต์

ถ้าคุณคิดถึงคำอธิบายในสองส่วนที่แล้ว หวังว่านี่จะสมเหตุสมผล แอปพลิเคชันของคุณรันหนึ่งครั้งบนเซิร์ฟเวอร์ ซึ่งมันสร้างต้นไม้ HTML ที่ถูกส่งไปยังไคลเอนต์ ในระหว่างการเรนเดอร์ครั้งแรกนี้ `where do I run?` จะล็อกบนเซิร์ฟเวอร์

เมื่อไบนารี WASM โหลดในเบราว์เซอร์เสร็จแล้ว แอปพลิเคชันของคุณจะรันครั้งที่สอง ไล่ไปตามต้นไม้ส่วนติดต่อผู้ใช้เดียวกันและเพิ่มความสามารถในการโต้ตอบ

> นั่นฟังดูสิ้นเปลืองไหม? ในแง่หนึ่งก็ใช่ แต่การลดความสิ้นเปลืองนั้นเป็นปัญหาที่ยากจริงๆ มันคือสิ่งที่ JS เฟรมเวิร์กบางตัวอย่าง Qwik ตั้งใจจะแก้ไข แม้ว่าอาจจะยังเร็วเกินไปที่จะบอกว่ามันให้ประสิทธิภาพดีกว่าเมื่อเทียบกับแนวทางอื่นๆ หรือไม่

## ศักยภาพของบั๊ก

โอเค หวังว่าทั้งหมดนั้นจะสมเหตุสมผล แต่มันเกี่ยวอะไรกับชื่อบทนี้ ซึ่งก็คือ “บั๊กการไฮเดรต (และวิธีหลีกเลี่ยง)”?

จำไว้ว่าแอปพลิเคชันต้องรันทั้งบนเซิร์ฟเวอร์และไคลเอนต์ สิ่งนี้ก่อให้เกิดชุดปัญหาที่อาจเกิดขึ้นได้หลายแบบที่คุณต้องรู้วิธีหลีกเลี่ยง

### ความไม่ตรงกันระหว่างโค้ดฝั่งเซิร์ฟเวอร์และฝั่งไคลเอนต์

วิธีหนึ่งในการสร้างบั๊กคือการสร้างความไม่ตรงกันระหว่าง HTML ที่เซิร์ฟเวอร์ส่งลงมา กับสิ่งที่เรนเดอร์บนไคลเอนต์ ที่จริงแล้วผมคิดว่าการทำเช่นนี้โดยไม่ตั้งใจค่อนข้างยาก (อย่างน้อยก็ตัดสินจากรายงานบั๊กที่ผมได้รับจากผู้คน) แต่ลองจินตนาการว่าผมทำแบบนี้

```rust
#[component]
pub fn App() -> impl IntoView {
    let data = if cfg!(target_arch = "wasm32") {
        vec![0, 1, 2]
    } else {
        vec![]
    };
    data.into_iter()
        .map(|value| view! { <span>{value}</span> })
        .collect_view()
}
```

กล่าวอีกนัยหนึ่ง ถ้ามันถูกคอมไพล์เป็น WASM มันมีสามสมาชิก มิฉะนั้นจะว่างเปล่า

เมื่อผมโหลดหน้าเพจในเบราว์เซอร์ ผมไม่เห็นอะไรเลย ถ้าเปิดคอนโซล ผมเห็นการแพนิก:

```
ssr_modes.js:423 panicked at /.../tachys/src/html/element/mod.rs:352:14:
called `Option::unwrap()` on a `None` value
```

เวอร์ชัน WASM ของแอปคุณที่รันในเบราว์เซอร์คาดหวังว่าจะพบเอลิเมนต์หนึ่งตัว (ที่จริงมันคาดหวังสามเอลิเมนต์!) แต่ HTML ที่ส่งมาจากเซิร์ฟเวอร์ไม่มีเลย

#### วิธีแก้

เป็นเรื่องค่อนข้างหายากที่คุณจะทำแบบนี้โดยตั้งใจ แต่มันอาจเกิดขึ้นได้จากการรันลอจิกที่ต่างกันบนเซิร์ฟเวอร์และในเบราว์เซอร์ ถ้าคุณเห็นคำเตือนแบบนี้และคุณไม่คิดว่าเป็นความผิดของคุณ มันน่าจะเป็นบั๊กของ `<Suspense/>` หรืออะไรทำนองนั้นมากกว่า เชิญเปิด [issue](https://github.com/leptos-rs/leptos/issues) หรือ [discussion](https://github.com/leptos-rs/leptos/discussions) บน GitHub เพื่อขอความช่วยเหลือได้เลย

### HTML ที่ไม่ถูกต้อง/กรณีขอบ และความไม่ตรงกันระหว่าง HTML กับ DOM

เซิร์ฟเวอร์ตอบสนองคำขอด้วย HTML เบราว์เซอร์จะแยกวิเคราะห์ HTML นั้นเป็นต้นไม้ที่เรียกว่า Document Object Model (DOM) ในระหว่างการไฮเดรต Leptos จะไล่ไปตามต้นไม้วิวของแอปพลิเคชันของคุณ ไฮเดรตเอลิเมนต์หนึ่งตัว แล้วเคลื่อนเข้าสู่ children ของมัน ไฮเดรตลูกตัวแรก แล้วเคลื่อนไปยังพี่น้องของมัน ไปเรื่อยๆ สิ่งนี้ตั้งอยู่บนสมมติฐานว่าต้นไม้ HTML ที่แอปพลิเคชันของคุณสร้างบนเซิร์ฟเวอร์นั้นแมปโดยตรงกับต้นไม้ DOM ที่เบราว์เซอร์แยกวิเคราะห์ HTML นั้นเข้าไป

มีบางกรณีที่ควรระวัง ซึ่งต้นไม้ HTML ที่สร้างโดย `view` ของคุณกับต้นไม้ DOM อาจไม่สอดคล้องกันพอดี: กรณีเหล่านี้อาจทำให้เกิดข้อผิดพลาดในการไฮเดรตได้

#### HTML ที่ไม่ถูกต้อง

นี่คือแอปพลิเคชันง่ายๆ ที่ทำให้เกิดข้อผิดพลาดในการไฮเดรต:
```rust
#[component]
pub fn App() -> impl IntoView {
    let count = RwSignal::new(0);

    view! {
        <p>
            <div class:blue=move || count.get() == 2>
                 "First"
            </div>
        </p>
    }
}
```

สิ่งนี้จะให้ข้อความข้อผิดพลาดประมาณนี้
```
A hydration error occurred while trying to hydrate an element defined at src/app.rs:6:14.

The framework expected a text node, but found this instead:  <p></p>

The hydration mismatch may have occurred slightly earlier, but this is the first time the framework found a node of an unexpected type.
```

(ใน devtools ของเบราว์เซอร์ส่วนใหญ่ คุณสามารถคลิกขวาที่ `<p></p>` นั้นเพื่อแสดงว่ามันปรากฏที่ไหนใน DOM ซึ่งมีประโยชน์มาก)

ถ้าคุณดูใน DOM inspector คุณจะเห็นว่ามันแสดงแบบนี้ แทนที่จะเป็น `<div>` อยู่ภายใน `<p>`:
```html
<p></p>
<div>First</div>
<p></p>
```
นั่นเป็นเพราะนี่คือ HTML ที่ไม่ถูกต้อง! `<div>` ไม่สามารถอยู่ภายใน `<p>` ได้ เมื่อเบราว์เซอร์แยกวิเคราะห์ `<div>` นั้น มันจะปิด `<p>` ที่อยู่ก่อนหน้าจริงๆ แล้วเปิด `<div>`; จากนั้นเมื่อมันเจอ `</p>` ปิดที่ (ตอนนี้) ไม่มีคู่ มันจะถือว่าเป็น `<p>` ใหม่ที่ว่างเปล่า

ผลก็คือ ต้นไม้ DOM ของเราไม่ตรงกับต้นไม้วิวที่คาดหวังอีกต่อไป และเกิดข้อผิดพลาดในการไฮเดรตตามมา

น่าเสียดายที่การรับประกันความถูกต้องของ HTML ในวิวตอนคอมไพล์นั้นทำได้ยากด้วยโมเดลปัจจุบันของเรา และหากไม่ส่งผลกระทบต่อเวลาคอมไพล์โดยรวม สำหรับตอนนี้ หากคุณเจอปัญหาประมาณนี้ ลองนำผลลัพธ์ HTML ไปผ่านตัวตรวจสอบความถูกต้อง (ในกรณีข้างต้น W3C HTML Validator แสดงข้อผิดพลาดจริงๆ!)

```admonish info
คุณอาจสังเกตเห็นบั๊กบางอย่างในลักษณะนี้เกิดขึ้นเมื่ออัปเกรดจาก 0.6 เป็น 0.7 นี่เป็นเพราะการเปลี่ยนแปลงวิธีที่การไฮเดรตทำงาน

Leptos 0.1-0.6 ใช้วิธีการไฮเดรตที่ให้ ID เฉพาะแก่ทุกเอลิเมนต์ HTML แล้วใช้ ID นั้นค้นหามันใน DOM Leptos 0.7 เปลี่ยนมาไล่ดู DOM โดยตรงแทน ไฮเดรตแต่ละเอลิเมนต์เมื่อเจอ สิ่งนี้มีคุณลักษณะด้านประสิทธิภาพที่ดีกว่ามาก (ผลลัพธ์ HTML ที่สั้นและสะอาดกว่า และเวลาการไฮเดรตที่เร็วกว่า) แต่ยืดหยุ่นต่อตัวอย่าง HTML ที่ไม่ถูกต้องหรือกรณีขอบข้างต้นได้น้อยกว่า และที่สำคัญกว่านั้นคือ แนวทางนี้ยังแก้กรณีขอบและบั๊ก_อื่นๆ_อีกหลายอย่างในการไฮเดรต ทำให้เฟรมเวิร์กมีความทนทานมากขึ้นโดยรวม
```

#### `<table>` ที่ไม่มี `<tbody>`

มีกรณีขอบเพิ่มเติมอีกกรณีหนึ่งที่ผมทราบ ซึ่ง HTML ที่_ถูกต้อง_สร้างต้นไม้ DOM ที่แตกต่างจากต้นไม้วิว นั่นก็คือ `<table>` เมื่อเบราว์เซอร์ (ส่วนใหญ่) แยกวิเคราะห์ HTML `<table>` พวกมันจะแทรก `<tbody>` เข้าไปใน DOM ไม่ว่าคุณจะใส่มาหรือไม่ก็ตาม

```rust
#[component]
pub fn App() -> impl IntoView {
    let count = RwSignal::new(0);

    view! {
        <table>
            <tr>
                <td class:blue=move || count.get() == 0>"First"</td>
            </tr>
        </table>
    }
}
```

อีกครั้ง สิ่งนี้ทำให้เกิดข้อผิดพลาดในการไฮเดรต เพราะเบราว์เซอร์ได้แทรก `<tbody>` เพิ่มเติมเข้าไปในต้นไม้ DOM ซึ่งไม่มีในวิวของคุณ

ตรงนี้ วิธีแก้ไขง่ายมาก: เพิ่ม `<tbody>`:
```rust
#[component]
pub fn App() -> impl IntoView {
    let count = RwSignal::new(0);

    view! {
        <table>
            <tbody>
                <tr>
                    <td class:blue=move || count.get() == 0>"First"</td>
                </tr>
            </tbody>
        </table>
    }
}
```

(น่าสนใจที่จะสำรวจในอนาคตว่าเราจะ lint กรณีเฉพาะนี้ได้ง่ายกว่าการ lint HTML ที่ถูกต้องหรือไม่)

#### คำแนะนำทั่วไป

ความไม่ตรงกันแบบนี้อาจเป็นเรื่องที่ยุ่งยาก โดยทั่วไปแล้ว คำแนะนำของผมสำหรับการดีบักคือ:
1. คลิกขวาที่เอลิเมนต์ในข้อความเพื่อดูว่าเฟรมเวิร์ก_สังเกตเห็น_ปัญหาครั้งแรกที่ไหน
2. เปรียบเทียบ DOM ณ จุดนั้นและด้านบนของมัน ตรวจหาความไม่ตรงกันกับต้นไม้วิวของคุณ มีเอลิเมนต์เกินมาหรือไม่? มีเอลิเมนต์หายไปหรือไม่?


### ไม่ใช่โค้ดฝั่งไคลเอนต์ทั้งหมดจะรันบนเซิร์ฟเวอร์ได้

ลองจินตนาการว่าคุณนำเข้าดีเพนเดนซีอย่าง `gloo-net` ที่คุณเคยชินกับการใช้ส่งคำขอในเบราว์เซอร์ อย่างมีความสุข และใช้มันใน `create_resource` ในแอปที่เรนเดอร์ฝั่งเซิร์ฟเวอร์

คุณคงเห็นข้อความที่น่ากลัวนี้ทันที

```
panicked at 'cannot call wasm-bindgen imported functions on non-wasm targets'
```

โอ๊ะ โอ

แต่แน่นอนว่านี่สมเหตุสมผล เราก็เพิ่งบอกว่าแอปของคุณต้องรันบนไคลเอนต์และเซิร์ฟเวอร์

#### วิธีแก้

มีหลายวิธีในการหลีกเลี่ยงปัญหานี้:

1. ใช้เฉพาะไลบรารีที่รันได้ทั้งบนเซิร์ฟเวอร์และไคลเอนต์ ตัวอย่างเช่น [`reqwest`](https://docs.rs/reqwest/latest/reqwest/) ใช้ส่งคำขอ HTTP ได้ในทั้งสองสภาพแวดล้อม
2. ใช้ไลบรารีต่างกันบนเซิร์ฟเวอร์และไคลเอนต์ แล้วจำกัดด้วยมาโคร `#[cfg]` ([คลิกที่นี่เพื่อดูตัวอย่าง](https://github.com/leptos-rs/leptos/blob/main/examples/hackernews/src/api.rs))
3. ห่อโค้ดที่ใช้เฉพาะไคลเอนต์ด้วย `Effect::new` เนื่องจากเอฟเฟกต์รันเฉพาะบนไคลเอนต์ วิธีนี้จึงมีประสิทธิภาพในการเข้าถึง API ของเบราว์เซอร์ที่ไม่จำเป็นสำหรับการเรนเดอร์ครั้งแรก

ตัวอย่างเช่น สมมติว่าผมต้องการเก็บบางอย่างไว้ใน `localStorage` ของเบราว์เซอร์ทุกครั้งที่สัญญาณเปลี่ยนแปลง

```rust
#[component]
pub fn App() -> impl IntoView {
    use gloo_storage::Storage;
	let storage = gloo_storage::LocalStorage::raw();
	logging::log!("{storage:?}");
}
```

โค้ดนี้แพนิกเพราะผมไม่สามารถเข้าถึง `LocalStorage` ระหว่างการเรนเดอร์ฝั่งเซิร์ฟเวอร์ได้

แต่ถ้าผมห่อมันในเอฟเฟกต์...

```rust
#[component]
pub fn App() -> impl IntoView {
    use gloo_storage::Storage;
    Effect::new(move |_| {
        let storage = gloo_storage::LocalStorage::raw();
		log!("{storage:?}");
    });
}
```

ก็ไม่มีปัญหา! โค้ดนี้จะเรนเดอร์อย่างเหมาะสมบนเซิร์ฟเวอร์ โดยไม่สนใจโค้ดที่ใช้เฉพาะไคลเอนต์ แล้วเข้าถึงที่จัดเก็บและล็อกข้อความในเบราว์เซอร์

### ไม่ใช่โค้ดฝั่งเซิร์ฟเวอร์ทั้งหมดจะรันบนไคลเอนต์ได้

WebAssembly ที่รันในเบราว์เซอร์เป็นสภาพแวดล้อมที่ค่อนข้างจำกัด คุณไม่มีสิทธิ์เข้าถึงระบบไฟล์หรือสิ่งอื่นๆ มากมายที่สแตนดาร์ดไลบรารีอาจเคยชิน ไม่ใช่ทุกครีตที่จะคอมไพล์เป็น WASM ได้ด้วยซ้ำ ไม่ต้องพูดถึงการรันในสภาพแวดล้อม WASM เลย

โดยเฉพาะอย่างยิ่ง บางครั้งคุณจะเห็นข้อผิดพลาดเกี่ยวกับครีต `mio` หรือสิ่งที่ขาดหายไปจาก `core` โดยทั่วไปนี่เป็นสัญญาณว่าคุณกำลังพยายามคอมไพล์บางอย่างเป็น WASM ที่ไม่สามารถคอมไพล์เป็น WASM ได้ หากคุณเพิ่มดีเพนเดนซีที่ใช้เฉพาะเซิร์ฟเวอร์ คุณจะต้องทำเครื่องหมาย `optional = true` ใน `Cargo.toml` แล้วเปิดใช้งานในนิยามฟีเจอร์ `ssr` (ดูไฟล์เทมเพลต `Cargo.toml` สักไฟล์เพื่อรายละเอียดเพิ่มเติม)

คุณสามารถสร้าง [`Effect`](https://docs.rs/leptos/latest/leptos/prelude/struct.Effect.html) เพื่อระบุว่าบางอย่างควรรันเฉพาะบนไคลเอนต์ ไม่ใช่บนเซิร์ฟเวอร์ แล้วมีวิธีระบุว่าบางอย่างควรรันเฉพาะบนเซิร์ฟเวอร์ ไม่ใช่ไคลเอนต์หรือไม่?

ที่จริงมีอยู่ บทถัดไปจะครอบคลุมหัวข้อฟังก์ชันฝั่งเซิร์ฟเวอร์ในรายละเอียดพอสมควร (ระหว่างนี้ คุณดูเอกสารของมันได้[ที่นี่](https://docs.rs/leptos/latest/leptos/attr.server.html))
