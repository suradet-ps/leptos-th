# ภาคผนวก: ระบบรีแอกทีฟทำงานอย่างไร?

คุณไม่จำเป็นต้องรู้เรื่องว่าระบบรีแอกทีฟทำงานจริงๆ อย่างไรมากนักเพื่อใช้ไลบรารีนี้ได้อย่างประสบความสำเร็จ แต่การเข้าใจสิ่งที่เกิดขึ้นเบื้องหลังก็มีประโยชน์เสมอเมื่อคุณเริ่มทำงานกับเฟรมเวิร์กนี้ในระดับสูง

พรีมิทีฟรีแอกทีฟที่คุณใช้แบ่งออกเป็นสามกลุ่ม:

- **สัญญาณ (Signals)** (`ReadSignal`/`WriteSignal`, `RwSignal`, `Resource`, `Trigger`) ค่าที่คุณเปลี่ยนได้เองเพื่อกระตุ้นการอัปเดตแบบรีแอกทีฟ
- **คอมพิวเทชัน (Computations)** (`Memo`) ค่าที่ขึ้นอยู่กับสัญญาณ (หรือคอมพิวเทชันอื่นๆ) และได้ค่าใหม่แบบรีแอกทีฟมาจากการคำนวณบริสุทธิ์บางอย่าง
- **เอฟเฟกต์ (Effects)** ตัวสังเกตการณ์ที่คอยฟังการเปลี่ยนแปลงของสัญญาณหรือคอมพิวเทชันบางตัว แล้วรันฟังก์ชันหนึ่งๆ ทำให้เกิดผลข้างเคียงบางอย่าง

สัญญาณอนุพัทธ์ (derived signal) เป็นคอมพิวเทชันแบบไม่ใช่พรีมิทีฟชนิดหนึ่ง ในฐานะโคลเชอร์ธรรมดา พวกมันแค่ช่วยให้คุณรีแฟกเตอร์การคำนวณที่อิงสัญญาณซึ่งซ้ำๆ กันให้เป็นฟังก์ชันที่ใช้ซ้ำได้และเรียกได้หลายที่ แต่พวกมันไม่ได้ถูกแทนอยู่ในระบบรีแอกทีฟเอง

พรีมิทีฟอื่นๆ ทั้งหมดมีอยู่จริงในระบบรีแอกทีฟในฐานะโหนดในกราฟรีแอกทิวิตี

งานส่วนใหญ่ของระบบรีแอกทีฟคือการแพร่กระจายการเปลี่ยนแปลงจากสัญญาณไปยังเอฟเฟกต์ โดยอาจผ่านเมโมที่คั่นอยู่กลางทาง

สมมติฐานของระบบรีแอกทีฟคือเอฟเฟกต์ (เช่น การเรนเดอร์ลง DOM หรือการส่งคำขอเครือข่าย) แพงกว่าสิ่งอย่างการอัปเดตโครงสร้างข้อมูล Rust ในแอปของคุณหลายเท่าตัว

ดังนั้น **เป้าหมายหลัก** ของระบบรีแอกทีฟคือ **รันเอฟเฟกต์ให้น้อยครั้งที่สุดเท่าที่จะเป็นไปได้**

## กราฟรีแอกทิวิตี

สัญญาณ เมโม และเอฟเฟกต์ ล้วนมีลักษณะร่วมกันสามประการ:

- **ค่า (Value)** พวกมันมีค่าปัจจุบัน ไม่ว่าจะเป็นค่าของสัญญาณ หรือ (สำหรับเมโมและเอฟเฟกต์) ค่าที่คืนมาจากการรันครั้งก่อนหน้า ถ้ามี
- **ซอร์ส (Sources)** พรีมิทีฟรีแอกทีฟอื่นใดก็ตามที่พวกมันขึ้นอยู่ด้วย (สำหรับสัญญาณ นี่เป็นเซตว่าง)
- **ผู้ติดตาม (Subscribers)** พรีมิทีฟรีแอกทีฟอื่นใดก็ตามที่ขึ้นอยู่กับพวกมัน (สำหรับเอฟเฟกต์ นี่เป็นเซตว่าง)

ในความเป็นจริงแล้ว สัญญาณ เมโม และเอฟเฟกต์ เป็นเพียงชื่อทั่วไปสำหรับแนวคิดทั่วไปหนึ่งเดียวที่เรียกว่า “โหนด” ในกราฟรีแอกทิวิตี สัญญาณเป็น “โหนดราก” เสมอ โดยไม่มีซอร์ส/พาเรนต์ เอฟเฟกต์เป็น “โหนดใบ” เสมอ โดยไม่มีผู้ติดตาม ส่วนเมโมมักมีทั้งซอร์สและผู้ติดตาม

> ในตัวอย่างต่อไปนี้ ผมจะใช้ไวยากรณ์ `nightly` เพียงเพื่อลดความยาวในเอกสารที่ตั้งใจให้คุณอ่าน ไม่ใช่ให้คัดลอกไปวาง!

### ความขึ้นต่อกันแบบง่าย

ลองจินตนาการว่าเรามีโค้ดต่อไปนี้:

```rust
// A
let (name, set_name) = signal("Alice");

// B
let name_upper = Memo::new(move |_| name.with(|n| n.to_uppercase()));

// C
Effect::new(move |_| {
	log!("{}", name_upper());
});

set_name("Bob");
```


คุณสามารถจินตนาการกราฟรีแอกทิวิตีตรงนี้ได้ง่ายๆ: `name` เป็นโหนดต้นทาง/สัญญาณเพียงตัวเดียว `Effect::new` เป็นเอฟเฟกต์/โหนดปลายทางเพียงตัวเดียว และมีเมโมคั่นอยู่หนึ่งตัว

```
A   (name)
|
B   (name_upper)
|
C   (the effect)
```

### การแยกสาขา

มาทำให้ซับซ้อนขึ้นอีกหน่อยกัน

```rust
// A
let (name, set_name) = signal("Alice");

// B
let name_upper = Memo::new(move |_| name.with(|n| n.to_uppercase()));

// C
let name_len = Memo::new(move |_| name.len());

// D
Effect::new(move |_| {
	log!("len = {}", name_len());
});

// E
Effect::new(move |_| {
	log!("name = {}", name_upper());
});
```

อันนี้ก็ตรงไปตรงมาเช่นกัน: สัญญาณต้นทาง (`name`/`A`) หนึ่งตัวแยกออกเป็นสองเส้นทางขนานกัน: `name_upper`/`B` และ `name_len`/`C` ซึ่งแต่ละเส้นก็มีเอฟเฟกต์ที่ขึ้นอยู่กับมัน

```
 __A__
|     |
B     C
|     |
E     D
```

ทีนี้มาอัปเดตสัญญาณกัน

```rust
set_name("Bob");
```

เราจะเห็นล็อกทันทีว่า

```
len = 3
name = BOB
```

ลองทำอีกครั้ง

```rust
set_name("Tim");
```

ล็อกควรแสดง

```
name = TIM
```

`len = 3` จะไม่ถูกบันทึกอีก

จำไว้ว่า เป้าหมายของระบบรีแอกทีฟคือการรันเอฟเฟกต์ให้น้อยครั้งที่สุดเท่าที่จะเป็นไปได้ การเปลี่ยน `name` จาก `"Bob"` เป็น `"Tim"` จะทำให้เมโมแต่ละตัวรันใหม่ แต่พวกมันจะแจ้งเตือนผู้ติดตามก็ต่อเมื่อค่าของมันเปลี่ยนจริงเท่านั้น `"BOB"` กับ `"TIM"` ต่างกัน เอฟเฟกต์นั้นจึงรันอีกครั้ง แต่ทั้งสองชื่อมีความยาว `3` พวกมันจึงไม่รันอีก

### การรวมสาขากลับเข้าด้วยกัน

อีกตัวอย่างหนึ่ง ของสิ่งที่บางครั้งเรียกว่า **ปัญหาสี่เหลี่ยมขนมเปียกปูน (the diamond problem)**

```rust
// A
let (name, set_name) = signal("Alice");

// B
let name_upper = Memo::new(move |_| name.with(|n| n.to_uppercase()));

// C
let name_len = Memo::new(move |_| name.len());

// D
Effect::new(move |_| {
	log!("{} is {} characters long", name_upper(), name_len());
});
```

กราฟจะเป็นหน้าตาอย่างไรสำหรับกรณีนี้?

```
 __A__
|     |
B     C
|     |
|__D__|
```

คุณคงเห็นแล้วว่าทำไมมันถึงเรียกว่า “ปัญหาสี่เหลี่ยมขนมเปียกปูน” ถ้าผมเชื่อมโหนดต่างๆ ด้วยเส้นตรงแทนที่จะเป็นอาร์ต ASCII แย่ๆ มันจะก่อตัวเป็นสี่เหลี่ยมขนมเปียกปูน: เมโมสองตัว ซึ่งแต่ละตัวขึ้นอยู่กับสัญญาณ แล้วป้อนเข้าสู่เอฟเฟกต์เดียวกัน

การอิมพลีเมนต์รีแอกทีฟแบบ push-based แบบไร้เดียงสาจะทำให้เอฟเฟกต์นี้รันสองครั้ง ซึ่งไม่ดีเลย (จำไว้ว่า เป้าหมายของเราคือรันเอฟเฟกต์ให้น้อยครั้งที่สุดเท่าที่ทำได้) ตัวอย่างเช่น คุณอาจอิมพลีเมนต์ระบบรีแอกทีฟที่สัญญาณและเมโมแพร่การเปลี่ยนแปลงของตัวเองลงไปตามกราฟทั้งหมดทันที ผ่านแต่ละดีเพนเดนซี ซึ่งโดยพื้นฐานคือการท่องกราฟแบบ depth-first กล่าวอีกนัยหนึ่ง การอัปเดต `A` จะแจ้งเตือน `B` ซึ่งจะแจ้งเตือน `D` จากนั้น `A` จะแจ้งเตือน `C` ซึ่งจะแจ้งเตือน `D` อีกครั้ง วิธีนี้ทั้งไม่มีประสิทธิภาพ (`D` รันสองครั้ง) และเกิดกลิตช์ (`D` จริงๆ แล้วรันด้วยค่าที่ไม่ถูกต้องของเมโมตัวที่สองระหว่างการรันครั้งแรกของมัน)

## การแก้ปัญหาสี่เหลี่ยมขนมเปียกปูน

การอิมพลีเมนตรีแอกทีฟใดๆ ที่ดีพอ ย่อมทุ่มเทให้กับการแก้ปัญหานี้ มีแนวทางที่แตกต่างกันหลายแบบ (อีกครั้ง [ดูบทความของ Milo](https://dev.to/modderme123/super-charging-fine-grained-reactive-performance-47ph) สำหรับภาพรวมที่ยอดเยี่ยม)

นี่คือวิธีที่ของเราทำงาน แบบสั้นๆ

โหนดรีแอกทีฟจะอยู่ในสถานะใดสถานะหนึ่งในสามสถานะเสมอ:

- `Clean`: รู้ได้ว่ามันไม่ได้เปลี่ยนแปลง
- `Check`: มันอาจจะเปลี่ยนแปลง
- `Dirty`: มันเปลี่ยนแปลงแน่นอน

การอัปเดตสัญญาณจะทำเครื่องหมายสัญญาณนั้นว่า `Dirty` และทำเครื่องหมายทายาททั้งหมดของมันว่า `Check` แบบเรียกซ้ำ ทายาทตัวใดที่เป็นเอฟเฟกต์จะถูกเพิ่มเข้าคิวเพื่อรันใหม่

```
    ____A (DIRTY)___
   |               |
B (CHECK)    C (CHECK)
   |               |
   |____D (CHECK)__|
```

ตอนนี้เอฟเฟกต์เหล่านั้นจะถูกรัน (เอฟเฟกต์ทั้งหมดจะถูกทำเครื่องหมายว่า `Check` ณ จุดนี้) ก่อนจะรันการคำนวณใหม่ เอฟเฟกต์จะตรวจสอบพาเรนต์ของตัวเองว่าสกปรกหรือไม่

- ดังนั้น `D` จึงไปที่ `B` แล้วตรวจว่ามัน `Dirty` หรือไม่
- แต่ `B` ก็ถูกทำเครื่องหมายว่า `Check` เช่นกัน ดังนั้น `B` จึงทำสิ่งเดียวกัน:
  - `B` ไปที่ `A` และพบว่ามัน `Dirty`
  - นั่นหมายความว่า `B` ต้องรันใหม่ เพราะซอร์สตัวหนึ่งของมันเปลี่ยนไป
  - `B` รันใหม่ สร้างค่าใหม่ และทำเครื่องหมายตัวเองว่า `Clean`
  - เพราะ `B` เป็นเมโม มันจึงตรวจค่าก่อนหน้ากับค่าใหม่
  - ถ้าค่าทั้งสองเท่ากัน `B` จะคืนค่า "ไม่เปลี่ยนแปลง" ไม่เช่นนั้น มันจะคืนค่า "ใช่ ฉันเปลี่ยนแล้ว"
- ถ้า `B` คืนค่า “ใช่ ฉันเปลี่ยนแล้ว” `D` จะรู้ว่ามันต้องรันแน่นอน และรันทันทีก่อนจะตรวจสอบซอร์สอื่นๆ
- ถ้า `B` คืนค่า “ไม่ ฉันไม่ได้เปลี่ยน” `D` จะตรวจสอบ `C` ต่อไป (ดูกระบวนการข้างต้นสำหรับ `B`)
- ถ้าทั้ง `B` และ `C` ต่างไม่เปลี่ยน เอฟเฟกต์ก็ไม่จำเป็นต้องรันใหม่
- ถ้า `B` หรือ `C` ตัวใดตัวหนึ่งเปลี่ยน เอฟเฟกต์ก็จะรันใหม่ตอนนี้

เพราะเอฟเฟกต์ถูกทำเครื่องหมาย `Check` เพียงครั้งเดียวและเข้าคิวเพียงครั้งเดียว มันจึงรันเพียงครั้งเดียว

ถ้าเวอร์ชันไร้เดียงสาเป็นระบบรีแอกทีฟแบบ “push-based” ที่แค่ผลักการเปลี่ยนแปลงแบบรีแอกทีฟลงไปตามกราฟทั้งหมดแล้วทำให้เอฟเฟกต์รันสองครั้ง เวอร์ชันนี้ก็อาจเรียกได้ว่า “push-pull” มันผลักสถานะ `Check` ลงไปตามกราฟทั้งหมด แต่แล้วก็ “ดึง” ตัวเองกลับขึ้นมา อันที่จริง สำหรับกราฟขนาดใหญ่ มันอาจเด้งขึ้นลงซ้ายขวาไปมาบนกราฟขณะพยายามระบุให้แน่ชัดว่าโหนดใดบ้างที่ต้องรันใหม่

**โปรดสังเกตการแลกเปลี่ยนที่สำคัญนี้**: รีแอกทิวิตีแบบ push-based แพร่การเปลี่ยนแปลงของสัญญาณได้เร็วกว่า โดยแลกกับการรันเมโมและเอฟเฟกต์ซ้ำเกินความจำเป็น จำไว้ว่า ระบบรีแอกทีฟถูกออกแบบมาเพื่อลดความถี่ในการรันเอฟเฟกต์ซ้ำให้เหลือน้อยที่สุด บนสมมติฐาน (ที่แม่นยำ) ว่าผลข้างเคียงแพงกว่าการท่องกราฟที่เป็นมิตรกับแคชแบบนี้ซึ่งเกิดขึ้นทั้งหมดภายในโค้ด Rust ของไลบรารีหลายเท่าตัว การวัดว่าระบบรีแอกทีฟดีนั้นไม่ได้วัดที่ความเร็วในการแพร่การเปลี่ยนแปลง แต่วัดที่ความเร็วในการแพร่การเปลี่ยนแปลง _โดยไม่แจ้งเตือนเกินความจำเป็น_

## เมโมกับสัญญาณ

โปรดสังเกตว่าสัญญาณจะแจ้งเตือนลูกๆ ของมันเสมอ กล่าวคือ สัญญาณจะถูกทำเครื่องหมาย `Dirty` ทุกครั้งที่มันอัปเดต แม้ว่าค่าใหม่ของมันจะเหมือนกับค่าเดิมก็ตาม ไม่เช่นนั้น เราคงต้องบังคับให้สัญญาณมี `PartialEq` ซึ่งจริงๆ แล้วเป็นการตรวจที่ค่อนข้างแพงสำหรับบางชนิดข้อมูล (ตัวอย่างเช่น การเพิ่มการตรวจความเท่ากันโดยไม่จำเป็นให้กับอะไรอย่าง `some_vec_signal.update(|n| n.pop())` ทั้งที่เห็นชัดว่ามันเปลี่ยนจริงๆ)

ในทางกลับกัน เมโมจะตรวจว่าตัวเองเปลี่ยนหรือไม่ก่อนแจ้งเตือนลูกๆ ของมัน พวกมันรันการคำนวณเพียงครั้งเดียว ไม่ว่าคุณจะ `.get()` ผลลัพธ์กี่ครั้ง แต่พวกมันจะรันทุกครั้งที่ซอร์สที่เป็นสัญญาณของมันเปลี่ยน นั่นหมายความว่าถ้าการคำนวณของเมโม _แพงมาก_ คุณอาจอยากเมโมไอซ์อินพุตของมันด้วย เพื่อให้เมโมคำนวณใหม่ก็ต่อเมื่อมั่นใจว่าอินพุตของมันเปลี่ยนแล้ว

## เมโมกับสัญญาณอนุพัทธ์

ทั้งหมดนี้เจ๋ง และเมโมก็เยี่ยมมาก แต่แอปพลิเคชันจริงส่วนใหญ่มีกราฟรีแอกทีฟที่ค่อนข้างตื้นและค่อนข้างกว้าง: คุณอาจมีสัญญาณต้นทาง 100 ตัวและเอฟเฟกต์ 500 ตัว แต่ไม่มีเมโมเลย หรือในกรณีที่พบได้ยากก็มีเมโมสามสี่ตัวคั่นระหว่างสัญญาณกับเอฟเฟกต์ เมโมเก่งมากในสิ่งที่มันทำ: การจำกัดความถี่ในการแจ้งเตือนผู้ติดตามว่ามันเปลี่ยน แต่ดังที่คำอธิบายระบบรีแอกทีฟนี้ควรแสดงให้เห็น พวกมันมีโอเวอร์เฮดในสองรูปแบบ:

1. การตรวจ `PartialEq` ซึ่งอาจแพงหรือไม่แพงก็ได้
2. ต้นทุนหน่วยความจำที่เพิ่มขึ้นจากการเก็บโหนดอีกหนึ่งโหนดในระบบรีแอกทีฟ
3. ต้นทุนการคำนวณที่เพิ่มขึ้นของการท่องกราฟรีแอกทิวิตี

ในกรณีที่การคำนวณเองถูกกว่าการทำงานของรีแอกทีฟนี้ คุณควรหลีกเลี่ยงการ “ห่อเกินจำเป็น” ด้วยเมโม และใช้สัญญาณอนุพัทธ์แทน นี่คือตัวอย่างที่ดีว่าทำไมคุณจึงไม่ควรใช้เมโม:

```rust
let (a, set_a) = signal(1);
// none of these make sense as memos
let b = move || a() + 2;
let c = move || b() % 2 == 0;
let d = move || if c() { "even" } else { "odd" };

set_a(2);
set_a(3);
set_a(5);
```

แม้ว่าในทางทฤษฎี การใช้เมโมจะช่วยประหยัดการคำนวณ `d` เพิ่มอีกหนึ่งครั้งระหว่างการตั้ง `a` เป็น `3` กับ `5` แต่การคำนวณเหล่านี้เองก็ถูกกว่าอัลกอริทึมรีแอกทีฟอยู่ดี

อย่างมากที่สุด คุณอาจพิจารณาใช้เมโมกับโหนดสุดท้ายก่อนรันผลข้างเคียงที่แพงบางอย่าง:

```rust
let text = Memo::new(move |_| {
    d()
});
Effect::new(move |_| {
    engrave_text_into_bar_of_gold(&text());
});
```
