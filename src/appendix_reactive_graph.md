# ภาคผนวก: ระบบรีแอกทีฟทำงานอย่างไร?

คุณไม่จำเป็นต้องเข้าใจกลไกการทำงานเชิงลึกของระบบ reactive มากนักก็สามารถใช้งานไลบรารีนี้ได้อย่างราบรื่น แต่การทำความเข้าใจสิ่งที่เกิดขึ้นเบื้องหลังย่อมมีประโยชน์อย่างยิ่ง เมื่อคุณเริ่มพัฒนาแอปพลิเคชันที่มีความซับซ้อนในระดับสูง

reactive primitives ที่คุณใช้งานจะถูกแบ่งออกเป็น 3 กลุ่มหลัก:

- **สัญญาณ (Signals)** (`ReadSignal`/`WriteSignal`, `RwSignal`, `Resource`, `Trigger`): ค่าที่คุณสามารถสั่งเปลี่ยนแปลงได้โดยตรงเพื่อกระตุ้นให้เกิด reactive update
- **คอมพิวเทชัน (Computations)** (`Memo`): ค่าที่ขึ้นอยู่กับ signal (หรือ computation อื่น) และคำนวณค่าใหม่แบบ reactive ออกมาผ่าน pure computation
- **เอฟเฟกต์ (Effects)**: ตัวสังเกตการณ์ (observers) ที่คอยดักฟังการเปลี่ยนแปลงของ signal หรือ computation แล้วสั่งรันฟังก์ชันเพื่อสร้าง side effect บางอย่าง

สำหรับ derived signal จัดเป็น computation ประเภทที่ไม่ใช่ primitive เพราะเป็นเพียง closure ธรรมดาที่ช่วยให้คุณรีแฟกเตอร์โค้ดคำนวณที่อิงกับ signal ซ้ำ ๆ ให้กลายเป็นฟังก์ชันที่นำกลับมาใช้ใหม่ได้หลายจุด โดยไม่ได้ถูกบันทึกเป็นโหนดในระบบ reactive โดยตรง

ส่วน primitives อื่น ๆ ทั้งหมดจะมีตัวตนอยู่จริงในระบบ reactive ในฐานะโหนด (nodes) บนกราฟของความรีแอกทีฟ (reactive graph)

หน้าที่หลักส่วนใหญ่ของระบบ reactive คือการส่งผ่าน (propagate) การเปลี่ยนแปลงจาก signal ไปยัง effect โดยอาจมีการเดินทางผ่าน memo ที่คั่นอยู่ระหว่างทาง

สมมติฐานพื้นฐานของระบบ reactive คือ effect (เช่น การเรนเดอร์ลง DOM หรือการส่ง network request) มีต้นทุนการประมวลผลสูงกว่าการอัปเดตโครงสร้างข้อมูลของ Rust ภายในแอปหลายเท่าตัว

ดังนั้น **เป้าหมายหลัก** ของระบบ reactive คือ **สั่งรัน effect ให้น้อยครั้งที่สุดเท่าที่จะเป็นไปได้**

Leptos บรรลุเป้าหมายนี้ได้ด้วยการสร้างกราฟรีแอกทิวิตี (Reactive Graph)

> ระบบ reactive ปัจจุบันของ Leptos อิงตามอัลกอริทึมของไลบรารี [Reactively](https://github.com/modderme123/reactively) บน JavaScript เป็นหลัก คุณสามารถอ่านบทความของ Milo เรื่อง “[Super-Charging Fine-Grained Reactivity](https://dev.to/modderme123/super-charging-fine-grained-reactive-performance-47ph)” เพื่อดูคำอธิบายที่ยอดเยี่ยมเกี่ยวกับอัลกอริทึมนี้ รวมถึงหลักการของ fine-grained reactivity ในภาพรวม พร้อมแผนภาพประกอบที่เข้าใจง่าย!

## กราฟรีแอกทิวิตี

สัญญาณ (Signal), เมโม (Memo) และเอฟเฟกต์ (Effect) ต่างมีคุณลักษณะร่วมกัน 3 ประการ:

- **ค่า (Value)**: ค่าปัจจุบันของโหนด ไม่ว่าจะเป็นค่าของ signal หรือ (สำหรับ memo และ effect) ค่าที่ได้จากการรันในรอบก่อนหน้า (ถ้ามี)
- **ซอร์ส (Sources)**: reactive primitive อื่น ๆ ที่โหนดนี้ขึ้นตรงด้วย (สำหรับ signal จะเป็นเซตว่าง)
- **ผู้ติดตาม (Subscribers)**: reactive primitive อื่น ๆ ที่มาคอยดักฟังหรือขึ้นตรงกับโหนดนี้ (สำหรับ effect จะเป็นเซตว่าง)

ในความเป็นจริงแล้ว signal, memo และ effect เป็นเพียงชื่อเรียกตามบริบทของแนวคิดหลักหนึ่งเดียว นั่นคือ “โหนด” (node) ในกราฟรีแอกทิวิตี โดย signal จะเป็น “โหนดราก” (root node) เสมอ (ไม่มี source/parent) effect จะเป็น “โหนดใบ” (leaf node) เสมอ (ไม่มี subscriber) ส่วน memo มักจะมีทั้ง source และ subscriber ควบคู่กัน

> ในตัวอย่างโค้ดต่อไปนี้ เราจะใช้ syntax แบบ `nightly` เพื่อความกระชับในการอ่านเนื้อหา (มีไว้สำหรับทำความเข้าใจ ไม่ได้ออกแบบมาเพื่อ copy-paste ไปใช้งานจริง)

### ความขึ้นต่อกันแบบง่าย

ลองจินตนาการว่าเรามีโค้ดต่อไปนี้:

```rust
// A
let (name, set_name) = signal("Alice");

// B
let name_upper = Memo::new(move |_| name.with(|n| n.to_uppercase()));

// C
Effect::new(move |_| {
	log!("{}", name_upper());
});

set_name("Bob");
```


คุณสามารถจินตนาการโครงสร้างกราฟได้ง่าย ๆ: `name` เป็นโหนดต้นทาง (source signal) เพียงตัวเดียว `Effect::new` เป็นโหนดปลายทาง (effect) เพียงตัวเดียว และมี memo คั่นอยู่ตรงกลางหนึ่งตัว

```
A   (name)
|
B   (name_upper)
|
C   (the effect)
```

### การแยกสาขา

มาทำให้ซับซ้อนขึ้นอีกหน่อยกัน

```rust
// A
let (name, set_name) = signal("Alice");

// B
let name_upper = Memo::new(move |_| name.with(|n| n.to_uppercase()));

// C
let name_len = Memo::new(move |_| name.len());

// D
Effect::new(move |_| {
	log!("len = {}", name_len());
});

// E
Effect::new(move |_| {
	log!("name = {}", name_upper());
});
```

ตัวอย่างนี้ก็ตรงไปตรงมาเช่นกัน: โหนด signal ต้นทาง (`name`/`A`) แตกแขนงออกเป็นสองเส้นทางคู่ขนาน: `name_upper`/`B` และ `name_len`/`C` โดยแต่ละเส้นทางจะมี effect ที่ขึ้นตรงกับมัน

```
 __A__
|     |
B     C
|     |
E     D
```

ทีนี้ลองมาอัปเดตค่าของ signal กัน

```rust
set_name("Bob");
```

เราจะเห็นล็อกทันทีว่า

```
len = 3
name = BOB
```

ลองทำอีกครั้ง

```rust
set_name("Tim");
```

ล็อกควรแสดง

```
name = TIM
```

`len = 3` จะไม่ถูกบันทึกอีก

โปรดระลึกไว้ว่า เป้าหมายสูงสุดของระบบ reactive คือการรัน effect ให้น้อยครั้งที่สุดเท่าที่จะทำได้ การเปลี่ยนค่า `name` จาก `"Bob"` เป็น `"Tim"` จะกระตุ้นให้ memo ทั้งสองตัวคำนวณใหม่ แต่ memo จะแจ้งเตือน subscriber ก็ต่อเมื่อผลลัพธ์ของมันเปลี่ยนแปลงไปจริง ๆ เท่านั้น ซึ่ง `"BOB"` กับ `"TIM"` มีค่าไม่เหมือนกัน effect ที่ฟังชื่อจึงต้องรันใหม่ แต่เนื่องจากชื่อทั้งสองมีความยาว `3` เท่ากัน effect ที่ฟังความยาวจึงไม่ถูกสั่งรันซ้ำ

### การรวมสาขากลับเข้าด้วยกัน

อีกหนึ่งตัวอย่างสำคัญที่ในวงการมักเรียกว่า **ปัญหาเพชร หรือปัญหาสี่เหลี่ยมขนมเปียกปูน (the diamond problem)**

```rust
// A
let (name, set_name) = signal("Alice");

// B
let name_upper = Memo::new(move |_| name.with(|n| n.to_uppercase()));

// C
let name_len = Memo::new(move |_| name.len());

// D
Effect::new(move |_| {
	log!("{} is {} characters long", name_upper(), name_len());
});
```

กราฟจะเป็นหน้าตาอย่างไรสำหรับกรณีนี้?

```
 __A__
|     |
B     C
|     |
|__D__|
```

คุณคงเห็นแล้วว่าทำไมถึงเรียกว่า “the diamond problem” หากเราลากเส้นเชื่อมระหว่างโหนดต่าง ๆ มันจะมีรูปทรงเหมือนเพชรหรือสี่เหลี่ยมขนมเปียกปูน: มี memo สองตัวที่ต่างก็ขึ้นอยู่กับ signal ตัวเดียวกัน แล้วผลลัพธ์ของ memo ทั้งสองก็ถูกส่งเข้าไปยัง effect เดียวกัน

หากระบบ reactive ถูกอิมพลีเมนต์แบบ push-based อย่างตรงไปตรงมา (naive) จะส่งผลให้ effect นี้ถูกรันซ้ำถึงสองครั้ง ซึ่งไม่เป็นผลดีเลย (จำไว้ว่าเป้าหมายของเราคือการรัน effect ให้น้อยครั้งที่สุด) ยกตัวอย่างเช่น หากระบบ reactive ส่งผ่านการเปลี่ยนแปลงของ signal และ memo ไล่ลงไปตามกราฟทันทีผ่านทีละ dependency ตามลำดับ (เทียบได้กับการท่องกราฟแบบ depth-first traversal) เมื่อมีการอัปเดต `A` ก็จะแจ้งเตือน `B` แล้ว `B` ก็จะสั่งรัน `D` จากนั้น `A` ก็จะแจ้งเตือน `C` แล้ว `C` ก็จะสั่งรัน `D` ซ้ำอีกรอบ วิธีการนี้นอกจากจะขาดประสิทธิภาพ (เพราะ `D` รันสองครั้ง) แล้ว ยังก่อให้เกิดอาการ “glitch” (โดยในการรันครั้งแรก `D` จะทำงานด้วยค่าเก่าที่ไม่สอดคล้องกันของ memo ตัวที่สอง)

## การแก้ปัญหาสี่เหลี่ยมขนมเปียกปูน

ระบบ reactive ที่มีคุณภาพทุกระบบต่างให้ความสำคัญกับการแก้ปัญหานี้ ซึ่งมีหลากหลายแนวทางในการจัดการ (สามารถศึกษาภาพรวมเชิงลึกได้จาก [บทความของ Milo](https://dev.to/modderme123/super-charging-fine-grained-reactive-performance-47ph))

ต่อไปนี้คือสรุปกระบวนการทำงานของระบบใน Leptos:

โหนด reactive แต่ละโหนดจะอยู่ในสถานะใดสถานะหนึ่งจาก 3 สถานะเสมอ:

- `Clean`: ยืนยันได้ว่าไม่มีการเปลี่ยนแปลง
- `Check`: มีความเป็นไปได้ที่จะเปลี่ยนแปลง
- `Dirty`: มีการเปลี่ยนแปลงอย่างแน่นอน

เมื่อมีการอัปเดต signal ระบบจะทำเครื่องหมายโหนด signal นั้นเป็น `Dirty` และไล่ทำเครื่องหมายโหนดลูกหลาน (descendants) ทั้งหมดเป็น `Check` แบบ recursive หากโหนดลูกหลานตัวใดเป็น effect ก็จะถูกจัดเข้าคิวเตรียมรันใหม่

```
    ____A (DIRTY)___
   |               |
B (CHECK)    C (CHECK)
   |               |
   |____D (CHECK)__|
```

จากนั้น effect เหล่านั้นจะเริ่มทำงาน (ณ จุดนี้ effect ทั้งหมดจะถือสถานะ `Check`) โดยก่อนที่จะเริ่มคำนวณใหม่ ตัว effect จะย้อนกลับไปตรวจโหนดแม่ (parents) ของตนเองก่อนว่ามีสถานะ dirty หรือไม่:

- โหนด `D` จะตรวจดูที่ `B` ก่อนว่ามีสถานะ `Dirty` หรือไม่
- แต่เนื่องจาก `B` เองก็ถือสถานะ `Check` อยู่ โหนด `B` จึงต้องทำกระบวนการเดียวกัน:
  - `B` ย้อนกลับไปตรวจที่ `A` และพบว่า `A` มีสถานะ `Dirty`
  - นั่นหมายความว่า `B` จำเป็นต้องคำนวณใหม่ เพราะ source ของมันตัวหนึ่งมีการเปลี่ยนแปลง
  - `B` จึงรันการคำนวณ ได้ค่าใหม่ และเปลี่ยนสถานะตัวเองเป็น `Clean`
  - และเนื่องจาก `B` เป็น memo มันจึงเปรียบเทียบค่าใหม่กับค่าเดิมในรอบก่อนหน้า
  - หากค่าทั้งสองเท่ากัน `B` จะแจ้งกลับว่า "ไม่มีการเปลี่ยนแปลง" แต่หากไม่เท่ากัน จะแจ้งว่า "ใช่ ฉันเปลี่ยนแล้ว"
- หาก `B` แจ้งว่า “ใช่ ฉันเปลี่ยนแล้ว” โหนด `D` จะรู้ทันทีว่าตนเองต้องรันแน่นอน จึงเริ่มรันทันทีโดยไม่จำเป็นต้องเสียเวลาตรวจ source อื่นต่อ
- หาก `B` แจ้งว่า “ไม่ ฉันไม่ได้เปลี่ยน” โหนด `D` จะไปตรวจดูที่โหนด `C` ต่อไป (ด้วยกระบวนการเดียวกับ `B`)
- หากทั้ง `B` และ `C` ต่างไม่มีการเปลี่ยนแปลง effect `D` ก็ไม่จำเป็นต้องรันใหม่
- แต่หาก `B` หรือ `C` ตัวใดตัวหนึ่งเปลี่ยน effect ก็จะถูกสั่งรันใหม่ ณ จุดนี้

และเนื่องจากตัว effect ถูกทำเครื่องหมาย `Check` เพียงครั้งเดียว และถูกจัดเข้าคิวเพียงครั้งเดียว มันจึงถูกรันเพียงครั้งเดียวเท่านั้น!

หากเวอร์ชันดั้งเดิมที่เรียบง่ายคือระบบ reactive แบบ “push-based” (ที่เพียงดันการเปลี่ยนแปลงลงไปตามแนวกราฟจนทำให้ effect รันซ้ำสองรอบ) ระบบเวอร์ชันนี้ก็เปรียบเสมือนแบบ “push-pull” คือมันจะผลักสถานะ `Check` ลงไปตามแนวกราฟก่อน แล้วค่อย “pull” หรือดึงย้อนกลับขึ้นมาตรวจสอบความถูกต้อง อันที่จริง ในโครงสร้างกราฟขนาดใหญ่ อัลกอริทึมอาจมีการกระโดดขึ้นลงและซ้ายขวาไปมาบนกราฟ เพื่อระบุให้แน่ชัดว่าโหนดใดบ้างที่จำเป็นต้องคำนวณใหม่จริง ๆ

**ข้อแลกเปลี่ยนสำคัญที่พึงตระหนัก**: ระบบ reactive แบบ push-based สามารถกระจายการเปลี่ยนแปลงของ signal ได้เร็วกว่า แต่ต้องแลกมาด้วยการรัน memo และ effect ซ้ำซ้อนเกินความจำเป็น โปรดจำไว้ว่าระบบ reactive ถูกออกแบบมาเพื่อลดความถี่ในการรัน effect ให้น้อยที่สุด ด้วยสมมติฐาน (ที่ถูกต้องแม่นยำ) ว่าการเกิด side effect มีต้นทุนแพงกว่าการท่องกราฟที่ cache-friendly ภายในหน่วยความจำของโค้ด Rust หลายเท่าตัว ดังนั้น มาตรวัดของระบบ reactive ที่ยอดเยี่ยม จึงไม่ใช่แค่ความเร็วในการกระจายการเปลี่ยนแปลง แต่คือความเร็วในการกระจายการเปลี่ยนแปลง _โดยปราศจากการแจ้งเตือนที่เกินความจำเป็น_

## เมโมกับสัญญาณ

โปรดสังเกตว่า signal จะแจ้งเตือนโหนดลูกของมันเสมอ กล่าวคือ signal จะถูกทำเครื่องหมายว่า `Dirty` ทุกครั้งที่มีการอัปเดต แม้ว่าค่าใหม่ที่ใส่เข้าไปจะเหมือนกับค่าเดิมก็ตาม เพราะหากไม่ทำเช่นนี้ เราจะต้องบังคับให้ signal ทุกตัวต้องอิมพลีเมนต์ `PartialEq` ซึ่งจริง ๆ แล้วการเปรียบเทียบความเท่ากันอาจมีต้นทุนที่สูงมากสำหรับบางประเภทข้อมูล (เช่น การต้องตรวจเช็กความเท่ากันโดยไม่จำเป็นกับคำสั่งอย่าง `some_vec_signal.update(|n| n.pop())` ทั้งที่เห็นได้ชัดว่าข้อมูลมีการเปลี่ยนแปลงแน่นอน)

ในทางตรงกันข้าม memo จะตรวจสอบก่อนเสมอว่าค่าของตนเองเปลี่ยนแปลงหรือไม่ ก่อนที่จะแจ้งเตือนไปยังโหนดลูก โดย memo จะคำนวณเพียงครั้งเดียวไม่ว่าคุณจะเรียก `.get()` กี่ครั้งก็ตาม แต่จะถูกสั่งคำนวณใหม่ทุกครั้งที่ signal ต้นทางเปลี่ยน นั่นหมายความว่าหากการคำนวณของ memo มีต้นทุน _สูงมาก_ คุณอาจต้องการ memoize ค่าอินพุตของมันไว้ด้วย เพื่อให้มั่นใจว่า memo จะเริ่มคำนวณใหม่เฉพาะเมื่ออินพุตเปลี่ยนจริง ๆ เท่านั้น

## เมโมกับสัญญาณอนุพัทธ์

แม้กลไกทั้งหมดนี้จะดูยอดเยี่ยมและ memo จะมีประโยชน์มาก แต่ในแอปพลิเคชันจริงส่วนใหญ่ กราฟรีแอกทีฟมักจะมีลักษณะค่อนข้างตื้นและกว้าง: คุณอาจมี signal ต้นทาง 100 ตัว และมี effect 500 ตัว แต่แทบไม่มี memo เลย หรือในกรณีที่ซับซ้อนก็อาจมี memo คั่นอยู่เพียง 3–4 ตัวเท่านั้น memo ทำหน้าที่จำกัดความถี่ในการแจ้งเตือน subscriber ได้อย่างยอดเยี่ยม แต่ดังที่ได้อธิบายไว้ข้างต้น ตัว memo เองก็มี overhead อยู่ 3 ประการ:

1. การตรวจสอบ `PartialEq` ซึ่งอาจมีต้นทุนสูงหรือต่ำขึ้นอยู่กับชนิดข้อมูล
2. ต้นทุนหน่วยความจำที่เพิ่มขึ้นจากการจัดเก็บโหนดเพิ่มขึ้นอีกหนึ่งโหนดในระบบ reactive
3. ต้นทุนการประมวลผลที่เพิ่มขึ้นในการท่องกราฟรีแอกทิวิตี

ในกรณีที่การคำนวณค่านั้นมีต้นทุนถูกกว่าการทำงานของระบบ reactive คุณควรหลีกเลี่ยงการ “ห่อหุ้มเกินความจำเป็น” (over-wrapping) ด้วย memo และหันมาใช้ derived signal แทน ด้านล่างนี้คือตัวอย่างที่ชัดเจนว่าเหตุใดคุณจึงไม่ควรใช้ memo:

```rust
let (a, set_a) = signal(1);
// none of these make sense as memos
let b = move || a() + 2;
let c = move || b() % 2 == 0;
let d = move || if c() { "even" } else { "odd" };

set_a(2);
set_a(3);
set_a(5);
```

แม้ในทางทฤษฎี การใช้ memo อาจช่วยประหยัดการคำนวณ `d` ได้ 1 ครั้งตอนเปลี่ยนค่า `a` จาก `3` เป็น `5` แต่การคำนวณบวกเลขและหารเอาเศษเหล่านี้มีต้นทุนที่ถูกกว่าการทำงานของอัลกอริทึม reactive มาก

อย่างมากที่สุด คุณอาจพิจารณาใช้ memo กับโหนดสุดท้ายก่อนที่จะส่งต่อไปยัง side effect ที่มีต้นทุนสูงมากจริง ๆ:

```rust
let text = Memo::new(move |_| {
    d()
});
Effect::new(move |_| {
    engrave_text_into_bar_of_gold(&text());
});
```
