# คั่นรายการ: รีแอกทิวิตีและฟังก์ชัน

หนึ่งในทีมผู้พัฒนาหลักของเราเคยพูดไว้เมื่อไม่นานมานี้ว่า: "ผมไม่เคยเขียนคลอเชอร์ (closures) บ่อยขนาดนี้มาก่อนเลยในชีวิต จนกระทั่งได้มาใช้ Leptos" ซึ่งนั่นเป็นเรื่องจริงอย่างยิ่ง เพราะคลอเชอร์คือหัวใจสำคัญของทุกแอปพลิเคชันที่สร้างด้วย Leptos จนบางครั้งเมื่อมองดูโค้ดก็อาจจะรู้สึกแปลกตาไปบ้าง:

```rust
// a signal holds a value, and can be updated
let (count, set_count) = signal(0);

// a derived signal is a function that accesses other signals
let double_count = move || count.get() * 2;
let count_is_odd = move || count.get() & 1 == 1;
let text = move || if count_is_odd() {
    "odd"
} else {
    "even"
};

// an effect automatically tracks the signals it depends on
// and reruns when they change
Effect::new(move |_| {
    logging::log!("text = {}", text());
});

view! {
    <p>{move || text().to_uppercase()}</p>
}
```

คลอเชอร์ คลอเชอร์ เต็มไปหมด!

แต่ทำไมถึงต้องเป็นแบบนั้นล่ะ?

## ฟังก์ชันและเฟรมเวิร์ก UI

ฟังก์ชันคือหัวใจของเฟรมเวิร์ก UI ทุกตัว ซึ่งเรื่องนี้สมเหตุสมผลอย่างยิ่ง เพราะโดยพื้นฐานแล้ว การสร้างและจัดการส่วนติดต่อผู้ใช้ (UI) จะแบ่งออกเป็น 2 ช่วงเวลาหลัก ๆ เสมอ:

1. การเรนเดอร์ครั้งแรก (Initial render)
2. การอัปเดตข้อมูล (Updates)

ในโลกของเว็บเฟรมเวิร์ก ตัวเฟรมเวิร์กจะทำการเรนเดอร์ UI รอบแรกสุดขึ้นมา จากนั้นจะคืนการควบคุมกลับไปให้เบราว์เซอร์ และเมื่อมีเหตุการณ์บางอย่างเกิดขึ้น (เช่น ผู้ใช้คลิกเมาส์) หรืองานแบบอะซิงโครนัสเสร็จสิ้นลง (เช่น ได้รับผลลัพธ์จากคำขอ HTTP) เบราว์เซอร์ก็จะปลุกเฟรมเวิร์กให้ตื่นขึ้นมาเพื่ออัปเดตหน้าจอ เฟรมเวิร์กก็จะรันโค้ดบางอย่างเพื่ออัปเดตส่วนติดต่อผู้ใช้ของคุณ แล้วกลับไปหลับต่อเพื่อรอให้เบราว์เซอร์มาปลุกอีกครั้งในรอบถัดไป

วลีสำคัญในที่นี้คือ **“รันโค้ดบางอย่าง”** วิธีที่เป็นธรรมชาติและตรงไปตรงมาที่สุดในการ “รันโค้ดบางอย่าง” ณ จุดเวลาใดก็ตาม ไม่ว่าจะในภาษา Rust หรือภาษาโปรแกรมอื่น ๆ ก็คือการเรียกฟังก์ชัน และในความเป็นจริง เฟรมเวิร์ก UI ทุกตัวล้วนสร้างขึ้นบนแนวคิดของการรันฟังก์ชันบางอย่างซ้ำแล้วซ้ำเล่า:

1. **เฟรมเวิร์กที่ใช้ Virtual DOM (VDOM)** เช่น React, Yew หรือ Dioxus จะรันคอมโพเนนต์หรือฟังก์ชันเรนเดอร์ทั้งฟังก์ชันซ้ำแล้วซ้ำเล่า เพื่อสร้าง Virtual DOM tree ขึ้นมาใหม่ แล้วนำไปเปรียบเทียบ (reconcile/diff) กับของเดิมเพื่อหาจุดที่ต้องแก้ไขและนำไปแพตช์ลง DOM จริง
2. **เฟรมเวิร์กที่อาศัยคอมไพลเลอร์** เช่น Angular และ Svelte จะแยกเทมเพลตของคอมโพเนนต์ออกเป็นฟังก์ชัน "create" และฟังก์ชัน "update" โดยจะสั่งรันฟังก์ชัน update ซ้ำเมื่อตรวจพบว่าสถานะของคอมโพเนนต์เปลี่ยนไป
3. **เฟรมเวิร์กแบบรีแอกทีฟแบบละเอียด (Fine-grained reactive frameworks)** เช่น SolidJS, Sycamore หรือ Leptos _ตัวคุณเอง_ จะเป็นผู้กำหนดว่าฟังก์ชันชิ้นใดบ้างที่จะถูกสั่งรันซ้ำ

นั่นคือสิ่งที่คอมโพเนนต์ทั้งหมดใน Leptos กำลังทำอยู่

ลองดูตัวอย่าง `<SimpleCounter/>` พื้นฐานของเราในรูปแบบที่เรียบง่ายที่สุด:

```rust
#[component]
pub fn SimpleCounter() -> impl IntoView {
    let (value, set_value) = signal(0);

    let increment = move |_| *set_value.write() += 1;

    view! {
        <button on:click=increment>
            {value}
        </button>
    }
}
```

ตัวฟังก์ชัน `SimpleCounter` เองจะถูกรันเพียงครั้งแรกครั้งเดียวเท่านั้น สัญญาณ `value` ก็ถูกสร้างขึ้นเพียงครั้งเดียว จากนั้นเฟรมเวิร์กจะส่งฟังก์ชัน `increment` ไปลงทะเบียนไว้กับเบราว์เซอร์ในฐานะตัวรับฟังเหตุการณ์ (event listener) เมื่อคุณคลิกปุ่ม เบราว์เซอร์จะเรียกฟังก์ชัน `increment` ซึ่งสั่งอัปเดตค่าใน `value` ผ่าน `set_value` และการอัปเดตค่านั้นก็จะไปกระตุ้นให้โหนดข้อความเพียงโหนดเดียวที่แสดงผล `{value}` ในวิวของเราถูกอัปเดตตามไปด้วย

ฟังก์ชันจึงเป็นกุญแจสำคัญที่สุดของระบบรีแอกทิวิตี เพราะมันมอบความสามารถให้เฟรมเวิร์กสั่งรันเฉพาะหน่วยที่เล็กที่สุดเท่าที่จะเป็นไปได้ของแอปพลิเคชันซ้ำ เมื่อเกิดการเปลี่ยนแปลงขึ้น

ดังนั้น ขอให้จำ 2 กฎทองนี้ไว้เสมอ:

1. ฟังก์ชันคอมโพเนนต์ของคุณคือ **ฟังก์ชันสำหรับติดตั้งค่าเริ่มต้น (setup function)** ไม่ใช่ฟังก์ชันสำหรับเรนเดอร์: มันจะรันเพียงครั้งเดียวเท่านั้น
2. หากต้องการให้ค่าใด ๆ ในเทมเพลตวิวเป็นแบบรีแอกทีฟ ค่านั้นจะต้องอยู่ในรูปของ **ฟังก์ชันรีแอกทีฟ**: ไม่ว่าจะเป็นตัวสัญญาณเองโดยตรง หรือคลอเชอร์ที่เข้าไปอ่านค่าจากสัญญาณ

```admonish note
ในความเป็นจริง นี่คือจุดแตกต่างหลักระหว่างโหมด stable และ nightly ของ Leptos โดยการใช้คอมไพเลอร์ Rust เวอร์ชัน nightly ร่วมกับฟีเจอร์ `nightly` จะเปิดให้คุณสามารถเรียกใช้สัญญาณในรูปของฟังก์ชันได้โดยตรง เช่น เขียน `value()` แทนที่จะต้องเขียน `value.get()`

สิ่งนี้ไม่ได้เป็นเพียงแค่ syntax sugar เท่านั้น แต่มันยังช่วยสร้างโมเดลทางความคิด (mental model) ที่สอดคล้องเป็นหนึ่งเดียวกันอย่างยิ่ง นั่นคือ: **ทุกสิ่งที่เป็นรีแอกทีฟคือฟังก์ชัน** การเข้าถึงสัญญาณทำได้ด้วยการเรียกฟังก์ชัน และหากคอมโพเนนต์ต้องการประกาศว่า "ขอรับสัญญาณเข้ามาเป็นอาร์กิวเมนต์" คุณก็เพียงแค่ระบุชนิดเป็น `impl Fn() -> T` โดยที่อินเทอร์เฟซของฟังก์ชันนี้ไม่จำเป็นต้องสนใจเลยว่าสิ่งที่ส่งเข้ามาจะเป็นสัญญาณ (signal), memo หรือ derived signal เพราะทั้งหมดล้วนเข้าถึงได้ด้วยการเรียกฟังก์ชันเหมือนกันทั้งสิ้น

ทว่าน่าเสียดายที่การอิมพลีเมนต์เทรต `Fn` ให้กับ struct ทั่วไป (เช่น สัญญาณ) นั้นจำเป็นต้องพึ่งพาฟีเจอร์พิเศษของ nightly Rust แม้ว่าฟีเจอร์นี้จะไม่มีการเปลี่ยนแปลงและทำงานได้นิ่งมานานแล้ว แต่ก็ยังไม่มีกำหนดการเข้าสู่เวอร์ชัน stable ในเร็ววันนี้ ประกอบกับนักพัฒนาจำนวนมากไม่สะดวกที่จะใช้คอมไพเลอร์เวอร์ชัน nightly ด้วยเหตุผลต่าง ๆ เมื่อเวลาผ่านไป เราจึงปรับให้เอกสารและค่าเริ่มต้นของไลบรารีอิงกับเวอร์ชัน stable เป็นหลัก ซึ่งทำให้โมเดลความคิดที่สวยงามอย่าง "สัญญาณคือฟังก์ชัน" อาจจะดูไม่ตรงไปตรงมาเท่าที่ควรในเวอร์ชัน stable
```
