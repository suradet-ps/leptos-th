# การจัดการสถานะส่วนกลาง

จนถึงตอนนี้ เราได้ทำงานกับสถานะระดับโลคอล (local state) ภายในคอมโพเนนต์เท่านั้น และได้เห็นวิธีประสานสถานะระหว่างคอมโพเนนต์แม่กับลูกกันไปแล้ว แต่ในบางครั้ง คุณอาจต้องการวิธีแก้ปัญหาที่เป็นสากลกว่านั้น สำหรับการจัดการสถานะส่วนกลาง (global state) ที่สามารถเข้าถึงและใช้งานได้ทั่วทั้งแอปพลิเคชัน

โดยทั่วไปแล้ว **คุณไม่จำเป็นต้องอ่านบทนี้ก็ได้** รูปแบบทั่วไปในการพัฒนาคือการประกอบแอปพลิเคชันขึ้นจากคอมโพเนนต์ย่อย ๆ โดยให้แต่ละตัวคอยจัดการสถานะโลคอลของตนเอง แทนที่จะเก็บสถานะทั้งหมดไว้ในโครงสร้างส่วนกลางเพียงแห่งเดียว อย่างไรก็ตาม ยังคงมีบางกรณี (เช่น การเปลี่ยนธีม, การบันทึกการตั้งค่าผู้ใช้ หรือการแชร์ข้อมูลระหว่างคอมโพเนนต์ที่อยู่คนละส่วนของ UI) ที่คุณอาจต้องการใช้การจัดการสถานะส่วนกลางในรูปแบบใดรูปแบบหนึ่ง

แนวทางที่ดีที่สุด 3 ประการสำหรับสถานะส่วนกลาง ได้แก่:

1. ใช้เราเตอร์ขับเคลื่อนสถานะส่วนกลางผ่าน URL
2. ส่งสัญญาณผ่านคอนเท็กซ์ (Context)
3. สร้างสตรัคต์สถานะส่วนกลางโดยใช้สโตร์ (Store)

## ทางเลือกที่ 1: URL เป็นสถานะส่วนกลาง

ในหลาย ๆ แง่มุม URL ถือเป็นวิธีที่ดีที่สุดในการเก็บสถานะส่วนกลางอย่างแท้จริง เพราะมันสามารถเข้าถึงได้จากทุกคอมโพเนนต์และทุกตำแหน่งในคอมโพเนนต์ทรีของคุณ ยิ่งไปกว่านั้น ยังมีเอลิเมนต์ HTML แบบเนทีฟอย่าง `<form>` และ `<a>` ที่ออกแบบมาเพื่ออัปเดต URL โดยเฉพาะ อีกทั้งสถานะยังคงอยู่แม้จะรีโหลดหน้าเว็บหรือเปลี่ยนอุปกรณ์ คุณสามารถแชร์ URL ให้เพื่อน หรือส่งต่อจากโทรศัพท์ไปยังแล็ปท็อป แล้วสถานะทั้งหมดที่บันทึกไว้ในนั้นก็จะถูกสร้างจำลองขึ้นมาใหม่ได้ทันที

เนื้อหาอีกไม่กี่หัวข้อถัดไปจะว่าด้วยเรื่องเราเตอร์ (Router) ซึ่งเราจะมาเจาะลึกประเด็นเหล่านี้กันให้ละเอียดยิ่งขึ้น

แต่สำหรับตอนนี้ เราจะมาดูทางเลือกที่ 2 และ 3 กันก่อน

## ทางเลือกที่ 2: การส่งสัญญาณผ่านคอนเท็กซ์

ในหัวข้อว่าด้วย[การสื่อสารระหว่างคอมโพเนนต์แม่กับลูก](view/08_parent_child.md) เราได้เห็นแล้วว่าสามารถใช้ `provide_context` เพื่อส่งสัญญาณจากคอมโพเนนต์แม่ไปยังลูก และใช้ `use_context` เพื่ออ่านค่านั้นในคอมโพเนนต์ลูกได้ แต่จริง ๆ แล้ว `provide_context` ทำงานข้ามระยะห่างในลำดับชั้นได้ไกลเท่าที่คุณต้องการ หากคุณต้องการสร้างสัญญาณระดับโกลบอลเพื่อเก็บสถานะบางอย่าง คุณก็สามารถ provide มันไว้ แล้วเข้าถึงผ่านคอนเท็กซ์ได้จากทุกตำแหน่งในบรรดาคอมโพเนนต์ลูกหลาน (descendants) ใต้คอมโพเนนต์ที่คุณ provide ไว้

สัญญาณที่ถูก provide ผ่านคอนเท็กซ์จะสั่งให้อัปเดตแบบรีแอกทีฟเฉพาะจุดที่มีการอ่านสัญญาณนั้นจริง ๆ เท่านั้น โดยไม่กระทบคอมโพเนนต์ใด ๆ ที่คั่นอยู่ตรงกลางเลย คุณจึงยังคงได้รับประโยชน์จากการอัปเดตแบบละเอียดระดับย่อย (fine-grained reactive updates) แม้จะอยู่ห่างกันในทรีก็ตาม

เราเริ่มต้นด้วยการสร้างสัญญาณที่รูทของแอป แล้ว provide มันให้กับ
คอมโพเนนต์ลูกและลูกหลานทั้งหมดโดยใช้ `provide_context`

```rust
#[component]
fn App() -> impl IntoView {
    // here we create a signal in the root that can be consumed
    // anywhere in the app.
    let (count, set_count) = signal(0);
    // we'll pass the setter to specific components,
    // but provide the count itself to the whole app via context
    provide_context(count);

    view! {
        // SetterButton is allowed to modify the count
        <SetterButton set_count/>
        // These consumers can only read from it
        // But we could give them write access by passing `set_count` if we wanted
        <FancyMath/>
        <ListItems/>
    }
}
```

`<SetterButton/>` เป็นคอมโพเนนต์ตัวนับในแบบที่เราเคยเขียนกันมาแล้วหลายครั้ง

ทั้ง `<FancyMath/>` และ `<ListItems/>` ต่างดึงสัญญาณที่เรา provide ไว้มาใช้งานผ่าน
`use_context` แล้วนำไปประมวลผลต่อ

```rust
/// A component that does some "fancy" math with the global count
#[component]
fn FancyMath() -> impl IntoView {
    // here we consume the global count signal with `use_context`
    let count = use_context::<ReadSignal<u32>>()
        // we know we just provided this in the parent component
        .expect("there to be a `count` signal provided");
    let is_even = move || count.get() & 1 == 0;

    view! {
        <div class="consumer blue">
            "The number "
            <strong>{count}</strong>
            {move || if is_even() {
                " is"
            } else {
                " is not"
            }}
            " even."
        </div>
    }
}
```

## ทางเลือกที่ 3: สร้างสโตร์สถานะส่วนกลาง

> เนื้อหาบางส่วนในหัวข้อนี้จะซ้ำกับหัวข้อการวนซ้ำข้อมูลที่ซับซ้อนด้วยสโตร์[ที่นี่](view/04b_iteration.md#ทางเลือกที-4-สโตร) เนื่องจากทั้งสองส่วนเป็นเนื้อหาระดับกลางและเป็นทางเลือกเสริม การมีเนื้อหาที่ทับซ้อนกันบ้างจึงช่วยให้เข้าใจได้สะดวกยิ่งขึ้น

สโตร์ (Store) เป็นพริมิทีฟเชิงรีแอกทีฟตัวใหม่ที่มีให้ใช้งานใน Leptos 0.7 ผ่านทางแครต `reactive_stores` ที่มาคู่กัน (ปัจจุบันแครตนี้ถูกแยกออกมาต่างหาก เพื่อให้เราสามารถพัฒนาฟีเจอร์เพิ่มเติมต่อไปได้โดยไม่ต้องเปลี่ยนเวอร์ชันของเฟรมเวิร์กทั้งหมด)

สโตร์ช่วยให้คุณสามารถห่อหุ้มสตรัคต์ทั้งตัว จากนั้นก็อ่านและอัปเดตแต่ละฟิลด์แยกกันได้อย่างเป็นอิสระในเชิงรีแอกทีฟ โดยไม่ไปกระตุ้นหรือติดตามการเปลี่ยนแปลงของฟิลด์อื่น ๆ เลย

วิธีใช้งานทำได้โดยเพิ่ม `#[derive(Store)]` ให้กับสตรัคต์ของคุณ (สามารถใช้ `use reactive_stores::Store;` เพื่อนำเข้าแมโครเข้ามา) ซึ่งจะสร้างเอกซ์เทนชันเทรตที่มีเมธอดเก็ตเตอร์สำหรับแต่ละฟิลด์ของสตรัคต์ เมื่อสตรัคต์นั้นถูกห่อหุ้มด้วย `Store<_>`

```rust
#[derive(Clone, Debug, Default, Store)]
struct GlobalState {
    count: i32,
    name: String,
}
```

สิ่งนี้จะสร้างเทรตชื่อ `GlobalStateStoreFields` ขึ้นมา ซึ่งเพิ่มเมธอด `count` และ `name` ให้กับ `Store<GlobalState>` โดยแต่ละเมธอดจะคืนค่าเป็น *ฟิลด์* ของสโตร์ที่ทำงานแบบรีแอกทีฟ

```rust
#[component]
fn App() -> impl IntoView {
    provide_context(Store::new(GlobalState::default()));

    // etc.
}

/// A component that updates the count in the global state.
#[component]
fn GlobalStateCounter() -> impl IntoView {
    let state = expect_context::<Store<GlobalState>>();

    // this gives us reactive access to the `count` field only
    let count = state.count();

    view! {
        <div class="consumer blue">
            <button
                on:click=move |_| {
                    *count.write() += 1;
                }
            >
                "Increment Global Count"
            </button>
            <br/>
            <span>"Count is: " {move || count.get()}</span>
        </div>
    }
}
```

การคลิกปุ่มนี้จะส่งผลให้อัปเดตเฉพาะ `state.count` เท่านั้น หากเรามีการอ่านค่าจาก `state.name` ที่ตำแหน่งอื่น
การคลิกปุ่มจะไม่ไปแจ้งเตือนหรือสั่งให้จุดนั้นทำงานใหม่เลย สิ่งนี้ช่วยให้คุณผสานข้อดีของโฟลว์ข้อมูลแบบบนลงล่าง (top-down data flow)
เข้ากับประสิทธิภาพของการอัปเดตแบบละเอียดระดับย่อย (fine-grained reactive updates) ได้อย่างลงตัว

ลองเข้าไปดู[ตัวอย่าง `stores`](https://github.com/leptos-rs/leptos/blob/main/examples/stores/src/lib.rs) ในคลังโค้ดเพื่อศึกษาตัวอย่างการใช้งานที่ครอบคลุมยิ่งขึ้น
