# การปรับขนาดไบนารี WASM ให้เหมาะสม

ไบนารี WebAssembly มีขนาดใหญ่กว่าบันเดิล JavaScript ที่คุณคาดว่าจะเจอสำหรับแอปพลิเคชันที่เทียบเท่ากันอย่างมีนัยสำคัญ เนื่องจากรูปแบบ WASM ถูกออกแบบมาสำหรับการคอมไพล์แบบสตรีม ไฟล์ WASM จึงคอมไพล์ได้เร็วกว่าไฟล์ JavaScript ต่อกิโลไบต์มาก (หากอยากเจาะลึก คุณสามารถ[อ่านบทความที่ยอดเยี่ยมนี้จากทีม Mozilla](https://hacks.mozilla.org/2018/01/making-webassembly-even-faster-firefoxs-new-streaming-and-tiering-compiler/) เกี่ยวกับการคอมไพล์ WASM แบบสตรีมได้) อย่างไรก็ตาม สิ่งสำคัญคือการส่งไบนารี WASM ที่เล็กที่สุดเท่าที่คุณจะทำได้ให้ผู้ใช้ เพราะมันจะลดการใช้เครือข่ายและทำให้แอปของคุณโต้ตอบได้เร็วที่สุด

แล้วมีขั้นตอนปฏิบัติอะไรบ้างล่ะ?

## สิ่งที่ควรทำ

1. ตรวจสอบให้แน่ใจว่าคุณกำลังดูบิลด์ release อยู่ (บิลด์ดีบักมีขนาดใหญ่กว่ามากๆ)
2. เพิ่มโปรไฟล์ release สำหรับ WASM ที่ปรับให้เหมาะกับขนาด ไม่ใช่ความเร็ว

ตัวอย่างเช่น สำหรับโปรเจกต์ `cargo-leptos` คุณสามารถเพิ่มสิ่งนี้ลงใน `Cargo.toml` ของคุณได้:

```toml
[profile.wasm-release]
inherits = "release"
opt-level = 'z'
lto = true
codegen-units = 1

# ....

[package.metadata.leptos]
# ....
lib-profile-release = "wasm-release"
```

วิธีนี้จะปรับแต่ง WASM สำหรับบิลด์ release ของคุณให้เหมาะกับขนาดอย่างสูงสุด ในขณะที่ยังคงให้บิลด์เซิร์ฟเวอร์ของคุณเหมาะสมกับความเร็ว (สำหรับแอปที่เรนเดอร์ฝั่งไคลเอนต์ล้วนๆ โดยไม่มีข้อคำนึงถึงเซิร์ฟเวอร์ เพียงใช้บล็อก `[profile.wasm-release]` เป็น `[profile.release]` ของคุณ)

3. ให้บริการ WASM แบบบีบอัดในโปรดักชันเสมอ WASM มักบีบอัดได้ดีมาก โดยทั่วไปแล้วลดลงเหลือน้อยกว่า 50% ของขนาดที่ไม่บีบอัด และการเปิดใช้การบีบอัดสำหรับไฟล์สแตติกที่ให้บริการจาก Actix หรือ Axum นั้นเป็นเรื่องง่ายมาก

4. หากคุณใช้ nightly Rust คุณสามารถบิลด์สแตนดาร์ดไลบรารีใหม่ด้วยโปรไฟล์เดียวกันนี้ แทนที่จะใช้สแตนดาร์ดไลบรารีที่บิลด์ไว้ล่วงหน้าซึ่งแจกจ่ายมากับเป้าหมาย `wasm32-unknown-unknown`

เมื่อต้องการทำเช่นนี้ ให้สร้างไฟล์ในโปรเจกต์ของคุณที่ `.cargo/config.toml`

```toml
[unstable]
build-std = ["std", "panic_abort", "core", "alloc"]
build-std-features = ["panic_immediate_abort"]
```

โปรดทราบว่าหากคุณใช้สิ่งนี้กับ SSR ด้วย โปรไฟล์ Cargo เดียวกันก็จะถูกนำไปใช้ด้วย คุณจะต้องระบุเป้าหมายของคุณอย่างชัดเจน:
```toml
[build]
target = "x86_64-unknown-linux-gnu" # or whatever
```

โปรดทราบเช่นกันว่าในบางกรณี ฟีเจอร์ cfg `has_std` จะไม่ถูกตั้งค่า ซึ่งอาจทำให้เกิดข้อผิดพลาดในการบิลด์กับบางดีเพนเดนซีที่ตรวจสอบ `has_std` คุณสามารถแก้ข้อผิดพลาดในการบิลด์ที่เกิดจากเรื่องนี้ได้โดยเพิ่ม:
```toml
[build]
rustflags = ["--cfg=has_std"]
```

และคุณจะต้องเพิ่ม `panic = "abort"` ลงใน `[profile.release]` ใน `Cargo.toml` โปรดทราบว่าวิธีนี้จะนำการตั้งค่า `build-std` และ panic เดียวกันไปใช้กับไบนารีเซิร์ฟเวอร์ของคุณด้วย ซึ่งอาจไม่ใช่สิ่งที่ต้องการ ตรงนี้น่าจะต้องศึกษากันเพิ่มเติม

5. สาเหตุหนึ่งที่ทำให้ไบนารี WASM มีขนาดใหญ่ขึ้นอาจมาจากโค้ดซีเรียลไลเซชัน/ดีซีเรียลไลเซชันของ `serde` โดยค่าเริ่มต้น Leptos ใช้ `serde` ในการซีเรียลไลซ์และดีซีเรียลไลซ์รีซอร์สที่สร้างด้วย `Resource::new()` `leptos_server` มีฟีเจอร์เพิ่มเติมสำหรับเปิดใช้การเข้ารหัสทางเลือก โดยเพิ่มเมธอด `new_` เพิ่มเติม ตัวอย่างเช่น การเปิดใช้ฟีเจอร์ `miniserde` บนครีต `leptos_server` จะเพิ่มเมธอด `Resource::new_miniserde()` และฟีเจอร์ `serde-lite` จะเพิ่ม `new_serde_lite` `miniserde` และ `serde-lite` อิมพลีเมนต์เพียงส่วนย่อยของฟังก์ชันการทำงานของ `serde` แต่โดยทั่วไปจะปรับให้เหมาะกับขนาดไบนารีมากกว่าความเร็ว

## สิ่งที่ควรหลีกเลี่ยง

มีครีตบางตัวที่มักทำให้ขนาดไบนารีบวมขึ้น ตัวอย่างเช่น ครีต `regex` พร้อมฟีเจอร์เริ่มต้นของมันเพิ่มขนาดไบนารี WASM ประมาณ 500kb (ส่วนใหญ่เป็นเพราะมันต้องดึงข้อมูลตาราง Unicode เข้ามา!) ในสภาพแวดล้อมที่คำนึงถึงขนาด คุณอาจพิจารณาหลีกเลี่ยง regex โดยทั่วไป หรือแม้กระทั่งเรียกใช้ API ของเบราว์เซอร์เพื่อใช้เอนจิน regex ที่มีในตัวแทน (นี่คือสิ่งที่ `leptos_router` ทำในไม่กี่ครั้งที่มันต้องการนิพจน์ปรกติ)

โดยทั่วไปแล้ว ความมุ่งมั่นของ Rust ต่อประสิทธิภาพขณะรันไทม์บางครั้งขัดแย้งกับความมุ่งมั่นที่จะมีไบนารีขนาดเล็ก ตัวอย่างเช่น Rust ทำ monomorphization กับฟังก์ชันเจเนอริก ซึ่งหมายความว่ามันสร้างสำเนาของฟังก์ชันแยกต่างหากสำหรับแต่ละชนิดเจเนอริกที่เรียกใช้ วิธีนี้เร็วกว่าการดิสแพตช์แบบไดนามิกอย่างมีนัยสำคัญ แต่ก็เพิ่มขนาดไบนารี Leptos พยายามรักษาสมดุลระหว่างประสิทธิภาพขณะรันไทม์กับข้อคำนึงถึงขนาดไบนารีอย่างระมัดระวังทีเดียว แต่คุณอาจพบว่าโค้ดที่ใช้เจเนอริกจำนวนมากมักเพิ่มขนาดไบนารี ตัวอย่างเช่น หากคุณมีคอมโพเนนต์แบบเจเนอริกที่มีโค้ดในบอดีจำนวนมากและเรียกใช้กับชนิดข้อมูลที่แตกต่างกันสี่ชนิด อย่าลืมว่าคอมไพเลอร์อาจใส่สำเนาโค้ดเดียวกันนั้นถึงสี่ชุด การรีแฟกเตอร์ให้ใช้ฟังก์ชันภายในหรือเฮลเปอร์ที่เป็นชนิดรูปธรรมมักรักษาประสิทธิภาพและความสะดวกในการใช้งานไว้ได้ พร้อมกับลดขนาดไบนารี

## การแยกโค้ด (Code Splitting)

`cargo-leptos` รวมถึงเฟรมเวิร์กและเราเตอร์ของ Leptos มีการรองรับการแยกไบนารี WASM (โปรดทราบว่าการรองรับนี้เปิดตัวในช่วงฤดูร้อนปี 2025; ขึ้นอยู่กับว่าคุณอ่านสิ่งนี้เมื่อไร เราอาจยังคงแก้บั๊กกันอยู่ก็ได้)

คุณสามารถใช้สิ่งนี้ได้ผ่านการผสมผสานของเครื่องมือสามอย่าง: `cargo leptos (serve|watch|build) --split`, มาโคร [`#[lazy]`](https://docs.rs/leptos/latest/leptos/attr.lazy.html) และมาโคร [`#[lazy_route]`](https://docs.rs/leptos_router/latest/leptos_router/attr.lazy_route.html) (คู่กับแทรต [`LazyRoute`](https://docs.rs/leptos_router/latest/leptos_router/trait.LazyRoute.html))

### `#[lazy]`

มาโคร `#[lazy]` บ่งชี้ว่าฟังก์ชันหนึ่งสามารถโหลดแบบเลซี (lazy-loaded) จากไบนารี WebAssembly (WASM) แยกต่างหากได้ มันใช้แอนโนเทตฟังก์ชันแบบซิงโครนัสหรือแบบอะซิงก์ก็ได้ ในทั้งสองกรณี มันจะสร้างฟังก์ชันแบบอะซิงก์ออกมา ครั้งแรกที่คุณเรียกฟังก์ชันที่โหลดแบบเลซี โค้ดส่วนแยกนั้นจะถูกโหลดจากเซิร์ฟเวอร์และถูกเรียก หลังจากนั้น มันจะถูกเรียกโดยไม่มีขั้นตอนการโหลดเพิ่มเติม

```rust
#[lazy]
fn lazy_synchronous_function() -> String {
    "Hello, lazy world!".to_string()
}

#[lazy]
async fn lazy_async_function() -> String {
    /* do something that requires async work */
    "Hello, lazy async world!".to_string()
}

async fn use_lazy_functions() {
    // synchronous function has been converted to async
    let value1 = lazy_synchronous_function().await;

    // async function is still async
    let value1 = lazy_async_function().await;
}
```

สิ่งนี้มีประโยชน์สำหรับฟังก์ชันเลซีแบบครั้งเดียว แต่การโหลดแบบเลซีจะทรงพลังที่สุดเมื่อจับคู่กับเราเตอร์

### `#[lazy_route]`

เส้นทางแบบเลซีช่วยให้คุณแยกโค้ดสำหรับวิวของเส้นทางออกมา และโหลดแบบเลซีพร้อมกับข้อมูลสำหรับเส้นทางนั้นขณะนำทางได้ ผ่านการใช้การจัดเส้นทางแบบซ้อน เส้นทางแบบเลซีหลายเส้นทางสามารถซ้อนกันได้ โดยแต่ละเส้นทางจะโหลดข้อมูลของตัวเองและวิวแบบเลซีของตัวเองพร้อมกัน

การแยกการโหลดข้อมูลออกจากวิว (ที่โหลดแบบเลซี) ช่วยให้คุณป้องกัน “waterfall” ซึ่งเป็นการรอให้วิวแบบเลซีโหลดเสร็จก่อน แล้วจึงเริ่มโหลดข้อมูล

```rust
use leptos::prelude::*;
use leptos_router::{lazy_route, LazyRoute};

// the route definition
#[derive(Debug)]
struct BlogListingRoute {
    titles: Resource<Vec<String>>
}

#[lazy_route]
impl LazyRoute for BlogListingRoute {
    fn data() -> Self {
        Self {
            titles: Resource::new(|| (), |_| async {
                vec![/* todo: load blog posts */]
            })
        }
    }

    // this function will be lazy-loaded, concurrently with data()
    fn view(this: Self) -> AnyView {
        let BlogListingRoute { titles } = this;

        // ... now you can use the `posts` resource with Suspense, etc.,
        // and return AnyView by calling .into_any() on a view
    }
}
```
