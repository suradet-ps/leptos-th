# ภาคผนวก: วงจรชีวิตของสัญญาณ

มีคำถามสามข้อที่นักพัฒนามักจะพบเจอเมื่อก้าวเข้าสู่ระดับกลางของการใช้งาน Leptos:
1. เราจะเข้าถึง lifecycle ของคอมโพเนนต์เพื่อสั่งรันโค้ดเมื่อคอมโพเนนต์ถูก mount หรือ unmount ได้อย่างไร?
2. เราจะรู้ได้อย่างไรว่า signal จะถูกทำลาย (disposed) เมื่อใด และทำไมบางครั้งถึงเกิด panic เมื่อพยายามเข้าถึง signal ที่ถูกทำลายไปแล้ว?
3. เป็นไปได้อย่างไรที่ signal เป็นชนิดข้อมูลแบบ `Copy` และสามารถย้าย (move) เข้าไปใน closure หรือโครงสร้างอื่น ๆ ได้โดยไม่ต้องสั่ง clone ให้ยุ่งยาก?

คำตอบของคำถามทั้งสามข้อนี้มีความเชื่อมโยงกันอย่างแนบแน่น และแต่ละข้อต่างก็มีรายละเอียดที่ซับซ้อน ภาคผนวกนี้จะช่วยปูบริบทและอธิบายเบื้องหลัง เพื่อให้คุณสามารถวิเคราะห์และทำความเข้าใจพฤติกรรมการทำงานของโค้ดในแอปพลิเคชันของคุณได้อย่างถูกต้องแม่นยำ

## ต้นไม้คอมโพเนนต์กับต้นไม้การตัดสินใจ

ลองพิจารณาโค้ดแอป Leptos แบบเรียบง่ายต่อไปนี้:

```rust
use leptos::logging::log;
use leptos::prelude::*;

#[component]
pub fn App() -> impl IntoView {
    let (count, set_count) = signal(0);

    view! {
        <button on:click=move |_| *set_count.write() += 1>"+1"</button>
        {move || if count.get() % 2 == 0 {
            view! { <p>"Even numbers are fine."</p> }.into_any()
        } else {
            view! { <InnerComponent count/> }.into_any()
        }}
    }
}

#[component]
pub fn InnerComponent(count: ReadSignal<usize>) -> impl IntoView {
    Effect::new(move |_| {
        log!("count is odd and is {}", count.get());
    });

    view! {
        <OddDuck/>
        <p>{count}</p>
    }
}

#[component]
pub fn OddDuck() -> impl IntoView {
    view! {
        <p>"You're an odd duck."</p>
    }
}
```

โค้ดนี้เพียงแค่แสดงปุ่มตัวนับ โดยจะแสดงข้อความหนึ่งหากตัวเลขเป็นเลขคู่ และแสดงอีกข้อความหนึ่งหากเป็นเลขคี่ ซึ่งหากเป็นเลขคี่ ก็จะพิมพ์ล็อกค่าตัวนับลงคอนโซลด้วย

วิธีหนึ่งในการทำแผนผังจำลองแอปพลิเคชันง่าย ๆ นี้ คือการวาดเป็นแผนภูมิต้นไม้ของคอมโพเนนต์ที่ซ้อนกัน:
```
App 
|_ InnerComponent
   |_ OddDuck
```

อีกวิธีหนึ่งคือการวาดเป็นแผนภูมิต้นไม้ของจุดตัดสินใจ:
```
root
|_ is count even?
   |_ yes
   |_ no
```

หากคุณนำทั้งสองภาพมารวมเข้าด้วยกัน คุณจะสังเกตเห็นว่าพวกมันไม่ได้ซ้อนทับกันอย่างลงตัว ต้นไม้การตัดสินใจได้ตัดแบ่ง view ที่เราสร้างขึ้นใน `InnerComponent` ออกเป็นสามส่วน และยุบรวมส่วนหนึ่งของ `InnerComponent` เข้ากับคอมโพเนนต์ `OddDuck`:
```
DECISION            COMPONENT           DATA    SIDE EFFECTS
root                <App/>              (count) render <button>
|_ is count even?   <InnerComponent/>
   |_ yes                                       render even <p>
   |_ no                                        start logging the count 
                    <OddDuck/>                  render odd <p> 
                                                render odd <p> (in <InnerComponent/>!)
```

เมื่อพิจารณาจากตารางนี้ จะพบข้อสังเกตสำคัญดังนี้:
1. ต้นไม้คอมโพเนนต์และต้นไม้การตัดสินใจไม่ได้สอดคล้องกัน: จุดตัดสินใจ "count เป็นเลขคู่หรือไม่?" ได้แบ่ง `<InnerComponent/>` ออกเป็นสามส่วน (ส่วนที่ไม่เคยเปลี่ยน, ส่วนที่เป็นเลขคู่, และส่วนที่เป็นเลขคี่) และยังควบรวมบางส่วนเข้ากับคอมโพเนนต์ `<OddDuck/>`
2. ต้นไม้การตัดสินใจกับรายการ side effect มีความสอดคล้องกันอย่างสมบูรณ์แบบ: side effect แต่ละตัวจะถูกสร้างขึ้น ณ จุดตัดสินใจที่เจาะจง
3. ต้นไม้การตัดสินใจกับโครงสร้างของข้อมูลก็สอดคล้องกันเช่นกัน: ในตารางที่มีเพียง signal ตัวเดียวอาจมองเห็นไม่ชัด แต่สิ่งที่ต่างจากคอมโพเนนต์ (ซึ่งเป็นเพียงฟังก์ชันที่อาจมีหรือไม่มีจุดตัดสินใจเลยก็ได้) คือ signal จะถูกสร้างขึ้นที่ตำแหน่งเฉพาะเจาะจงบนต้นไม้การตัดสินใจเสมอ

ใจความสำคัญคือ: โครงสร้างของข้อมูลและโครงสร้างของ side effect ต่างหากที่เป็นตัวกำหนดพฤติกรรมการทำงานจริงของแอปพลิเคชัน ส่วนโครงสร้างของคอมโพเนนต์เป็นเพียงความสะดวกในการจัดระเบียบโค้ดเท่านั้น คุณไม่จำเป็นต้องสนใจ (และไม่ควรต้องใส่ใจ) ว่าคอมโพเนนต์ไหนเป็นตัวเรนเดอร์แท็ก `<p>` ตัวใด หรือคอมโพเนนต์ไหนเป็นผู้สร้าง effect เพื่อบันทึกค่า สิ่งสำคัญคือการกระทำเหล่านั้นเกิดขึ้นในจังหวะเวลาที่ถูกต้องหรือไม่

ใน Leptos *คอมโพเนนต์ไม่มีตัวตนอยู่จริงตอนรันไทม์* กล่าวคือ คุณสามารถเขียนแอปพลิเคชันในรูปแบบของต้นไม้คอมโพเนนต์ได้เพราะมันสะดวกในการพัฒนา และเราก็มีเครื่องมือดีบักและ logging ที่สร้างขึ้นมารองรับคอมโพเนนต์เพราะความสะดวกเช่นกัน แต่คอมโพเนนต์ไม่ได้คงอยู่ขณะที่โปรแกรมทำงาน: คอมโพเนนต์ไม่ใช่หน่วยของการตรวจจับการเปลี่ยนแปลง (change detection) หรือหน่วยของการเรนเดอร์ หากแต่เป็นเพียงการเรียกใช้ฟังก์ชันธรรมดา คุณจะเขียนโค้ดทั้งแอปไว้ในคอมโพเนนต์เดียว หรือจะแยกย่อยเป็นร้อยคอมโพเนนต์ พฤติกรรมตอนรันไทม์ก็แทบไม่แตกต่างกันเลย เพราะตัวคอมโพเนนต์ไม่ได้มีตัวตนอยู่จริง

ในทางกลับกัน ต้นไม้การตัดสินใจ (Decision Tree) ต่างหากที่มีตัวตนอยู่จริงและมีความสำคัญอย่างยิ่งยวด!

## ต้นไม้การตัดสินใจ การเรนเดอร์ และความเป็นเจ้าของ

ทุกจุดตัดสินใจล้วนเป็นนิพจน์แบบ reactive: อาจเป็น signal หรือฟังก์ชันที่ค่าเปลี่ยนแปลงไปตามกาลเวลา เมื่อคุณส่ง signal หรือฟังก์ชันเข้าไปยัง renderer ตัว renderer จะห่อหุ้มสิ่งนั้นด้วย effect โดยอัตโนมัติ ซึ่งจะคอยติดตาม signal ใด ๆ ที่ถูกเรียกใช้ภายใน และคอยอัปเดต view ให้สอดคล้องกัน

นั่นหมายความว่า เมื่อแอปพลิเคชันถูกเรนเดอร์ ระบบจะสร้างต้นไม้ของ effect ที่ซ้อนกันเป็นชั้น ๆ ซึ่งถอดแบบมาจากต้นไม้การตัดสินใจอย่างแม่นยำ ดังแสดงในโค้ดจำลอง (pseudo-code) ต่อไปนี้:
```rust
// root
let button = /* render the <button> once */;

// the renderer wraps an effect around the `move || if count() ...`
Effect::new(|_| {
    if count.get() % 2 == 0 {
        let p = /* render the even <p> */;
    } else {
        // the user created an effect to log the count
        Effect::new(|_| {
            log!("count is odd and is {}", count.get());
        });

        let p1 = /* render the <p> from OddDuck */;
        let p2 = /* render the second <p> */ 

        // the renderer creates an effect to update the second <p>
        Effect::new(|_| {
            // update the content of the <p> with the signal
            p2.set_text_content(count.get());
        });
    }
})
```

ค่าที่เป็น reactive แต่ละตัวจะถูกครอบด้วย effect ของตัวเองเพื่อคอยอัปเดต DOM หรือรัน side effect เมื่อ signal เปลี่ยนแปลง แต่คุณคงไม่ต้องการให้ effect เหล่านี้ทำงานค้างอยู่ตลอดไป ตัวอย่างเช่น เมื่อ `count` สลับจากเลขคี่กลับมาเป็นเลขคู่ แท็ก `<p>` ตัวที่สองจะหายไปจาก DOM แล้ว effect ที่คอยอัปเดตข้อความในแท็กนั้นจึงไม่มีประโยชน์อีกต่อไป แทนที่จะปล่อยให้รันอยู่ตลอดกาล effect เหล่านี้จะถูกยกเลิก (cancel) เมื่อจุดตัดสินใจที่เป็นผู้ให้กำเนิดมันมีการเปลี่ยนแปลง หรือกล่าวให้ชัดเจนยิ่งขึ้น: **effect จะถูกยกเลิกทุกครั้งที่ effect แม่ (parent effect) ที่ครอบมันอยู่ถูกสั่งรันใหม่** หาก effect ลูกถูกสร้างอยู่ภายใต้เงื่อนไขสาขาใดสาขาหนึ่ง แล้วการรันใหม่ของ effect แม่ยังคงตกลงในเงื่อนไขเดิม effect ลูกก็จะถูกสร้างขึ้นใหม่ แต่หากตกในเงื่อนไขอื่น effect ลูกเดิมก็จะถูกยกเลิกไปโดยไม่สร้างซ้ำ

หากมองจากมุมมองของระบบ reactive “ต้นไม้การตัดสินใจ” ของแอปพลิเคชันก็คือ “ต้นไม้ความเป็นเจ้าของ” (Reactive Ownership Tree) นั่นเอง อธิบายง่าย ๆ คือ “เจ้าของ” (Owner) ในระบบ reactive ก็คือ effect หรือ memo ที่กำลังทำงานอยู่ในขณะนั้น โดยมันจะเป็นเจ้าของ effect ย่อยที่ถูกสร้างขึ้นภายในตัวมัน และ effect ย่อยเหล่านั้นก็จะเป็นเจ้าของลูกหลานในชั้นถัดไปเรื่อย ๆ เมื่อ effect ใดกำลังจะถูกรันใหม่ มันจะทำหน้าที่ “ล้างข้อมูล” (clean up) โหนดลูก ๆ ของมันทิ้งก่อน แล้วจึงค่อยเริ่มทำงานรอบใหม่

จนถึงจุดนี้ โมเดลความเป็นเจ้าของดังกล่าวเป็นรูปแบบเดียวกับที่ใช้ในเฟรมเวิร์ก JavaScript อย่าง S.js หรือ Solid ซึ่งมีแนวคิดเรื่อง ownership ไว้เพื่อยกเลิก effect โดยอัตโนมัติ

ทว่าสิ่งที่ Leptos ต่อยอดเพิ่มเติม คือการให้ความหมายที่สองแก่ความเป็นเจ้าของ: ตัว owner ในระบบ reactive ไม่เพียงเป็นเจ้าของ effect ย่อยเพื่อยกเลิกพวกมันเท่านั้น แต่ยังเป็นเจ้าของ signal (รวมถึง memo ฯลฯ) เพื่อคอยทำลายทิ้ง (dispose) จากหน่วยความจำเมื่อไม่ใช้งานแล้วด้วย

## ความเป็นเจ้าของและอารีนาของ `Copy`

นี่คือนวัตกรรมสำคัญที่ทำให้ Leptos สามารถใช้งานเป็น UI framework บน Rust ได้อย่างมีประสิทธิภาพ เพราะโดยธรรมเนียมดั้งเดิมแล้ว การจัดการสถานะ UI ใน Rust เป็นเรื่องที่ท้าทายมาก เนื่องจาก UI เป็นเรื่องของ shared mutability (เพียงแค่ปุ่มนับเลขง่าย ๆ ปุ่มเดียวก็เห็นปัญหาแล้ว: คุณต้องการ immutable reference เพื่อแสดงผลค่าตัวเลขใน text node และต้องการ mutable reference ใน event handler เพื่อปรับค่าตัวนับ ซึ่ง UI framework ในภาษา Rust ทุกตัวต้องรับมือกับความจริงที่ว่า ระบบ Type และ Ownership ของ Rust ถูกออกแบบมาเพื่อป้องกันพฤติกรรมนี้โดยเฉพาะ!) ในอดีต การเขียน event handler ใน Rust มักต้องพึ่งพาพรีมิทีฟสำหรับการแชร์หน่วยความจำพร้อม interior mutability (`Rc<RefCell<_>>`, `Arc<Mutex<_>>`) หรือผ่านทาง channel ซึ่งทั้งสองวิธีมักบังคับให้ต้องเขียน `.clone()` ซ้ำ ๆ เพื่อส่งค่าเข้าไปใน event listener แม้จะทำงานได้แต่ก็สร้างความยุ่งยากอย่างยิ่ง

Leptos จึงเลือกใช้รูปแบบการจัดสรรหน่วยความจำแบบ arena allocation สำหรับ signal โดยตัว signal แท้จริงแล้วเป็นเพียงดัชนี (index) ที่ชี้ไปยังโครงสร้างข้อมูลที่ถูกจัดเก็บไว้ใน arena ส่วนกลาง มันจึงเป็นชนิดข้อมูลจำนวนเต็ม (integer) ที่มีต้นทุนการคัดลอกต่ำมาก และไม่ได้ทำการนับ reference counting ภายในตัว ทำให้สามารถคัดลอกไปมาและย้ายเข้าไปใน event listener ได้ทันทีโดยไม่ต้องสั่ง clone ให้วุ่นวาย

วงจรชีวิต (lifecycle) ของ signal เหล่านี้จึงไม่ได้ถูกผูกติดกับ Rust lifetime หรือ reference counting แต่ถูกควบคุมผ่านต้นไม้ความเป็นเจ้าของ (Ownership Tree)

เช่นเดียวกับที่ effect ย่อยทั้งหมดเป็นของ effect แม่ และจะถูกยกเลิกเมื่อ effect แม่รันใหม่ signal ทั้งหมดก็มี owner เป็นเจ้าของ และจะถูกทำลายทิ้ง (disposed) เมื่อ owner แม่ของมันถูกรันใหม่เช่นกัน

ในกรณีส่วนใหญ่ กลไกนี้ทำงานได้อย่างสมบูรณ์แบบ ลองจินตนาการว่าในตัวอย่างข้างต้น `<OddDuck/>` มีการสร้าง signal อื่นเพื่ออัปเดต UI ภายในของตัวเอง signal ดังกล่าวจะถูกใช้เป็น local state ภายในคอมโพเนนต์นั้น หรือถูกส่งต่อไปยังคอมโพเนนต์ลูก ซึ่งแทบจะไม่มีกรณีที่ signal นั้นจะถูกยกข้ามต้นไม้การตัดสินใจไปใช้งานในส่วนอื่นของแอปพลิเคชัน และเมื่อ `count` สลับกลับมาเป็นเลขคู่ ตัว `<OddDuck/>` ก็ไม่จำเป็นต้องมีอยู่อีกต่อไป signal นั้นจึงสามารถถูกทำลายทิ้งได้อย่างปลอดภัย

อย่างไรก็ตาม การทำงานเช่นนี้อาจนำไปสู่ปัญหาได้ 2 ประการ:

### สัญญาณสามารถถูกใช้หลังจากการทิ้งได้

ตัวแปร `ReadSignal` หรือ `WriteSignal` ที่คุณถืออยู่ เป็นเพียงตัวเลขจำนวนเต็ม (เช่น เลข 3 หากเป็น signal ตัวที่ 3 ของระบบ) คุณสามารถคัดลอกตัวเลขนั้นส่งต่อไปยังที่ใดก็ได้ และนำไปสั่งว่า "ขอดูค่าของ signal ตัวที่ 3 หน่อย" เมื่อ owner ทำการ clean up *ค่าจริง* ของ signal ตัวที่ 3 ใน arena จะถูกทำลายไป แต่ตัวเลข 3 ที่ถูกก็อปปี้กระจายออกไปจะไม่สามารถถูกยกเลิกตามได้ (เว้นแต่จะมีระบบ Garbage Collector ทั้งระบบ) นั่นหมายความว่า หากคุณส่ง signal ย้อนกลับ "ขึ้นไป" บนต้นไม้การตัดสินใจ และเก็บไว้ในขอบเขตที่ "สูงกว่า" จุดที่มันถูกสร้างขึ้น signal นั้นก็อาจถูกเรียกใช้งานหลังจากที่มันถูกทำลายไปแล้ว

หากคุณพยายาม *อัปเดต* signal หลังจากที่มันถูกทำลายไปแล้ว จะไม่มีข้อผิดพลาดร้ายแรงเกิดขึ้น โดยเฟรมเวิร์กจะเพียงแจ้งเตือนว่าคุณกำลังพยายามอัปเดต signal ที่ไม่มีอยู่อีกต่อไป แต่หากคุณพยายาม *อ่านค่า* (access) จากมัน ระบบจะไม่มีคำตอบอื่นใดนอกจากทำให้เกิด panic เนื่องจากไม่มีค่าหลงเหลือให้ส่งคืนแล้ว (ทั้งนี้ Leptos มีเมธอดตระกูล `try_` เช่น `try_get()` และ `try_with()` ที่จะคืนค่า `None` อย่างปลอดภัยแทนการ panic หาก signal นั้นถูกทำลายไปแล้ว)

### สัญญาณอาจรั่วได้ถ้าคุณสร้างมันในสโคปที่สูงกว่าและไม่ทิ้งมันเลย

ในทางกลับกัน ปัญหานี้มักเกิดขึ้นเมื่อทำงานกับคอลเลกชันของ signal เช่น `RwSignal<Vec<RwSignal<_>>>` หากคุณสร้าง signal ไว้ที่ระดับบน แล้วส่งต่อลงไปให้คอมโพเนนต์ระดับล่าง signal นั้นจะไม่ถูกทำลายจนกว่า owner ระดับบนจะถูก clean up

ตัวอย่างเช่น หากคุณทำแอป To-Do List ที่สร้าง `RwSignal<Todo>` ใหม่สำหรับแต่ละรายการ เก็บไว้ใน `RwSignal<Vec<RwSignal<Todo>>>` แล้วส่งลงไปให้ `<Todo/>` เมื่อคุณลบรายการออกจากลิสต์ ตัว signal ของรายการนั้นจะไม่ถูกทำลายโดยอัตโนมัติ แต่คุณจำเป็นต้องสั่งทำลายทิ้งด้วยตนเอง มิฉะนั้น signal นั้นจะ "รั่วไหล" (leak) ค้างอยู่ในหน่วยความจำตราบเท่าที่ owner ตัวบนยังมีชีวิตอยู่ (สามารถดู [ตัวอย่าง TodoMVC](https://github.com/leptos-rs/leptos/blob/main/examples/todomvc/src/lib.rs#L77-L85) เพื่อศึกษาเพิ่มเติม)

ปัญหานี้จะเกิดขึ้นเฉพาะเมื่อคุณสร้าง signal แล้วเก็บไว้ในคอลเลกชัน จากนั้นนำมันออกจากคอลเลกชันโดยไม่ได้สั่งทำลายทิ้งควบคู่กันไปด้วย

### การแก้ปัญหาเหล่านี้ด้วย Reference-Counted Signals

ใน Leptos 0.7 ได้เปิดตัว signal แบบนับจำนวนการอ้างอิง (reference-counted) ควบคู่กับ primitive แบบเดิมที่จัดสรรบน arena: สำหรับทุก `RwSignal` จะมี `ArcRwSignal` มาคู่กันเสมอ (`ArcReadSignal`, `ArcWriteSignal`, `ArcMemo` ฯลฯ)

primitive เหล่านี้จะจัดการหน่วยความจำและการทำลายทิ้งผ่านระบบ reference counting แทนที่จะอาศัยต้นไม้ความเป็นเจ้าของ

นั่นหมายความว่า คุณสามารถนำมันไปใช้งานได้อย่างปลอดภัยในทุกสถานการณ์ที่ตัว arena-allocated อาจเสี่ยงต่อการเกิด memory leak หรือการถูกเรียกใช้หลัง dispose

สิ่งนี้มีประโยชน์อย่างยิ่งเมื่อต้องจัดการกับคอลเลกชันของ signal: คุณสามารถสร้าง `ArcRwSignal<_>` ขึ้นมาแทน `RwSignal<_>` แล้วค่อยแปลงเป็น `RwSignal<_>` ในแต่ละแถวของตารางข้อมูลได้ตามต้องการ

สามารถดูตัวอย่างการใช้งาน `ArcRwSignal<i32>` ได้จาก [ตัวอย่าง `counters`](https://github.com/leptos-rs/leptos/blob/main/examples/counters/src/lib.rs)

## เชื่อมโยงทุกประเด็นเข้าด้วยกัน

เมื่อเข้าใจกลไกทั้งหมดแล้ว คำตอบของคำถามสามข้อแรกที่เราตั้งไว้จึงชัดเจนขึ้น:

### วงจรชีวิตของคอมโพเนนต์ (Component Lifecycle)

แท้จริงแล้วไม่มีสิ่งที่เรียกว่า lifecycle ของคอมโพเนนต์ เพราะตัวคอมโพเนนต์ไม่ได้คงอยู่จริงตอนรันไทม์ แต่สิ่งที่มีอยู่จริงคือ lifecycle ของความเป็นเจ้าของ (ownership) ซึ่งคุณสามารถนำมาประยุกต์ใช้เพื่อจุดประสงค์เดียวกันได้:
- *ก่อน mount*: โค้ดใด ๆ ที่เขียนไว้ในบอดี้ของคอมโพเนนต์จะถูกรันทันที ซึ่งเทียบเท่ากับ "ก่อนที่คอมโพเนนต์จะ mount"
- *ตอน mount*: `Effect::new` จะรันหลังจากส่วนอื่น ๆ ของคอมโพเนนต์ถูกประมวลผลไปแล้วหนึ่งรอบ (tick) จึงเหมาะสำหรับ effect ที่จำเป็นต้องรอให้ view ถูก mount เข้ากับ DOM เรียบร้อยก่อน
- *ตอน unmount*: คุณสามารถใช้ `on_cleanup` เพื่อส่งโค้ดให้ระบบ reactive เรียกใช้งานในระหว่างที่ owner ปัจจุบันกำลัง clean up ตัวเอง และเนื่องจาก owner จะครอบอยู่รอบ ๆ จุดตัดสินใจ จึงทำให้ `on_cleanup` ถูกเรียกเมื่อคอมโพเนนต์ถูก unmount เสมอ: เพราะหากสิ่งใดสามารถ unmount ได้ ย่อมหมายความว่าตัว renderer ได้สร้าง effect ครอบเพื่อจัดการ unmount มันไว้อย่างแน่นอน!

### ปัญหาเกี่ยวกับ Signal ที่ถูกทำลาย (Disposed)

โดยทั่วไป ปัญหานี้จะเกิดขึ้นเฉพาะเมื่อคุณสร้าง signal ไว้ในตำแหน่งที่อยู่ลึกบนต้นไม้ความเป็นเจ้าของ แต่กลับนำไปจัดเก็บไว้ในขอบเขตที่อยู่สูงกว่า หากคุณพบปัญหานี้ วิธีแก้คือให้ "ยก" (hoist) การสร้าง signal นั้นขึ้นไปยังคอมโพเนนต์แม่ แล้วค่อยส่ง signal ที่สร้างแล้วลงมายังคอมโพเนนต์ลูก (และอย่าลืมสั่ง dispose ด้วยตนเองเมื่อนำออกจากรายการ หากจำเป็น!)

### Signal ที่เป็น `Copy`

ระบบ wrapper type ที่เป็น `Copy` ทั้งหมดของ Leptos (ทั้ง signal, `StoredValue` ฯลฯ) ใช้ต้นไม้ความเป็นเจ้าของในการจำลองวงจรชีวิตของ UI แต่ละส่วนได้อย่างใกล้ชิด ในทางปฏิบัติ มันเปรียบเสมือนการนำระบบ lifetime ของ Rust ที่อิงตามบล็อกโค้ด มาแปลงเป็นระบบ lifetime ที่อิงตามโครงสร้างของส่วนต่าง ๆ บนหน้า UI แม้ว่ากลไกนี้อาจไม่สามารถตรวจจับได้สมบูรณ์แบบ 100% ในขั้นตอนคอมไพล์ แต่ในภาพรวมแล้ว มันมอบผลลัพธ์และประสบการณ์การพัฒนาที่เป็นประโยชน์อย่างมหาศาล
