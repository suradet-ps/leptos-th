# ภาคผนวก: วงจรชีวิตของสัญญาณ

มีคำถามสามข้อที่มักเกิดขึ้นในระดับกลางเมื่อใช้ Leptos:
1. จะเชื่อมต่อกับวงจรชีวิตของคอมโพเนนต์ เพื่อรันโค้ดบางอย่างเมื่อคอมโพเนนต์เมานต์หรืออันเมานต์ได้อย่างไร?
2. จะรู้ได้อย่างไรว่าสัญญาณถูกทิ้งเมื่อไหร่ และทำไมบางครั้งจึงเจอแพนิกเมื่อพยายามเข้าถึงสัญญาณที่ถูกทิ้งไปแล้ว?
3. เป็นไปได้อย่างไรที่สัญญาณเป็น `Copy` และสามารถถูกมูฟเข้าไปในโคลเชอร์และโครงสร้างอื่นๆ ได้โดยไม่ต้องโคลนอย่างชัดเจน?

คำตอบของคำถามสามข้อนี้เชื่อมโยงกันอย่างใกล้ชิด และแต่ละข้อก็ค่อนข้างซับซ้อน ภาคผนวกนี้จะพยายามให้บริบทสำหรับการทำความเข้าใจคำตอบ เพื่อให้คุณให้เหตุผลเกี่ยวกับโค้ดของแอปพลิเคชันและวิธีการทำงานของมันได้อย่างถูกต้อง

## ต้นไม้คอมโพเนนต์กับต้นไม้การตัดสินใจ

พิจารณาแอป Leptos ง่ายๆ ต่อไปนี้:

```rust
use leptos::logging::log;
use leptos::prelude::*;

#[component]
pub fn App() -> impl IntoView {
    let (count, set_count) = signal(0);

    view! {
        <button on:click=move |_| *set_count.write() += 1>"+1"</button>
        {move || if count.get() % 2 == 0 {
            view! { <p>"Even numbers are fine."</p> }.into_any()
        } else {
            view! { <InnerComponent count/> }.into_any()
        }}
    }
}

#[component]
pub fn InnerComponent(count: ReadSignal<usize>) -> impl IntoView {
    Effect::new(move |_| {
        log!("count is odd and is {}", count.get());
    });

    view! {
        <OddDuck/>
        <p>{count}</p>
    }
}

#[component]
pub fn OddDuck() -> impl IntoView {
    view! {
        <p>"You're an odd duck."</p>
    }
}
```

มันแค่แสดงปุ่มตัวนับ แล้วก็ข้อความหนึ่งถ้าเป็นเลขคู่ และข้อความอีกแบบถ้าเป็นเลขคี่ ถ้าเป็นเลขคี่ มันยังบันทึกค่าลงคอนโซลด้วย

วิธีหนึ่งในการวางแผนผังแอปพลิเคชันง่ายๆ นี้คือการวาดต้นไม้ของคอมโพเนนต์ที่ซ้อนกัน:
```
App 
|_ InnerComponent
   |_ OddDuck
```

อีกวิธีหนึ่งคือการวาดต้นไม้ของจุดตัดสินใจ:
```
root
|_ is count even?
   |_ yes
   |_ no
```

ถ้าคุณรวมทั้งสองเข้าด้วยกัน คุณจะสังเกตว่าพวกมันไม่สอดคล้องกันอย่างสมบูรณ์ ต้นไม้การตัดสินใจแบ่งวิวที่เราสร้างขึ้นใน `InnerComponent` ออกเป็นสามส่วน และรวมส่วนหนึ่งของ `InnerComponent` เข้ากับคอมโพเนนต์ `OddDuck`:
```
DECISION            COMPONENT           DATA    SIDE EFFECTS
root                <App/>              (count) render <button>
|_ is count even?   <InnerComponent/>
   |_ yes                                       render even <p>
   |_ no                                        start logging the count 
                    <OddDuck/>                  render odd <p> 
                                                render odd <p> (in <InnerComponent/>!)
```

เมื่อดูตารางนี้ ผมสังเกตเห็นสิ่งต่อไปนี้:
1. ต้นไม้คอมโพเนนต์และต้นไม้การตัดสินใจไม่สอดคล้องกัน: การตัดสินใจ "นับเป็นเลขคู่หรือไม่?" แบ่ง `<InnerComponent/>` ออกเป็นสามส่วน (ส่วนที่ไม่เคยเปลี่ยน ส่วนที่เป็นเลขคู่ และส่วนที่เป็นเลขคี่) และรวมส่วนหนึ่งของมันเข้ากับคอมโพเนนต์ `<OddDuck/>` 
2. ต้นไม้การตัดสินใจและรายการผลข้างเคียงสอดคล้องกันอย่างสมบูรณ์: ผลข้างเคียงแต่ละอย่างถูกสร้างขึ้นที่จุดตัดสินใจที่เฉพาะเจาะจง
3. ต้นไม้การตัดสินใจและต้นไม้ข้อมูลก็สอดคล้องกันเช่นกัน ในตารางที่มีสัญญาณเพียงตัวเดียวอาจดูยาก แต่ต่างจากคอมโพเนนต์ซึ่งเป็นฟังก์ชันที่อาจมีการตัดสินใจหลายอย่างหรือไม่มีการตัดสินใจเลย สัญญาณจะถูกสร้างขึ้นที่บรรทัดที่เฉพาะเจาะจงในต้นไม้การตัดสินใจเสมอ

ประเด็นคือ โครงสร้างของข้อมูลและโครงสร้างของผลข้างเคียงส่งผลต่อฟังก์ชันการทำงานจริงของแอปพลิเคชันของคุณ โครงสร้างของคอมโพเนนต์เป็นเพียงความสะดวกในการเขียนโค้ดเท่านั้น คุณไม่สนใจ และไม่ควรสนใจ ว่าคอมโพเนนต์ใดเรนเดอร์แท็ก `<p>` ใด หรือคอมโพเนนต์ใดสร้างเอฟเฟกต์เพื่อบันทึกค่า สิ่งที่สำคัญคือมันเกิดขึ้นในเวลาที่เหมาะสม

ใน Leptos *คอมโพเนนต์ไม่ได้มีอยู่จริง* นั่นคือ คุณสามารถเขียนแอปพลิเคชันของคุณเป็นต้นไม้ของคอมโพเนนต์ได้ เพราะมันสะดวก และเรามีเครื่องมือดีบักและล็อกกิงที่สร้างขึ้นรอบคอมโพเนนต์ให้ด้วย เพราะมันสะดวกเช่นกัน แต่คอมโพเนนต์ของคุณไม่ได้มีอยู่ตอนรันไทม์: คอมโพเนนต์ไม่ใช่หน่วยของการตรวจจับการเปลี่ยนแปลงหรือของการเรนเดอร์ พวกมันเป็นเพียงการเรียกฟังก์ชัน คุณจะเขียนแอปทั้งหมดในคอมโพเนนต์เดียวหรือแยกเป็นร้อยคอมโพเนนต์ก็ได้ และมันไม่ส่งผลต่อพฤติกรรมตอนรันไทม์ เพราะคอมโพเนนต์ไม่ได้มีอยู่จริงๆ

ในทางกลับกัน ต้นไม้การตัดสินใจ *มีอยู่จริง* และมันสำคัญมาก!

## ต้นไม้การตัดสินใจ การเรนเดอร์ และความเป็นเจ้าของ

ทุกจุดตัดสินใจเป็นคำสั่งแบบรีแอกทีฟบางรูปแบบ: สัญญาณหรือฟังก์ชันที่เปลี่ยนไปตามเวลาได้ เมื่อคุณส่งสัญญาณหรือฟังก์ชันเข้าไปในเรนเดอเรอร์ มันจะห่อสิ่งนั้นด้วยเอฟเฟกต์ที่ติดตามสัญญาณใดๆ ที่อยู่ภายในโดยอัตโนมัติ และอัปเดตวิวตามเวลาที่เปลี่ยนไป

นั่นหมายความว่าเมื่อแอปพลิเคชันของคุณถูกเรนเดอร์ มันจะสร้างต้นไม้ของเอฟเฟกต์ที่ซ้อนกันซึ่งสะท้อนต้นไม้การตัดสินใจอย่างสมบูรณ์ ในรหัสเทียม:
```rust
// root
let button = /* render the <button> once */;

// the renderer wraps an effect around the `move || if count() ...`
Effect::new(|_| {
    if count.get() % 2 == 0 {
        let p = /* render the even <p> */;
    } else {
        // the user created an effect to log the count
        Effect::new(|_| {
            log!("count is odd and is {}", count.get());
        });

        let p1 = /* render the <p> from OddDuck */;
        let p2 = /* render the second <p> */ 

        // the renderer creates an effect to update the second <p>
        Effect::new(|_| {
            // update the content of the <p> with the signal
            p2.set_text_content(count.get());
        });
    }
})
```

ค่าที่เป็นรีแอกทีฟแต่ละตัวถูกห่อด้วยเอฟเฟกต์ของตัวเองเพื่ออัปเดต DOM หรือรันผลข้างเคียงอื่นๆ ของการเปลี่ยนแปลงสัญญาณ แต่คุณไม่จำเป็นต้องให้เอฟเฟกต์เหล่านี้รันตลอดไป ตัวอย่างเช่น เมื่อ `count` เปลี่ยนจากเลขคี่กลับเป็นเลขคู่ `<p>` ตัวที่สองไม่มีอยู่แล้ว เอฟเฟกต์ที่คอยอัปเดตมันจึงไม่มีประโยชน์อีกต่อไป แทนที่จะรันตลอดไป เอฟเฟกต์จะถูกยกเลิกเมื่อการตัดสินใจที่สร้างมันขึ้นมาเปลี่ยนไป กล่าวอีกนัยหนึ่ง และชัดเจนยิ่งขึ้น: เอฟเฟกต์จะถูกยกเลิกทุกครั้งที่เอฟเฟกต์ที่กำลังรันอยู่ตอนที่พวกมันถูกสร้างขึ้นรันใหม่ ถ้าพวกมันถูกสร้างในสาขาเงื่อนไข และการรันเอฟเฟกต์ใหม่ผ่านสาขาเดิม เอฟเฟกต์นั้นจะถูกสร้างขึ้นใหม่ ถ้าไม่ ก็จะไม่ถูกสร้าง

จากมุมมองของระบบรีแอกทีฟเอง “ต้นไม้การตัดสินใจ” ของแอปพลิเคชันของคุณก็คือ “ต้นไม้ความเป็นเจ้าของ” แบบรีแอกทีฟนั่นเอง พูดง่ายๆ “เจ้าของ” แบบรีแอกทีฟคือเอฟเฟกต์หรือเมโมที่กำลังรันอยู่ในขณะนั้น มันเป็นเจ้าของเอฟเฟกต์ที่ถูกสร้างขึ้นภายในมัน พวกเหล่านั้นก็เป็นเจ้าของลูกๆ ของตัวเองต่อไปเรื่อยๆ เมื่อเอฟเฟกต์กำลังจะรันใหม่ มันจะ “ทำความสะอาด” ลูกๆ ของมันก่อน แล้วจึงรันอีกครั้ง

จนถึงตอนนี้ โมเดลนี้เป็นโมเดลเดียวกับที่ระบบรีแอกทีฟใช้ในเฟรมเวิร์ก JavaScript อย่าง S.js หรือ Solid ซึ่งแนวคิดเรื่องความเป็นเจ้าของมีอยู่เพื่อยกเลิกเอฟเฟกต์โดยอัตโนมัติ

สิ่งที่ Leptos เพิ่มเข้ามาคือเราเพิ่มความหมายที่สองที่คล้ายกันให้กับความเป็นเจ้าของ: เจ้าของแบบรีแอกทีฟไม่เพียงเป็นเจ้าของเอฟเฟกต์ลูกๆ ของมันเพื่อที่จะยกเลิกพวกมันได้ แต่ยังเป็นเจ้าของสัญญาณ (เมโม ฯลฯ) ของมันด้วยเพื่อที่จะทิ้งพวกมันได้

## ความเป็นเจ้าของและอารีนาของ `Copy`

นี่คือวัตกรรมที่ทำให้ Leptos ใช้เป็นเฟรมเวิร์ก UI สำหรับ Rust ได้ ตามธรรมเนียมแล้ว การจัดการสถานะ UI ใน Rust เป็นเรื่องยาก เพราะ UI ล้วนเกี่ยวกับความสามารถในการกลายพันธุ์ร่วมกัน (ปุ่มตัวนับง่ายๆ ก็เพียงพอที่จะเห็นปัญหา: คุณต้องมีทั้งการเข้าถึงแบบไม่เปลี่ยนค่าเพื่อตั้งค่าโหนดข้อความที่แสดงค่าของตัวนับ และการเข้าถึงแบบเปลี่ยนค่าได้ในตัวจัดการเหตุการณ์คลิก และเฟรมเวิร์ก UI ของ Rust ทุกตัวก็ถูกออกแบบรอบข้อเท็จจริงที่ว่า Rust ถูกออกแบบมาเพื่อป้องกันสิ่งนั้นโดยเฉพาะ!) การใช้สิ่งอย่างตัวจัดการเหตุการณ์ใน Rust ตามธรรมเนียมอาศัยพรีมิทีฟสำหรับการสื่อสารผ่านหน่วยความจำร่วมด้วยการกลายพันธุ์ภายใน (`Rc<RefCell<_>>`, `Arc<Mutex<_>>`) หรือการสื่อสารผ่านแชนเนล ซึ่งทั้งสองแบบมักต้อง `.clone()` อย่างชัดเจนเพื่อมูฟเข้าไปในตัวรับฟังเหตุการณ์ นี่ก็พอใช้ได้ แต่ก็เป็นความไม่สะดวกมหาศาล

Leptos ใช้รูปแบบการจัดสรรแบบอารีนาสำหรับสัญญาณมาตลอดแทน สัญญาณหนึ่งตัวก็คือดัชนีเข้าไปในโครงสร้างข้อมูลที่ถูกเก็บไว้ที่อื่นโดยพื้นฐาน มันเป็นชนิดจำนวนเต็มที่คัดลอกได้ในราคาถูก และไม่ได้ทำการนับรีเฟอเรนซ์ด้วยตัวเอง ดังนั้นจึงสามารถถูกคัดลอกไปมา มูฟเข้าไปในตัวรับฟังเหตุการณ์ ฯลฯ ได้โดยไม่ต้องโคลนอย่างชัดเจน

แทนที่จะใช้ไลฟ์ไทม์ของ Rust หรือการนับรีเฟอเรนซ์ วงจรชีวิตของสัญญาณเหล่านี้ถูกกำหนดโดยต้นไม้ความเป็นเจ้าของ

เช่นเดียวกับที่เอฟเฟกต์ทั้งหมดเป็นของเอฟเฟกต์พาเรนต์ที่เป็นเจ้าของ และลูกๆ จะถูกยกเลิกเมื่อเจ้าของรันใหม่ สัญญาณทั้งหมดก็เป็นของเจ้าของเช่นกัน และจะถูกทิ้งเมื่อพาเรนต์รันใหม่

ในกรณีส่วนใหญ่ เรื่องนี้ไม่เป็นปัญหาเลย ลองนึกภาพว่าในตัวอย่างข้างต้น `<OddDuck/>` สร้างสัญญาณอื่นบางตัวที่มันใช้เพื่ออัปเดตส่วนหนึ่งของ UI ของตัวเอง ในกรณีส่วนใหญ่ สัญญาณนั้นจะถูกใช้สำหรับสถานะโลคอลในคอมโพเนนต์นั้น หรืออาจถูกส่งต่อเป็นพร็อพให้คอมโพเนนต์อื่น เป็นเรื่องผิดปกติที่มันจะถูกยกขึ้นออกจากต้นไม้การตัดสินใจและถูกใช้ที่อื่นในแอปพลิเคชัน เมื่อ `count` เปลี่ยนกลับเป็นเลขคู่ มันก็ไม่จำเป็นอีกต่อไปและสามารถถูกทิ้งได้

อย่างไรก็ตาม นั่นหมายความว่าอาจมีปัญหาที่เป็นไปได้สองประการเกิดขึ้น

### สัญญาณสามารถถูกใช้หลังจากการทิ้งได้

`ReadSignal` หรือ `WriteSignal` ที่คุณถืออยู่ก็แค่จำนวนเต็มตัวหนึ่ง เช่น 3 ถ้ามันเป็นสัญญาณตัวที่ 3 ในแอปพลิเคชัน (ตามเคย ความเป็นจริงซับซ้อนกว่านั้นเล็กน้อย แต่ไม่มาก) คุณสามารถคัดลอกตัวเลขนั้นไปทั่วทุกที่และใช้มันเพื่อพูดว่า "เฮ้ ขอสัญญาณตัวที่ 3 หน่อย" เมื่อเจ้าของทำความสะอาด *ค่า* ของสัญญาณตัวที่ 3 จะถูกทำให้ไม่ถูกต้อง แต่เลข 3 ที่คุณคัดลอกไปทั่วทุกที่นั้นไม่สามารถถูกทำให้ไม่ถูกต้องได้ (ไม่เว้นแต่จะมีตัวเก็บขยะทั้งระบบ!) นั่นหมายความว่าถ้าคุณผลักสัญญาณกลับ "ขึ้น" ไปตามต้นไม้การตัดสินใจ และเก็บมันไว้ที่ใดที่หนึ่งซึ่งตามแนวคิดแล้ว "สูงกว่า" ในแอปพลิเคชันของคุณกว่าตอนที่มันถูกสร้าง พวกมันสามารถถูกเข้าถึงได้หลังจากการทิ้งไปแล้ว

ถ้าคุณพยายาม *อัปเดต* สัญญาณหลังจากที่มันถูกทิ้งไปแล้ว ก็ไม่มีอะไรแย่ๆ เกิดขึ้นจริงๆ เฟรมเวิร์กจะแค่เตือนคุณว่าคุณพยายามอัปเดตสัญญาณที่ไม่มีอยู่แล้ว แต่ถ้าคุณพยายาม *เข้าถึง* มัน ก็ไม่มีคำตอบที่สอดคล้องกันนอกจากแพนิก: ไม่มีค่าที่จะคืนกลับมาได้ (มีเมธอดเทียบเท่าที่ขึ้นต้นด้วย `try_` สำหรับ `.get()` และ `.with()` ที่จะคืนค่า `None` เฉยๆ ถ้าสัญญาณถูกทิ้งไปแล้ว)

### สัญญาณอาจรั่วได้ถ้าคุณสร้างมันในสโคปที่สูงกว่าและไม่ทิ้งมันเลย

ตรงกันข้ามก็จริงเช่นกัน และมักเกิดขึ้นโดยเฉพาะเมื่อทำงานกับคอลเลกชันของสัญญาณ เช่น `RwSignal<Vec<RwSignal<_>>>` ถ้าคุณสร้างสัญญาณที่ระดับสูงกว่า และส่งมันลงไปให้คอมโพเนนต์ที่ระดับต่ำกว่า มันจะไม่ถูกทิ้งจนกว่าเจ้าของที่สูงกว่าจะถูกทำความสะอาด

ตัวอย่างเช่น ถ้าคุณมีแอปทำรายการสิ่งที่ต้องทำที่สร้าง `RwSignal<Todo>` ใหม่สำหรับแต่ละรายการ เก็บมันไว้ใน `RwSignal<Vec<RwSignal<Todo>>>` แล้วส่งมันลงไปให้ `<Todo/>` สัญญาณนั้นจะไม่ถูกทิ้งโดยอัตโนมัติเมื่อคุณลบรายการนั้นออกจากลิสต์ แต่ต้องถูกทิ้งด้วยมือ ไม่เช่นนั้นมันจะ "รั่ว" ตราบเท่าที่เจ้าของของมันยังมีชีวิตอยู่ (ดู[ตัวอย่าง TodoMVC](https://github.com/leptos-rs/leptos/blob/main/examples/todomvc/src/lib.rs#L77-L85) สำหรับการอภิปรายเพิ่มเติม)

เรื่องนี้จะเป็นปัญหาเฉพาะเมื่อคุณสร้างสัญญาณ เก็บมันไว้ในคอลเลกชัน แล้วลบมันออกจากคอลเลกชันโดยไม่ทิ้งมันด้วยมือเช่นกัน

### การแก้ปัญหาเหล่านี้ด้วยสัญญาณแบบนับรีเฟอเรนซ์

0.7 แนะนำสิ่งที่เทียบเท่าแบบนับรีเฟอเรนซ์สำหรับพรีมิทีฟแบบจัดสรรอารีนาแต่ละตัวของเรา: สำหรับทุก `RwSignal` จะมี `ArcRwSignal` (`ArcReadSignal`, `ArcWriteSignal`, `ArcMemo` และอื่นๆ)

หน่วยความจำและการทิ้งของพวกมันถูกจัดการด้วยการนับรีเฟอเรนซ์ แทนที่จะเป็นต้นไม้ความเป็นเจ้าของ

นั่นหมายความว่าพวกมันสามารถถูกใช้ได้อย่างปลอดภัยในสถานการณ์ที่ตัวเทียบเท่าแบบจัดสรรอารีนาจะรั่วหรือถูกใช้หลังจากถูกทิ้งไปแล้ว

เรื่องนี้มีประโยชน์เป็นพิเศษเมื่อสร้างคอลเลกชันของสัญญาณ: คุณอาจสร้าง `ArcRwSignal<_>` แทน `RwSignal<_>` แล้วแปลงมันเป็น `RwSignal<_>` ในแต่ละแถวของตาราง เป็นต้น

ดูการใช้งาน `ArcRwSignal<i32>` ใน[ตัวอย่าง `counters`](https://github.com/leptos-rs/leptos/blob/main/examples/counters/src/lib.rs) สำหรับตัวอย่างที่ชัดเจนยิ่งขึ้น

## เชื่อมโยงจุดต่างๆ

คำตอบสำหรับคำถามที่เราเริ่มต้นน่าจะพอเข้าใจได้แล้วตอนนี้

### วงจรชีวิตของคอมโพเนนต์

ไม่มีวงจรชีวิตของคอมโพเนนต์ เพราะคอมโพเนนต์ไม่ได้มีอยู่จริง แต่มีวงจรชีวิตของความเป็นเจ้าของ และคุณสามารถใช้มันเพื่อทำสิ่งเดียวกันได้:
- *ก่อนเมานต์*: การรันโค้ดในบอดีของคอมโพเนนต์เฉยๆ จะรันมัน "ก่อนที่คอมโพเนนต์จะเมานต์"
- *ตอนเมานต์*: `create_effect` รันหลังจากส่วนที่เหลือของคอมโพเนนต์หนึ่งติ๊ก ดังนั้นจึงมีประโยชน์สำหรับเอฟเฟกต์ที่ต้องรอให้วิวถูกเมานต์ลง DOM
- *ตอนอันเมานต์*: คุณสามารถใช้ `on_cleanup` เพื่อให้โค้ดแก่ระบบรีแอกทีฟที่ควรรันขณะที่เจ้าของปัจจุบันกำลังทำความสะอาด ก่อนจะรันอีกครั้ง เพราะเจ้าของอยู่รอบๆ "การตัดสินใจ" นั่นหมายความว่า `on_cleanup` จะรันเมื่อคอมโพเนนต์ของคุณอันเมานต์: ถ้ามีอะไรบางอย่างอันเมานต์ได้ เรนเดอเรอร์ต้องสร้างเอฟเฟกต์ที่กำลังอันเมานต์มันอยู่แน่นอน!

### ปัญหากับสัญญาณที่ถูกทิ้ง

โดยทั่วไปแล้ว ปัญหาจะเกิดขึ้นได้ที่นี่ก็ต่อเมื่อคุณสร้างสัญญาณที่ต่ำลงไปในต้นไม้ความเป็นเจ้าของแล้วเก็บมันไว้ที่สูงกว่า ถ้าคุณเจอปัญหาในลักษณะนี้ คุณควร "ยก" การสร้างสัญญาณขึ้นไปไว้ในพาเรนต์แทน แล้วส่งสัญญาณที่สร้างแล้วลงมา โดยอย่าลืมทิ้งมันเมื่อลบออกด้วยถ้าจำเป็น!

### สัญญาณแบบ `Copy`

ระบบทั้งหมดของชนิดตัวห่อที่ `Copy` ได้ (สัญญาณ `StoredValue` และอื่นๆ) ใช้ต้นไม้ความเป็นเจ้าของเป็นตัวประมาณวงจรชีวิตของส่วนต่างๆ ของ UI ของคุณอย่างใกล้ชิด ในทางปฏิบัติ มันเทียบเคียงกับระบบไลฟ์ไทม์ของภาษา Rust ที่อิงกับบล็อกโค้ด ด้วยระบบไลฟ์ไทม์ที่อิงกับส่วนต่างๆ ของ UI เรื่องนี้ไม่สามารถตรวจสอบได้อย่างสมบูรณ์แบบทุกครั้งในเวลาคอมไพล์ แต่โดยรวมแล้วเราคิดว่ามันเป็นผลดีสุทธิ
