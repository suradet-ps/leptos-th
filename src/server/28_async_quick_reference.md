# อ้างอิง: โคลเชอร์/ฟิวเจอร์แบบอะซิงโครนัส

เมื่อมีการแนะนำชนิดต่างๆ ของโคลเชอร์และฟิวเจอร์แบบอะซิงโครนัสเข้ามาแล้ว การติดตามว่าพวกมันทำงานที่ไหนและเมื่อไรในบริบทต่างๆ อาจเป็นเรื่องยาก ตารางต่อไปนี้อธิบายสั้นๆ ว่าโค้ดถูกทำงานที่ไหนและเมื่อไรสำหรับชนิดโคลเชอร์แบบอะซิงโครนัสแต่ละชนิดที่ได้แนะนำไป สังเกตว่าชนิดโคลเชอร์แบบอะซิงโครนัสแต่ละชนิดมีพฤติกรรมแตกต่างกันอย่างไรเมื่อทำงานบนเซิร์ฟเวอร์และบนไคลเอนต์ ร่วมกับขั้นตอนการทำงานที่เกี่ยวข้อง (SSR/การไฮเดรต/CSR)

|      | การเรนเดอร์ฝั่งเซิร์ฟเวอร์ | ระหว่างการไฮเดรต (เตรียมพร้อมสำหรับ CSR) | การเรนเดอร์ฝั่งไคลเอนต์ |
|------|-----------------------|--------------------------------------|-----------------------|
| ฟังก์ชันฝั่งเซิร์ฟเวอร์ (บนเซิร์ฟเวอร์) | ถูกเรียกใช้เป็นฟังก์ชันอะซิงโครนัสปกติ โดยโค้ดที่นิยามในเนื้อความถูกทำงานโดยตรง และผลลัพธ์ถูกคืนให้ผู้เรียก เมื่อทำงานภายในคอมโพเนนต์ จะเข้าถึงคอนเท็กซ์รีแอกทีฟทั้งหมดได้ | - | (ถูกเรียกโดยการตอบสนองต่อคำขอ HTTP ที่ส่งไปยังเอนด์พอยต์แบบสแตนด์อโลนของฟังก์ชันฝั่งเซิร์ฟเวอร์ โดยการตอบกลับจะเป็นผลลัพธ์ที่ซีเรียลไลซ์แล้ว เนื่องจากเอนด์พอยต์นี้เป็นแบบสแตนด์อโลนโดยสมบูรณ์ โดยทั่วไปคอนเท็กซ์รีแอกทีฟจึงไม่พร้อมใช้งาน) |
| ฟังก์ชันฝั่งเซิร์ฟเวอร์ (บนไคลเอนต์) | - | ไม่ถูกทำงาน (เมื่อนิยามไว้ภายในโคลเชอร์แบบอะซิงก์ชนิดรีซอร์ส) | ส่งคำขอ HTTP ไปยังเอนด์พอยต์ของฟังก์ชันฝั่งเซิร์ฟเวอร์ เนื้อความของการตอบกลับจะถูกดีซีเรียลไลซ์เป็นผลลัพธ์ โปรดทราบว่าโค้ดในเนื้อความของฟังก์ชันไม่เคยถูกคอมไพล์เข้าไปในไคลเอนต์ |
| รีซอร์ส (บนเซิร์ฟเวอร์) | โคลเชอร์แบบอะซิงก์ของพวกมันถูกทำงานแบบ*ขนาน*เมื่อเป็นไปได้โดยตัวรันอะซิงก์; ผลลัพธ์ถูกเข้ารหัสเข้าไปในเนื้อความของการตอบกลับภายในแท็ก `<script>` | - | - |
| รีซอร์ส (บนไคลเอนต์) | - | ไม่ถูกทำงาน; แท็ก `<script>` ภายในเนื้อความของการตอบกลับเป็นตัวให้ผลลัพธ์ | โคลเชอร์แบบอะซิงก์ของพวกมันถูกทำงานเมื่อใดก็ตามที่ระบบรีแอกทีฟต้องการเพื่อคืนผลลัพธ์ใหม่ๆ |
| รีซอร์สแบบโลคอล (ไคลเอนต์เท่านั้น) | - | ไม่ถูกทำงาน (จะถูกทำงานหนึ่งครั้งหลังการไฮเดรตเพื่อให้ค่าเริ่มต้น) | โคลเชอร์แบบอะซิงก์ของพวกมันถูกทำงานเมื่อใดก็ตามที่ระบบรีแอกทีฟต้องการเพื่อคืนผลลัพธ์ใหม่ๆ |
| Suspend (บนเซิร์ฟเวอร์) | ฟิวเจอร์เหล่านี้ถูกทำงานแบบ*ขนาน*เมื่อเป็นไปได้โดยตัวรันอะซิงก์ `SsrMode` ที่เลือกสามารถปรับเปลี่ยนว่าเมื่อไรและอย่างไร: 1) ฟิวเจอร์เหล่านี้ถูก poll, 2) ลำดับของสตรีมเอาต์พุต | - | - |
| Suspend (บนไคลเอนต์) | - | ฟิวเจอร์เหล่านี้ถูกทำงานอย่างสมบูรณ์อีกครั้งในไคลเอนต์เป็นส่วนหนึ่งของการไฮเดรต; `view! {}` ที่คืนมาจะถูกใช้เพื่อไฮเดรต HTML | ฟิวเจอร์เหล่านี้ถูกทำงานเมื่อใดก็ตามที่ระบบรีแอกทีฟต้องการ; `view! {}` ที่คืนมาจะถูกเรนเดอร์ ณ ที่ที่พวกมันถูกนิยาม |

หมายเหตุที่มีประโยชน์ควรจดจำคือ มีขั้นตอนการทำงานได้ถึงสามขั้นตอนที่แตกต่างกัน แบ่งระหว่างเซิร์ฟเวอร์และไคลเอนต์ ผลที่ตามมาอย่างหนึ่งคือศักยภาพที่จะเกิดบั๊กการไฮเดรตหรือพฤติกรรมโปรแกรมที่ไม่คาดคิดหากมีผลข้างเคียงภายในรีซอร์สหรือ Suspend ผลข้างเคียงเหล่านี้อาจไม่ถูกทำงานตามเวลาที่คาดหวังหรือในลำดับที่เหมือนกันในแต่ละขั้นตอนการทำงาน และความไม่ตรงกันนี้อาจนำไปสู่ข้อผิดพลาดในการไฮเดรต

ยกตัวอย่างเช่น ผลข้างเคียงอาจเกิดขึ้นจากรีซอร์สที่ตั้งค่าสัญญาณ รีซอร์สอาจส่งค่าที่ได้มาแบบอะซิงโครนัสผ่านสัญญาณรีแอกทีฟในโคลเชอร์แบบอะซิงโครนัสของมัน ซึ่งทำงานได้อย่างสมบูรณ์ภายใต้ SSR และ CSR แต่จะไม่ทำงานตามที่คาดหวังหากเกี่ยวข้องกับการไฮเดรต ในระหว่างการไฮเดรต เนื้อความของโคลเชอร์แบบอะซิงก์_จะไม่_ถูกทำงาน ดังนั้นสัญญาณจึงไม่ถูกตั้งค่าระหว่างการไฮเดรต; และเนื่องจากโคลเชอร์นั้นภายใต้ SSR จะถูกทำงานและสัญญาณจึงถูกตั้งค่าที่นั่น ความไม่ตรงกันระหว่างสัญญาณที่ถูกตั้งค่าภายใต้ SSR กับไม่ถูกตั้งค่าระหว่างการไฮเดรตอาจนำไปสู่ข้อผิดพลาดในการไฮเดรต เพื่อแก้ไขปัญหานี้ ให้รีซอร์สคืนค่าแทน เพื่อให้ Suspend สามารถ `.await` มันก่อนส่งผ่านสัญญาณรีแอกทีฟ ทำให้มั่นใจได้ว่าสัญญาณถูกตั้งค่าในทั้งสามขั้นตอนการทำงาน

อีกวิธีที่ความไม่ตรงกันนี้อาจเกิดขึ้นคือเมื่อสัญญาณตัวเดียวถูกใช้โดย Suspend หลายตัว Suspend เหล่านี้อาจถูก poll ในลำดับที่ต่างกันบนเซิร์ฟเวอร์เมื่อเทียบกับวิธีที่พวกมันถูก poll บนไคลเอนต์ นี่เป็นเพียงเพราะตัวรันอะซิงก์ที่แตกต่างกันถูกใช้ในสองบริบทนี้ ซึ่งส่งผลให้เกิดลำดับการทำงานที่ไม่เสถียร นำไปสู่การเปลี่ยนลำดับของค่าที่ถูกส่งผ่านสัญญาณ สุดท้ายผลลัพธ์ก็คือศักยภาพอีกประการหนึ่งที่ค่าต่างๆ จะไม่ตรงกันภายใต้ SSR เมื่อเทียบกับการไฮเดรต และในกรณีนี้โดยเฉพาะ ข้อผิดพลาดในการไฮเดรตอาจกลายเป็นแบบไม่กำหนดแน่นอนและทำให้ยากต่อการระบุต้นเหตุ

อีกตัวอย่างหนึ่ง ในระหว่าง SSR ฟังก์ชันฝั่งเซิร์ฟเวอร์จะเข้าถึงชุดคอนเท็กซ์ทั้งหมดที่แอปพลิเคชันตั้งค่าไว้ได้ เพราะมันถูกเรียกใช้เป็นฟังก์ชันอะซิงก์มาตรฐานระหว่างการเรนเดอร์แอปพลิเคชัน ในทางกลับกัน คู่เอนด์พอยต์ API ของมันมีอยู่ในฐานะตัวจัดการเอนด์พอยต์แบบสแตนด์อโลนที่เรียบง่ายกว่ามาก ดังนั้นพวกมันจะรันโดยไม่มีคอนเท็กซ์ใดๆ ที่แอปพลิเคชันตั้งค่าไว้ ดังนั้นการใช้ `expect_context` และ `use_context` กับชนิดข้อมูลที่แอปพลิเคชันตั้งค่าไว้จะไม่ทำงาน เว้นแต่ค่าต่างๆ จะถูกให้ไว้กับคอนเท็กซ์โดย `.leptos_routes_with_context()`

ข้างต้นเป็นเพียงตัวอย่างบางส่วนเพื่อใช้เป็นข้อมูลอ้างอิงอย่างรวดเร็วเกี่ยวกับพฤติกรรมของชนิดต่างๆ ภายใต้การกำหนดค่ามาตรฐานตามเอกสาร (กล่าวคือ ฟังก์ชันฝั่งเซิร์ฟเวอร์ถูกเรียก/await เฉพาะภายในรีซอร์ส และรีซอร์สถูก await เฉพาะภายใน Suspend) เนื่องจากการรวมหรือซ้อนโคลเชอร์แบบอะซิงโครนัสเหล่านี้ในลักษณะอื่นอาจทำให้เกิดพฤติกรรมอื่นๆ ได้
