# อ้างอิง: โคลเชอร์/ฟิวเจอร์แบบอะซิงโครนัส

เมื่อมีชนิดข้อมูลของโคลเชอร์และฟิวเจอร์แบบอะซิงโครนัสหลากหลายรูปแบบเข้ามาใช้งาน การคอยติดตามว่าโค้ดส่วนไหนจะถูกสั่งรันที่ใดและเมื่อใดในแต่ละบริบทอาจทำให้สับสนได้ไม่น้อย ตารางสรุปด้านล่างนี้จะช่วยอธิบายอย่างกระชับว่า โค้ดของโคลเชอร์แบบอะซิงโครนัสแต่ละชนิดจะถูกสั่งรันเมื่อใดและที่ไหน โดยโปรดสังเกตว่าโคลเชอร์แต่ละชนิดจะมีพฤติกรรมที่แตกต่างกันอย่างสิ้นเชิงเมื่อทำงานบนเซิร์ฟเวอร์เทียบกับบนไคลเอนต์ ควบคู่ไปกับขั้นตอนของวงจรชีวิตที่เกี่ยวข้อง (SSR, การไฮเดรต, หรือ CSR)

|      | การเรนเดอร์ฝั่งเซิร์ฟเวอร์ | ระหว่างการไฮเดรต (เตรียมพร้อมสำหรับ CSR) | การเรนเดอร์ฝั่งไคลเอนต์ |
|------|-----------------------|--------------------------------------|-----------------------|
| ฟังก์ชันฝั่งเซิร์ฟเวอร์ (บนเซิร์ฟเวอร์) | ถูกเรียกใช้เป็นฟังก์ชัน async ปกติ โดยโค้ดในเนื้อหาฟังก์ชันจะถูกสั่งรันโดยตรงและส่งผลลัพธ์กลับไปยังผู้เรียก เมื่อรันอยู่ภายในคอมโพเนนต์ จะสามารถเข้าถึงคอนเทกซ์รีแอกทีฟทั้งหมดได้อย่างสมบูรณ์ | - | (ถูกเรียกใช้งานผ่านการตอบสนองต่อคำขอ HTTP ที่ส่งมายังเอนด์พอยต์แบบสแตนด์อโลนของฟังก์ชันฝั่งเซิร์ฟเวอร์ โดยคำตอบที่ส่งกลับไปจะเป็นผลลัพธ์ที่ผ่านการแปลงเป็นอนุกรมแล้ว เนื่องจากเอนด์พอยต์นี้ทำงานแบบสแตนด์อโลนโดยสมบูรณ์ จึงมักไม่มีคอนเทกซ์รีแอกทีฟให้ใช้งาน) |
| ฟังก์ชันฝั่งเซิร์ฟเวอร์ (บนไคลเอนต์) | - | ไม่ถูกสั่งรัน (เมื่อนิยามไว้ภายในโคลเชอร์แบบ async ของรีซอร์ส) | ส่งคำขอ HTTP ไปยังเอนด์พอยต์ของฟังก์ชันฝั่งเซิร์ฟเวอร์ โดยเนื้อหาของคำตอบจะถูกดีซีเรียลไลซ์กลับมาเป็นผลลัพธ์ โปรดทราบว่าโค้ดที่อยู่ภายในเนื้อหาของฟังก์ชันจะไม่ถูกคอมไพล์ลงมายังฝั่งไคลเอนต์เลย |
| รีซอร์ส (บนเซิร์ฟเวอร์) | โคลเชอร์แบบ async จะถูกสั่งรันแบบ*ขนาน*กันโดยตัวรันอะซิงก์ (async executor) เท่าที่เป็นไปได้; ผลลัพธ์จะถูกเข้ารหัสลงในเนื้อหาของคำตอบตอบกลับภายในแท็ก `<script>` | - | - |
| รีซอร์ส (บนไคลเอนต์) | - | ไม่ถูกสั่งรัน; แท็ก `<script>` ที่อยู่ในเนื้อหาคำตอบจะทำหน้าที่ส่งมอบผลลัพธ์ให้โดยตรง | โคลเชอร์แบบ async จะถูกสั่งรันเมื่อใดก็ตามที่ระบบรีแอกทีฟต้องการผลลัพธ์ชุดใหม่ |
| รีซอร์สเฉพาะที่ (ไคลเอนต์เท่านั้น) | - | ไม่ถูกสั่งรัน (จะถูกสั่งรันหนึ่งรอบหลังเสร็จสิ้นขั้นตอนการไฮเดรต เพื่อเตรียมค่าเริ่มต้นให้) | โคลเชอร์แบบ async จะถูกสั่งรันเมื่อใดก็ตามที่ระบบรีแอกทีฟต้องการผลลัพธ์ชุดใหม่ |
| Suspend (บนเซิร์ฟเวอร์) | ฟิวเจอร์เหล่านี้จะถูกสั่งรันแบบ*ขนาน*กันโดยตัวรันอะซิงก์เท่าที่เป็นไปได้ ค่า `SsrMode` ที่เลือกไว้สามารถปรับเปลี่ยนเงื่อนไขว่า: 1) ฟิวเจอร์เหล่านี้จะถูก poll เมื่อใดและอย่างไร, 2) ลำดับการเรียงตัวของสตรีมเอาต์พุต | - | - |
| Suspend (บนไคลเอนต์) | - | ฟิวเจอร์เหล่านี้จะถูกสั่งรันจนเสร็จสิ้นอีกครั้งบนไคลเอนต์ในฐานะส่วนหนึ่งของขั้นตอนการไฮเดรต; โดยผลลัพธ์ `view! {}` ที่ได้จะถูกนำไปใช้ไฮเดรตโครงสร้าง HTML | ฟิวเจอร์เหล่านี้จะถูกสั่งรันเมื่อใดก็ตามที่ระบบรีแอกทีฟร้องขอ; โดยผลลัพธ์ `view! {}` จะถูกเรนเดอร์ในตำแหน่งที่พวกมันถูกนิยามไว้ |

ข้อสังเกตสำคัญที่ควรตระหนักไว้คือ ระบบมีขั้นตอนการทำงานที่แตกต่างกันสูงสุดถึง 3 ขั้นตอน ซึ่งแบ่งแยกระหว่างเซิร์ฟเวอร์และไคลเอนต์ ผลพวงจากสถาปัตยกรรมนี้คือ โอกาสที่จะเกิดบั๊กการไฮเดรตหรือพฤติกรรมของโปรแกรมที่ไม่คาดคิด หากมีการใส่ผลข้างเคียง (side effects) ไว้ภายใน Resource หรือ Suspend เนื่องจากผลข้างเคียงเหล่านี้อาจไม่ถูกประมวลผลในช่วงเวลาที่คาดหมาย หรืออาจไม่ได้รันตามลำดับเดียวกันในแต่ละขั้นตอนการทำงาน และความไม่ตรงกันนี้เองที่จะนำไปสู่ข้อผิดพลาดในการไฮเดรต

ตัวอย่างเช่น ผลข้างเคียงอาจเกิดขึ้นจากการที่รีซอร์สไปกำหนดค่าให้กับสัญญาณ (signal) รีซอร์สอาจนำค่าที่ได้มาแบบอะซิงโครนัสไปอัปเดตผ่านสัญญาณรีแอกทีฟภายในโคลเชอร์แบบอะซิงโครนัสของมันเอง—ซึ่งการกระทำนี้จะทำงานได้อย่างราบรื่นไร้ปัญหาภายใต้โหมด SSR และ CSR ทว่ามันจะไม่ทำงานตามที่คาดหวังหากมีขั้นตอนการไฮเดรตเข้ามาเกี่ยวข้อง เพราะในระหว่างการไฮเดรต เนื้อหาของโคลเชอร์แบบอะซิงก์นั้น *จะไม่ถูกสั่งรัน* จึงส่งผลให้สัญญาณไม่ได้รับการกำหนดค่าในระหว่างการไฮเดรต; แต่เนื่องจากโคลเชอร์เดียวกันนี้เคยถูกสั่งรันไปแล้วในระหว่าง SSR และสัญญาณก็ถูกกำหนดค่าไว้เรียบร้อยแล้ว ความไม่ตรงกันระหว่างการที่สัญญาณถูกตั้งค่าภายใต้ SSR แต่กลับไม่ถูกตั้งค่าในระหว่างการไฮเดรต จึงนำไปสู่ข้อผิดพลาดในการไฮเดรตได้ วิธีแก้ไขที่ถูกต้องคือ ให้รีซอร์สส่งคืนค่านั้นออกมาโดยตรง เพื่อให้ Suspend สามารถรอ `.await` รับค่าดังกล่าวก่อนจะนำไปอัปเดตสัญญาณรีแอกทีฟ ซึ่งจะช่วยรับประกันได้ว่าสัญญาณจะได้รับการตั้งค่าอย่างถูกต้องครบถ้วนในทั้งสามขั้นตอนการทำงาน

อีกกรณีหนึ่งที่อาจก่อให้เกิดความไม่ตรงกัน คือเมื่อมี Suspend หลายตัวเรียกใช้งานสัญญาณตัวเดียวกัน โดยที่ Suspend เหล่านี้อาจถูก poll ตามลำดับที่แตกต่างกันระหว่างบนเซิร์ฟเวอร์กับบนไคลเอนต์ ซึ่งมีสาเหตุมาจากการที่ตัวรันอะซิงก์ (async executors) บนทั้งสองสภาพแวดล้อมเป็นคนละตัวกัน ส่งผลให้ลำดับการประมวลผลไม่เสถียร และทำให้ลำดับของค่าที่ถูกส่งผ่านเข้าไปยังสัญญาณเกิดการสลับที่กัน ผลลัพธ์สุดท้ายคือความเสี่ยงที่ค่าข้อมูลจะเกิดความคลาดเคลื่อนระหว่างขั้นตอน SSR กับการไฮเดรต และในกรณีเฉพาะเช่นนี้ ข้อผิดพลาดในการไฮเดรตมักจะเกิดขึ้นแบบไม่แน่นอน (non-deterministic) จึงยากต่อการสืบหาต้นตอเป็นอย่างยิ่ง

อีกตัวอย่างหนึ่ง ในระหว่าง SSR ฟังก์ชันฝั่งเซิร์ฟเวอร์จะสามารถเข้าถึงชุดคอนเทกซ์ทั้งหมดที่แอปพลิเคชันสร้างขึ้นได้อย่างสมบูรณ์ เพราะพวกมันจะถูกเรียกใช้เสมือนเป็นฟังก์ชัน async มาตรฐานทั่วไปในระหว่างการเรนเดอร์แอปพลิเคชัน ในทางตรงกันข้าม เอนด์พอยต์ API ของมันจะทำหน้าที่เป็นตัวจัดการคำขอแบบสแตนด์อโลนที่เรียบง่ายกว่ามาก ทำให้พวกมันทำงานโดยไม่มีคอนเทกซ์ใด ๆ ที่แอปพลิเคชันเคยตั้งค่าไว้เลย ด้วยเหตุนี้ การเรียกใช้ `expect_context` และ `use_context` กับชนิดข้อมูลที่ตั้งค่าไว้ในแอปพลิเคชันจึงจะไม่ทำงาน เว้นแต่ว่าค่านั้นจะได้รับการส่งมอบให้แก่คอนเทกซ์ผ่าน `.leptos_routes_with_context()` มาก่อนแล้ว

เนื้อหาข้างต้นเป็นเพียงตัวอย่างบางส่วนเพื่อใช้เป็นแนวทางอ้างอิงฉบับย่อ สำหรับทำความเข้าใจพฤติกรรมของชนิดข้อมูลต่าง ๆ ภายใต้รูปแบบการตั้งค่ามาตรฐานตามที่ระบุไว้ในเอกสาร (นั่นคือ การเรียกหรือรอ `.await` ฟังก์ชันฝั่งเซิร์ฟเวอร์เฉพาะภายใน Resources และการรอ `.await` Resources เฉพาะภายใน Suspend) เนื่องจากการนำโคลเชอร์แบบอะซิงโครนัสเหล่านี้ไปผสมผสานหรือซ้อนทับกันด้วยวิธีอื่น อาจนำไปสู่พฤติกรรมในรูปแบบที่แตกต่างออกไปได้
