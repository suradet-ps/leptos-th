# ฟังก์ชันฝั่งเซิร์ฟเวอร์

ถ้าคุณสร้างอะไรที่มากกว่าแอปของเล่น คุณจะต้องรันโค้ดบนเซิร์ฟเวอร์อยู่ตลอดเวลา: การอ่านหรือเขียนฐานข้อมูลที่รันเฉพาะบนเซิร์ฟเวอร์ การรันการคำนวณที่แพงด้วยไลบรารีที่คุณไม่อยากส่งลงไปที่ไคลเอนต์ การเข้าถึง API ที่ต้องเรียกจากเซิร์ฟเวอร์แทนไคลเอนต์ด้วยเหตุผลด้าน CORS หรือเพราะคุณต้องใช้คีย์ API ลับที่เก็บไว้บนเซิร์ฟเวอร์และไม่ควรส่งลงไปในเบราว์เซอร์ของผู้ใช้อย่างแน่นอน

ตามธรรมเนียมแล้ว สิ่งนี้ทำได้โดยการแยกโค้ดเซิร์ฟเวอร์และไคลเอนต์ออกจากกัน และตั้งค่าสิ่งอย่าง REST API หรือ GraphQL API เพื่อให้ไคลเอนต์ของคุณดึงและกลายพันธุ์ข้อมูลบนเซิร์ฟเวอร์ได้ วิธีนี้ใช้ได้ แต่ต้องเขียนและดูแลโค้ดในหลายที่แยกจากกัน (โค้ดฝั่งไคลเอนต์สำหรับการดึงข้อมูล ฟังก์ชันฝั่งเซิร์ฟเวอร์สำหรับการรัน) รวมทั้งต้องสร้างสิ่งที่สามเพื่อจัดการ คือสัญญา API ระหว่างทั้งสองฝ่าย

Leptos เป็นหนึ่งในเฟรมเวิร์กสมัยใหม่จำนวนหนึ่งที่แนะนำแนวคิดของ **ฟังก์ชันฝั่งเซิร์ฟเวอร์** ฟังก์ชันฝั่งเซิร์ฟเวอร์มีคุณลักษณะสำคัญสองประการ:

1. ฟังก์ชันฝั่งเซิร์ฟเวอร์ถูก**วางไว้ร่วมกัน (co-located)** กับโค้ดคอมโพเนนต์ของคุณ เพื่อให้คุณจัดระเบียบงานตามฟีเจอร์ ไม่ใช่ตามเทคโนโลยี ตัวอย่างเช่น คุณอาจมีฟีเจอร์ “โหมดมืด” ที่ควรคงค่าการตั้งค่าโหมดมืด/สว่างของผู้ใช้ไว้ข้ามเซสชัน และนำมาใช้ระหว่างการเรนเดอร์ฝั่งเซิร์ฟเวอร์เพื่อไม่ให้เกิดการกะพริบ สิ่งนี้ต้องมีคอมโพเนนต์ที่ต้องโต้ตอบได้บนไคลเอนต์ และงานบางอย่างที่ต้องทำบนเซิร์ฟเวอร์ (ตั้งคุกกี้ บางทีอาจเก็บผู้ใช้ในฐานข้อมูลด้วยซ้ำ) ตามธรรมเนียมแล้ว ฟีเจอร์นี้อาจถูกแยกออกเป็นสองที่ในโค้ดของคุณ ที่หนึ่งใน “ฟรอนต์เอนด์” และอีกที่ใน “แบ็กเอนด์” แต่ด้วยฟังก์ชันฝั่งเซิร์ฟเวอร์ คุณอาจเขียนทั้งสองอย่างในไฟล์ `dark_mode.rs` เดียวแล้วลืมมันไปเลย
2. ฟังก์ชันฝั่งเซิร์ฟเวอร์เป็น**ไอโซมอร์ฟิก** กล่าวคือ สามารถเรียกได้ทั้งจากเซิร์ฟเวอร์หรือเบราว์เซอร์ สิ่งนี้ทำได้โดยสร้างโค้ดต่างกันสำหรับสองแพลตฟอร์ม บนเซิร์ฟเวอร์ ฟังก์ชันฝั่งเซิร์ฟเวอร์เพียงแค่รัน ในเบราว์เซอร์ เนื้อความของฟังก์ชันฝั่งเซิร์ฟเวอร์จะถูกแทนที่ด้วยสตับที่ส่งคำขอ fetch ไปยังเซิร์ฟเวอร์จริงๆ โดยซีเรียลไลซ์อาร์กิวเมนต์เข้าไปในคำขอและดีซีเรียลไลซ์ค่าที่คืนมาจากการตอบกลับ แต่ไม่ว่าจะฝั่งไหน ฟังก์ชันก็เรียกได้เฉยๆ: คุณสามารถสร้างฟังก์ชัน `add_todo` ที่เขียนลงฐานข้อมูลของคุณ แล้วเรียกมันจากตัวจัดการการคลิกบนปุ่มในเบราว์เซอร์ได้เลย!

## การใช้ฟังก์ชันฝั่งเซิร์ฟเวอร์

ที่จริงแล้ว ผมค่อนข้างชอบตัวอย่างนั้นนะ มันจะหน้าตาเป็นอย่างไร? จริงๆ ก็ง่ายมาก

```rust
// todo.rs

#[server]
pub async fn add_todo(title: String) -> Result<(), ServerFnError> {
    let mut conn = db().await?;

    match sqlx::query("INSERT INTO todos (title, completed) VALUES ($1, false)")
        .bind(title)
        .execute(&mut conn)
        .await
    {
        Ok(_row) => Ok(()),
        Err(e) => Err(ServerFnError::ServerError(e.to_string())),
    }
}

#[component]
pub fn BusyButton() -> impl IntoView {
	view! {
        <button on:click=move |_| {
            spawn_local(async {
                add_todo("So much to do!".to_string()).await;
            });
        }>
            "Add Todo"
        </button>
	}
}
```

คุณจะสังเกตเห็นสองสามอย่างตรงนี้ทันที:

- ฟังก์ชันฝั่งเซิร์ฟเวอร์สามารถใช้ดีเพนเดนซีที่ใช้เฉพาะเซิร์ฟเวอร์อย่าง `sqlx` และเข้าถึงรีซอร์สที่ใช้เฉพาะเซิร์ฟเวอร์อย่างฐานข้อมูลของเราได้
- ฟังก์ชันฝั่งเซิร์ฟเวอร์เป็น `async` แม้ว่ามันจะทำงานซิงโครนัสบนเซิร์ฟเวอร์เท่านั้น ลายเซ็นของฟังก์ชันก็ยังต้องเป็น `async` เพราะการเรียกมันจากเบราว์เซอร์_ต้อง_เป็นแบบอะซิงโครนัส
- ฟังก์ชันฝั่งเซิร์ฟเวอร์คืนค่า `Result<T, ServerFnError>` อีกครั้ง แม้ว่ามันจะทำงานที่ไม่มีทางล้มเหลวบนเซิร์ฟเวอร์เท่านั้น เรื่องนี้ก็ยังจริง เพราะตัวแปรต่างๆ ของ `ServerFnError` รวมถึงสิ่งต่างๆ ที่อาจผิดพลาดได้ในระหว่างกระบวนการส่งคำขอผ่านเครือข่าย
- ฟังก์ชันฝั่งเซิร์ฟเวอร์สามารถเรียกได้จากไคลเอนต์ ลองดูตัวจัดการการคลิกของเรา นี่คือโค้ดที่จะรันบนไคลเอนต์_เท่านั้น_ แต่สามารถเรียกฟังก์ชัน `add_todo` (โดยใช้ `spawn_local` เพื่อรัน `Future`) ราวกับว่ามันเป็นฟังก์ชัน async ธรรมดาได้:

```rust
move |_| {
	spawn_local(async {
		add_todo("So much to do!".to_string()).await;
	});
}
```

- ฟังก์ชันฝั่งเซิร์ฟเวอร์เป็นฟังก์ชันระดับบนสุดที่นิยามด้วย `fn` ต่างจากตัวรับฟังเหตุการณ์ สัญญาณอนุพัทธ์ และเกือบทุกอย่างใน Leptos พวกมันไม่ใช่โคลเชอร์! ในฐานะการเรียก `fn` พวกมันไม่มีสิทธิ์เข้าถึงสถานะรีแอกทีฟของแอปคุณหรือสิ่งอื่นใดที่ไม่ถูกส่งเข้ามาเป็นอาร์กิวเมนต์ และอีกครั้ง นี่สมเหตุสมผลอย่างยิ่ง: เมื่อคุณส่งคำขอไปยังเซิร์ฟเวอร์ เซิร์ฟเวอร์ไม่มีสิทธิ์เข้าถึงสถานะฝั่งไคลเอนต์เว้นแต่คุณจะส่งมันไปอย่างชัดเจน (ไม่เช่นนั้นเราคงต้องซีเรียลไลซ์ระบบรีแอกทีฟทั้งหมดแล้วส่งข้ามเครือข่ายไปกับทุกคำขอ ซึ่งไม่ใช่ความคิดที่ดีเท่าไร)
- อาร์กิวเมนต์และค่าที่คืนกลับของฟังก์ชันฝั่งเซิร์ฟเวอร์ต้องซีเรียลไลซ์ได้ทั้งคู่ อีกครั้ง หวังว่านี่จะสมเหตุสมผล: แม้ว่าโดยทั่วไปอาร์กิวเมนต์ของฟังก์ชันไม่จำเป็นต้องซีเรียลไลซ์ การเรียกฟังก์ชันฝั่งเซิร์ฟเวอร์จากเบราว์เซอร์หมายถึงการซีเรียลไลซ์อาร์กิวเมนต์แล้วส่งไปทาง HTTP

ยังมีอีกสองสามอย่างที่ควรทราบเกี่ยวกับวิธีที่คุณนิยามฟังก์ชันฝั่งเซิร์ฟเวอร์

- ฟังก์ชันฝั่งเซิร์ฟเวอร์ถูกสร้างขึ้นโดยใช้[มาโคร `#[server]`](https://docs.rs/leptos/latest/leptos/attr.server.html) เพื่อกำกับฟังก์ชันระดับบนสุด ซึ่งสามารถนิยามที่ไหนก็ได้

ฟังก์ชันฝั่งเซิร์ฟเวอร์ทำงานโดยใช้การคอมไพล์แบบมีเงื่อนไข บนเซิร์ฟเวอร์ ฟังก์ชันฝั่งเซิร์ฟเวอร์สร้างเอนด์พอยต์ HTTP ที่รับอาร์กิวเมนต์ของมันเป็นคำขอ HTTP และคืนผลลัพธ์ของมันเป็นการตอบกลับ HTTP ส่วนบิลด์ฝั่งไคลเอนต์/เบราว์เซอร์ เนื้อความของฟังก์ชันฝั่งเซิร์ฟเวอร์จะถูกแทนที่ด้วยคำขอ HTTP

```admonish warning
### หมายเหตุสำคัญเกี่ยวกับความปลอดภัย

ฟังก์ชันฝั่งเซิร์ฟเวอร์เป็นเทคโนโลยีที่เจ๋ง แต่สิ่งสำคัญมากที่ต้องจำ **ฟังก์ชันฝั่งเซิร์ฟเวอร์ไม่ใช่เวทมนตร์; มันเป็นน้ำตาลไวยากรณ์สำหรับการนิยาม API สาธารณะ** เนื้อความ_ของฟังก์ชันฝั่งเซิร์ฟเวอร์ไม่เคยถูกเปิดเผยต่อสาธารณะ มันเป็นเพียงส่วนหนึ่งของไบนารีเซิร์ฟเวอร์ของคุณ แต่ฟังก์ชันฝั่งเซิร์ฟเวอร์เป็นเอนด์พอยต์ API ที่เข้าถึงได้จากสาธารณะ และค่าที่คืนกลับของมันก็เป็นแค่ JSON หรือข้อมูลก้อนอื่นๆ เท่านั้น อย่าคืนข้อมูลจากฟังก์ชันฝั่งเซิร์ฟเวอร์เว้นแต่ข้อมูลนั้นเป็นข้อมูลสาธารณะ หรือคุณได้ดำเนินการด้านความปลอดภัยที่เหมาะสมแล้ว กระบวนการเหล่านี้อาจรวมถึงการยืนยันตัวตนของคำขอที่เข้ามา การรับประกันการเข้ารหัสที่เหมาะสม การจำกัดอัตราการเข้าถึง และอื่นๆ
```

## การปรับแต่งฟังก์ชันฝั่งเซิร์ฟเวอร์

โดยค่าเริ่มต้น ฟังก์ชันฝั่งเซิร์ฟเวอร์เข้ารหัสอาร์กิวเมนต์ของมันเป็นคำขอ HTTP POST (โดยใช้ `serde_qs`) และค่าที่คืนกลับเป็น JSON (โดยใช้ `serde_json`) ค่าเริ่มต้นนี้มีจุดประสงค์เพื่อส่งเสริมความเข้ากันได้กับเอลิเมนต์ `<form>` ซึ่งรองรับการส่งคำขอ POST โดยธรรมชาติ แม้ในขณะที่ WASM ถูกปิดใช้งาน ไม่รองรับ หรือยังโหลดไม่เสร็จ พวกมันติดตั้งเอนด์พอยต์ที่ URL ที่แฮชแล้วเพื่อป้องกันการชนกันของชื่อ

อย่างไรก็ตาม มีหลายวิธีในการปรับแต่งฟังก์ชันฝั่งเซิร์ฟเวอร์ พร้อมการเข้ารหัสอินพุตและเอาต์พุตที่รองรับหลากหลาย ความสามารถในการตั้งค่าเอนด์พอยต์เฉพาะ และอื่นๆ

ลองดูเอกสารของ[มาโคร `#[server]`](https://docs.rs/leptos/latest/leptos/attr.server.html) และ[ครีต `server_fn`](https://docs.rs/server_fn/latest/server_fn/) รวมถึง[ตัวอย่าง `server_fns_axum`](https://github.com/leptos-rs/leptos/blob/main/examples/server_fns_axum/src/app.rs) ที่ครอบคลุมมากในรีโพ สำหรับข้อมูลและตัวอย่างเพิ่มเติม

## การใช้ข้อผิดพลาดแบบกำหนดเอง

ฟังก์ชันฝั่งเซิร์ฟเวอร์สามารถคืนข้อผิดพลาดชนิดใดก็ได้ที่อิมพลีเมนต์แทรต `FromServerFnError`
สิ่งนี้ทำให้การจัดการข้อผิดพลาดสะดวกขึ้นมาก และช่วยให้คุณให้ข้อมูลข้อผิดพลาดเฉพาะโดเมนแก่ไคลเอนต์ของคุณได้:

```rust
use leptos::prelude::*;
use server_fn::codec::JsonEncoding;
use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Deserialize, Serialize)]
pub enum AppError {
    ServerFnError(ServerFnErrorErr),
    DbError(String),
}

impl FromServerFnError for AppError {
    type Encoder = JsonEncoding;

    fn from_server_fn_error(value: ServerFnErrorErr) -> Self {
        AppError::ServerFnError(value)
    }
}

#[server]
pub async fn create_user(name: String, email: String) -> Result<User, AppError> {
    // Try to create user in database
    match insert_user_into_db(&name, &email).await {
        Ok(user) => Ok(user),
        Err(e) => Err(AppError::DbError(e.to_string())),
    }
}
```

## ข้อควรทราบเฉพาะตัว

ฟังก์ชันฝั่งเซิร์ฟเวอร์มีลักษณะเฉพาะบางประการที่ควรจดจำ:

- การใช้ชนิดจำนวนเต็มที่มีขนาดเท่าพอยน์เตอร์อย่าง `isize` และ `usize` อาจทำให้เกิดข้อผิดพลาดเมื่อเรียกข้ามระหว่างสถาปัตยกรรม WASM 32 บิตกับสถาปัตยกรรมเซิร์ฟเวอร์ 64 บิต; หากเซิร์ฟเวอร์ตอบกลับด้วยค่าที่ไม่พอดีกับ 32 บิต สิ่งนี้จะทำให้เกิดข้อผิดพลาดในการดีซีเรียลไลซ์ ใช้ชนิดขนาดคงที่อย่าง `i32` หรือ `i64` เพื่อบรรเทาปัญหานี้
- อาร์กิวเมนต์ที่ส่งไปยังเซิร์ฟเวอร์ถูกเข้ารหัส URL โดยใช้ `serde_qs` เป็นค่าเริ่มต้น สิ่งนี้ทำให้มันทำงานร่วมกับเอลิเมนต์ `<form>` ได้ดี แต่ก็อาจมีลักษณะเฉพาะบางอย่าง: ตัวอย่างเช่น `serde_qs` เวอร์ชันปัจจุบันไม่ทำงานร่วมกับชนิดข้อมูลแบบ optional ได้ดีเสมอไป (ดู[ที่นี่](https://github.com/leptos-rs/leptos/issues/3832) หรือ[ที่นี่](https://github.com/leptos-rs/leptos/issues/4016)) หรือกับอีนัมที่มีตัวแปรแบบทูเพิล (ดู[ที่นี่](https://github.com/leptos-rs/leptos/issues/4464)) คุณสามารถใช้วิธีเลี่ยงที่อธิบายในประเด็นเหล่านั้น หรือ[เปลี่ยนไปใช้การเข้ารหัสอินพุตแบบอื่น](https://docs.rs/leptos/latest/leptos/attr.server.html#named-arguments)

## การผสานรวมฟังก์ชันฝั่งเซิร์ฟเวอร์กับ Leptos

จนถึงตอนนี้ ทุกอย่างที่ผมพูดมาจริงๆ แล้วไม่ผูกกับเฟรมเวิร์กใด (และที่จริง ครีตฟังก์ชันฝั่งเซิร์ฟเวอร์ของ Leptos ก็ถูกผสานรวมเข้ากับ Dioxus ด้วย!) ฟังก์ชันฝั่งเซิร์ฟเวอร์เป็นเพียงวิธีนิยามการเรียก RPC ที่เหมือนฟังก์ชัน ซึ่งอาศัยมาตรฐานเว็บอย่างคำขอ HTTP และการเข้ารหัส URL

แต่ในแง่หนึ่ง พวกมันยังเติมพริดิมิตีฟตัวสุดท้ายที่ขาดหายไปในเรื่องราวของเราจนถึงตอนนี้ด้วย เพราะฟังก์ชันฝั่งเซิร์ฟเวอร์เป็นเพียงฟังก์ชัน async ของ Rust ธรรมดา มันจึงผสานรวมกับพริดิมิตีฟแบบอะซิงก์ของ Leptos ที่เราพูดถึง[ก่อนหน้านี้](../async/index.html)ได้อย่างสมบูรณ์ ดังนั้นคุณจึงผสานรวมฟังก์ชันฝั่งเซิร์ฟเวอร์ของคุณกับส่วนอื่นๆ ของแอปพลิเคชันได้อย่างง่ายดาย:

- สร้าง**รีซอร์ส**ที่เรียกฟังก์ชันฝั่งเซิร์ฟเวอร์เพื่อโหลดข้อมูลจากเซิร์ฟเวอร์
- อ่านรีซอร์สเหล่านี้ภายใต้ `<Suspense/>` หรือ `<Transition/>` เพื่อเปิดใช้งาน SSR แบบสตรีมและสถานะฟอลแบ็กขณะข้อมูลโหลด
- สร้าง**แอ็กชัน**ที่เรียกฟังก์ชันฝั่งเซิร์ฟเวอร์เพื่อกลายพันธุ์ข้อมูลบนเซิร์ฟเวอร์

ส่วนสุดท้ายของหนังสือเล่มนี้จะทำให้เรื่องนี้เป็นรูปธรรมมากขึ้นโดยแนะนำแพตเทิร์นที่ใช้ฟอร์ม HTML แบบเสริมความสามารถอย่างค่อยเป็นค่อยไปเพื่อรันแอ็กชันฝั่งเซิร์ฟเวอร์เหล่านี้

แต่ในบทต่อๆ ไป เราจะมาดูรายละเอียดบางอย่างของสิ่งที่คุณอาจต้องการทำกับฟังก์ชันฝั่งเซิร์ฟเวอร์ รวมถึงวิธีที่ดีที่สุดในการผสานรวมกับเอกซ์แทรกเตอร์อันทรงพลังที่ Actix และ Axum เซิร์ฟเวอร์เฟรมเวิร์กมีให้
