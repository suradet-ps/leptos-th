# ฟังก์ชันฝั่งเซิร์ฟเวอร์

หากคุณกำลังพัฒนาแอปพลิเคชันที่จริงจังกว่าแค่โปรเจกต์ทดลองเล่นทั่วไป (toy app) คุณย่อมจำเป็นต้องสั่งรันโค้ดบนฝั่งเซิร์ฟเวอร์อยู่ตลอดเวลา: ไม่ว่าจะเป็นการอ่านหรือเขียนข้อมูลลงฐานข้อมูลที่รันอยู่เฉพาะบนเซิร์ฟเวอร์, การประมวลผลคำนวณที่มีต้นทุนสูงด้วยไลบรารีขนาดใหญ่ที่คุณไม่ต้องการส่งไปให้ไคลเอนต์ดาวน์โหลด, หรือการเข้าถึง API ภายนอกที่จำเป็นต้องเรียกจากเซิร์ฟเวอร์เท่านั้น ไม่ว่าจะด้วยเหตุผลด้านข้อจำกัดของ CORS หรือเพราะต้องใช้คีย์ API ลับที่เก็บเป็นความลับบนเซิร์ฟเวอร์และต้องไม่รั่วไหลลงไปยังเบราว์เซอร์ของผู้ใช้อย่างเด็ดขาด

ตามแนวทางดั้งเดิม สิ่งนี้มักทำโดยการแยกโค้ดฝั่งเซิร์ฟเวอร์และฝั่งไคลเอนต์ออกจากกันอย่างสิ้นเชิง แล้วสร้าง REST API หรือ GraphQL API ขึ้นมาเป็นตัวกลางเพื่อให้ไคลเอนต์สามารถดึงข้อมูลและส่งการเปลี่ยนแปลงแก้ไขข้อมูล (mutate) กลับไปยังเซิร์ฟเวอร์ได้ แม้วิธีนี้จะใช้งานได้ดี แต่ก็บีบให้คุณต้องเขียนและคอยดูแลรักษาโค้ดในหลายที่แยกจากกัน (โค้ดฝั่งไคลเอนต์สำหรับดึงข้อมูล, ฟังก์ชันฝั่งเซิร์ฟเวอร์สำหรับประมวลผล) ซ้ำยังต้องคอยจัดการชิ้นส่วนที่สามเพิ่มขึ้นมา นั่นคือข้อตกลงหรือสัญญาของ API (API contract) ระหว่างทั้งสองฝั่ง

Leptos เป็นหนึ่งในกลุ่มเฟรมเวิร์กสมัยใหม่ที่นำเสนอแนวคิดของ **ฟังก์ชันฝั่งเซิร์ฟเวอร์** (server functions) ซึ่งมีคุณลักษณะสำคัญ 2 ประการดังนี้:

1. ฟังก์ชันฝั่งเซิร์ฟเวอร์จะถูก **เขียนไว้ร่วมกัน (co-located)** กับโค้ดคอมโพเนนต์ของคุณ ช่วยให้คุณสามารถจัดระเบียบโครงสร้างงานตามฟีเจอร์ได้โดยตรง แทนที่จะต้องแบ่งแยกตามเทคโนโลยี ตัวอย่างเช่น คุณอาจมีฟีเจอร์ “โหมดมืด” (dark mode) ที่ต้องการจดจำค่าการตั้งค่าของผู้ใช้ข้ามเซสชัน และต้องการให้นำค่านั้นไปใช้งานตั้งแต่ขั้นตอนการเรนเดอร์บนเซิร์ฟเวอร์เพื่อป้องกันปัญหาหน้าจอกะพริบ (flicker) ฟีเจอร์นี้จำเป็นต้องมีทั้งคอมโพเนนต์ที่ตอบสนองการคลิกบนไคลเอนต์ และงานบางอย่างที่ต้องทำบนเซิร์ฟเวอร์ (เช่น การเซ็ตคุกกี้ หรือบันทึกข้อมูลผู้ใช้ลงฐานข้อมูล) ในแบบดั้งเดิม ฟีเจอร์นี้อาจต้องถูกแยกโค้ดออกเป็น 2 ฝั่ง คือส่วนหนึ่งอยู่ใน “ฟรอนต์เอนด์” และอีกส่วนอยู่ใน “แบ็กเอนด์” แต่เมื่อมีฟังก์ชันฝั่งเซิร์ฟเวอร์ คุณสามารถเขียนทั้งสองส่วนรวมกันไว้ในไฟล์ `dark_mode.rs` เพียงไฟล์เดียวได้อย่างสบายใจ
2. ฟังก์ชันฝั่งเซิร์ฟเวอร์มีคุณสมบัติเป็น **ไอโซมอร์ฟิก (isomorphic)** กล่าวคือ สามารถเรียกใช้งานได้จากทั้งบนเซิร์ฟเวอร์และบนเบราว์เซอร์ สิ่งนี้ทำได้โดยระบบจะสร้างโค้ดสำหรับการคอมไพล์ของแต่ละแพลตฟอร์มที่แตกต่างกัน: บนเซิร์ฟเวอร์ ฟังก์ชันจะสั่งรันการทำงานตามปกติ แต่บนเบราว์เซอร์ เนื้อหาของฟังก์ชันจะถูกแทนที่ด้วยโค้ดจำลอง (stub) ที่จะส่งคำขอ fetch ไปยังเซิร์ฟเวอร์โดยอัตโนมัติ พร้อมทั้งแปลงอาร์กิวเมนต์เป็นอนุกรม (serialize) ใส่ในคำขอ และแปลงผลลัพธ์ตอบกลับมาเป็นข้อมูล (deserialize) ทว่าจากมุมมองของผู้พัฒนา คุณสามารถเรียกใช้งานฟังก์ชันนี้ได้ตรง ๆ จากทั้งสองฝั่ง: คุณสามารถสร้างฟังก์ชัน `add_todo` ที่เขียนข้อมูลลงฐานข้อมูล แล้วเรียกใช้ฟังก์ชันนั้นจากตัวจัดการเหตุการณ์คลิกของปุ่มบนเบราว์เซอร์ได้ทันที!

## การใช้ฟังก์ชันฝั่งเซิร์ฟเวอร์

ที่จริงแล้ว ตัวอย่างนี้น่าสนใจทีเดียว หน้าตาของมันจะเป็นอย่างไร? บอกได้เลยว่าเรียบง่ายมาก:

```rust
// todo.rs

#[server]
pub async fn add_todo(title: String) -> Result<(), ServerFnError> {
    let mut conn = db().await?;

    match sqlx::query("INSERT INTO todos (title, completed) VALUES ($1, false)")
        .bind(title)
        .execute(&mut conn)
        .await
    {
        Ok(_row) => Ok(()),
        Err(e) => Err(ServerFnError::ServerError(e.to_string())),
    }
}

#[component]
pub fn BusyButton() -> impl IntoView {
	view! {
        <button on:click=move |_| {
            spawn_local(async {
                add_todo("So much to do!".to_string()).await;
            });
        }>
            "Add Todo"
        </button>
	}
}
```

คุณจะสังเกตเห็นจุดสำคัญหลายประการได้ทันทีจากโค้ดข้างต้น:

- ฟังก์ชันฝั่งเซิร์ฟเวอร์สามารถเรียกใช้ดีเพนเดนซีสำหรับเซิร์ฟเวอร์โดยเฉพาะได้ เช่น `sqlx` และสามารถเข้าถึงทรัพยากรเฉพาะของเซิร์ฟเวอร์ได้ เช่น ฐานข้อมูลของเรา
- ฟังก์ชันฝั่งเซิร์ฟเวอร์ต้องเป็น `async` เสมอ แม้ว่าลอจิกการทำงานบนเซิร์ฟเวอร์จะเป็นแบบซิงโครนัสล้วน ๆ ก็ตาม ซิกเนเจอร์ของฟังก์ชันก็ยังต้องเป็น `async` อยู่ดี เพราะการเรียกใช้งานมันจากเบราว์เซอร์*จำเป็น*ต้องเป็นแบบอะซิงโครนัส
- ฟังก์ชันฝั่งเซิร์ฟเวอร์จะคืนค่าเป็น `Result<T, ServerFnError>` เสมอ แม้ว่าโค้ดบนเซิร์ฟเวอร์จะไม่มีทางเกิดข้อผิดพลาดขึ้นเลยก็ตาม เพราะตัวแปร (variants) ของ `ServerFnError` จะครอบคลุมถึงข้อผิดพลาดต่าง ๆ ที่อาจเกิดขึ้นได้ในระหว่างขั้นตอนการส่งคำขอผ่านเครือข่าย
- ฟังก์ชันฝั่งเซิร์ฟเวอร์สามารถถูกเรียกใช้จากฝั่งไคลเอนต์ได้โดยตรง ลองดูที่ตัวจัดการการคลิก (click handler) ของเรา โค้ดส่วนนี้จะทำงานบนฝั่งไคลเอนต์*เท่านั้น* แต่มันสามารถเรียกใช้ฟังก์ชัน `add_todo` (โดยใช้ `spawn_local` เพื่อสั่งรัน `Future`) ได้ราวกับเป็นฟังก์ชัน async ธรรมดาทั่วไป:

```rust
move |_| {
	spawn_local(async {
		add_todo("So much to do!".to_string()).await;
	});
}
```

- ฟังก์ชันฝั่งเซิร์ฟเวอร์เป็นฟังก์ชันระดับบนสุดที่นิยามด้วยคีย์เวิร์ด `fn` ซึ่งแตกต่างจากตัวรับฟังเหตุการณ์, สัญญาณอนุพัทธ์ (derived signals) หรือแทบทุกสิ่งใน Leptos ตรงที่พวกมัน**ไม่ใช่โคลเชอร์**! ในฐานะที่เป็นฟังก์ชัน `fn` ทั่วไป พวกมันจึงไม่สามารถเข้าถึงสถานะรีแอกทีฟของแอปพลิเคชันของคุณ หรือข้อมูลอื่นใดที่ไม่ได้ถูกส่งผ่านเข้ามาเป็นอาร์กิวเมนต์ได้เลย และนี่ก็เป็นหลักการที่สมเหตุสมผลอย่างยิ่ง: เพราะเมื่อคุณส่งคำขอไปยังเซิร์ฟเวอร์ เซิร์ฟเวอร์จะไม่มีทางเข้าถึงสถานะบนไคลเอนต์ได้ เว้นแต่คุณจะส่งข้อมูลนั้นข้ามฝั่งไปอย่างชัดเจน (มิฉะนั้นเราคงต้องแปลงสถานะของทั้งระบบรีแอกทีฟเป็นอนุกรมแล้วส่งข้ามเครือข่ายไปพร้อมกับทุก ๆ คำขอ ซึ่งคงไม่ใช่วิธีคิดที่ดีแน่)
- ทั้งอาร์กิวเมนต์และค่าที่คืนกลับของฟังก์ชันฝั่งเซิร์ฟเวอร์จำเป็นต้องแปลงเป็นอนุกรม (serializable) ได้ทั้งคู่ ซึ่งคงเห็นภาพได้ชัดเจนอยู่แล้ว: แม้ว่าโดยปกติอาร์กิวเมนต์ของฟังก์ชันทั่วไปจะไม่จำเป็นต้อง serialize แต่การเรียกใช้ฟังก์ชันฝั่งเซิร์ฟเวอร์จากเบราว์เซอร์ย่อมหมายถึงการแปลงอาร์กิวเมนต์เป็นอนุกรมเพื่อส่งผ่านเครือข่ายทางโพรโทคอล HTTP

นอกจากนี้ ยังมีประเด็นที่ควรทราบเกี่ยวกับวิธีการนิยามฟังก์ชันฝั่งเซิร์ฟเวอร์อีกเล็กน้อย:

- ฟังก์ชันฝั่งเซิร์ฟเวอร์จะถูกสร้างขึ้นโดยใช้ [มาโคร `#[server]`](https://docs.rs/leptos/latest/leptos/attr.server.html) เพื่อกำกับไว้เหนือฟังก์ชันระดับบนสุด ซึ่งสามารถนิยามไว้ที่ตำแหน่งใดก็ได้ในโปรเจกต์ของคุณ

หลักการทำงานของฟังก์ชันฝั่งเซิร์ฟเวอร์อาศัยการคอมไพล์แบบมีเงื่อนไข (conditional compilation): บนฝั่งเซิร์ฟเวอร์ ฟังก์ชันฝั่งเซิร์ฟเวอร์จะสร้างเอนด์พอยต์ HTTP ที่คอยรับอาร์กิวเมนต์จากคำขอ HTTP และคืนผลลัพธ์กลับไปเป็นคำตอบ HTTP ส่วนในบิลด์ฝั่งไคลเอนต์/เบราว์เซอร์ เนื้อหาฟังก์ชันจะถูกแทนที่ด้วยโค้ดส่งคำขอ HTTP แทน

```admonish warning
### ข้อควรระวังสำคัญเกี่ยวกับความปลอดภัย

ฟังก์ชันฝั่งเซิร์ฟเวอร์เป็นเทคโนโลยีที่ยอดเยี่ยม แต่มีสิ่งสำคัญอย่างยิ่งที่คุณต้องตระหนักไว้เสมอ: **ฟังก์ชันฝั่งเซิร์ฟเวอร์ไม่ใช่เวทมนตร์ แต่เป็นเพียง syntax sugar สำหรับการนิยาม public API เท่านั้น** แม้ว่า *เนื้อหาภายใน* (body) ของฟังก์ชันจะไม่ถูกเปิดเผยต่อสาธารณะเพราะมีอยู่เฉพาะในไบนารีของเซิร์ฟเวอร์ แต่ตัวฟังก์ชันฝั่งเซิร์ฟเวอร์เองนั้นเป็นเอนด์พอยต์ API ที่ใครก็สามารถเข้าถึงได้จากสาธารณะ และค่าที่คืนกลับมาก็เป็นเพียงก้อนข้อมูล JSON หรือรูปแบบใกล้เคียงกัน อย่าส่งข้อมูลสำคัญหรือข้อมูลลับกลับมาจากฟังก์ชันฝั่งเซิร์ฟเวอร์เด็ดขาด เว้นแต่ว่าข้อมูลนั้นจะเป็นข้อมูลสาธารณะอยู่แล้ว หรือคุณได้วางมาตรการรักษาความปลอดภัยที่รัดกุมไว้เรียบร้อยแล้ว เช่น การตรวจสอบและยืนยันตัวตนของคำขอที่ส่งเข้ามา (authentication), การเข้ารหัสข้อมูลอย่างถูกต้อง, การจำกัดอัตราการส่งคำขอ (rate limiting) และมาตรการอื่น ๆ
```

## การปรับแต่งฟังก์ชันฝั่งเซิร์ฟเวอร์

โดยค่าเริ่มต้น ฟังก์ชันฝั่งเซิร์ฟเวอร์จะเข้ารหัสอาร์กิวเมนต์ในรูปแบบคำขอ HTTP POST (โดยใช้ `serde_qs`) และแปลงค่าที่คืนกลับเป็น JSON (โดยใช้ `serde_json`) ค่าเริ่มต้นนี้ถูกออกแบบมาเพื่อส่งเสริมความเข้ากันได้กับเอลิเมนต์ `<form>` ซึ่งรองรับการส่งคำขอแบบ POST อยู่แล้วในตัว แม้ว่า WASM จะถูกปิดใช้งาน ไม่รองรับ หรือยังโหลดไม่เสร็จก็ตาม นอกจากนี้ ระบบจะติดตั้งเอนด์พอยต์ไว้ที่ URL ที่ผ่านการแฮชเพื่อป้องกันไม่ให้เกิดปัญหาชื่อเอนด์พอยต์ชนกัน

อย่างไรก็ดี มีหลากหลายวิธีที่คุณสามารถปรับแต่งฟังก์ชันฝั่งเซิร์ฟเวอร์ได้ตามต้องการ ไม่ว่าจะเป็นการรองรับรูปแบบการเข้ารหัสอินพุตและเอาต์พุตที่หลากหลาย, การกำหนดเส้นทางเอนด์พอยต์แบบเฉพาะเจาะจง และอื่น ๆ อีกมากมาย

สามารถศึกษาข้อมูลและตัวอย่างเพิ่มเติมได้จากเอกสารของ [มาโคร `#[server]`](https://docs.rs/leptos/latest/leptos/attr.server.html) และ [ครีต `server_fn`](https://docs.rs/server_fn/latest/server_fn/) รวมถึงตัวอย่างโค้ดแบบละเอียดใน [`server_fns_axum`](https://github.com/leptos-rs/leptos/blob/main/examples/server_fns_axum/src/app.rs) บนคลังเก็บโค้ดของเรา

## การใช้ข้อผิดพลาดแบบกำหนดเอง

ฟังก์ชันฝั่งเซิร์ฟเวอร์สามารถส่งคืนข้อผิดพลาดชนิดใดก็ได้ที่อิมพลีเมนต์แทรต `FromServerFnError` สิ่งนี้ช่วยให้การจัดการข้อผิดพลาดมีความสะดวก เป็นไปตามหลักสรีรศาสตร์ (ergonomic) และเปิดโอกาสให้คุณส่งข้อมูลข้อผิดพลาดเฉพาะทางของโดเมนธุรกิจกลับไปยังฝั่งไคลเอนต์ได้อย่างชัดเจน:

```rust
use leptos::prelude::*;
use server_fn::codec::JsonEncoding;
use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Deserialize, Serialize)]
pub enum AppError {
    ServerFnError(ServerFnErrorErr),
    DbError(String),
}

impl FromServerFnError for AppError {
    type Encoder = JsonEncoding;

    fn from_server_fn_error(value: ServerFnErrorErr) -> Self {
        AppError::ServerFnError(value)
    }
}

#[server]
pub async fn create_user(name: String, email: String) -> Result<User, AppError> {
    // Try to create user in database
    match insert_user_into_db(&name, &email).await {
        Ok(user) => Ok(user),
        Err(e) => Err(AppError::DbError(e.to_string())),
    }
}
```

## ข้อควรทราบเฉพาะตัว

ฟังก์ชันฝั่งเซิร์ฟเวอร์มีข้อควรระวังและพฤติกรรมเฉพาะบางประการที่ควรทราบ:

- การใช้ชนิดข้อมูลจำนวนเต็มที่มีขนาดตามพอยน์เตอร์ เช่น `isize` และ `usize` อาจทำให้เกิดข้อผิดพลาดขึ้นได้เมื่อมีการเรียกใช้งานข้ามระหว่างสถาปัตยกรรม WASM แบบ 32 บิตกับสถาปัตยกรรมเซิร์ฟเวอร์แบบ 64 บิต หากเซิร์ฟเวอร์ตอบกลับด้วยค่าขนาดใหญ่ที่ไม่พอดีกับ 32 บิต จะส่งผลให้เกิดข้อผิดพลาดในการดีซีเรียลไลซ์ทันที เพื่อบรรเทาปัญหานี้ แนะนำให้เลือกใช้ชนิดข้อมูลที่มีขนาดคงที่แน่นอน เช่น `i32` หรือ `i64` แทน
- อาร์กิวเมนต์ที่ส่งไปยังเซิร์ฟเวอร์จะถูกเข้ารหัสแบบ URL-encoded โดยใช้ `serde_qs` เป็นค่าเริ่มต้น ซึ่งช่วยให้ทำงานร่วมกับเอลิเมนต์ `<form>` ได้อย่างราบรื่น แต่ก็มีพฤติกรรมเฉพาะบางอย่างที่ต้องระวัง: ตัวอย่างเช่น `serde_qs` เวอร์ชันปัจจุบันอาจทำงานร่วมกับชนิดข้อมูลแบบ optional ได้ไม่สมบูรณ์ในบางกรณี (ดูรายละเอียดเพิ่มเติม [ที่นี่](https://github.com/leptos-rs/leptos/issues/3832) หรือ [ที่นี่](https://github.com/leptos-rs/leptos/issues/4016)) รวมถึงชนิดข้อมูล enum ที่มี variant แบบ tuple (ดู [ที่นี่](https://github.com/leptos-rs/leptos/issues/4464)) คุณสามารถใช้วิธีแก้ปัญหาชั่วคราวตามที่ระบุไว้ใน issue ดังกล่าว หรือ [เปลี่ยนไปใช้รูปแบบการเข้ารหัสอินพุตแบบอื่น](https://docs.rs/leptos/latest/leptos/attr.server.html#named-arguments) แทนได้

## การผสานรวมฟังก์ชันฝั่งเซิร์ฟเวอร์กับ Leptos

จนถึงตอนนี้ ทุกสิ่งที่เราพูดถึงแท้จริงแล้วไม่ได้ผูกติดอยู่กับเฟรมเวิร์กตัวใดตัวหนึ่งโดยเฉพาะ (อันที่จริง ครีตฟังก์ชันฝั่งเซิร์ฟเวอร์ของ Leptos ก็ถูกนำไปผสานรวมใช้งานใน Dioxus ด้วยเช่นกัน!) โดยพื้นฐานแล้ว ฟังก์ชันฝั่งเซิร์ฟเวอร์เป็นเพียงแนวทางการนิยามการเรียกใช้ฟังก์ชันทางไกล (RPC) ที่อิงตามมาตรฐานเว็บทั่วไป เช่น คำขอ HTTP และการเข้ารหัสแบบ URL

ทว่าในอีกแง่หนึ่ง พวกมันยังทำหน้าที่เป็นพรีมิตีฟชิ้นส่วนสุดท้ายที่ช่วยเติมเต็มภาพรวมของระบบที่เราได้เรียนรู้มา เพราะเมื่อฟังก์ชันฝั่งเซิร์ฟเวอร์เป็นเพียงฟังก์ชัน async ทั่วไปของ Rust มันจึงสามารถผสานรวมเข้ากับพรีมิตีฟแบบอะซิงก์ของ Leptos ที่เราพูดถึงไปแล้ว [ในบทก่อนหน้านี้](../async/index.html) ได้อย่างสมบูรณ์แบบ คุณจึงสามารถนำฟังก์ชันฝั่งเซิร์ฟเวอร์มาเชื่อมต่อกับส่วนอื่น ๆ ของแอปพลิเคชันได้อย่างราบรื่น:

- สร้าง **รีซอร์ส** ที่เรียกฟังก์ชันฝั่งเซิร์ฟเวอร์เพื่อโหลดข้อมูลจากเซิร์ฟเวอร์
- อ่านรีซอร์สเหล่านี้ภายใต้ `<Suspense/>` หรือ `<Transition/>` เพื่อเปิดใช้งานการสตรีม SSR และแสดงสถานะสำรองขณะข้อมูลกำลังโหลด
- สร้าง **แอ็กชัน** ที่เรียกฟังก์ชันฝั่งเซิร์ฟเวอร์เพื่อแก้ไขเปลี่ยนแปลงข้อมูลบนเซิร์ฟเวอร์

ในส่วนสุดท้ายของหนังสือเล่มนี้ เราจะทำให้ภาพนี้เป็นรูปธรรมยิ่งขึ้นด้วยการแนะนำแพตเทิร์นที่ใช้ฟอร์ม HTML ที่ได้รับการเสริมประสิทธิภาพอย่างต่อเนื่อง (progressively-enhanced forms) เพื่อสั่งรันการทำงานของแอ็กชันฝั่งเซิร์ฟเวอร์เหล่านี้

แต่ในบทถัดไป เราจะมาสำรวจรายละเอียดเพิ่มเติมเกี่ยวกับสิ่งที่คุณสามารถทำได้ด้วยฟังก์ชันฝั่งเซิร์ฟเวอร์ รวมถึงแนวทางที่ดีที่สุดในการผสานการทำงานร่วมกับเอกซ์แทรกเตอร์อันทรงพลังที่เซิร์ฟเวอร์เฟรมเวิร์กอย่าง Actix และ Axum มีให้
